# 概述

Ubuntu 上安装 PostgreSQL，我的习惯是：**源码编译，整套收进 `/opt/postgresql` 一个目录**，多版本目录 + `current` 稳定入口。但 PostgreSQL 有个结构性特点，决定了它的布局不能照搬一般服务"配置随版本走"的做法：

- 它的**配置就住在数据目录里**（`postgresql.conf`、`pg_hba.conf` 都在 PGDATA 内），和数据文件生死与共；
- 数据目录不可能"随二进制版本走"，只能**每个版本初始化一个数据目录，用 `pg_upgrade` 把数据迁过去，配置手工对齐**。

所以这套布局的完整表述是：**程序多版本目录 + 数据目录也按版本分家 + `pg_upgrade` 迁移数据 + diff 对齐配置**；`app/current` 只作命令行与运维脚本的稳定入口，服务进程由 systemd 用真实版本路径写死托管。回滚 = 旧数据目录还完整躺在 `data/pg<旧版本>` 里，改回 unit 指旧目录即可。

要点速览：

| 项目 | 值 |
|------|---|
| 安装根目录 | `/opt/postgresql` |
| 程序目录 | `/opt/postgresql/app/versions/18.7`（编译 `--prefix`，不可变） |
| 命令行入口 | `/opt/postgresql/app/current -> app/versions/18.7`（软链接，供 PATH/脚本引用；不驱动服务） |
| 数据目录 | `/opt/postgresql/data/pg18.7`（`initdb` 创建，配置在其中） |
| 运行用户 | `postgres`（二进制 root 安装，数据目录 postgres 属主） |
| 服务单元 | `/etc/systemd/system/postgresql.service` |
| 升级工具 | 新版本目录里的 `pg_upgrade`（`-b/-B` 指新旧 bin，`-d/-D` 指新旧 data） |
| 版本口径 | PostgreSQL 18.x，本文以 **18.7** 为例，从 18.4 升级演示 |

# 目录布局

```text
/opt/postgresql
├── app
│   ├── current -> /opt/postgresql/app/versions/18.7
│   └── versions
│       ├── 18.4                 # 旧版本，升级后保留作回滚底账
│       └── 18.7                 # 新版本程序（bin/lib/share）
├── data
│   ├── pg18.4                   # 旧数据目录（含旧配置），升级后冻结
│   └── pg18.7                   # 新数据目录（initdb 生成 + pg_upgrade 迁入）
└── tmp                          # 扩展编译等临时工作区
```

三条对应关系：一个版本一套 `versions/<ver>`（程序）+ 一个 `data/pg<ver>`（数据+配置）；`app/current` 是命令行与运维脚本的稳定入口（不影响 systemd 服务，服务用真实版本路径）；数据目录名带版本号，新旧并存是回滚的前提，不是垃圾。

# 环境准备

> [!note]
> 以下命令以 **Ubuntu 26.04** 为基线实测。源码编译必需的 `flex`/`bison`（用于解析器生成）在 26.04 上包名与可用性保持不变，照装即可；个别库若在新版本里有包名调整，以下方依赖表为准。

```bash
apt update

apt install -y build-essential flex bison pkg-config \
  libreadline-dev zlib1g-dev libssl-dev \
  libxml2-dev libxslt1-dev uuid-dev
```

| 依赖 | 用途 |
|------|------|
| `build-essential` / `flex` / `bison` / `pkg-config` | 编译工具链；flex/bison 用于解析器生成（源码编译必装） |
| `libreadline-dev` | `psql` 的行编辑与命令历史 |
| `zlib1g-dev` / `libssl-dev` | 压缩与 TLS（`--with-zlib` / `--with-openssl` 默认探测） |
| `libxml2-dev` / `libxslt1-dev` | `xml2` 扩展支持 |
| `uuid-dev` | `uuid-ossp` 扩展支持 |
| `libsystemd-dev` | **可选**：configure 加 `--with-systemd` 时需要，装完记得见下文 systemd 节的 Type 选择 |

源码包的获取见 [01.下载PostgreSQL安装包](./01.下载PostgreSQL安装包.md)。

# 下载与编译

```bash
cd /opt/postgresql/tmp
tar xjf postgresql-18.7.tar.bz2      # 官方源码包，可能是 .tar.bz2 或 .tar.gz
cd postgresql-18.7

./configure --prefix=/opt/postgresql/app/versions/18.7

make && make install
```

`--prefix` 指进版本目录：产物全部收进不可变单元，切版本只动 `current` 软链。

> [!important]
> `--with-systemd` 加不加，决定 systemd 单元的 `Type` 写法（见下文托管节的两种方案），编译时就要想好：
> - 加了：需要 `libsystemd-dev`，postgres 二进制支持 `sd_notify`，单元用 `Type=notify`；
> - 没加：单元**只能**用 `Type=simple`（或 `forking` 配 pg_ctl，不推荐），用 `notify` 会卡死在 activating。

# 运行用户与目录权限

```bash
# 系统用户（数据目录属主；二进制目录归 root，编译安装期用 root）
sudo adduser postgres

# 数据目录与临时目录的归属
mkdir -p /opt/postgresql/data
chown postgres:postgres /opt/postgresql/data
```

权限模型一句话：**程序目录 root 装、postgres 用；数据目录 postgres 全权**。`initdb`、`pg_upgrade` 必须以 `postgres` 用户执行（`pg_upgrade` 官方明确**不能以 root 运行**）。

# 初始化新版本数据目录

切到 `postgres` 用户（`su - postgres`），对**新目录跑新版本的 initdb**：

```bash
/opt/postgresql/app/versions/18.7/bin/initdb -E UTF8 -D /opt/postgresql/data/pg18.7
```

- `-E UTF8`：服务端编码；collate/ctype 如需指定可加 `--locale=C.UTF-8` 等，取决于业务排序需求；
- **18 起 initdb 默认启用数据校验和（data checksums）**。老集群若当初是用 `--no-data-checks` 建的，新库要加 `--no-data-checksums` 对齐——`pg_upgrade` 要求新旧集群校验和设置**一致**，不一致直接拒绝升级。

initdb 完成后，`data/pg18.7` 里就有了出厂的 `postgresql.conf` 与 `pg_hba.conf`——它们是升级流程里 diff 对齐的对象。

# systemd 托管

configure 没加 `--with-systemd` 时，PostgreSQL 二进制不支持 `sd_notify`，此时 `Type=notify` 会让服务卡在 `activating` 状态直到超时。两种应对：

| 编译方式 | Type | 说明 |
|---------|------|------|
| 加了 `--with-systemd` | `notify` | 服务就绪由 sd_notify 上报，systemd 感知精确 |
| 没加（本文默认） | `simple` | ExecStart 直接指向 postgres 二进制，由 systemd 跟踪主进程 |

两种情况 **ExecStart 都不要用 `pg_ctl` 包装**——社区明确建议 systemd 下直接托管 postgres 进程，`pg_ctl` 的 fork 语义和信号通道与 systemd 的进程模型打架。

`/etc/systemd/system/postgresql.service`（本文按"未加 --with-systemd"的 `simple` 版）：

```ini
[Unit]
Description=PostgreSQL database server
After=network.target

# simple: 【默认】启动的进程为主进程，服务进程不会 fork
# forking: 以fork()方式从父进程创建子进程启动，创建后父进程会立即退出，子进程成为主进程
# oneshot: 只执行一次，systemd会等当前服务退出，再继续往下执行
# dbus: 当前服务通过 D-Bus 信号启动。当指定的 BusName 出现在 DBus 系统总线上时，Systemd认为服务就绪
# notify: 当前服务启动完毕会发出通知信号，通知 Systemd，然后 Systemd 再启动其他服务
[Service]
Type=simple
User=postgres
Group=postgres
ExecStart=/opt/postgresql/app/versions/18.7/bin/postgres -D /opt/postgresql/data/pg18.7
ExecReload=/bin/kill -HUP $MAINPID
KillMode=mixed
KillSignal=SIGINT
TimeoutSec=300
Restart=on-failure
RestartSec=10s

[Install]
WantedBy=multi-user.target
```

- `KillSignal=SIGINT`：对应 PostgreSQL 的 **fast shutdown**（等事务结束、回滚未提交事务）；想改成 smart（等客户端全部断开）就设 `SIGTERM`，`SIGQUIT`（立即关闭、下次启动走崩溃恢复）永远别给 systemd 用；
- `KillMode=mixed`：先只对主进程发 `KillSignal`，超时后对全部子进程（backend、walwriter 等）补 SIGKILL——正好匹配 postgres 主进程自己管理 worker 的进程树；
- `ExecReload` 走 `SIGHUP`，与 `pg_ctl reload` 语义等价。

```bash
systemctl daemon-reload
systemctl enable --now postgresql
```

# 程序入口与命令行 PATH

给命令行和运维脚本留一个**不随版本变化**的入口——`app/current` 软链，再挂进 `PATH`：

```bash
ln -sfn /opt/postgresql/app/versions/18.7 /opt/postgresql/app/current
```

```bash
# /etc/profile.d/postgresql.sh（或写进 postgres 用户的 ~/.bashrc）
export PATH=/opt/postgresql/app/current/bin:$PATH
```

这样 `psql`、`pg_dump`、`pg_restore` 等命令在任意目录都能直接敲；升级时把 `current` 一拨，**新开的 shell 自动用上新版本客户端**（已登录的旧 shell 要重开或重新 `source` 才切换）。`current` 的第二个用途，是给**备份、巡检等运维脚本**当固定引用路径（脚本写 `/opt/postgresql/app/current/bin/pg_dump`，切版本不用改脚本来回）。

> [!note]
> **`current` 不驱动 systemd 服务**。服务侧 `ExecStart` 刻意写死真实版本路径（`versions/18.7/bin/postgres` + `-D data/pg18.7`），因为 PostgreSQL 的数据目录按版本分家，二进制与 `-D` 必须钉成同一对匹配的版本，不能让两者各切各的。所以换服务版本靠**改 unit + `daemon-reload`**（见升级收尾节），`current` 只服务命令行与脚本这类与版本无强绑定的调用方。

# 版本升级（pg_upgrade）

以 `18.4 -> 18.7` 为例。`pg_upgrade` 支持任意大版本间迁移，本文的多版本布局下**每个版本各配一个新数据目录**，所以小版本切换也走同一条流水线，换来的是"旧数据目录原样冻结、回滚零成本"。

> [!tip]
> **停服窗口最小化**：`pg_upgrade` 正式执行时要求新旧集群都干净停止，所以凡是能离线做的准备——装程序、initdb、迁移配置、编译扩展、`-c` 干跑检查——一律赶在旧实例照常服务时做完，直到最后一步正式升级才停旧库。停机时间就只剩「停旧 → pg_upgrade → 起新」这一段。

## 1) 装新版本程序目录

```bash
cd /opt/postgresql/tmp
tar xjf postgresql-18.7.tar.bz2 && cd postgresql-18.7
./configure --prefix=/opt/postgresql/app/versions/18.7
make && make install
```

## 2) 初始化新数据目录

`postgres` 用户执行（见上一节命令）：`versions/18.7/bin/initdb -E UTF8 -D data/pg18.7`。initdb 完成后，新数据目录里就多了出厂的 `postgresql.conf`、`pg_hba.conf`——这正是配置迁移能提前到停服之前做的前提。

## 3) 配置迁移（提前做，旧实例仍在服务）

`pg_upgrade` **不会自动迁移自定义配置**：新数据目录里的 `postgresql.conf`、`pg_hba.conf` 是 initdb 生成的出厂版。趁旧库还在跑，先逐个 diff、把定制项落到新文件：

```bash
diff -u /opt/postgresql/data/pg18.4/postgresql.conf /opt/postgresql/data/pg18.7/postgresql.conf
diff -u /opt/postgresql/data/pg18.4/pg_hba.conf     /opt/postgresql/data/pg18.7/pg_hba.conf
```

配置迁移的原则：以**新版出厂文件为底**（不丢新版本的默认值变化与新参数），把旧版的定制行搬过来，而不是简单覆盖回去。提前对齐还有一层好处：下一步的 `-c` 干跑会读这些配置，等于顺带验证迁移后的配置本身没问题。

## 4) 检查扩展兼容性（-c 干跑）

```bash
# postgres 用户；必须用【新版本】的 pg_upgrade 二进制
/opt/postgresql/app/versions/18.7/bin/pg_upgrade \
  -c \
  -b /opt/postgresql/app/versions/18.4/bin \
  -B /opt/postgresql/app/versions/18.7/bin \
  -d /opt/postgresql/data/pg18.4 \
  -D /opt/postgresql/data/pg18.7
```

`-c` 只做检查不动数据，**旧实例可以继续运行**：新旧集群的扩展**控制文件与共享库必须在新版本目录下也存在**，否则报 `could not access the status of extension "xxx"` 类失败。第三方扩展（如 pgvector）在 `-B` 里找不到就会卡在这一步。

## 5) 补齐缺失扩展（pgvector 例）

```bash
# 1. 进入临时目录，下载源码
mkdir -p /opt/postgresql/tmp
cd /opt/postgresql/tmp
git clone --branch v0.8.7 https://github.com/pgvector/pgvector.git

# 2. 使用当前 PostgreSQL 版本路径的 pg_config 进行编译
cd /opt/postgresql/tmp/pgvector
make PG_CONFIG=/opt/postgresql/app/versions/18.7/bin/pg_config

# 3. 安装（写进 versions/18.7 的 lib/extension，需要 root）
sudo make install PG_CONFIG=/opt/postgresql/app/versions/18.7/bin/pg_config
```

`PG_CONFIG` 指向哪个版本目录，扩展就装进哪个版本——这是"程序目录不可变"布局下扩展管理的唯一正确姿势：**旧版本的扩展不会自动跟着新二进制存在，每个新版本目录都要重装一遍依赖**。扩展用法见 [08章 025.pgvector](../08.PostgreSQL%20生态插件/025.pgvector.md)。

## 6) 再次检查

重跑第 4 步的 `-c` 命令，确认全部通过。至此所有离线准备就绪——接下来才进入唯一需要停服的环节。

## 7) 执行升级（这一步才停旧实例）

先干净停掉旧集群，杜绝 `pg_upgrade` 迁移期间还有新写入落进来：

```bash
# 1) 停旧实例：fast 模式等事务结束、拒绝新连接
/opt/postgresql/app/versions/18.4/bin/pg_ctl -D /opt/postgresql/data/pg18.4 stop -m fast
# 若旧库由 systemd 托管，等价于 systemctl stop postgresql

# 2) postgres 用户，用新版本的 pg_upgrade 正式升级（此时新旧集群都必须已停止）
/opt/postgresql/app/versions/18.7/bin/pg_upgrade \
  -b /opt/postgresql/app/versions/18.4/bin \
  -B /opt/postgresql/app/versions/18.7/bin \
  -d /opt/postgresql/data/pg18.4 \
  -D /opt/postgresql/data/pg18.7
```

`pg_upgrade` 非 `-c` 模式**要求新旧两个集群都处于停止状态**才肯执行——这正是把前面所有准备都挪到停服之前的原因：停机窗口从这一刻才开始计时，直到第 8 步新库起来才结束。

两个可选加速项：

- `-k`（`--link`）：硬链接代替复制，大库秒级完成；**代价**是新旧集群共享 inode，升级后一旦启动新集群，旧数据目录就不可再写。跨文件系统时不可用；
- `--jobs=N`：并行处理，18 起检查阶段也并行。

不加参数则默认 copy 模式，慢但新旧目录立刻物理独立。

## 8) 收尾三件套

1. **切换程序入口、起新库**（停机到此结束）：先把 `current` 指过去（源目录末尾不要带斜杠，`/versions/18.7/` 是错的），再把 `postgresql.service` 的 `ExecStart` 里二进制与 `-D` 路径换成 `18.7`，`systemctl daemon-reload && systemctl start postgresql`，确认业务连上、查询正常。

   ```bash
   ln -sfn /opt/postgresql/app/versions/18.7 /opt/postgresql/app/current
   ```

2. **补齐统计信息**（新库启动后才能跑）：18 起 `pg_upgrade` 会保留旧集群**大部分列级**优化器统计（`--no-statistics` 可关），但**扩展统计（Extended Statistics，即 `CREATE STATISTICS` 建的）不会迁移**。官方推荐补两条命令（可加 `--jobs=N` 并行，N 不超过 CPU 核数）：

   ```bash
   # 第一条：给"完全没有统计信息"的关系快速生成最小统计（含扩展统计）
   /opt/postgresql/app/versions/18.7/bin/vacuumdb \
     --all --analyze-in-stages --missing-stats-only

   # 第二条：更新所有关系的累积统计，让 autovacuum / autoanalyze 正常接管
   /opt/postgresql/app/versions/18.7/bin/vacuumdb \
     --all --analyze-only
   ```

   两条跑完，新集群的查询计划质量才能接近旧集群的水平。

3. **归档旧目录**：确认新集群业务正常后，旧 `versions/18.4` 与 `data/pg18.4` 冻结归档（`pg_upgrade` 生成的 `delete_old_cluster.sh` 别急着在 link 模式启动新库之前执行）。

回滚路径：停新服务 → `ExecStart` 改回 `18.4` 二进制 + `data/pg18.4` → `daemon-reload` + 启动。数据一行没动，这就是数据目录按版本分家的意义。

# 避坑

- **`--with-systemd` 与 `Type` 不匹配**：编译时没加 `--with-systemd`，二进制不支持 `sd_notify`，单元却写 `Type=notify`——服务永远卡在 `activating (start)` 直到 `TimeoutSec` 超时被杀。要么两边同时改（加编译 + notify），要么都保持默认（不加 + simple）。
- **ExecStart 用 pg_ctl 包装**：`pg_ctl start` 干完就退出，systemd 认为主进程消失随即清理整个进程树（`KillMode=control-group` 默认行为），数据库说没就没。直接跑 `postgres` 二进制是唯一正确姿势。
- **`ln -sfn` 源目录带尾斜杠**：`ln -sfn .../versions/18.7/ .../current` 这类写法在部分场景会让链接目标解析出意外层级，养成不带尾斜杠的习惯；切链接永远 `-sfn`。
- **误以为切 `current` 就能换服务版本**：`ExecStart` 写死真实版本路径（二进制与 `-D` 数据目录必须钉成匹配的一对），`current` 只管命令行与脚本；切 `current` 后 `systemctl restart` 仍是旧版。换服务版本必须改 unit + `daemon-reload`。
- **校验和不匹配直接拒升**：18 起 initdb 默认开 data checksums。旧集群建得早、没开校验和的话，`pg_upgrade` 检查阶段就失败；新库 initdb 时加 `--no-data-checksums` 对齐（或提前规划好旧库何时重建启用校验和）。
- **root 跑 pg_upgrade**：官方明确禁止——它以启停两个集群为手段完成迁移，必须用数据属主 `postgres` 用户执行；`initdb` 同样不能以 root 跑。
- **忘了停旧集群就正式升级**：非 `-c` 模式下 `pg_upgrade` 会直接拒绝——旧库仍在写入会让迁出来的数据不一致。把停旧放在最后一步正式升级之前，其余准备全部提前做完，才能既正确、又把停机压到最短。
- **扩展只装在旧版本目录**：新版本目录 `lib/`、`extension/` 里没有 pgvector 等第三方库，`-c` 检查就不过；正式升级中途失败回退更难看。每个新版本目录都要**先对着新 `pg_config` 补完扩展、`-c` 复核通过，再进正式升级**。
- **以为 pg_upgrade 会带走配置**：它只管数据与系统目录，`postgresql.conf`/`pg_hba.conf` 的定制项一律留在旧目录里等你 diff 搬运。上线前用 `psql -c 'show <关键参数>'` 逐项确认新库生效值。
- **link 模式启动新库后又去动旧库**：共享 inode，旧库再写入会污染新库数据。link 模式升级后旧数据目录只读不启动；要让新旧彻底物理独立，正式升级就用默认 copy（或事后重建备份）。
- **升级后不做收尾核对**：`pg_upgrade` 会在执行目录留下 `analyze_new_cluster.sh` / `delete_old_cluster.sh`，按第 8 步的节奏处理；处理完前不要删旧目录——那是唯一回滚保险。

# 总结

`/opt/postgresql` 这套布局把 PostgreSQL 的升级做成一条**准备在前、停机在最后、可回滚**的流水线：**新版本目录 `make install` → `initdb` 新数据目录 → 趁旧库还在跑提前 diff 对齐 `postgresql.conf`/`pg_hba.conf` → `pg_upgrade -c` 干跑查扩展 → 缺什么扩展就在 `tmp` 里对着新 `pg_config` 补编、再 `-c` → 停旧实例、去 `-c` 正式升级 → 改 unit（真实版本路径）+ `daemon-reload` 起新库、顺带拨 `current` 给命令行 → 收尾统计**。PostgreSQL 的配置随**数据目录**走（而非随二进制版本目录走），回滚靠的是"旧数据目录原地冻结 + unit 路径改回"，原子且可逆。日常记住三条：二进制和扩展归 root 装、数据库进程 postgres 跑、`pg_upgrade` 永远用新版本的。启停与参数管理细节在 [05章 070.服务器启停与配置](../05.PostgreSQL%20数据库管理/070.服务器启停与配置.md)，装好库后进 [04.PostgreSQL 示例数据库](./04.PostgreSQL%20示例数据库.md)。
