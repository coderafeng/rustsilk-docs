# 概述

[03.Ubuntu系统安装PostgreSQL](./03.Ubuntu系统安装PostgreSQL.md) 里的 `pg_upgrade` 升级，本质是**停机换目录**：干净停掉旧库 → 迁移数据 → 起新库。它步骤简单、技术要求低，代价是有一段能感知到的停服窗口，适合能接受短时间停服的业务。

本篇讲的是另一条路——**用户几乎无感的大版本升级**，核心是**蓝绿部署 + 逻辑复制**：新旧两套集群同时在线，用逻辑复制把数据从旧库（蓝）持续同步到新库（绿），在一个秒级到分钟级的切换窗口里把写入从旧库搬到新库，并立刻建一条反向复制作为回滚保险。整个过程业务最长的一次中断，通常只是切换瞬间的那几秒。

> [!important]
> 这套方案成不成，**在切换之前就已经由三件事决定**：① 所有表是否有主键；② DDL 能否冻结；③ 扩展在新版本上是否可用。三者有一样不满足，切换就会失败或数据错乱，务必在准备阶段先逐一拍板（见下文「切换前三问」）。

> [!warning]
> 这套流程步骤多、环环相扣，一旦某步出错又直接在生产上操作，代价极高。**上线前务必先在与生产同构的模拟/孪生环境完整跑一遍（含切换与回滚演练）**，确认全链路走得通再对生产动手，把“第一次跑”的风险留在测试环境，而不是留给线上业务。

要点速览：

| 项目 | 值 |
|------|---|
| 原理 | 蓝绿部署 + 逻辑复制（发布/订阅） |
| 停机窗口 | 秒级～分钟级，主要耗在 Sequence 同步 |
| 数据同步 | `CREATE PUBLICATION` / `CREATE SUBSCRIPTION`，初始快照 + 增量持续追平 |
| 目标端建库 | 只导 Schema（`pg_dump --schema-only`），数据靠逻辑复制灌 |
| 回滚保障 | 切换后立即建反向订阅（新→旧），旧库不再过时 |
| 版本要求 | 源库 `wal_level=logical`；PG 17+ 有额外省力特性 |

两条升级路径怎么选：

| 维度 | 短停服 `pg_upgrade`（03） | 不停服 蓝绿+逻辑复制（本篇） |
|------|------------------------|------------------------------|
| 停服时长 | 分钟～小时级（取决于数据量） | 秒级切换窗口 |
| 复杂度/门槛 | 低 | 高（需应用配合停写、切连接） |
| 需要应用改造 | 否 | 是（连接可切换、能下发只读/停写） |
| 数据量特别大 | 耗时长 | 初始同步可并行、在线追平，更从容 |
| 回滚 | 靠旧数据目录原地冻结 | 靠反向逻辑复制 + 保留旧库 |
| 回滚数据损失 | **切流后写进新库的数据回滚带不走**（旧目录冻结在升级点，只能丢或手工补写） | 反向复制让旧库持续追新库，回退不丢切流后的写入 |

# 核心原理

蓝绿部署负责"两套环境并存、随时可切"，逻辑复制负责"让绿的环境持续追上蓝的数据"。整体数据流：

```text
准备期        旧库(蓝) ──wal_level=logical──> CREATE PUBLICATION
              新库(绿，已建好 Schema) ──CREATE SUBSCRIPTION──> 初始快照 + 增量追平
              （业务照常读写旧库，新库在后台同步）

切换窗口      ①旧库停写 → ②新库追平到同 LSN → ③同步 Sequence → ④断开订阅
              → ⑤应用连接切到新库 → ⑥建反向订阅(新→旧) 保回滚

稳定期        业务读写新库；旧库作为回退点保留，观察期过后下线
```

逻辑复制的基础概念（发布、订阅、复制槽、`pg_stat_subscription`）见 [05章 085.复制与高可用](../05.PostgreSQL%20数据库管理/085.复制与高可用.md) 的"逻辑复制简述"，本篇不重复铺基础，只讲升级编排。

# 切换前三问（成败因素）

这三问在**开始搭复制之前**就要有明确答案，任一不过关都要先解决再往下走。

## 1) 所有表都有主键吗？

逻辑复制对 `UPDATE`/`DELETE` 依赖行标识（Replica Identity）。没有主键的表，订阅端要么同步不了、要么退化成全表匹配，极慢甚至报错。

```sql
-- 找出所有没有主键的表（切换前必须清零，或显式设 REPLICA IDENTITY FULL）
SELECT n.nspname AS schema, c.relname AS table
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'r'
  AND n.nspname NOT IN ('pg_catalog', 'information_schema')
  AND NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conrelid = c.oid AND contype = 'p');
```

处理办法：优先**补主键**；确实无法加主键的表，在源库执行 `ALTER TABLE <表名> REPLICA IDENTITY FULL;`（代价是每条更新都要写整行旧值，仅对小表/低频表可接受）。

## 2) DDL 能冻结吗？

逻辑复制**只同步数据，不同步 DDL**。切换窗口内如果还在改表结构，新旧 Schema 就会漂移，复制直接崩。所以切换前必须**冻结 DDL**：结构变更全部提前落到新库，切换期间禁止任何 `ALTER`。

实操上：把发布设为只同步数据，切换前进入"结构变更冻结期"，应用侧也停掉会改表的迁移脚本/自动 DDL。

## 3) 扩展在新版本上可用吗？

订阅端要能接收带扩展类型/运算符的数据，新库必须**先装好对应扩展**。像 pgvector 这类第三方扩展，要在 `versions/<新版本>` 目录里对新版 `pg_config` 编译安装（做法见 [03 篇「补齐缺失扩展」](./03.Ubuntu系统安装PostgreSQL.md)），并在目标库 `CREATE EXTENSION`。扩展用法见 [08章 025.pgvector](../08.PostgreSQL%20生态插件/025.pgvector.md)。

# 跨多大版本的额外功课（如 PG 15 → 18）

上面三问是**任何版本跨度都要过**的通用闸门；**只有当你跨两个及以上大版本**（如 15 → 18）时，才需要额外做这一节的功课。

逻辑复制的一条好处是**不要求新旧只隔一个版本**：发布端与订阅端可以隔着好几个大版本，因此理论上可以一次从 15 直接升到 18，而不必 15→16→17→18 逐级跳。但“可以一步到位”不等于“可以忽略中间版本的变更”——**跳过的每一个大版本，它的行为变化、被删对象、默认值改动都会一次性积压到切换后的新库上**。

因此跨多大版本时，切换前多一项必做的功课：**逐一阅读沿途每个大版本 Release Notes 的 “Migration to version N” 章节**（从源版本的下一版一直到目标版），重点排查：

| 排查项 | 典型风险 |
|--------|---------|
| 被移除/重命名的**配置参数** | `postgresql.conf` 里还写着旧参数，新库启动直接报错或告警 |
| 被移除的**函数/运算符/系统视图** | 业务 SQL、视图、触发器、备份脚本调到了不存在的对象 |
| 废弃/改变的**数据类型与隐式转换** | 某些列类型、序列、聚合行为变化导致查询报错或结果错乱 |
| **默认值变化** | 不改参数但行为静默变了（如各种 `default_*`、优化器/统计开关） |
| **认证/加密默认值** | 直接影响能否连上（见下方 warning） |

> [!warning]
> 一个高频坑：PG 15 起 `password_encryption` 默认从 `md5` 改为 `scram-sha-256`。跨版本升级后，旧口令、`pg_hba.conf` 里的认证方法、连接串可能对不上而导致**连不上库**。这类“默认值变化”在多个大版本里陆续发生过，逐个核对 Migration 章节才能提前发现。

做法上建一张“版本迁移清单”：把沿途每版 Migration 章节里**与你实例相关**的条目抓下来（可用 `grep` 对照自己的参数/对象），逐项在新库上确认。若社区工具（如 `pg_upgradechecker` 类）能静态扫描被删对象引用，可拿来辅查，但**不能替代人工读 Migration 章节**。实在担心跨太大不可控，也可以拆成逐级升级（先 15→17、观察稳定后再 17→18），用多次小跳换每次改动面可控。

> [!note]
> 本篇 runbook 拿相邻版本（17 → 18.7）做演示，但多跳走的是**同一套流程**，只是额外叠上本节功课。另注：本项跨版本排查对 [03 篇](./03.Ubuntu系统安装PostgreSQL.md) 的 `pg_upgrade` 短停服升级同样适用（那里不要求逐版本跳，但删改项一样会一次性生效）；只是本篇的无感升级通常面向不能停的核心库、跨距可能更大，故单列强调。

# 完整流程（runbook）

以源 `17.x` 升级到 `18.7` 为例。旧库记作 **blue**，新库记作 **green**。

## 阶段 0：把 green 建起来（不停业务）

按 [03 篇](./03.Ubuntu系统安装PostgreSQL.md) 的编译流程把新版本装进 `versions/18.7`、`initdb` 出 `data/pg18.7`、配好 `postgresql.conf`/`pg_hba.conf`。关键参数两侧对齐：

```ini
# blue（源库）：必须开逻辑复制级别
wal_level = logical
max_replication_slots = 10     # 至少留够发布端要建的槽
max_wal_senders = 10

# green（目标库）：订阅要吃的 worker
max_logical_replication_workers = 8
max_worker_processes = 16
```

> [!warning]
> `wal_level` 从 `replica` 改成 `logical` 需要重启 blue 源库。这是整套流程里唯一一次**无法避免**的旧库重启，安排在低峰做；改完源库不必停业务即可继续。

## 阶段 1：目标端只建 Schema

用 `pg_dump` 把 blue 的结构导出来，灌进 green——**只导 Schema，不导数据**，数据留给逻辑复制。

```bash
# 在能连 blue 的机器上，导结构（含扩展、序列定义，不含 owner/权限按需要调整）
/opt/postgresql/app/current/bin/pg_dump -h <blue_host> -U postgres --schema-only --no-owner \
  -d <db> -f schema.sql

# 恢复到 green
/opt/postgresql/app/current/bin/psql -h <green_host> -U postgres -d <db> -f schema.sql
# 别忘了在 green 上建扩展（DDL 里若含 CREATE EXTENSION 会一并建，验证一下）
```

> [!note]
> 逻辑复制的订阅端**必须预先存在同名表**才能接收数据（订阅不会自动建表），所以这一步的 Schema 一定要导全。触发器、外键、规则这类对象在初始同步阶段建议先在 green 上禁用、切完再启用，避免数据灌入时被约束挡住。

## 阶段 2：搭发布与订阅，在线同步数据

blue 侧建发布，green 侧建订阅并做初始快照。

```sql
-- blue：发布全表（也可按需 FOR TABLE 白名单）
CREATE PUBLICATION upgrade FOR ALL TABLES;

-- green：订阅。默认 copy_data=true 会把已有数据灌进来，之后持续追增量
CREATE SUBSCRIPTION upgrade
  CONNECTION 'host=<blue_host> port=5432 dbname=<db> user=replicator password=<密码>'
  PUBLICATION upgrade;
```

监控 green 是否追平：

```sql
-- green：有活跃的 apply worker 说明订阅在跑
SELECT subname, pid, received_lsn, last_msg_send_time FROM pg_stat_subscription;

-- blue：发布端槽的滞留 WAL，confirmed_flush_lsn 越贴近当前 LSN 越说明快追平
SELECT slot_name, active, confirmed_flush_lsn,
       pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn) AS lag_bytes
FROM pg_replication_slots;
```

这个阶段业务照常读写 blue，green 在后台不停追；同步一晚上也没关系，因为它不影响线上。

## 阶段 3：切换（秒级窗口）

这是唯一让用户短暂感知的一步，按顺序执行，尽量在几十秒内走完：

**① 冻结写入。** 停掉 blue 上的写流量——应用层置只读/摘掉写连接池，或在 blue 上兜底：

```sql
-- 让 blue 拒绝新写入（会话级/库级，视手段选用）
ALTER SYSTEM SET default_transaction_read_only = on;
SELECT pg_reload_conf();
-- 断开残留写连接，等没有长事务/空闲事务再往下
SELECT pg_terminate_backend(pid) FROM pg_stat_activity
 WHERE state IN ('idle in transaction') AND backend_type = 'client backend';
```

**② 确认 green 追平到同 LSN。** 停写后，green 的 `received_lsn`/`replay_lsn` 会停在 blue 最后的写入点，核对两边一致。

**③ 同步 Sequence（主要耗时点）。** 逻辑复制**不会自动同步序列当前值**——切过去若不把 blue 上的序列最新值搬到 green，插入主键就会冲突。逐个把 blue 的序列值刷到 green：

```sql
-- 在 blue 上生成一批 setval 语句（停写后 last_value 已稳定）
SELECT format('SELECT setval(%L, %s);',
              schemaname || '.' || sequencename,
              last_value)
FROM pg_sequences
WHERE last_value IS NOT NULL;

-- 把生成的结果拿到 green 执行；也可用 pg_dump 单独导序列值再灌
```

**④ 断开订阅。** green 上删除订阅（顺带释放 blue 的复制槽）：

```sql
-- green
DROP SUBSCRIPTION upgrade;
```

**⑤ 切换连接。** 把应用的数据库连接指向 green（改 DNS / VIP / 连接池 / 代理路由）。这一步做完，业务就写进新库了。

**⑥ 建反向复制，保回滚。** 立刻反向搭一条 green→blue 的发布/订阅，让 blue 持续追 green 的新数据。这样万一新库有问题，blue 的数据还来得及回退：

```sql
-- green：建反向发布
CREATE PUBLICATION rollback_pub FOR ALL TABLES;
-- blue：建反向订阅（结构两侧一致，数据已在切换点对齐）
CREATE SUBSCRIPTION rollback_sub
  CONNECTION 'host=<green_host> port=5432 dbname=<db> user=replicator password=<密码>'
  PUBLICATION rollback_pub;
```

> [!tip]
> 停写 → 追平 → 同步序列 → 断订阅 → 切连接 → 建反向，这几步一气呵成，中间 blue 处于只读/摘流量状态。切换窗口长短主要由第 ③ 步的序列数量决定，序列越多越久。

## 阶段 4：验证与收尾

- 抽样核对：`count`、关键业务查询、自增主键是否正常增长；
- 观察期内 blue 通过反向订阅持续同步，保持"随时可回退"；
- 确认 green 稳定运行数天后，解除反向订阅、下线 blue、清理遗留复制槽：

```sql
-- blue：观察期结束、确定不再回滚时
DROP SUBSCRIPTION rollback_sub;   -- 会连带删除它对应的复制槽
```

# PG 17+ 的两处省力

从 **PG 17** 起有两个特性，能明显减少切换前的准备量：

- **`pg_upgrade` 保留逻辑复制槽与订阅状态。** 老版本 `pg_upgrade` 后订阅/槽会丢，得重建；17 起这些状态被带到新集群。于是"**先对目标集群做原地 `pg_upgrade`，再把它转为逻辑订阅者**"这条路更顺——不用再手工恢复发布/订阅配置。
- **`pg_createsubscriber`：把物理备库直接转成逻辑订阅者。** 如果 blue 本来就带着一个物理流复制备库，可以用它把该备库原地变身为指向新集群的逻辑订阅者，**省掉逻辑复制最耗时的初始快照/全量数据拷贝**（数据早已通过流复制备好了），初始同步时间大幅缩短。示例（参数以官方手册为准）：

  ```bash
  # 示意：把一个物理备库的数据目录转换成 green 的逻辑订阅者
  /opt/postgresql/app/versions/18.7/bin/pg_createsubscriber \
    --pgdata <standby_datadir> --all \
    --publisher-server <green_host> --publisher-port 5432 \
    --publisher-user replicator -v
  ```

> [!note]
> 若源版本低于 17，上面两条都不适用，老老实实走「阶段 1 导 Schema + 阶段 2 全量逻辑同步」的通用路径即可。

# 避坑

- **跨多大版本却不读 Migration 章节**：从 15 直接到 18 时，沿途几个大版本删掉的参数/函数/类型、改掉的默认值（典型如 `password_encryption` 转 scram）会一次性积压到新库，切换后才暴雷。务必逐版读 “Migration to version N” 并建版本迁移清单（见「跨多大版本的额外功课」）。
- **无主键表漏网**：切到一半 UPDATE/DELETE 报错或复制卡住。切换前三问第一问过一遍，主键补齐或 `REPLICA IDENTITY FULL`。
- **切换期没冻结 DDL**：新旧 Schema 漂移、订阅中断。结构变更要全部抢在切换前落到 green，窗口内禁 DDL。
- **忘了同步序列**：切换后主键冲突、业务报 duplicate key。这是切换窗口的主要耗时项，务必在停写后把 blue 序列值刷到 green。
- **green 缺扩展**：订阅初始化或写入时因未知类型/运算符失败。先在新版本目录装好扩展、`CREATE EXTENSION` 再搭订阅。
- **`wal_level` 没改就建发布**：`CREATE PUBLICATION`/建槽会失败或发布不动。blue 必须先 `wal_level=logical` 并重启。
- **订阅端表不存在**：逻辑复制不会自动建表，Schema 那步没导全就订阅会报错。确保 green 上同名表齐备。
- **复制槽泄漏**：中途放弃却没 `DROP SUBSCRIPTION`，发布端残留非活跃槽，WAL 只增不减、磁盘被撑爆。收尾务必清理 `pg_replication_slots` 里的孤儿槽。
- **长事务拖住追平**：停写后仍有大事务/空闲事务占着，`confirmed_flush_lsn` 推不动，切换一直等不到追平。切前先 kill 掉空闲事务。
- **反向订阅建得太晚**：切换后到建反向复制之间有空档，这期间 green 上的新写入 blue 没有，一旦回滚就丢数据。停写窗口内就该把反向链路拉起来。

# 总结

不停服升级的内核就一句话：**蓝绿并存，逻辑复制在线同步，切换只停写一个短窗口，再靠反向复制兜回滚**。落地节奏是「建 green（wal_level=logical + 装扩展）→ `pg_dump --schema-only` 只导结构 → 建发布/订阅全量+增量同步 → 切换（停写·追平·同步序列·断订阅·切连接·建反向）→ 观察后下线旧库」。成败早在切换前就定了：**主键、DDL 冻结、扩展可用**三样缺一不可。切换窗口主要耗在序列同步，序列越多越久。相比 [03 篇](./03.Ubuntu系统安装PostgreSQL.md) 的 `pg_upgrade` 短停服法，它用更高的复杂度和一点应用改造，换来秒级的用户无感。源版本 ≥ 17 时，`pg_upgrade` 保订阅状态 + `pg_createsubscriber`（物理备库转逻辑订阅）能再省一大截准备与初始同步时间。
