# 概述

**复制（replication）** 把一个 PostgreSQL 实例（**主库 / primary**）的数据变化持续同步到另一个实例（**备库 / standby**），用于**读扩展**（分流只读查询）、**高可用**（主库故障时备库顶上）、以及**就近灾备**。PostgreSQL 内建两类复制：

- **流复制（streaming replication）**：基于 **WAL** 的物理复制，备库是主库的字节级镜像，可开 **hot_standby** 提供只读查询。本篇重点。
- **逻辑复制（logical replication）**：按表/发布订阅，异构版本、可选择性同步，见文末简述。

# 流复制工作原理

主库把事务产生的 **WAL（预写日志）** 通过专门的 **walsender** 进程流式传给备库的 **walreceiver**，备库不断重放 WAL 保持一致。整个过程异步（也可配置半同步），因此主备之间存在**复制延迟（replication lag）**。

前提：主库 **wal_level=replica**（默认已是）、预留足够 **max_wal_senders** / **max_replication_slots**。

# 配置主库

## 参数（postgresql.conf）

```ini
wal_level = replica
max_wal_senders = 10          # 可并发的 walsender 数
max_replication_slots = 10    # 复制槽数量
listen_addresses = '*'        # 允许远程连接
```

## 认证（pg_hba.conf）

给复制连接放行（用专门的 **replicator** 角色）：

```text
host    replication    replicator    10.0.0.0/24    scram-sha-256
```

创建复制角色并改后 **reload**：

```sql
CREATE ROLE replicator REPLICATION LOGIN PASSWORD 'Repl#2026';
```

# 搭建备库

最省事的方式是用 **pg_basebackup** 直接从主库克隆一份基础备份作为备库起点（详见 **[备份和恢复](./040.备份和恢复.md)** 的物理备份）：

```bash
pg_basebackup -h 10.0.0.1 -U replicator -D /var/lib/pgsql/18/data \
    -P -R -X stream -c prompt -S standby1
```

- **-R** 自动生成备库连接配置（写入 **primary_conninfo** 并创建 **standby.signal**）。
- **-X stream** 一并流式拉取所需 WAL，保证备份自洽。
- **-S standby1** 顺便创建名为 standby1 的物理复制槽（可选）。

启动备库后，它会自动进入恢复模式，持续拉取并重放主库 WAL。用 **postgresql.conf** 里的 **primary_conninfo** 指定源，例如：

```ini
primary_conninfo = 'host=10.0.0.1 port=5432 user=replicator password=Repl#2026 application_name=standby1'
```

# 监控复制状态

## 主库侧：pg_stat_replication

```sql
SELECT pid, application_name, client_addr, state, sync_state,
       sent_lsn, write_lsn, flush_lsn, replay_lsn,
       replay_lag
FROM pg_stat_replication;
```

```text
  pid  | application_name | client_addr |   state   | sync_state | replay_lag
-------+------------------+-------------+-----------+------------+------------
  4820 | standby1         | 10.0.0.2    | streaming | async      | 00:00:00
```

- **state = streaming** 表示正在正常传输。
- 比较 **sent_lsn** 与 **replay_lsn** 的差距即复制延迟；**replay_lag** 直接给出时间。

## 备库侧

```sql
SELECT pg_is_in_recovery();          -- true 表示这是备库/恢复中
SELECT last_wal_replay_lsn, receiver_status
FROM pg_stat_wal_receiver;
```

## 复制槽

物理槽确保主库在备库追上之前不回收对应 WAL（避免"备库跟不上被主库清掉 WAL"）：

```sql
SELECT slot_name, slot_type, active, restart_lsn
FROM pg_replication_slots;
```

> 注意：不活跃（**active=false**）的槽会**持续占用并堆积 WAL**，可能导致主库磁盘撑满，务必及时 **pg_drop_replication_slot()** 清理失效槽。

# 同步 vs 异步复制

默认**异步**：主库提交不等备库确认，性能最好，但主库彻底宕机可能丢失极少量未传输的事务。要求零数据丢失可配**同步复制**：

```ini
synchronous_standby_names = 'FIRST 1 (standby1, standby2)'
```

代价是每次提交都要等至少一个备库落盘确认，写延迟上升。折中方案还有 **remote_write**、**remote_apply** 等同步级别，以及半同步。

# 故障切换与提升

备库可在需要时**提升（promote）**为新主库：

```bash
pg_ctl promote -D /var/lib/pgsql/18/data
# 或 SQL：SELECT pg_promote();
```

手工提升门槛低，但要自动检测主库故障并自动切换，一般交给 **Patroni**、**repmgr**、**Pgpool-II** 等高可用工具，配合 etcd/consul 做分布式共识，避免"脑裂"。生产高可用方案应明确：故障检测、自动提升、旧主修复后作为新备库回归（**pg_rewind**）的完整流程。

# 逻辑复制简述

**逻辑复制**基于"发布/订阅"，只同步指定表、支持跨大版本、可从副本继续，适合零停机迁移、数据分发、ETL：

```sql
-- 主库
CREATE PUBLICATION pub_orders FOR TABLE orders;
-- 备库
CREATE SUBSCRIPTION sub_orders
    CONNECTION 'host=10.0.0.1 dbname=app user=svc password=...'
    PUBLICATION pub_orders;
```

监控用 **pg_stat_subscription**。物理 vs 逻辑：

| 维度     | 流复制（物理）   | 逻辑复制             |
|----------|------------------|----------------------|
| 粒度     | 整个实例         | 按库/表              |
| 备库可写 | 否（只读）       | 订阅端可独立写       |
| 跨版本   | 通常需一致       | 支持异构版本         |
| 典型用途 | HA、读扩展、灾备 | 迁移、分发、增量同步 |

# 总结

流复制通过传输并重放 **WAL** 让备库与主库保持一致，配置要点是主库 **wal_level=replica** + 复制角色 + **pg_hba.conf** 放行，用 **pg_basebackup -R** 快速拉起备库。运维上盯 **pg_stat_replication** 的 **replay_lag** 与复制槽的 **active** 状态（防 WAL 堆积），按数据安全性需要在**异步/同步**间取舍，故障时用 **pg_promote()** 提升、并用 **pg_rewind** 让旧主回归，自动化则由 Patroni/repmgr 等完成。需要按表同步或跨版本时用**逻辑复制**。
