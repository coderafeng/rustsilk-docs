# 概述

PostgreSQL 采用 **MVCC（多版本并发控制）**：UPDATE / DELETE 并不真正覆盖旧行，而是把旧版本标记为**死元组（dead tuple）**。回收死元组、维护统计信息、抑制表膨胀，是数据库长期稳定运行的日常维护工作，主要由 **VACUUM** 与 **ANALYZE**（合称 **vacuumdb / autoanalyze**）承担。

# VACUUM：回收死元组

普通 **VACUUM** 做两件事：把死元组占用的空间标记为可复用、清除事务 ID 以防回卷（wraparound），**但不会缩小表文件、不归还磁盘空间**。

```sql
-- 清理单表
VACUUM customer;

-- 清理当前库所有表（不设表名）
VACUUM;
```

## VACUUM FULL：真正收缩文件

**VACUUM FULL** 会把表（及索引）重写到更小的物理文件、真正归还磁盘空间，代价是**对目标表持有排他锁、阻塞读写**，只应在维护窗口、且确认膨胀严重时对个别表使用：

```sql
VACUUM (FULL, ANALYZE, VERBOSE) customer;
```

**VACUUM** 常用选项（写在括号里）：

| 选项            | 作用                                 |
|-----------------|--------------------------------------|
| **FULL**        | 重写表以回收磁盘空间（持重锁，慎用） |
| **FREEZE**      | 强制冻结元组事务 ID，防回卷          |
| **ANALYZE**     | 清理后顺带更新统计                   |
| **VERBOSE**     | 打印每张表的清理细节                 |
| **PARALLEL n**  | 并行处理索引（PG13+）                |
| **SKIP_LOCKED** | 表被锁定时跳过而非等待               |

## 判断是否需要清理

通过 **[监控活动与连接](./060.监控活动与连接.md)** 提到的 **pg_stat_user_tables** 看死元组堆积：

```sql
SELECT relname, n_live_tup, n_dead_tup,
       round(n_dead_tup * 100.0 / nullif(n_live_tup + n_dead_tup, 0), 1) AS dead_pct,
       last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;
```

**dead_pct** 偏高（例如长期 > 20%）说明该表写放大严重、清理跟不上。

# ANALYZE：更新统计信息

**ANALYZE** 采样表的列分布，写入 **pg_statistic**，供查询优化器估算行数、选择执行计划（直接影响 **[EXPLAIN](./045.EXPLAIN.md)** 的质量）。大批量增删改后应手动 ANALYZE：

```sql
ANALYZE customer;    -- 分析单表
ANALYZE;             -- 分析当前库所有表
```

VACUUM 与 ANALYZE 常配合使用：**VACUUM ANALYZE**。

# Autovacuum：自动后台清理

默认开启的 **autovacuum** 后台守护进程会在表变更达到阈值时自动执行 VACUUM / ANALYZE，无需人工干预。核心参数：

| 参数                                | 默认 | 含义                               |
|-------------------------------------|------|------------------------------------|
| **autovacuum**                      | on   | 总开关                             |
| **autovacuum_vacuum_scale_factor**  | 0.2  | 死元组超过表大小的 20% 触发 vacuum |
| **autovacuum_vacuum_threshold**     | 50   | 触发 vacuum 的最小死元组数         |
| **autovacuum_analyze_scale_factor** | 0.1  | 变更超 10% 触发 analyze            |
| **autovacuum_max_workers**          | 3    | 并发工作进程数                     |

对**热点大表**（20% 阈值对应绝对量太大、清理不及时），可针对单表调小阈值，让 autovacuum 更积极：

```sql
ALTER TABLE rental SET (
    autovacuum_vacuum_scale_factor = 0.02,
    autovacuum_analyze_scale_factor = 0.01
);
```

用 **pg_stat_progress_vacuum** 可观测正在进行的 vacuum 进度；**pg_stat_user_tables** 的 **last_autovacuum / last_autoanalyze** 反映上次自动清理时间。

# 索引维护：REINDEX

长期增删改后索引可能膨胀，PostgreSQL 提供 **REINDEX**（PG12+ 支持 **CONCURRENTLY** 在线重建，不长时间阻塞写）：

```sql
REINDEX INDEX  idx_name;
REINDEX TABLE  concurrently customer;   -- 在线重建某表所有索引
REINDEX DATABASE concurrently sakila;   -- 在线重建某库索引
```

关于索引的类型与创建，见 **[06.PostgreSQL 索引](../06.PostgreSQL%20索引/000.索引类型.md)**。

# 命令行工具 vacuumdb

**vacuumdb** 在 Shell 中对整库/多库批量执行 VACUUM / ANALYZE，便于放进定时任务：

```bash
# 对 sakila 做 VACUUM ANALYZE
vacuumdb -U postgres --analyze-in-stages sakila

# 仅 ANALYZE 所有库
vacuumdb -U postgres --all --analyze-only
```

# 维护节奏建议

- **依赖 autovacuum 为主**，保证默认开启且资源充足（**max_workers**、维护窗口内存）。
- 对**大表/热点表**单独收紧阈值，避免膨胀失控。
- **VACUUM FULL / REINDEX** 属于重操作，安排在低峰维护窗口，优先用 **CONCURRENTLY** 变体。
- 大批量导入后立即 **ANALYZE**，让计划尽快恢复准确。

# 总结

日常维护三件套：**VACUUM** 回收死元组、防事务 ID 回卷（**VACUUM FULL** 才真正缩文件但持重锁），**ANALYZE** 更新统计以保障优化器决策，二者常被 **autovacuum** 自动完成。热点大表应针对性调低 autovacuum 阈值，索引膨胀用 **REINDEX ... CONCURRENTLY** 处理，命令行 **vacuumdb** 便于自动化。监控死元组与清理时间则依赖 **pg_stat_user_tables**。
