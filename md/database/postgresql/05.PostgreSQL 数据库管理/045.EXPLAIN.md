# 概述

**EXPLAIN** 用来查看一条语句的 **执行计划（execution plan）** ——即 PostgreSQL 的查询优化器决定"如何执行"这条查询，包括使用哪些扫描方式、哪些索引、表之间的连接顺序与算法、每一步的预估代价与行数。

它是性能分析的入口：当一条查询慢时，第一步通常是 **EXPLAIN** 看优化器的选择是否合理。

# EXPLAIN 语法

```sql
EXPLAIN [ (选项) ] 语句;
```

最常用的两种形式：

```sql
EXPLAIN SELECT ...;            -- 只显示预估的执行计划（不真正执行）
EXPLAIN ANALYZE SELECT ...;    -- 真正执行并显示"实际"耗时与行数
```

| 选项                               | 作用                                                             |
|------------------------------------|------------------------------------------------------------------|
| **ANALYZE**                        | 实际执行语句，输出每步真实时间与行数（会真的跑一遍，写操作慎用） |
| **VERBOSE**                        | 输出更详细信息（如完整输出列、表名）                             |
| **COSTS**                          | 显示代价估算（默认开启）                                         |
| **BUFFERS**                        | 显示缓冲区/磁盘块读取统计，判断是否命中缓存                      |
| **TIMING**                         | 显示每步实际耗时（配合 ANALYZE）                                 |
| **FORMAT {TEXT\|JSON\|YAML\|XML}** | 输出格式，默认 TEXT                                              |

> 提示：**ANALYZE** 会真正执行语句。对 **SELECT** 安全，对 **INSERT/UPDATE/DELETE** 若要避免修改数据，需包在外层 **BEGIN ... ROLLBACK** 事务中。

# 读执行计划

先看一个未使用索引的例子：

```sql
EXPLAIN ANALYZE
SELECT * FROM customer WHERE store_id = 1;
```

```text
Seq Scan on customer  (cost=0.00..29.30 rows=131 width=320) (actual time=0.030..0.180 rows=131 loops=1)
  Filter: (store_id = 1)
  Rows Removed by Filter: 343
Planning Time: 0.085 ms
Execution Time: 0.245 ms
```

解读要点：

- **算子名称**：**Seq Scan**（顺序扫描）、**Index Scan**（索引扫描）、**Nested Loop**、**Hash Join**、**Sort**、**Aggregate** 等，表示"做了什么操作"。缩进的算子是输入，先执行最内层。
- **cost=0.00..29.30**：启动代价 .. 总代价（单位是抽象的"代价"，反映磁盘页与 CPU 工作量，用于比较而非绝对时间）。**rows** 是预估行数，**width** 是每行平均字节数。
- **actual time ... rows=131**：仅 ANALYZE 时出现，是真实的每行累计毫秒与**实际**行数。**loops** 是该算子被重复执行的次数。
- **Filter / Rows Removed by Filter**：被过滤条件筛掉多少行。
- **Planning Time / Execution Time**：优化器规划耗时与实际执行总耗时。

**关注"预估 rows 与 actual rows 是否接近"**：差距大说明统计信息过期，应执行 **ANALYZE 表名;** 更新统计（见下文）。

# 用索引前后对比

**customer.store_id** 没有索引时走 **Seq Scan**。若为其建立索引：

```sql
CREATE INDEX idx_customer_store ON customer (store_id);
```

再次 **EXPLAIN ANALYZE** 同一查询，计划变为：

```text
Bitmap Heap Scan on customer  (cost=4.65..24.30 rows=131 width=320) (actual time=0.020..0.080 rows=131 loops=1)
  Recheck Cond: (store_id = 1)
  Heap Blocks: exact=... 
  ->  Bitmap Index Scan on idx_customer_store  (cost=0.00..4.61 rows=131 width=0) (actual time=0.015..0.015 rows=131 loops=1)
        Index Cond: (store_id = 1)
```

从全表 **Seq Scan** 变成走 **idx_customer_store** 的索引扫描，扫描的数据量显著下降。这正是通过 EXPLAIN 判断"要不要加索引"的典型用法。更多索引内容见 **[创建索引](../06.PostgreSQL%20索引/010.索引的基本操作.md)**。

# 常见算子速查

| 算子                               | 含义 / 关注点                                                                    |
|------------------------------------|----------------------------------------------------------------------------------|
| **Seq Scan**                       | 全表顺序扫描；大表上频繁出现往往提示缺索引                                       |
| **Index Scan / Bitmap Index Scan** | 走索引；选择性越好收益越大                                                       |
| **Nested Loop**                    | 嵌套循环连接，小结果集快，大表笛卡尔会爆炸                                       |
| **Hash Join**                      | 哈希连接，等值连接大表常用                                                       |
| **Merge Join**                     | 归并连接，要求输入已排序                                                         |
| **Sort**                           | 排序；若为 ORDER BY 触发大量外置排序（external merge）需关注 work_mem 或索引顺序 |
| **Aggregate / GroupAggregate**     | 聚合；配合 GROUP BY                                                              |

# 让优化器选对计划

执行计划的质量高度依赖**统计信息**。定期（或大批量数据变更后手动）运行：

```sql
ANALYZE customer;      -- 更新单表统计
ANALYZE;               -- 更新当前库所有表统计
```

统计信息更新后，**EXPLAIN** 中预估 **rows** 会更贴近实际，优化器也更容易选对索引与连接方式。

# 总结

**EXPLAIN** 显示预估执行计划，**EXPLAIN ANALYZE** 实际执行并给出真实耗时与行数。读计划要抓三件事：**用了什么算子**（Seq Scan 还是 Index Scan）、**预估行数与实际行数是否接近**、**代价与耗时最高的一步在哪**。据此判断是否需要建索引、改写查询或用 **ANALYZE** 更新统计，是 PostgreSQL 查询调优的基本功。
