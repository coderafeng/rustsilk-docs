# 概述

系统允许一张表上建多个索引。查询条件复杂时，PostgreSQL 能**把多个索引组合起来**使用——例如同时用 `title` 上的索引和 `release_year` 上的索引去找"1994 年发行的某部电影"。

但组合有明确的强弱边界：

- **AND 组合**（多个条件同时成立）：多列索引几乎总是**更好**的选择；
- **OR 组合**（条件二选一）：单靠多列索引无能为力，必须把多个索引的结果**求并集**——这正是 PostgreSQL 独有的位图组合能力。

# 位图扫描（Bitmap Scan）

索引组合靠的是**位图扫描**机制。计划中通常看到两个节点：

```text
Bitmap Heap Scan on film
  Recheck Cond: (...)
  ->  Bitmap Index Scan on idx_film_title
        Index Cond: (title = 'AWESOME TOUCHDOWN')
```

工作方式：

1. **Bitmap Index Scan**：扫索引，把命中的行的物理位置记录进一张**内存位图**（每个表块 1 bit）。这一步可以**同时跑多个索引**，并对位图做 **AND / OR 合并**；
2. **Bitmap Heap Scan**：按位图**顺序**访问表块（把随机 I/O 变成按块号有序的批量读），每块内再按位图取行。

位图扫描的优点：**每个数据块只读一次**（普通 Index Scan 命中同一块多次就会读多次）、大块命中时 I/O 接近顺序读。代价：**不保持索引顺序**（所以位图扫描不能服务 ORDER BY，见 **[索引和 ORDER BY](./020.索引和%20ORDER%20BY.md)**），且位图要占 `work_mem`。

# 用 AND 组合多列

设 film 表上分别有 `idx_film_title (title)` 与 `idx_film_year (release_year)`：

```sql
SELECT * FROM film WHERE title = 'AWESOME TOUCHDOWN' AND release_year = 2006;
```

两个单列索引的位图 **AND** 起来即可加速。但**更优解是建一个多列索引**：

```sql
CREATE INDEX idx_film_title_year ON film (title, release_year);
```

原因：

- 多列 B-tree 可以只用**一次索引下降**精确定位，选择性直接是两列乘积；
- AND 组合的单列索引方案里，若其中一个条件选择性差（比如 year 命中 300 行、title 命中 2 行），要为"最终只有 2 行"先付出扫 300 行位图的代价。

> **能力边界**：PostgreSQL **不能**用两个索引高效完成"**同一列**上的两个不同约束"（如 `release_year > 2000 AND release_year < 2005` 只需一个索引的范围端点即可），也**不推荐**指望"每个 WHERE 条件都各配一个索引"——把多条件 AND 的期望交给**一个排序合理的多列索引**（见 **[多列索引](./015.多列索引.md)**）。

# 用 OR 组合多列

```sql
SELECT * FROM film WHERE release_year = 2006 OR rating = 'PG';
```

**OR 条件是多列索引的死角**：`(release_year, rating)` 索引只能加速"约束前导列"的查询，对"第二列单独成立"的分支无能为力。此时优化器会：

- 为每个分支各扫一个索引，生成两张位图；
- **OR（并集）** 合并位图，再 Bitmap Heap Scan。

所以服务"频繁 OR 查询"的列，**各建单列索引**比硬凑多列索引更合理。若 OR 两边列重叠复杂，也可改写成 `UNION ALL` 子查询让每个分支独立走索引（注意去重语义）。

# 位图的质量控制：lossy 与 recheck

位图默认**只记录到块级**，不记录块内具体行偏移（省内存）。当命中块很多、`work_mem` 不够用时，位图退化为**纯块集合**——此时：

- 计划中出现 `Heap Blocks: lossy=n`；
- 整块都要被读取并**重新用查询条件逐行检查**（`Recheck Cond`），产生额外 CPU。

调优手段：适度增大会话级 `work_mem`（比如 `SET work_mem = '16MB';`）让更多行偏移能记进位图；`max_bitmapmessage_size` 限制位图消息体积。

# 元组剪枝与懒惰 VACUUM

**索引条目是"懒惰"的**：UPDATE 后索引里可能同时存在新旧两条目，死元组要等 VACUUM 才清理。被位图扫描挡在门外就好——**Bitmap Heap Scan 在扫表块时会直接丢弃过期/死元组（tuple pruning），不必为它们回表检查可见性**。这意味着：

> 长时间不 VACUUM 的热点表，Index Scan 会因大量死索引项而变慢，但位图扫描受影响较小——**膨胀的索引建议及时清理**（见 **[日常维护](../05.PostgreSQL%20数据库管理/065.日常维护.md)** 的 autovacuum 与 REINDEX）。

# 索引与 NULL

索引**不是只索引非 NULL 值**——B-tree 把 NULL 也当作"可排序的特殊值"存进索引（默认全部排在最大端）。因此：

```sql
SELECT * FROM film WHERE replacement_cost > 20;   -- NULL 行不会命中（比较结果为 NULL）
SELECT * FROM film WHERE replacement_cost IS NULL; -- ✅ 能用 B-tree 索引找 NULL
```

官方结论：**B-tree、Hash、GiST、SP-GiST、GIN 都会索引 NULL 值**（各自的排序/比较策略不同），因此它们的 `IS NULL` 检索都能用索引；**BRIN 是例外——它不索引 NULL，也无法用于检索 NULL**。如果查询频繁按 `IS NULL` / `IS NOT NULL` 过滤，B-tree 索引完全胜任，无须特殊设计；但注意 `IS NOT NULL` 通常选择性极差，优化器多数时候仍会选顺序扫描。

# 总结

- **AND 多条件** → 优先设计**一个多列索引**；多个单列索引靠位图 AND 只是兜底。
- **OR 条件** → 只能**各列各建索引**，靠位图 OR 合并；多列索引帮不上。
- 位图扫描把随机回表变顺序读，但丢序、受 `work_mem` 制约，lossy 时回表 recheck。
- NULL 会被 B-tree 索引，`IS NULL` 可走索引；BRIN 除外。
