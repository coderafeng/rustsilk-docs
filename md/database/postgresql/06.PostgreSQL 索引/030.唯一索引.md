# 概述

**唯一索引（Unique Index）** 在加速查询之外，还承担一份更重要的职责：**保证数据完整性**——它强制索引列（列组合）的值在全表内不重复。PostgreSQL 会自动为 `PRIMARY KEY` 和 `UNIQUE` 约束创建对应的唯一索引；你也可以用 `CREATE UNIQUE INDEX` 手动创建。

作为后端开发，你应该把唯一索引理解为**最后一道数据防线**：应用层的"先查后插"在并发下必然有竞态，只有数据库的唯一约束能真正做到"绝不重复"。

# 创建唯一索引

## 约束方式（推荐）

```sql
CREATE TABLE staff (
    staff_id  serial PRIMARY KEY,          -- 主键约束 → 自动唯一索引，且 NOT NULL
    store_id  int REFERENCES store(store_id),
    email     varchar(50) UNIQUE NOT NULL  -- 唯一约束 → 自动唯一索引 staff_email_key
);

-- 表级多列唯一
ALTER TABLE rental ADD CONSTRAINT uq_rental_inv_date
    UNIQUE (inventory_id, rental_date);
```

## 直接建索引方式

```sql
CREATE UNIQUE INDEX uk_customer_email ON customer (email);
```

两种写法效果等价，但**约束方式语义更清晰**、便于用 `ALTER TABLE ... DROP CONSTRAINT` 管理，还能被 `INSERT ... ON CONFLICT` 按约束名引用。列级与表级 `UNIQUE` 的差别只在多列：列级 `UNIQUE (a, b)` 写法的约束作用于列组合，而分开两个列级 UNIQUE 是两个独立约束。

> **约束与索引的对应关系**：主键/唯一约束"拥有"它的支撑索引。直接 `DROP INDEX staff_email_key` 会因依赖而失败（或 CASCADE 删掉约束）；正确姿势是 `ALTER TABLE staff DROP CONSTRAINT staff_email_key;`。

# NULL 与唯一性

在 SQL 的标准语义（PostgreSQL 遵循）里，**NULL 与任何值都不相等，包括另一个 NULL**。因此：

> **唯一索引允许出现多行 NULL**——`email` 上 10 行全是 NULL 不违反唯一约束。

| PostgreSQL 版本 | 行为                                                                                                  |
|-----------------|-------------------------------------------------------------------------------------------------------|
| 15 以前         | 只有 `NULLS DISTINCT`（默认）行为：多 NULL 可共存                                                     |
| 15 起           | 可显式选择：`UNIQUE NULLS DISTINCT`（默认）/ `UNIQUE NULLS NOT DISTINCT`（NULL 也视作相等，只许一个） |

```sql
-- PostgreSQL 15+：即使 email 为 NULL，也只允许出现一行
CREATE UNIQUE INDEX uk_customer_email_strict
    ON customer (email) NULLS NOT DISTINCT;
```

若在不支持该语法的旧版本上想要"NULL 也只许一个"，可用**部分索引**变通：`CREATE UNIQUE INDEX ... ON t (col) WHERE col IS NOT NULL;`（见 **[部分索引](./040.部分索引.md)**）。

# 唯一性对性能的影响

唯一约束不是白给的，写入路径上有真实成本：

1. **每次 INSERT/UPDATE 都要做冲突检查**：需要按新键值下降索引，找到已有同名条目后，**还必须取出整行**检查其可见性（对方事务是否已提交/回滚）。这使得唯一索引比非唯一索引的插入更慢，且**无法做"仅索引插入"的极简路径**。
2. **ON CONFLICT 依赖唯一索引**：`INSERT ... ON CONFLICT (cols) DO UPDATE`（upsert）的目标列**必须有唯一索引/约束支撑**，否则报"没有匹配的约束/索引"。

```sql
-- 依赖 uk_customer_email 的 upsert
INSERT INTO customer (email, first_name, last_name, ...)
VALUES ('new@mail.com', 'New', 'Name', ...)
ON CONFLICT (email) DO UPDATE SET first_name = EXCLUDED.first_name;
```

3. **读路径无额外开销**：查询时唯一索引与普通 B-tree 行为一致；而且对 `WHERE email = 'x'` 这类等值查询，优化器**知道最多返回一行**，计划代价估算更准。

# 用表达式实现"业务唯一"

唯一性经常是**业务语义**的而非字面的——比如"邮箱大小写不敏感唯一"。把 **[表达式索引](./035.表达式索引.md)** 与 UNIQUE 组合即可：

```sql
CREATE UNIQUE INDEX uk_customer_email_lower ON customer (lower(email));
```

查询/写入时只要条件写成同样的 `lower(email) = ...`，既享受加速又享受约束。更进一步，配合 **[部分索引](./040.部分索引.md)** 可以表达"仅在用的记录才要求唯一"：

```sql
-- 只有未删除的账号占用用户名
CREATE UNIQUE INDEX uk_username_active ON "user" (username) WHERE deleted_at IS NULL;
```

# 什么时候不该用唯一索引

- **列值天然多对一**（如 `store_id`、外键、状态列）：普通索引或不建。
- **高频随机写入的大表**：唯一检查带来的"取行验可见性"在热点键上可能引发锁等待，评估是否改为"批量导入前查重 + 导入后建约束"。
- **不要靠唯一索引"兼职"外键**：跨表引用完整性用 `FOREIGN KEY` 表达（性能上记得给外键列建索引）。

# 总结

唯一索引 = **B-tree 的查询加速 + 数据库级完整性承诺**。优先用 `PRIMARY KEY` / `UNIQUE` 约束声明它；记住"多个 NULL 允许共存"（或 15+ 用 `NULLS NOT DISTINCT` 收紧）；用表达式 + 部分索引可以表达几乎任何业务唯一语义。它的对偶话题是"函数结果能不能建索引"，见 **[表达式索引](./035.表达式索引.md)**；建完后同样要在 **[检查索引使用情况](./060.检查索引使用情况.md)** 里确认约束索引未被意外禁用。
