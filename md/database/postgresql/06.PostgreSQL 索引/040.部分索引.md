# 概述

**部分索引（partial index）** 是对表的**一个子集**建立的索引——通过 `CREATE INDEX` 末尾的 `WHERE` 条件（索引谓词）指定。

它的价值主张很直接：**如果只有一小部分行需要被索引，就别为全部行付索引的钱**。带来的收益包括：

- **索引更小**：构建更快、占用磁盘与缓存更少；
- **维护更便宜**：不匹配谓词的行写入时完全不必碰这个索引；
- **可以更聪明**：配合 UNIQUE 表达"子集内唯一"这类普通索引做不到的约束。

# 语法

```sql
CREATE INDEX 名称 ON 表名 [ USING 方法 ] ( 索引列 [, ...] )
    [ WHERE 谓词 ];
```

谓词是一个**普通的 SQL 条件**。PostgreSQL 在插入/更新每一行时求值，只有结果为真的行才会生成索引条目；查询时，优化器必须**证明查询条件是该谓词的子集**才会使用这个索引。

# 典型场景

## 1. 只索引"值得查"的那部分行

Sakila 的 `payment` 表绝大多数是历史记录，业务只频繁查询"未退款/近 7 天"的支付：

```sql
-- 只索引近段数据（谓词列需固定区间，见下文"不要用 now()"）
CREATE INDEX idx_payment_recent ON payment (customer_id, payment_date)
    WHERE payment_date >= '2026-09-01';
```

对绝大多数以 `payment_date >= '2026-09-01'` 起步的查询，优化器能推断"查询范围 ⊆ 索引范围"，走这个**又小又快**的索引。

## 2. 避免索引"显然不需要查"的值

低基数列上某个值占 95%（如 `active` 列，历史客户全是 false，仅活跃客户 true 占 5%）。全量索引几乎没过滤力还拖累写入，**部分索引只索引那 5%**：

```sql
CREATE INDEX idx_customer_active ON customer (store_id)
    WHERE active;          -- 等价于 WHERE active = true

-- ✅ 能用上：条件蕴含谓词
SELECT * FROM customer WHERE active AND store_id = 1;

-- ❌ 用不上：查的是补集，索引里根本没有这些行
SELECT * FROM customer WHERE NOT active;
```

## 3. 表达"子集唯一"的业务约束

经典需求："同一租户内的用户名唯一，但已软删除的记录不占用用户名"：

```sql
CREATE UNIQUE INDEX uk_user_tenant_name ON "user" (tenant_id, username)
    WHERE deleted_at IS NULL;
```

这是**普通唯一索引做不到**的——它允许 `(tenant, 'bob')` 在"已删除"的世界里出现任意多次，却在"存活"的世界里强制唯一。

## 4. 只为某种类型的数据建索引

继承表或多态表中只索引特定子类型：

```sql
CREATE INDEX idx_doc_pdf_meta ON document (uploaded_at) WHERE kind = 'application/pdf';
```

## 5. 与表达式索引组合

只索引"确实包含某特征"的行，配合数组/JSONB 存在性检查（见 **[表达式索引](./035.表达式索引.md)**）：

```sql
CREATE INDEX idx_film_first_feature ON film
    ((special_features[1]))
    WHERE cardinality(special_features) > 0;
```

表达式列 + 部分谓词可以叠加使用，两者互不冲突。

# 陷阱与限制

## 谓词不能用 volatile 函数

`now()`、`current_date`、`random()` 一律禁止——索引条目一旦生成就不会随时间"漂移"，用 `WHERE payment_date >= now() - interval '7 days'` 会把"昨天的行"永远留在索引里，**语义错误**。"滚动窗口"的正确解法是**固定界限 + 定期重建/分区**。

## 优化器不会自动"脑补"等价条件

谓词与查询条件必须**可证明蕴含**。大小写、函数包装、表达式写法不同都可能让匹配失败：

```sql
-- 索引: WHERE status = 'paid'
SELECT ... WHERE status IN ('paid');        -- ✅ 通常能用
SELECT ... WHERE status = 'PAID';           -- ❌ 用不上（字符串不同）
```

这是双刃剑：**用错谓词的查询默默走顺序扫描**。上线路径务必用 **[EXPLAIN](../05.PostgreSQL%20数据库管理/045.EXPLAIN.md)** 验证。

## 数据分布会变

部分索引赌的是"子集永远小"。如果 `WHERE active` 的行从 5% 涨到 60%，索引收益消失但维护成本还在。低基数列上的部分索引要**随数据演化定期复查**（配合 **[检查索引使用情况](./060.检查索引使用情况.md)**）。

## 统计信息同样缺失

与表达式索引类似，`ANALYZE` 不为"谓词子集"单独收集列统计，优化器对部分索引的选择性推断可能偏差。PG 14+ 的**扩展统计**只对多列组合有效，覆盖不到这个盲区；严重时同样可考虑生成列物化。

# 总结

部分索引是"**少即是多**"哲学的数据库表达：索引更小、写得更省、还能表达子集唯一这样的高级约束。它有三个纪律——**谓词必须不可变、查询必须被谓词蕴含、子集占比必须长期稳定**。当查询条件与索引列完全匹配却需要"把非键列也装进索引"时，看下一篇 **[仅搜索索引和覆盖索引](./045.仅搜索索引和覆盖索引.md)**。
