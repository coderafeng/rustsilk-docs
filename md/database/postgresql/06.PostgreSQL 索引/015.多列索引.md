# 概述

一张表可以建很多单列索引，但**多列索引（multicolumn index）** 经常更优——它能用一次索引查找同时满足多个条件。B-tree 索引的键可以包含**最多 32 个列**（可按需调大编译常量），列也可以重复出现在同一个索引中。

理解多列索引的一切规则，都建立在一个前提上：**B-tree 的"排序"是按列的先后顺序逐级进行的**——先按第一列排序，第一列相同的再按第二列排序，以此类推。这个"字典序"结构决定了它能加速什么、不能加速什么。

> **索引类型边界**：多列 B-tree 索引的这个概念**只对 B-tree（以及 GiST/GIN 的部分场景）成立**。GIN 的多列（如 JSONB 多键）语义完全不同——它检索的是"多个键的任意组合"，列的先后顺序无关紧要；GiST 则把多维数据编织成统一的树。本篇聚焦 B-tree。

# 最左前缀原则

设有一个 customer 表上的多列索引 `(last_name, first_name)`。B-tree 中的键序为：先按 `last_name` 排，同名再按 `first_name` 排。于是：

| 查询条件                                            | 能否用到索引   | 原因                                         |
|-----------------------------------------------------|----------------|----------------------------------------------|
| `WHERE last_name = 'WONG' AND first_name = 'JANE'`  | ✅ 两列都用    | 完全匹配前缀                                 |
| `WHERE last_name = 'WONG'`                          | ✅ 用到第一列  | 最左前缀                                     |
| `WHERE first_name = 'JANE'`                         | ❌（几乎无效） | **跳过了第一列**，索引对 first_name 整体无序 |
| `WHERE last_name LIKE 'W%' AND first_name = 'JANE'` | ✅ 部分        | 第一列范围扫描中过滤第二列                   |

**核心结论：条件必须约束住索引的"前导列"（第一列），后面的列才有资格参与加速。** 如果业务里存在大量"只按 first_name 查"的请求，官方建议**再单独建一个 `(first_name)` 索引**：

> 如果你经常需要按 second key 检索而 first key 不限，请单独为 second key 建索引。

**skip scan（跳跃扫描）**：**PostgreSQL 18 新增**——当查询没有约束前导列（或对前导列不是等值约束）、但对后续列有有效约束时，规划器可以对 `(a, b)` 索引"跳过" a：内部把 a 的每个不同值依次当作已绑定再扫 b（在 a 的不同值很少时尤其划算）。它是补救手段，不能替代合理的列序设计，也不要在设计上依赖它。

# 等值列在前，范围列在后

列顺序的第二个经验法则：**把用 `=` 的列放前面，用范围（`<`、`BETWEEN`、`LIKE 'x%'`）的列放最后**。

以租赁业务为例，高频查询是"某客户在某时间段内的租赁"：

```sql
SELECT * FROM rental
WHERE customer_id = 13
  AND rental_date BETWEEN '2005-07-01' AND '2005-08-01';
```

正确的设计：

```sql
-- ✅ customer_id 等值在前，rental_date 范围在后
CREATE INDEX idx_rental_cust_date ON rental (customer_id, rental_date);
```

扫描过程：先定位 `customer_id = 13` 的连续区间，**在该区间内** rental_date 恰好有序，可直接取范围边界——一次索引扫描完成两个条件。

反过来 `(rental_date, customer_id)` 就差很多：日期范围命中后，段内 customer_id 无序，第二列帮不上定位，只能边扫边过滤。

# 覆盖多条件的排序与分组

多列索引不仅服务 WHERE，也服务 ORDER BY / GROUP BY（详见 **[索引和 ORDER BY](./020.索引和%20ORDER%20BY.md)**）：

```sql
-- 按门店列出活跃客户，天然按 store_id → last_name → first_name 有序
CREATE INDEX idx_customer_store_name ON customer (store_id, last_name, first_name);

SELECT last_name, first_name FROM customer
WHERE store_id = 2
ORDER BY last_name, first_name;   -- 免排序
```

对 `GROUP BY` 同理：与索引前缀一致的分组列可以利用索引顺序走 GroupAggregate，省掉哈希或排序开销。

# 实战：为查询模式设计索引（Sakila）

场景与索引设计对照：

```sql
-- 场景 1：后台按"姓或姓名"搜客户（姓必填）
--   (last_name, first_name) 一个索引同时服务两种查询
CREATE INDEX idx_customer_name ON customer (last_name, first_name);

-- 场景 2：查某门店 + 状态有效的客户
--   两个都是等值，放一起即可；布尔列无需单独建索引
CREATE INDEX idx_customer_store_active ON customer (store_id, active);

-- 场景 3：支付报表——某客户某时段的支付
CREATE INDEX idx_payment_cust_time ON payment (customer_id, payment_date);
```

**不要为 `(a)`、`(a,b)`、`(a,b,c)` 各建一个索引**——`(a,b,c)` 已覆盖对 a、对 (a,b) 的查找能力，只在"需要 (a,c) 顺序"或统计需求特殊时才考虑加第二个。多余的重复前缀索引是典型的**低收益高写开销**。

# 总结

多列 B-tree 索引的灵魂是**列序即语义**：

- **最左前缀**：条件必须约束第一列，后续列逐级接力；
- **等值在前、范围在后**：范围列一旦出现在中间，其右邻居失去定位能力；
- 一个精心排序的多列索引常常抵得上三个单列索引，还省写开销；
- skip scan 是补救，不是设计依据。

当无法用单个多列索引满足"多条件 OR/AND 混合"的查询时，优化器会转向另一条路——**[组合多个索引](./025.组合多个索引.md)**。
