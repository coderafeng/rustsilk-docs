# 概述

**排序规则（collation）** 决定字符串比较与排序的语义（`a` 与 `A` 谁先、`ä` 算不算字母 a 的变体、`C` 与 `POSIX` 的字节序……）。对索引而言，规则很冷酷也很简单：

> **一个索引列只能支持一种排序规则。** 查询比较时用的排序规则若与索引列的不一致，这个索引就用不上。

这是很多"明明有索引却不走"疑难杂症背后的真凶，尤其在多语言环境与 ICU 排序规则普及之后。

# 索引默认继承列的排序规则

```sql
CREATE TABLE test1c (
    id      integer,
    content varchar COLLATE "x"
);

CREATE INDEX test1c_content_index ON test1c (content);
```

索引**自动采用底层列的排序规则 `"x"`**。因此形如：

```sql
SELECT * FROM test1c WHERE content > constant;
```

的查询可以用索引——比较默认使用列的排序规则，与索引一致。

但这个索引**无法加速涉及其他排序规则的查询**：

```sql
SELECT * FROM test1c WHERE content > constant COLLATE "y";  -- ❌ 用不上上面的索引
```

如果这类查询也重要，就再建一个**支持 `"y"` 规则**的额外索引：

```sql
CREATE INDEX test1c_content_y_index ON test1c (content COLLATE "y");
```

# 排序规则的解析链

一条语句里比较运算用哪个规则，按以下优先级解析：

1. 表达式里**显式**的 `COLLATE`（子句级，如 `WHERE a = b COLLATE "C"`）；
2. 否则取**列的隐式规则**（建表时定义的 `COLLATE`）；
3. 否则用数据库的默认规则（`lc_collate` / ICU locale）。

显式 `COLLATE` **优先于**列定义。所以即使列是 `"en_US"`、索引也是 `"en_US"`，只要查询写成 `WHERE content > 'x' COLLATE "C"`，优化器就得放弃这个索引——除非恰好有 `"C"` 规则的索引。

# 实操：为多种排序需求建多个索引

场景：客户姓名列经常按两种方式使用——业务列表按语言习惯排序（如拼音/英文字典序），而导入对账要求字节级精确比较。

```sql
-- 列默认排序规则跟随数据库（如 en_US.UTF-8）
CREATE INDEX idx_customer_lname ON customer (last_name);          -- 服务默认规则的 = < > 与 ORDER BY

CREATE INDEX idx_customer_lname_c ON customer (last_name COLLATE "C");  -- 服务显式 COLLATE "C" 的查询
```

```sql
SELECT * FROM customer ORDER BY last_name;                       -- ✅ 走 idx_customer_lname
SELECT * FROM customer ORDER BY last_name COLLATE "C";           -- ✅ 走 idx_customer_lname_c
```

两个索引内容有重叠，但**这是官方认可的做法**——排序语义不同的比较无法共用一份有序结构。能用一个就不要加第二个：统一应用层的比较规则往往比堆索引更划算。

# 非确定性排序规则（nondeterministic collation）

PostgreSQL 12+ 使用 ICU 时可以创建**非确定性排序规则**（`deterministic = false`）：`'ß'` 与 `'ss'` 判等、大小写不敏感等语义都由规则定义。它带来两个索引相关的后果：

1. **等值语义变"宽"**：唯一索引会在"等价"意义上判重——`'ß'` 和 `'ss'` 不能共存（这可能正是你要的）。
2. **模式匹配失去索引支持**：`LIKE`/前缀/正则依赖"排序序与字符前缀序一致"，非确定性规则下这个前提不成立，**`LIKE 'abc%'` 不能用 B-tree 索引加速**，`text_pattern_ops` 类也不可用。模糊搜索请改用 **pg_trgm + GIN/GiST**。

```sql
CREATE COLLATION de_nondet (provider = icu, locale = 'de@colalt=standard', deterministic = false);

CREATE TABLE doc (title text COLLATE de_nondet);
CREATE INDEX idx_doc_title ON doc (title);        -- 可建，服务 = < > 与 ORDER BY
SELECT * FROM doc WHERE title LIKE 'Abc%';        -- ❌ 不走索引（非确定 + 前缀语义失效）
```

> **PostgreSQL 18 提示**：18 起允许在**非确定性排序规则**上使用 `LIKE` 与文本定位函数（以往直接报错），但这只是"能算"，**B-tree 索引仍不会因此加速这类模式匹配**；18 还新增了内置排序规则提供器 `PG_UNICODE_FAST`。另外，主外键关系现在要求双方要么用确定性规则、要么用**完全相同**的非确定性规则。

# 总结

索引列与排序规则是**一对一绑定**：继承列定义，或在 `CREATE INDEX ... (col COLLATE "...")` 中显式指定。查询要享受索引，比较时解析出的规则必须与索引**完全相同**。使用 ICU 非确定性规则时，记住"唯一性变宽、前缀匹配失去索引资格"两条铁律。下一篇收尾：如何从系统视图里**[检查索引使用情况](./060.检查索引使用情况.md)**，把这一章所有设计验证闭环。
