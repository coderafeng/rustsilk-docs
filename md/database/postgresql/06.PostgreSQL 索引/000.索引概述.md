# 概述

**索引（Index）** 是数据库中最常见的性能增强手段。它允许服务器比没有索引时**更快地查找和检索特定的行**。但索引并不是免费的午餐——它同时给整个数据库系统带来额外开销，因此应当**合理使用**。

用一个熟悉的类比：PostgreSQL 的表数据存放在**堆（heap）**中，行的物理顺序与插入顺序相关、与查询条件无关。这就像一本没有目录的书——想找到"讲 VACUUM 的那一页"，只能从第一页读到最后一页（**Seq Scan 顺序扫描**）。索引就是给书的某些"关键内容"单独建一份**目录**：先查目录定位页码，再翻到对应页。这份"目录"是一个独立的、按键值有序组织的辅助结构（默认是 B-tree），其中每一项记录了**键值 → 行的物理位置（块号 + 元组偏移）**的映射。

# 索引为什么快

以一个典型的 B-tree 索引查找为例：

```sql
SELECT * FROM customer WHERE email = 'mary.smith@sakilacustomer.org';
```

- **没有索引**：必须读取 customer 表**所有数据块**，逐行比较 email，代价随表的大小线性增长。
- **有索引**：从索引根节点出发，沿中间节点逐层比较，只需 **3~4 次块读取**即可定位到目标行的物理位置，再去堆中取出整行。表从 1 万行涨到 1 亿行，索引查找的层数往往只增加 1 层。

代价换来的是：每次 **INSERT / UPDATE / DELETE** 表数据时，**每一个覆盖该列的索引都要同步维护**；每个索引还各自占用磁盘空间与共享缓存（缓存被索引页挤占，反过来又会影响其他查询）。

# 索引的成本与副作用

作为有几年经验的开发者，建立"索引不是越多越好"的直觉非常重要：

1. **写放大**：一张表上有 N 个索引，则一次写入近似变成 1 + N 次结构维护。对高并发写入的表（如日志、订单流水），盲目加索引会显著拉低 TPS。
2. **空间占用**：索引可能和表本身一样大，甚至更大（多列、宽列、低填充因子）。可用 `pg_relation_size()` 检查，见 **[查看空间](../05.PostgreSQL%20数据库管理/020.查看空间.md)**。
3. **优化器负担**：候选索引越多，规划阶段要枚举与比较的执行计划越多，**Planning Time** 会上升。
4. **可能根本不被使用**：以下场景优化器通常宁可全表扫描：
   - **小表**（数据只占几个页，读全部比"查目录再回表"更便宜）；
   - **选择性差的列**（如 `active` 布尔列，命中一半的行，回表随机 I/O 反而更慢）；
   - **条件与索引不匹配**（前导通配的 `LIKE '%bar'`、列上套了函数但没建表达式索引等）；
   - **统计信息过期**，优化器误判。

判断"索引到底有没有被用上"，靠的不是猜，而是 **[EXPLAIN](../05.PostgreSQL%20数据库管理/045.EXPLAIN.md)** 执行计划与 **[检查索引使用情况](./060.检查索引使用情况.md)** 中的统计视图。

# 什么时候值得建索引（经验法则）

| 场景                                           | 建议                                                     |
|------------------------------------------------|----------------------------------------------------------|
| 主键 / 外键连接列                              | 主键自动有索引；**外键列常被忽略**，连接与级联删除都靠它 |
| 高频等值 / 范围查询的过滤列                    | 建 B-tree 索引，选择性越高收益越大                       |
| 唯一性业务约束（手机号、邮箱）                 | 用 **UNIQUE 索引**，约束与加速一举两得                   |
| 大表上的排序分页（ORDER BY id LIMIT）          | 让索引顺序与排序方向匹配，避免大排序                     |
| JSONB / 数组 / 全文检索 / 几何GIS              | 考虑 **GIN / GiST / BRIN** 等特殊索引类型                |
| 极低基数列（性别、状态位）且查询总伴随其他条件 | 通常不必单建索引，考虑**部分索引**或**多列索引**         |
| 只写不改、按时间追加的超大规模表               | **BRIN** 用极小空间换回范围裁剪能力                      |

# 总结

索引本质是**用写开销和空间换读速度的有序辅助结构**。是否建索引、建什么类型的索引，取决于查询模式与数据分布；建完之后要用执行计划和索引统计去**验证它真的被使用**。接下来从最核心的话题开始：PostgreSQL 提供的各类 **[索引类型](./005.索引类型.md)**。
