# 概述

普通索引只能建立在**列的原始值**上。但真实查询经常对列做函数转换后再比较——最经典的就是"邮箱大小写不敏感查找"：

```sql
SELECT * FROM customer WHERE lower(email) = lower($1);
```

这种写法在 `email` 上建有普通索引也**完全用不到**——索引里存的是原始 `email`，而查询比较的是 `lower(email)`，两者对不上。**表达式索引（expression index）** 就是为了解决这个问题：对**函数/表达式的计算结果**建索引。

# 语法

```sql
CREATE INDEX 名称 ON 表名 [ USING 方法 ] ( { 列名 | ( 表达式 ) } [ ... ] );
```

表达式**必须用括号包裹**（语法要求）：

```sql
-- 在 lower(email) 的结果上建 B-tree 索引
CREATE INDEX idx_customer_lower_email ON customer (lower(email));

-- 多列表达式：按"姓+名"组合的小写形式建索引
CREATE INDEX idx_customer_full_lower ON customer (lower(last_name || ' ' || first_name));
```

表达式索引也可以同时是**唯一的**、**多列的**、**部分的**，各种能力自由组合（见 **[唯一索引](./030.唯一索引.md)**、**[部分索引](./040.部分索引.md)**）。

# 生效条件：查询必须"原样匹配"表达式

表达式索引不是万能加速器，**只有当查询条件中出现与索引定义完全相同的表达式时**，优化器才会考虑使用它：

```sql
-- ✅ 与索引表达式一字不差，能用上
SELECT * FROM customer WHERE lower(email) = 'mary.smith@sakilacustomer.org';

-- ❌ 表达式不同，用不上
SELECT * FROM customer WHERE email = '...';                    -- 没套 lower
SELECT * FROM customer WHERE lower(email::text) = '...';       -- 多了类型转换写法差异时可能匹配失败
SELECT * FROM customer WHERE upper(email) = '...';             -- 函数不同
```

这带来一个工程约束：**应用里所有想走索引的查询都必须统一写成索引定义的那个表达式**。如果团队混用 `email = $1` 和 `lower(email) = lower($1)`，往往需要同时建两个索引——这时应该统一编码规范，而不是堆索引。

# 限制：只能用于 IMMUTABLE 函数

表达式**只能使用 immutable（不可变）函数**——即在相同输入下永远返回相同结果、不依赖数据库状态的函数。建索引时就会检查：

```sql
-- ❌ 报错：functions in index expression must be marked IMMUTABLE
--    （random() 是 volatile，now() 是 stable，都不能出现在索引表达式里）
CREATE INDEX bad ON film ((release_year + (random() * 0)::int));
```

常见可安全使用的：`lower()`、`upper()`、`abs()`、`split_part()`、`coalesce()`（参数含不可变部分时）、大多数算术运算。自写函数若标记了 `IMMUTABLE` 但行为实际依赖外部数据，会**悄悄损坏索引**——标记函数 volatility 级别是开发者的责任。

# 实战场景

## 大小写不敏感的等值/前缀查询

```sql
CREATE INDEX idx_film_title_lower ON film (lower(title));

-- 搜索标题（无论用户输入什么大小写）
SELECT title FROM film WHERE lower(title) LIKE 'alo%';
```

> 注意：`LIKE` 走 B-tree 要求模式锚定开头；非 C locale 下还可能需要 `text_pattern_ops` 操作符类（见 **[操作符类和操作符族](./050.操作符类和操作符族.md)**）。如果业务需要任意位置模糊搜索，正确工具是 pg_trgm + GIN/GiST，不是表达式索引。

## JSONB 深层字段

对 JSONB 里固定的热键建表达式索引，避免整个文档进 GIN：

```sql
CREATE INDEX idx_payload_uid ON events ((payload ->> 'user_id'));

SELECT * FROM events WHERE payload ->> 'user_id' = '42';
```

`(payload ->> 'user_id')` 外层括号是表达式索引语法要求（`->>` 返回 text）。这与 `jsonb_path_ops` 的 GIN 索引互补：前者适合**高频等值查某键**，后者适合**键组合多变的包含查询**（见 **[JSON类型](../04.PostgreSQL%20数据类型/070.JSON类型.md)**）。

## 函数排序

```sql
-- 免排序地按邮箱域名排列表，详见 索引和 ORDER BY
CREATE INDEX idx_customer_email_domain ON customer (split_part(email, '@', 2));
```

# 表达式索引的盲区：统计信息

PostgreSQL 的 `ANALYZE` 收集的是**列**的统计信息，**不会为表达式结果单独收集**。这导致优化器对表达式索引的选择性只能**靠函数性质粗略推算**，个别情况下会误判（宁可顺序扫描）。

官方给出的对策是"物化表达式"：

```sql
-- 加一个生成列存储表达式结果，让统计信息建立在真实列上
ALTER TABLE customer ADD COLUMN email_domain text GENERATED ALWAYS AS (split_part(email, '@', 2)) STORED;
CREATE INDEX idx_customer_email_domain_gen ON customer (email_domain);
```

生成列（PostgreSQL 12+，STORED 方式）既保证值与表达式同步，又能让普通索引与列统计同时受益。PostgreSQL 18 起生成列默认是 **VIRTUAL**（读取时计算）——注意**虚拟生成列上不能直接建索引**，只能对其生成表达式建表达式索引，所以"要索引就要 STORED"。是否值得这么做，取决于误判带来的实际损失——多数场景下直接建表达式索引就够。

# 总结

表达式索引把 B-tree 的加速能力从"列原值"扩展到"列的函数结果"，代价是**查询必须原样复用表达式**、函数必须 IMMUTABLE。它是大小写不敏感查询、JSONB 热键、业务唯一性（配合 UNIQUE）的标准解法；而当查询只是"取值范围固定"的子集时，更轻量的方案是 **[部分索引](./040.部分索引.md)**。
