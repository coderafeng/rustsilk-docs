# 概述

选定索引类型（见 **[索引类型](./005.索引类型.md)**）之后，本篇解决工程落地问题：**怎么建、怎么删、怎么改名调参、怎么重建，以及线上大表建索引如何不锁业务**。

索引的日常管理涉及四类语句：

| 操作 | 语句 | 关键点 |
| --- | --- | --- |
| 创建 | `CREATE INDEX` | 大表用 `CONCURRENTLY` 避免长锁 |
| 删除 | `DROP INDEX` | 注意 `CASCADE` 会连带删除约束 |
| 修改 | `ALTER INDEX` | 改名、调参数、换表空间 |
| 重建 | `REINDEX` | 修复膨胀与失效索引 |

# 创建索引 CREATE INDEX

## 语法

```sql
CREATE [ UNIQUE ] INDEX [ CONCURRENTLY ] [ [ IF NOT EXISTS ] 名称 ]
    ON 表名 [ USING 方法 ] ( { 列名 | ( 表达式 ) } [ COLLATE 排序规则 ] [ 操作符类 ] [ ASC | DESC ] [ NULLS { FIRST | LAST } ] [, ...] )
    [ INCLUDE ( 列名 [, ...] ) ]
    [ WITH ( 存储参数 = 值 [, ...] ) ]
    [ TABLESPACE 表空间名 ]
    [ WHERE 谓词 ];
```

看起来很长，常用的其实只有 `UNIQUE`、`CONCURRENTLY`、`USING`、`WITH`、`WHERE` 几处，其中表达式、INCLUDE、WHERE 分别对应 **[表达式索引](./035.表达式索引.md)**、**[覆盖索引](./045.仅搜索索引和覆盖索引.md)**、**[部分索引](./040.部分索引.md)**。

## 基本示例

```sql
-- 为 customer.store_id 建普通 B-tree 索引
CREATE INDEX idx_customer_store ON customer (store_id);

-- 显式指定类型与存储参数
CREATE INDEX idx_film_title ON film USING B-tree (title);

-- IF NOT EXISTS：重复执行不报错，适合迁移脚本
CREATE INDEX IF NOT EXISTS idx_rental_customer ON rental (customer_id);
```

> **命名规范**：索引名在 **schema 内必须唯一**（不与表、其他索引重名）。推荐 `idx_表名_列义` 或 `uk_表名_列义`（唯一）风格，便于在 **[检查索引使用情况](./060.检查索引使用情况.md)** 中一眼定位归属表。不写索引名时系统会自动生成 `表名_列名_idx`。

## 用主键/唯一约束自动创建

`PRIMARY KEY` 与 `UNIQUE` 约束会**自动创建同名的支撑索引**，不需要（也不应该）再手动重复建：

```sql
CREATE TABLE member (
    member_id serial PRIMARY KEY,        -- 自动创建唯一索引 member_pkey
    phone      varchar(20) UNIQUE        -- 自动创建唯一索引 member_phone_key
);
```

## CONCURRENTLY：线上不加锁建索引

普通 `CREATE INDEX` 会**阻塞对表的写入**（只读锁），在大表上可能锁几分钟到几小时。`CONCURRENTLY` 改为**边允许写入边构建**：

```sql
CREATE INDEX CONCURRENTLY idx_payment_customer ON payment (customer_id);
```

代价与铁律：

- 总耗时更长（要扫描表**两遍**并等待现存事务结束）；
- **不能在事务块（BEGIN/COMMIT）内执行**；
- 失败时会留下一个标记为 INVALID 的"残骸"索引，**不占功能但拖累写入**，必须 `DROP INDEX` 后重来；
- 极端情况下可能产生**违反唯一性**的残留数据，完成后建议校验（见 060 篇的 `indisvalid` 查询）。

> psql 里可以用 `\d 表名` 查看索引列表，失效索引会以 `INVALID` 标注。

# 删除索引 DROP INDEX

```sql
DROP INDEX [ CONCURRENTLY ] [ IF EXISTS ] 名称 [, ...] [ CASCADE | RESTRICT ];
```

两个必须心里有数的点：

1. **CASCADE 很危险**：删除支撑约束的索引会**连带删除该 UNIQUE/PRIMARY KEY 约束**。默认用 `RESTRICT`，遇到依赖直接报错更安全。
2. **CONCURRENTLY 删索引不阻塞查询**，适合在业务高峰移除大索引；同样不能放在事务块里。

```sql
-- 删掉不再使用的索引
DROP INDEX IF EXISTS idx_payment_amount_hash;
```

约束本身也可以用 `ALTER TABLE ... DROP CONSTRAINT` 删除，语义更清晰（参见 **[创建表](../03.PostgreSQL%20数据库和表/020.创建表.md)**）。

# 修改索引 ALTER INDEX

`ALTER INDEX` 不能改索引的"内容结构"（列、类型都不能变，要变得**先建新再删旧**），常用于：

```sql
-- 改名
ALTER INDEX idx_customer_store RENAME TO idx_customer_store_id;

-- 调整 B-tree 填充因子：给页内分裂留空间，适合写多读少的索引
ALTER INDEX idx_customer_store SET (fillfactor = 70);

-- 设置为表空间（参见 05 章-表空间）
ALTER INDEX idx_customer_store SET TABLESPACE fast_ssd;

-- 重置存储参数为默认值
ALTER INDEX idx_customer_store RESET (fillfactor);

-- GIN 索引可关闭 fastupdate（仅对 GIN 有效）
ALTER INDEX idx_film_features SET (fastupdate = off);
```

B-tree 的 `fillfactor` 默认 90（页留 10% 空间）；对**热点键追加型**（如自增 id）可调到 100 减小体积，对**随机更新多**的键调小可减少页分裂。GIN 则有 `fastupdate`、`pending_list_limit` 等参数。

# 重建索引 REINDEX

索引会因大量更新而**膨胀**（页内空洞），或因 `CONCURRENTLY` 失败而**失效**，这时需要重建：

```sql
REINDEX INDEX  idx_customer_store;        -- 重建单个索引
REINDEX TABLE  customer;                  -- 重建某表全部索引
REINDEX SCHEMA public;                    -- 重建某模式
REINDEX DATABASE sakila;                  -- 重建某库（系统目录除外）
REINDEX SYSTEM sakila;                    -- 只重建系统目录索引
```

**普通 REINDEX 会锁住表阻塞写入**。对线上表应使用并发模式：

```sql
REINDEX INDEX CONCURRENTLY idx_customer_store;
```

`CONCURRENTLY` 同样不能在事务块内执行，且不能用于系统目录索引（那只能在单用户维护模式做）。

> **膨胀排查思路**：索引体积远大于同等数据量表（`pg_relation_size` 对比），且该表历史上有过大范围 DELETE/UPDATE——先 `VACUUM`，仍不见效再 `REINDEX CONCURRENTLY`。参见 **[日常维护](../05.PostgreSQL%20数据库管理/065.日常维护.md)**。

# 建索引前的好习惯

1. **先看执行计划确认瓶颈**：别凭感觉建索引，用 **[EXPLAIN ANALYZE](../05.PostgreSQL%20数据库管理/045.EXPLAIN.md)** 证明"这里在扫大表且条件可被索引加速"。
2. **先 ANALYZE 再观察**：有时只是统计信息旧了，`ANALYZE 表名;` 后计划自然变好。
3. **大表低峰期操作**：非 CONCURRENTLY 的建/删索引务必避开高峰，并设置 `lock_timeout` 防止排队雪崩：

```sql
SET lock_timeout = '5s';
CREATE INDEX idx_rental_date ON rental (rental_date);
```

# 总结

`CREATE INDEX`（大表加 `CONCURRENTLY`）→ `ALTER INDEX`（改名调参）→ `REINDEX CONCURRENTLY`（治膨胀、救失效）→ `DROP INDEX`（回收），构成索引生命周期的基本闭环。所有操作完成后，都应回到 **[检查索引使用情况](./060.检查索引使用情况.md)** 验证索引真的生效且被使用。下一篇进入索引设计的第一个关键决策：**[多列索引](./015.多列索引.md)** 怎么建。
