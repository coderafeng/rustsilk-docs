# 概述

PostgreSQL 的索引**不需要例行的维护与调优**（不像某些数据库要定期"重建统计/合并碎片"才算能用），但这不代表建完就能撒手——**必须检查索引是否真的被真实业务负载使用**。

检查分两个层次：

- **单条查询级**：用 **[EXPLAIN](../05.PostgreSQL%20数据库管理/045.EXPLAIN.md)** 看这次执行有没有走索引；
- **全局统计级**：用系统统计视图看一段时间内每个索引被扫描了多少次，找出"零使用"与"负资产"索引。

# 官方方法论：检查索引使用五步

官方文档给出的排查流程，值得逐条内化：

## 1. 永远先 ANALYZE

统计信息是优化器给每个计划"标价"的依据。**没跑过 ANALYZE 就去审视索引使用，是徒劳的**（lost cause）——默认假设值几乎必然失真。

```sql
ANALYZE customer;    -- 或全库 ANALYZE;
```

## 2. 用真实数据做实验

用测试数据只能告诉你"测试数据需要什么索引"。**尤其致命的是数据集太小**：从 10 万行里选 1000 行是索引的候选场景，从 100 行里选 1 行几乎不会是——100 行可能只占一个磁盘页，顺序读 1 页无法被任何计划击败。构造数据时也要注意：过于雷同、完全随机、有序插入的值都会让统计分布失真。

## 3. 索引不走时，先"逼"它走

通过运行期参数关闭备选计划类型，强制优化器使用索引：

```sql
SET enable_seqscan = off;      -- 关顺序扫描
SET enable_nestloop = off;     -- 关嵌套循环（最基础的计划）
EXPLAIN SELECT ...;
RESET enable_seqscan;
```

**如果关了顺序扫描它仍不走索引，说明存在根本性问题**——多半是查询条件与索引不匹配（回顾本篇各章：[多列索引](./015.多列索引.md) 的前缀、[表达式索引](./035.表达式索引.md) 的原样匹配、[排序规则](./055.索引和排序规则.md) 的一致性）。

## 4. 逼出来之后，比时间

强制走索引了，仍有两种可能：**优化器是对的**（索引确实不合适），或**代价估算失真**。用 `EXPLAIN ANALYZE` 分别对两种计划计时，拿实测行数与耗时说话。

> **PostgreSQL 18 增强**：EXPLAIN ANALYZE 现在会报告每个索引扫描节点**实际执行的索引查找（index lookups）次数**，判断"索引扫描到底省不省"更直观。

## 5. 代价失真时的出路

总代价 = 每行代价 × 选择率。前者可用运行期参数（`cpu_index_tuple_cost` 等）微调；后者失真则用 `ALTER TABLE ... SET STATISTICS` 调高列统计目标值再 `ANALYZE`。都救不了时，才考虑显式强制索引并反馈社区。

# 全局视角：索引使用统计视图

## pg_stat_user_indexes

```sql
SELECT schemaname, relname AS table, indexrelname AS index,
       idx_scan,            -- 通过该索引完成的扫描次数
       idx_tup_read,        -- 索引条目读取数
       idx_tup_fetch        -- 堆行抓取数
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC;
```

**`idx_scan = 0` 的索引是删除候选**。配套看体积：

```sql
SELECT s.indexrelname,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size,
       s.idx_scan
FROM pg_stat_user_indexes s
JOIN pg_index i USING (indexrelid)
WHERE NOT i.indisunique          -- 唯一索引承担约束，另当别论
ORDER BY pg_relation_size(s.indexrelid) DESC LIMIT 20;
```

> 三个坑：① 这些统计**自上次统计重置以来**累计（`SELECT pg_stat_reset();` 会清零），观察周期要覆盖完整业务周期（含月末报表等低频场景）；② 只读副本上的查询不计入主库统计；③ **PostgreSQL 15+ 有 `stats_fetch_consistency` 缓存语义**，快照读同一事务内多次查询统计视图结果可能不完全实时。

## 索引的定义与状态

```sql
-- 建表语句原样（含 WHERE、INCLUDE、opclass）
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'customer';

-- 有效性状态：indisvalid=false 即 CONCURRENTLY 失败的残骸
SELECT c.relname AS index, i.indisvalid, i.indisready, i.indislive,
       i.indisunique, i.indnatts
FROM pg_index i JOIN pg_class c ON c.oid = i.indexrelid
WHERE i.indrelid = 'customer'::regclass;
```

psql 里 `\d customer` 的 Indexes 段会直接标注 `INVALID`；处理办法见 **[索引的基本操作](./010.索引的基本操作.md)** 的 REINDEX/DROP。

## 索引膨胀粗查

```sql
-- 索引体积与表体积的比例，超过预期的先记下
SELECT relname,
       pg_size_pretty(pg_total_relation_size(relid)) AS table_size
FROM pg_stat_user_tables WHERE relname = 'rental';
```

怀疑膨胀再上 `pgstatindex`（pgstattuple 扩展）做页级检查，详见 **[日常维护](../05.PostgreSQL%20数据库管理/065.日常维护.md)**。

# 工程实践：季度索引巡检清单

1. `idx_scan = 0` 且持续一个完整业务周期的普通索引 → 标记观察 → `DROP INDEX CONCURRENTLY`；
2. `INVALID` 索引 → `REINDEX CONCURRENTLY` 或删除重建；
3. 体积最大的前 20 个索引逐个核对 `EXPLAIN`：是否还服务它们的原始查询；
4. 新增慢查询涉及的高频过滤列 → 走本篇设计流程补索引；
5. 检查重复前缀索引（`(a)` 与 `(a,b)` 并存是否都有必要，见 **[多列索引](./015.多列索引.md)**）。

# 总结

"索引不需要维护"指的是结构自管理，而**使用效果必须靠检查闭环**：单查询用 EXPLAIN + 强制计划五步法定位"为什么不走"，全局用 pg_stat_user_indexes 定位"建了没人用"。把这两招固化成巡检，索引体系才能长期保持"小而准"。至此本章完结——回头复习 **[索引概述](./000.索引概述.md)** 的知识地图，或直接实战 **[pg_trgm](../08.PostgreSQL%20生态插件/060.pg_trgm.md)** 的模糊查询。
