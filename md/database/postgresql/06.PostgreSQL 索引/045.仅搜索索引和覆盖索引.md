# 概述

你可能见过执行计划里的 **Index Only Scan**——只扫索引、完全不碰表数据就返回结果。它是索引加速的"最高形态"：**省去回表（堆访问）**，I/O 进一步下降。

**仅索引扫描（index-only scan）** 之所以可能，是因为 B-tree 索引条目本身就包含键列的值（它不是指针列表，而是"值 + 行位置"的有序副本）。如果查询需要的**所有列**都在索引里，理论上根本不需要读堆。

"所有需要的列都在索引里"的索引，被称为**覆盖（covering）查询的索引**。PostgreSQL 提供两种覆盖方式：把列放进**键**，或用 `INCLUDE` 把列作为**非键载荷**附加。

# 成立条件

一个查询要走 Index Only Scan，需要同时满足：

1. **查询引用的每一列**都是某个索引的键列或 INCLUDE 列（WHERE 条件列 + SELECT 输出列全部被覆盖）；
2. 优化器认为**索引扫描比"索引+回表"或顺序扫描更便宜**；
3. **可见性检查可以被跳过**——这是 PostgreSQL 特有的坎，见下节。

示例：

```sql
-- 索引覆盖 (last_name)，查询也只需要 last_name
CREATE INDEX idx_customer_lname ON customer (last_name);

SELECT last_name FROM customer WHERE last_name LIKE 'G%';
```

```text
Index Only Scan using idx_customer_lname on customer
  Index Cond: (last_name ~ 'G'::text)
  Heap Fetches: 0
```

# 可见性地图（Visibility Map）与 Heap Fetches

PostgreSQL 用 MVCC，每行有自己的可见性位（xmin/xmax）。仅索引扫描没法逐行看这些位——于是它依赖**可见性地图（visibility map）**：每个表块 1 bit，记录"该块是否**所有事务都看得见其中所有行**"（即整块对所有快照可见且无死元组）。

- 块在 VM 中标记为 **all-visible** → 索引条目直接返回，不碰堆；
- 否则 → 仍需**回堆取元组检查可见性**，计划中显示 `Heap Fetches: n`。n 越大，仅索引扫描的优势越小。

**新写入/更新的行所在块尚未标记 all-visible**，因此刚导入的数据 Index Only Scan 会大量 Heap Fetches。**VACUUM 会更新可见性地图**——这是"VACUUM 不只是回收空间，还喂饱仅索引扫描"的经典结论。autovacuum 通常会自动处理；大量批量写入后可手动：

```sql
VACUUM ANALYZE customer;
```

# HOT 更新与索引维护

仅索引扫描还影响 UPDATE 的成本。PostgreSQL 的 **HOT（heap-only tuple）更新**：当更新**不涉及任何索引列**，且新行能放进同一页时，只需更新堆元组、**跳过所有索引的写入维护**（只在页内挂一条指针）。

这给索引设计两条经验：

1. **别把不会变的列放进键**——把宽表上少变的查询列用 `INCLUDE` 携带，HOT 更新完全不用碰它；
2. **`fillfactor` 留白**：默认 B-tree 索引页留 10% 空间，正是为了配合 HOT 链的索引项复用。对几乎不更新的表/索引可设 `fillfactor = 100` 省空间；更新频繁时保持默认。

# 覆盖索引：键列 vs INCLUDE

`INCLUDE` 选项（PostgreSQL 11+）让索引携带**不参与排序搜索**的列：

```sql
-- 键: (customer_id)；载荷: amount, payment_date
CREATE INDEX idx_payment_cust_cover ON payment (customer_id)
    INCLUDE (amount, payment_date);

-- 查某客户的支付金额：条件用键，输出用载荷 → Index Only Scan
SELECT amount, payment_date FROM payment WHERE customer_id = 13;
```

与"把列都放进键"相比，`INCLUDE` 的意义：

|                       | 键列                   | INCLUDE 列                           |
|-----------------------|------------------------|--------------------------------------|
| 参与 B-tree 排序/比较 | ✅                     | ❌ 只存值                            |
| 可用于 WHERE 加速     | ✅                     | ❌                                   |
| 键体积                | 变长（影响树高与去重） | 不占键                               |
| HOT 更新时是否维护    | 是                     | 否（只要该列不在**任何**索引的键里） |

经验：**搜索用的列进键，展示用的列进 INCLUDE**。多列索引的键序原则见 **[多列索引](./015.多列索引.md)**。

> INCLUDE 项只能是**裸列名**（不能写表达式），且与键列一样受索引条目大小限制（单个条目须能放进约 1/3 页），超宽的 `text`/`jsonb` 列并不适合做 INCLUDE。

# 何时反而不该追求仅索引扫描

- **需要读的行很多时**：Index Only Scan 按索引顺序访问堆的代价可能高于顺序扫描；小表/低选择性场景优化器通常会放弃它。
- **Heap Fetches 占比高**：说明块大多 not-all-visible，仅索引扫描退化成"索引+回表"还多读一份索引。先解决 VACUUM 节奏，再评估是否值得维持覆盖。
- **为覆盖而覆盖**：给索引塞进五六列只为"包住"一个报表查询，换来巨大的写放大——一列多几个索引项，等于每次写多维护几个结构。覆盖索引适合**点查类高频窄查询**，别拿它做"迷你表"。

# 总结

仅索引扫描 = 覆盖的列 + 干净的可见性地图。设计动作有三：**查询列进索引（键或 INCLUDE）**、**用 VACUUM/autovacuum 维持 all-visible 覆盖**、**让不搜索的列避开键以保住 HOT 红利**。它与 **[部分索引](./040.部分索引.md)** 可以叠加（部分 + 覆盖），是"小而美"索引组合的天花板。下一层抽象是索引"怎么比较值"——**[操作符类和操作符族](./050.操作符类和操作符族.md)**。
