# 概述

**B-tree 索引天生按键有序**，因此除了加速 WHERE 条件，还能直接按有序方式返回数据，让数据库**跳过额外的排序步骤**。这在大表"取前 N 条"的分页场景里收益巨大：理想情况下只需读 N 行即可返回，而不是全表取出再排序。

但优化器**并不总会选择用索引来满足排序**——它会比较"索引逐行取数 + 回表"与"顺序扫描 + 显式排序"的代价，小表或命中率高的查询往往仍是后者更快。本篇讲清楚：**什么样的 ORDER BY 能免排序**。

> 目前**只有 B-tree 索引**能按排序方式返回数据。GiST 例外地支持特定操作符类（如几何、`<->` 距离）的最近邻排序；Hash/GIN/BRIN 不支持任何排序输出。

# 能被 ORDER BY 使用的索引条件

要理解规则，先接受一个事实：**多列 B-tree 的排序方向是"列序 + 每列方向"的组合**，且索引既能正着扫也能**反向扫**。因此：

## 单列索引

```sql
CREATE INDEX idx_rental_date ON rental (rental_date);

-- ✅ 匹配索引顺序，正向扫
SELECT * FROM rental ORDER BY rental_date;

-- ✅ 与索引反向，倒序扫即可，同样免排序
SELECT * FROM rental ORDER BY rental_date DESC;

-- ❌ 无法用该索引：索引列里没有 customer_id
SELECT * FROM rental ORDER BY customer_id;
```

## 多列索引

索引 `(customer_id, rental_date)` 的全局序是"先 customer_id，后 rental_date"：

```sql
-- ✅ 前缀匹配索引序
SELECT * FROM rental ORDER BY customer_id, rental_date;

-- ✅ 整体反向（等价于反向扫描索引）
SELECT * FROM rental ORDER BY customer_id DESC, rental_date DESC;

-- ⚠️ 部分匹配：第一列与索引一致即可利用，但只对"带等值前缀"的查询有意义
SELECT * FROM rental WHERE customer_id = 13 ORDER BY rental_date;

-- ❌ 列方向混用（一正一倒）与索引序不符，需要显式排序
SELECT * FROM rental ORDER BY customer_id, rental_date DESC;
```

**方向混用的解法**：在建索引时就写成一致的列方向，PostgreSQL 允许索引列各带 `ASC/DESC`：

```sql
-- 专门服务 ORDER BY customer_id ASC, rental_date DESC 的查询
CREATE INDEX idx_rental_cust_asc_date_desc ON rental (customer_id ASC, rental_date DESC);
```

# NULLS FIRST / LAST 的配合

B-tree 默认把 **NULL 排在最大位置**（`NULLS LAST` 相当于升序时 NULL 在尾部）。当 ORDER BY 的 NULL 位置与索引不匹配时，就无法顺畅地"扫到 LIMIT 就停"：

```sql
-- 默认索引 (rental_date)：升序 = NULLS LAST，倒序 = NULLS FIRST
SELECT * FROM rental ORDER BY rental_date NULLS LAST;       -- ✅
SELECT * FROM rental ORDER BY rental_date DESC;             -- ✅ 倒扫
SELECT * FROM rental ORDER BY rental_date NULLS FIRST;      -- ❌ 需先排序
```

若某类查询确实要"升序且 NULL 在前"，建索引时显式声明：

```sql
CREATE INDEX idx_rental_date_nulls_first ON rental (rental_date NULLS FIRST);
```

> 直观理解：索引只能朝头或朝尾一个方向连续扫；NULL 的摆放位置必须与"该方向上 NULL 该在前还是在后"一致，才能让 `LIMIT` 提前终止。

# 表达式与排序规则的 ORDER BY

当 ORDER BY 的不是裸列，而是**函数、表达式或不同排序规则的列**时，普通索引帮不上忙。解法是建对应的**表达式索引**（见 **[表达式索引](./035.表达式索引.md)**）：

```sql
-- 按邮箱域名排序
CREATE INDEX idx_customer_email_domain ON customer (split_part(email, '@', 2));

SELECT email FROM customer ORDER BY split_part(email, '@', 2);  -- ✅ 免排序
```

带 `COLLATE` 的排序则需要索引列使用同一排序规则（见 **[索引和排序规则](./055.索引和排序规则.md)**）：

```sql
SELECT title FROM film ORDER BY title COLLATE "C";
-- 需要: CREATE INDEX ON film (title COLLATE "C");
```

# 混合排序场景

`NULLS FIRST/LAST`、升降序混用、表达式、多表连接内排序——只要**有一环与任何可用索引的序不匹配**，计划里就会出现 `Sort` 节点。看计划时的判断方法：

```sql
EXPLAIN (ANALYZE, COSTS) SELECT * FROM payment ORDER BY amount DESC LIMIT 20;
```

- 若出现 `Sort` + 大量 `Rows`，且 work_mem 不够会落盘（`external merge`），考虑为排序列建索引；
- 若走了 `Index Scan` 但 `actual loops/rows` 很大（要扫很多索引行才凑够 LIMIT），说明过滤条件与索引序不匹配，索引排序可能帮倒忙。

# 总结

能让 `ORDER BY` 免排序的索引，必须满足"**列序一致、方向一致（或整体反向）、NULL 位置一致、表达式与排序规则一致**"。其中最常被忽视的是第二点——方向混用要在**建索引时**就设计好 `DESC` 列。反过来说：不是所有 ORDER BY 都值得用索引满足，优化器会算账，我们要做的是让它**有合适的索引可选**。索引不满足单列/多列序时，还可以看看 **[组合多个索引](./025.组合多个索引.md)** 与 **[仅搜索索引](./045.仅搜索索引和覆盖索引.md)** 的取舍。
