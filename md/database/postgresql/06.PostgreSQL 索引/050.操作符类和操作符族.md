# 概述

前几篇里反复出现一个隐含假设：索引按"列的自然顺序"比较值。但真实需求经常更刁钻——"这一列我想**按字节序**而不是按语言排序比较"、"这个数值列我只关心**四舍五入到 10 以内**是否相等"。

**操作符类（operator class）** 就是答案：它告诉索引——**对这一列，用哪套比较语义、支持哪些操作符**。每个索引列都必须指定一个操作符类；不指定时，系统为该列类型选择**默认操作符类**（B-tree 的类型默认类通常就叫 `类型名_ops`）。

**操作符族（operator family）** 则是更高一层的组织：把同一数据类型上**多个相关操作符类**归到一族，让优化器可以在一族内跨类推导（典型例子：一族里既有"严格相等"类又有"前缀包含"类，`LIKE` 与 `=` 可以互相借力）。

# 语法位置

操作符类写在索引列定义的末尾：

```sql
CREATE INDEX 名称 ON 表名 [ USING 方法 ]
    ( { 列名 | ( 表达式 ) } [ COLLATE 排序规则 ] [ 操作符类 ] [ ... ] );
```

例如为 `varchar` 列选择**模式匹配专用**的操作符类：

```sql
CREATE INDEX idx_film_title_pattern ON film (title varchar_pattern_ops);
```

# 一个典型例子：text_pattern_ops

背景：B-tree 索引要加速 `LIKE 'abc%'`，需要索引内部的比较规则与 `LIKE` 使用的**逐字节前缀序**一致。若数据库的排序规则（collation）不是 `C`（比如 `en_US.UTF-8` 或 ICU 规则），默认操作符类按语言规则排序，"前缀在字节序上连续"不成立，`LIKE 'abc%'` 就无法转成索引范围扫描。

```sql
-- 数据库使用非 C locale 时：
CREATE INDEX idx_film_title ON film (title);                 -- 默认类，加速 =、<、>、BETWEEN
CREATE INDEX idx_film_title_pat ON film (title text_pattern_ops);  -- 加速 LIKE 'x%' / ~ '^x'
```

区别只由操作符类决定——**同一种数据类型，两套索引语义**。想同时两类查询都快，可以两个索引并存；若库本身就是 `C`/`POSIX` locale，默认类即可支持模式匹配，不必额外建。

# 常见内置操作符类速查

| 索引方法 | 列类型       | 操作符类                                    | 支持的查询                                 |
|----------|--------------|---------------------------------------------|--------------------------------------------|
| B-tree   | text/varchar | 默认 `text_ops`                             | `= < <= > >=`、`IN`、排序                  |
| B-tree   | text/varchar | `text_pattern_ops`（varchar/text 同名变体） | `LIKE 'x%'`、`~ '^x'`（字节序前缀）        |
| B-tree   | inet/cidr    | `inet_ops`                                  | `<<`、`<<=`、`>=` 等包含比较               |
| hash     | 多数类型     | `默认类型_hash_ops`                         | 仅 `=`                                     |
| GiST     | 几何         | `gist_geometry_ops_2d`                      | 空间关系 + 最近邻 `<->`                    |
| GiST     | inet/cidr    | `gist_inet_ops`                             | `<<=`、`&&` 等                             |
| SP-GiST  | text         | `text_ops`                                  | 前缀 `<^`、`^@` 等（基数树）               |
| SP-GiST  | point        | `quad_point_ops` / `kd_point_ops`           | 方向包含 + 最近邻 `<->`                    |
| GIN      | jsonb        | `jsonb_ops`                                 | `@>`、`?`、`?\|`、`?&`（每个键值都建条目） |
| GIN      | jsonb        | `jsonb_path_ops`                            | 仅 `@>`（更小的索引）                      |
| GIN      | 数组         | `array_ops`                                 | `@>`、`&&`、`<@`、`= `                     |
| BRIN     | 多数有序类型 | `brin_minmax_ops`                           | 范围操作符                                 |
| BRIN     | bloom 扩展   | `brin_bloom_ops`                            | 布隆过滤器包含判断                         |

> 扩展会注册更多类：`pg_trgm` 提供 `gin_trgm_ops`/`gist_trgm_ops`（任意位置模糊 `LIKE '%x%'`），`btree_gin`/`btree_gist` 让 B-tree 语义的数据能进 GIN/GiST（见 **[生态插件概览](../08.PostgreSQL%20生态插件/000.生态插件概览.md)**）。

# 用系统目录查询操作符类

```sql
-- 所有操作符类及其所属族、默认类型、索引方法
SELECT a.amname, oc.opcname, oc.opcfamily, oc.opcdefault
FROM pg_opclass oc JOIN pg_am a ON a.oid = oc.opcmethod
ORDER BY a.amname, oc.opcname;

-- 简化视图：某类型有哪些可用类
SELECT oc.opcname, a.amname
FROM pg_opclass oc JOIN pg_am a ON a.oid = oc.opcmethod
WHERE oc.opcintype = 'text'::regtype;
```

看某个具体索引用了什么类，最直观仍是：

```sql
SELECT indexdef FROM pg_indexes WHERE indexname = 'idx_film_title_pattern';
-- CREATE INDEX idx_film_title_pattern ON public.film USING btree (title varchar_pattern_ops)
```

# 操作符族解决了什么

单看一个操作符类，优化器只知道"这个索引能处理哪些操作符"。**族**把相关的类挂在一起后，多了两个能力：

1. **跨类推导**：查询条件命中族内 A 类的操作符，规划器可换算到 B 类的索引上尝试使用；
2. **一致的语义描述**：比如 `integer_ops` 族把 int2/int4/int8 的类与 hash、order 变体归拢，表达"这些是同一语义家族的不同实现"。

日常开发很少需要**创建**族（那是索引扩展作者的工作：`CREATE OPERATOR FAMILY ... USING btree;` + `CREATE OPERATOR CLASS ... FAMILY ...`），但**理解族**有助于明白为什么 `LIKE 'x%'` 有时能在非 pattern 类的索引上"顺便"被使用——因为两个类在同一族里，规划器可以借用其求值器。

# 什么时候需要自定义操作符类

典型答案：**几乎从不**。99% 的场景内置类 + 表达式索引（见 **[表达式索引](./035.表达式索引.md)**）已覆盖。剩下 1% 是真正的扩展开发——例如你有一种自定义类型"金额(带四舍五入语义)"，希望 B-tree 按"分"粒度比较、范围按"元"跳跃：

```sql
CREATE OPERATOR CLASS acctg_ops FOR TYPE acctg USING btree FAMILY acctg_ops AS
    OPERATOR 1 <, OPERATOR 2 <=, OPERATOR 3 = , OPERATOR 4 >=, OPERATOR 5 >,
    FUNCTION 1 bt_acctg_cmp(acctg, acctg);
```

这类代码出现在索引方法扩展里，属于"造轮子"范畴；应用开发者更多是**选对现成的类**。

# 总结

操作符类 = **索引列的比较语义说明书**；操作符族 = **同类型多语义类的联合登记处**。日常开发需要它的时刻主要有三个：非 C locale 下建 `text_pattern_ops`、JSONB 在 `jsonb_ops` 与 `jsonb_path_ops` 间做选择、以及为 inet/数组挑对类。它与**[索引和排序规则](./055.索引和排序规则.md)**是一对孪生话题——排序规则决定"顺序"，操作符类决定"索引是否按这个顺序组织"。
