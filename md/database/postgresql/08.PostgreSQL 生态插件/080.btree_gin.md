# 概述

> 官方文档：**[btree_gin — 在 GIN 索引里支持 B-tree 操作符类](https://www.postgresql.org/docs/18/btree-gin.html)**
> 
> 中文版镜像：**[btree_gin — 在 GIN 索引里支持 B-tree 操作符类](https://pgsql.cc/docs/18/btree-gin.html)**

GIN 索引天生只认"能拆成元素"的类型（数组、tsvector、jsonb、范围），而真实表往往是**混合结构**：一个 JSONB/数组列 + 一堆 int/timestamp 过滤列。想把它们**编进同一个 GIN 索引**做组合搜索，没有 btree_gin 就只能拆成多个索引靠 BitmapAnd 合并。

**btree_gin** 让普通 B-tree 类型（数值、日期、字符串、网络地址……）作为操作符类进入 GIN 索引：支持等值与范围查询，语义上等价于"把 B-tree 的列塞进 GIN"。官方对性能的定性结论：**搜索性能与普通 B-tree 相当，但索引构建时间慢数倍**——它的价值在"组合索引"，不在"替代 B-tree"。

# 安装

contrib 自带，装库即用（无需重启）：

```sql
CREATE EXTENSION btree_gin;
```

# 使用示例

## 混合列组合 GIN 索引

典型场景：事件表既有标量过滤列，又有 jsonb/数组列，希望一条查询同时命中：

```sql
CREATE TABLE events (
    user_id   int4,
    ts        timestamptz,
    tags      text[],
    payload   jsonb
);

-- 每个非原生 GIN 类型都要显式挂 btree_gin 提供的操作符类
-- （int4_ops、timestamptz_ops 等名字与 B-tree 操作符类同名，由 btree_gin 扩展提供 GIN 实现）
CREATE INDEX events_mixed_idx ON events
USING gin (user_id int4_ops, ts timestamptz_ops, tags array_ops, payload jsonb_path_ops);
```

多列 GIN 的查询收益方式：**单条查询里多个索引列各自贡献元素键**，避免"每个列一个索引 + BitmapAnd"的合并开销：

```sql
SELECT * FROM events
WHERE user_id = 42
  AND ts >= now() - interval '1 day'
  AND tags @> ARRAY['click']
  AND payload @> '{"source": "web"}';
```

## 部分类型与全文列混排

btree_gin 覆盖的类型清单很长（`int2/int4/int8/numeric/timestamp/date/time/interval/inet/cidr/macaddr/uuid/text/varchar/char/bytea/enum/domain...`），配合官方全文检索列可以建"标量 + tsvector"混合 GIN：

```sql
CREATE INDEX ON articles USING gin (status int2_ops, body tsvector_ops);
```

# 怎么选：btree_gin vs 多个单列索引

| 维度           | 混合 btree_gin 索引                    | 各列独立索引（B-tree/GIN） |
|----------------|----------------------------------------|----------------------------|
| 多条件组合查询 | 单索引命中，规划器省事                 | BitmapAnd 合并，堆访问翻倍 |
| 构建速度       | 慢（GIN 本质）                         | B-tree 快                  |
| 更新开销       | 每次改动重建键，pending list 开销      | 常规                       |
| 适用           | 列组合相对固定、读多写少、含数组/jsonb | 单列高选择过滤、写多       |

> 若表里只有标量列、没有原生 GIN 类型，混合索引通常**没有收益**——那是 **[btree_gist](./085.btree_gist.md)** / 普通 B-tree 复合索引（见 **[多列索引](../06.PostgreSQL%20索引/015.多列索引.md)**）的地盘。

# 避坑

- **范围查询支持有限**：GIN 结构决定范围条件要扫描大量键，时间列范围特别宽时可能不如 B-tree——用 `EXPLAIN` 对比。
- **每个索引列都必须有对应操作符类**：忘了 `int4_ops` 这类标注，`CREATE INDEX` 直接报"数据类型没有 GIN 操作符类"。
- **不要拿它替代主键索引**：btree_gin 是组合索引零件，不是通用加速器。
- 大量写入 + GIN pending list 膨胀会拖慢查询，关注 `gin_pending_list_limit` 与 autovacuum。

# 总结

btree_gin 的唯一使命：**把标量列带进 GIN 索引**，让"等值/范围 + 数组/JSONB/全文"在同一个索引里完成。它是数组/JSONB 表设计的常用配角（见 **[数组](../04.PostgreSQL%20数据类型/075.数组.md)**、**[JSON类型](../04.PostgreSQL%20数据类型/070.JSON类型.md)**）；而"标量列进 GiST + 排他约束"的对称需求，由兄弟扩展 **[btree_gist](./085.btree_gist.md)** 负责。
