# 概述

> 官方仓库：**[timescale/timescaledb](https://github.com/timescale/timescaledb)**

**TimescaleDB** 是 Postgres 最著名的时序扩展：在完全保留 SQL、ACID、生态工具的前提下，为**时间序列数据**（物联网传感器、应用监控指标、金融行情、日志事件）做了三件系统性的事——

1. **自动分区（hypertable）**：一张逻辑表按时间（可再按空间维度）自动切成成千上万个小 chunk，写入路由与查询裁剪全部由扩展完成，用户看不见分区管理；
2. **时序专属优化**：针对"按时间追加、按时间窗口查询"的负载做 chunk 排除、按时间下推聚合、Last Token 扫描（`time_bucket` + 索引）等优化，官方基准写入与查询性能大幅领先"裸 Postgres 分区表"；
3. **生命周期自动化**：连续聚合（增量刷新的物化视图）、原生列式压缩（历史 chunk 10~20 倍压缩比）、保留/降级策略，全部用 SQL 策略声明，由后台调度器执行。

它本质仍是一张张普通 Postgres 表——JOIN、事务、外键、**[pg_partman](./105.pg_partman.md)** 不适用之处（它自带更深的时序自动化）都按需选择。注意许可：核心功能 Apache-2.0，部分企业特性（如多层级聚合的部分能力、Rebalance 管理等）在新版本划入商业许可，选型时核对功能矩阵。

# 安装

必须预加载，配置后重启：

```ini
# postgresql.conf
shared_preload_libraries = 'timescaledb'
```

```bash
# Docker（tag 以官网为准）
docker run -d --name timescaledb \
  -e POSTGRES_PASSWORD=postgres -p 5432:5432 \
  timescale/timescaledb:latest-pg18

# Debian/Ubuntu（Timescale 官方源）
apt install timescaledb-tools postgresql-18-timescaledb
timescaledb-tune --quiet --yes     # 官方调参器，按内存自动给 postgresql.conf 建议
```

启用扩展（每个业务库）：

```sql
CREATE EXTENSION timescaledb;
```

# 核心概念：hypertable

把普通表"升级"为超表，指定时间列（之后该表不再需要手工分区）：

```sql
CREATE TABLE metrics (
    time       TIMESTAMPTZ      NOT NULL,
    device_id  INTEGER          NOT NULL,
    temperature DOUBLE PRECISION
);

-- 转换为超表：默认按 1 天切 chunk，自动创建过去的分区
SELECT table_name
FROM create_hypertable('metrics', 'time');

-- 再按设备做空间分区（高基数维度慎用，chunk 数 = 时间 × 空间）
SELECT create_hypertable('metrics_big', 'time', 'device_id', 4);

-- 或者直接建表即超表
CREATE TABLE cpu_usage (
    time TIMESTAMPTZ NOT NULL,
    host text, value double precision
) USING timescaledb;
```

写入与查询**就是普通 SQL**，收益来自自动分区裁剪：

```sql
INSERT INTO metrics (time, device_id, temperature)
SELECT now() - (random() * interval '30 days'), (random()*99)::int, 20 + 10*random();

-- 只扫命中天数的 chunk
SELECT device_id, avg(temperature)
FROM metrics
WHERE time > now() - interval '1 day'
GROUP BY device_id ORDER BY 2 DESC LIMIT 10;
```

# 时间桶聚合与连续聚合

`time_bucket()` 是时序版 `date_trunc`（支持任意秒数桶），配合**连续聚合**把"每 5 分钟的均值"增量维护起来：

```sql
-- 连续聚合：形似物化视图，由后台任务增量刷新
CREATE MATERIALIZED VIEW metrics_1h WITH (timescaledb.continuous) AS
SELECT
    time_bucket('1 hour', time) AS bucket,
    device_id,
    avg(temperature) AS avg_temp,
    max(temperature) AS max_temp
FROM metrics
GROUP BY 1, 2;

-- 注册刷新策略：过去 3 小时滚动重算，每 30 分钟跑一次
SELECT add_continuous_aggregate_policy('metrics_1h',
    start_offset    => interval '3 hours',
    end_offset      => interval '15 minutes',
    schedule_interval => interval '30 minutes');

-- 查历史直接打聚合视图，毫秒级
SELECT * FROM metrics_1h
WHERE bucket >= now() - interval '7 days' ORDER BY bucket;
```

# 压缩与保留

历史 chunk 用列式压缩（官方口径常见 90%+ 空间节省），策略化自动执行：

```sql
ALTER TABLE metrics SET (
    timescaledb.compress,
    timescaledb.compress_segmentby = 'device_id'   -- 按设备分段，设备内列存
);

-- 7 天前的 chunk 自动压缩
SELECT add_compression_policy('metrics', interval '7 days');

-- 90 天前的 chunk 自动删除（保留策略）
SELECT add_retention_policy('metrics', interval '90 days');
```

压缩后的 chunk 依然可以正常 SELECT（列式 + min/max 元数据还能加速过滤），但更新/删除需要解压，策略上应把"不可变的历史"才纳入压缩窗口。

# 其它常用能力速览

- **插入去重**：超表 + 唯一索引实现 last-value upsert（`INSERT ... ON CONFLICT`）；
- **`time_bucket_gapfill`**：缺报数据前向填充/线性插值，画监控曲线必备；
- **`first()/last()` 聚合**：取桶内首末值，替代手写窗口函数；
- **告警/Reorder**：`add_reorder_policy` 改 chunk 排序键；较新版本的重切片、多层连续聚合属于商业/cloud 特性，先查功能矩阵。

# 避坑

- **忘配 shared_preload_libraries**：`CREATE EXTENSION` 直接报错，扩展无法半启用。
- **空间分区维度基数失控**：`device_id × 时间` 双维分区最忌高基数（百万设备），chunk 数量爆炸后文件句柄与规划开销都受害；一般空间分片数 ≤ CPU 核数。
- **时间列选择**：超表必须以单列时间分区；业务上"事件发生时间"与"入库时间"要预先想清楚用哪个。
- 连续聚合**不支持 outer join / 窗口函数**等，聚合定义受限于物化视图规则；延迟到达数据靠 `start_offset` 回补。
- 版本许可分界（Community vs Cloud/Tiered）在 2.x 后期调整过，采购评估以官方 License 文档为准，别拿旧博客当依据。

# 总结

TimescaleDB 把时序负载需要的"分区、聚合、压缩、保留"全部策略化，让 Postgres 直接扛住每秒数十万点的指标写入与两年尺度的热查询。若你的负载就是**带时间戳的追加型大表**，它比手工分区（**[pg_partman](./105.pg_partman.md)**）省掉整个 DBA 维护面；若是 OLTP 主数据，保持原生 Postgres，必要时只引入它的 `time_bucket` 工具函数层。
