# 概述

> 官方仓库：**[citusdata/citus](https://github.com/citusdata/citus)**
> 
> 官方文档：https://docs.citusdata.com/
> 
> 中文文档：https://learn.microsoft.com/zh-cn/postgresql/citus/?view=citus-14

Citus 是一个开源 PostgreSQL 扩展，可**水平缩放 PostgreSQL**。可以在单个节点上启动并增长到分布式集群。由于 Citus 是一个扩展（而不是分支），因此可以保留本机 PostgreSQL 兼容性、功能、生态系统工具和扩展。

关键功能包括：

- 分布式表（基于行的分片和基于架构的分片）
- 维度/共享数据的引用表
- 并置联接（colocation）和分布式查询规划器
- 跨工作线程的并行查询执行
- 列式存储选项（columnar 访问方法）
- 从 MX 模式下的任何节点进行查询（自 Citus 11.0 起；新版为 Adaptive Executor 默认能力）

通常采用 Citus 来提高多租户 SaaS、实时分析仪表板、时序和微服务状态管理的性能和可伸缩性。

其核心模型一句话：**coordinator（协调节点）把 SQL 拆成分片级任务，下发给 worker 节点并行执行，再汇总返回**——应用看到的仍是一个 Postgres。

# 安装

Citus 需要在**所有节点**安装扩展并预加载，然后按角色组网。Docker 快速体验：

```bash
docker run -d --name citus_coordinator -p 5432:5432 \
  -e POSTGRES_PASSWORD=postgres citusdata/citus:13.0
docker run -d --name citus_worker1 -p 5433:5432 \
  -e POSTGRES_PASSWORD=postgres citusdata/citus:13.0
```

裸机/包管理（PGDG 源提供 `citus_18` 包）：

```ini
# 每个节点的 postgresql.conf
shared_preload_libraries = 'citus'
citus.node_name = 'worker1'      # 可选：给节点命名
```

```sql
CREATE EXTENSION citus;   -- 所有节点都要建
```

组网（在 coordinator 上执行）：

```sql
SELECT citus_set_coordinator_host('coordinator', 5432);
SELECT citus_add_node('worker1', 5432);
SELECT citus_add_node('worker2', 5432);

-- 查看所有节点与分片分布
SELECT * FROM citus_get_active_worker_nodes();
```

# 使用示例

## 分布式表：一张表切成 N 个分片

```sql
-- 用户事件表：按 user_id 哈希分片（分布列选择是架构第一决策）
CREATE TABLE user_events (
    user_id bigint NOT NULL,
    ts timestamptz NOT NULL,
    event jsonb,
    PRIMARY KEY (user_id, ts)          -- 主键必须包含分布列
) PARTITION BY RANGE (ts);             -- 分布式表上还能叠加分区

SELECT create_distributed_table('user_events', 'user_id');
```

`create_distributed_table` 在 worker 上创建真实分片（默认 32 个），之后的读写、JOIN、聚合由 Citus 规划器自动拆分下推：

```sql
INSERT INTO user_events VALUES (42, now(), '{"page":"/home"}');

-- 单租户点查：只会路由到 user_id=42 所在的那一个分片
SELECT count(*) FROM user_events WHERE user_id = 42;

-- 跨分片聚合：worker 并行局部聚合 + coordinator 汇总
SELECT date_trunc('hour', ts) h, count(*)
FROM user_events GROUP BY 1 ORDER BY 1;
```

## 引用表：小维度表全节点复制

```sql
CREATE TABLE countries (code char(2) primary key, name text);
SELECT create_reference_table('countries');

-- 分布式表 × 引用表 的 JOIN 在分片本地完成，零网络 Shuffle
SELECT e.user_id, c.name
FROM user_events e JOIN countries c ON c.code = left(e.event->>'country', 2)
WHERE e.user_id = 42;
```

## 并置（colocation）：共分片键的表放同一 worker

```sql
-- 与 user_events 共用分片布局（同分布列/同分片数），实现本地化 JOIN
SELECT create_distributed_table('user_profiles', 'user_id',
                                colocate_with => 'user_events');
-- 同组表之间按 user_id 的 JOIN 全部本地化；不同组才会触发 Rebalance
```

## 列存：分析加速

```sql
CREATE TABLE bids (item_id bigint, ts timestamptz, price numeric)
USING columnar;
SELECT create_distributed_table('bids', 'item_id');

-- 列存 + 分布式执行：扫描类大聚合快于行存数倍；点更新较弱，热写表勿用
```

## 再平衡与运维

```sql
-- worker 扩缩容：触发分片重分布（在线）
SELECT citus_add_node('worker3', 5432);
SELECT rebalance_table_shards();

-- 分片复制（高可用）：复制分布式表到 replica 节点
SELECT replicate_table_shards('user_events', replica_count => 2);
```

# 避坑

- **分布列决定一切**：选错（低基数、不参与过滤）会让"分片本地 JOIN"退化为跨节点搬运；多租户 SaaS 天然选 `tenant_id`。
- **主键/唯一约束必须包含分布列**（引用表除外）——分布式无法高效校验全局唯一，这是硬限制不是 Bug。
- **分布式事务与隔离级别**：跨分片写走两阶段提交（默认 relaxed 模式性能优先，可配 strict），对全局一致性敏感的业务要读透文档。
- 版本兼容矩阵很严：Citus 大版本 × PG 大版本 × 节点间 Citus 版本必须一致，滚动升级前先查 Compatibility 表。
- 托管形态（Azure Cosmos DB for PostgreSQL / Citus Cloud 已退役转自营）与自建运维面差异大，PoC 先用单机 citus-lite 形态验证模型。

# 总结

Citus 的答案是"**把一个 Postgres 变成集群，SQL 方言不变**"：多租户按 `tenant_id` 分片解决 SaaS 膨胀，引用表 + 并置解决大 JOIN，columnar + 并行执行解决实时分析。它不是万金油——跨分片事务、全局唯一、分布式 OLAP 深度场景都有明确边界；数据量到"单机 Postgres 加不动"而团队又想守住 Postgres 技术栈时，它是迁移成本最低的水平扩展路线。
