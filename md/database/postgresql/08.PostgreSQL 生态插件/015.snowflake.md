# 概述

> 官方仓库：**[pgEdge/snowflake](https://github.com/pgEdge/snowflake)**

**snowflake** 是一个基于 **int8 + sequence** 的全局唯一 ID 解决方案，可用来替换 Postgres 内置的 **bigserial**。它实现了 Twitter Snowflake 算法的思想——把 64 位整数拆成三段：

```
| 时间戳（毫秒，相对 2023-01-01） | 节点 ID（10 bit） | 毫秒内计数（12 bit） |
```

由此得到的 ID 具备普通自增序列不具备的性质：

- **多节点不冲突**：每个实例配置唯一的 `snowflake.node`（1~1023），即可在分布式/多主复制环境下安全并发生成；
- **趋势递增、可反解**：ID 里内嵌了生成时间与节点，事后可以从 ID 直接解析出"这条记录大约什么时候、在哪个节点生成"；
- **兼容现有生态**：ID 仍然存在普通 `bigint` 序列里，`bigserial`/`IDENTITY` 列、JDBC/ORM 一概无需改造。

代价：同一毫秒单节点最多 4096 个 ID；且必须保证节点号不重复——这是运维责任，扩展不会替你检测冲突。

# 安装

源码安装（pgEdge 发行版已内置）：

```bash
cd contrib
git clone https://github.com/pgEdge/snowflake.git
cd snowflake
USE_PGXS=1 make
USE_PGXS=1 make install
```

在数据库中启用，并**为每个实例配置唯一节点号**：

```sql
CREATE EXTENSION snowflake;
```

```ini
# postgresql.conf —— 每个节点必须不同（1~1023）
snowflake.node = 11
```

或用 ALTER SYSTEM 动态设置后 reload：

```sql
ALTER SYSTEM SET snowflake.node = 10;
SELECT pg_reload_conf();
```

> 这个 GUC 的默认值是"故意非法"的：不设置就调用 `snowflake.nextval()` 会直接抛异常，防止你漏配节点号导致多节点撞 ID。

# 使用：转换现有序列

snowflake **不能直接创建**，必须先把普通 Postgres 序列转换为雪花序列（`bigserial`、`GENERATED AS IDENTITY` 隐式创建的序列都可以转）：

```sql
CREATE TABLE orders (
    customer text,
    invoice  text,
    id       bigserial PRIMARY KEY      -- 隐式创建 orders_id_seq
);

-- 把序列转换为雪花算法（只改序列定义，不动已有数据）
SELECT snowflake.convert_sequence_to_snowflake('orders_id_seq'::regclass);
```

转换后新插入的行拿到的就是雪花 ID：

```sql
INSERT INTO orders (customer, invoice) VALUES ('Acme', 'art_9338');
SELECT id, snowflake.format(id) FROM orders ORDER BY id DESC LIMIT 1;
--            id         |                        format
--  136169504773242881   | {"id": 10, "ts": "2024-01-11 13:08:59.845+00", "count": 3}
```

不调用转换函数时，也可以直接使用数据库级全局序列 `snowflake.id_seq` 生成裸雪花 ID（用于应用层发号）：

```sql
SELECT snowflake.nextval();          -- 使用 snowflake.id_seq
SELECT snowflake.nextval('orders_id_seq'::regclass);  -- 指定序列
```

# 解析雪花 ID

| 函数                            | 说明                                                     |
|---------------------------------|----------------------------------------------------------|
| `snowflake.nextval([regclass])` | 生成下一个雪花 ID（可指定序列，默认 `snowflake.id_seq`） |
| `snowflake.currval([regclass])` | 当前会话最近一次生成的值                                 |
| `snowflake.get_epoch(int8)`     | 取出时间部分（相对 2023-01-01 的秒数，精确到毫秒）       |
| `snowflake.get_node(int8)`      | 取出生成它的 `snowflake.node` 值                         |
| `snowflake.get_count(int8)`     | 取出毫秒内计数（每毫秒从 0 重置）                        |
| `snowflake.format(int8)`        | 一次性输出 `{id, ts, count}` 的 JSONB                    |

```sql
-- 从 ID 反查生成时间
SELECT to_timestamp(snowflake.get_epoch(136169504773242881));
-- → 2024-01-11 13:08:59.845
```

这些函数让"订单号即时间戳"成为可能：对账、排障、分库路由时不再需要回表查 `created_at`。

# 与 ORM/驱动集成

因为雪花 ID 仍是 `bigint` 序列，Hibernate 等框架的 sequence 缓存策略照常工作，但注意：**increment 抓取步长不要超过 4096**（同一毫秒内的容量上限）：

```sql
ALTER SEQUENCE orders_id_seq INCREMENT 100 NO MAXVALUE;  -- 允许
ALTER SEQUENCE orders_id_seq INCREMENT 5000;              -- 危险：单毫秒容量只有 4096
```

# 避坑

- **每个实例的 `snowflake.node` 必须唯一**：多主集群里两个节点配置相同数字时**没有任何保护**，会静默生成重复 ID。
- **时钟回拨**：雪花算法对回拨敏感，节点时间被 NTP 往回调时可能生成"过去时间"的 ID（不会重复，但破坏趋势递增语义），生产节点务必配好 `ntpd/chrony` 的平滑调整。
- **转换不追溯历史**：`convert_sequence_to_snowflake()` 之后，旧行仍是 1、2、3……小数字——按 ID 排序时旧数据永远在前，一般正好符合业务预期，但做时间切片统计时别忘了旧行没有可靠时间信息。
- ID **看起来是随机大数**：用作对外暴露的主键时注意它无法像 UUID 那样防枚举猜测时间之外的信息——恰恰相反，它把生成时间"广播"出去了，敏感业务要评估。

# 总结

snowflake 用"一个 bigint"同时解决了**分布式唯一**、**趋势递增**、**可反解时间/节点**三件事，且完全复用现有序列生态（bigserial/IDENTITY/ORM），是多节点写 ID 场景对 bigserial 的平滑升级；如果不需要节点语义、也不介意 128 位字符串，UUIDv7（PG18 原生 `uuidv7()`，见 **[UUID函数](../07.PostgreSQL%20内置函数/065.UUID函数.md)**）是零扩展的替代方案。
