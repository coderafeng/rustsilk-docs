# 概述

> 官方仓库：**[timescale/pgvectorscale](https://github.com/timescale/pgvectorscale)**

**pgvectorscale** 是 Timescale 出品的向量检索扩展（Rust 编写），专门解决 pgvector 在**高维、大表、高召回**场景下的性能瓶颈——官方基准测试宣称在 Cohere 1000 万级数据集上，99% 召回率的查询速度比单节点 Pinecone 快 2.8 倍、成本低 75%。它是对 **[pgvector](./025.pgvector.md#概述)** 的有力补充，不是替代品：**数据存储仍用 pgvector 的 `vector` 类型，pgvectorscale 只负责更聪明的索引与查询执行**。

为 **pgvector** 数据引入了以下关键创新：

- 一种名为 **StreamingDiskANN** 的新型索引类型（访问方法名 `diskann`），灵感来源于 **[DiskANN](https://github.com/microsoft/DiskANN)** 算法，基于微软的研究成果——图结构常驻磁盘，配合智能缓存，内存需求远低于 HNSW；
- **统计二进制量化（SBQ, Statistical Binary Quantization）**：由 Timescale 研究人员开发，这种压缩方法改进了标准二进制量化，在压缩 32 倍的同时用统计分布选阈值，把量化误差降到最低；
- **基于标签的过滤向量搜索**：基于微软的过滤 DiskANN 研究，它允许你把向量相似性搜索与标签过滤相结合，以获得更精确更高效的结果。

# 安装

pgvectorscale 依赖 pgvector，且需要预加载后台缓存进程：

```bash
# Docker（Timescale 官方镜像预装了 pgvector + pgvectorscale，tag 以官网最新为准）
docker run -d --name pgvectorscale \
  -e POSTGRES_PASSWORD=postgres -p 5432:5432 \
  timescale/timescaledb-ha:pg18

# Debian/Ubuntu（PGDG + Timescale 源）
apt install postgresql-18-pgvectorscale
```

配置并重启：

```ini
# postgresql.conf
shared_preload_libraries = 'vectorscale'
```

```sql
-- CASCADE 会自动安装 pgvector
CREATE EXTENSION IF NOT EXISTS vectorscale CASCADE;
```

# 快速上手：StreamingDiskANN 索引

表结构与查询语法**和 pgvector 完全一致**，只是把索引类型换掉：

```sql
CREATE TABLE document_embedding (
    id        BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    metadata  JSONB,
    contents  TEXT,
    embedding VECTOR(1536)         -- 仍是 pgvector 的类型
);

-- 建 StreamingDiskANN 索引（旧文档中也写作 streaming_diskann）
CREATE INDEX document_embedding_idx ON document_embedding
USING diskann (embedding vector_cosine_ops);

-- 查询照常写，优化器自动走新索引
SELECT * FROM document_embedding
ORDER BY embedding <=> $1
LIMIT 10;
```

支持的距离与操作符类同 pgvector：`<=>` 余弦 / `<->` L2 / `<#>` 内积，需与建索引时的 `vector_*_ops` 匹配。

# 索引调优参数

构建期参数（`WITH` 子句）：

| 参数                     | 默认                | 说明                                                                       |
|--------------------------|---------------------|----------------------------------------------------------------------------|
| `storage_layout`         | `memory_optimized`  | `memory_optimized` 用 SBQ 压缩存图；`plain` 不压缩（内积索引不支持 plain） |
| `num_neighbors`          | 50                  | 图节点最大邻居数，越大精度越高、遍历越慢                                   |
| `search_list_size`       | 100                 | 构建期搜索宽度 S，越大图质量越高、构建越慢                                 |
| `max_alpha`              | 1.2                 | 图连通性参数                                                               |
| `num_dimensions`         | 0（全部）           | 只索引前 N 维，可配合 Matryoshka 嵌入降维                                  |
| `num_bits_per_dimension` | <900 维为 2，否则 1 | SBQ 每维编码位数                                                           |

```sql
CREATE INDEX ON document_embedding
USING diskann (embedding vector_cosine_ops)
WITH (num_neighbors = 64, storage_layout = 'memory_optimized');
```

> 大图表征索引构建很吃内存，先 `SET maintenance_work_mem = '2GB';` 再建。

查询期用 `SET vectorscale.` 系列 GUC（如 `num_neighbors`、`accumulation_factor`）在单条查询内权衡精度与延迟，多数场景保持默认即可。

# 过滤检索

**标签过滤（索引原生，推荐）**——把 `smallint[]` 标签列直接写进索引：

```sql
CREATE TABLE documents (
    id        SERIAL PRIMARY KEY,
    embedding VECTOR(1536),
    labels    SMALLINT[]        -- 类目/租户等标签，值域 -32768~32767
);

CREATE INDEX ON documents USING diskann (embedding vector_cosine_ops, labels);

-- && 重叠操作符走索引，延迟远低于事后过滤
SELECT * FROM documents
WHERE labels && ARRAY[1, 3]
ORDER BY embedding <=> '[...]'
LIMIT 10;
```

任意 `WHERE` 条件也支持，但属于**后过滤**（向量搜索出候选再过滤），过滤率极高时召回会不足——高频过滤维度请改造成标签列。

# SBQ 标量量化检索（不建全量索引）

对小表或临时集合，可以直接用 `<~>`（SBQ 距离）配合 `sbqquery()` 做流式量化扫描，无需 DiskANN 索引：

```sql
SELECT contents, embedding <~> sbqquery('document_embedding_idx', '[...]') AS distance
FROM document_embedding
ORDER BY distance
LIMIT 10;
```

# 避坑

- **必须重启才生效**：忘了把 `vectorscale` 加进 `shared_preload_libraries` 时索引能建、查询却退化成精确扫描。
- **构建内存峰值高**：默认 `maintenance_work_mem` 64MB 对百万级向量太小，构建前先调大，否则报错或极慢。
- **标签必须是 `smallint[]`**：text/UUID 标签需要先建整数字典型表做映射（官方推荐 label_definitions 模式）。
- **内积索引不兼容 `plain` 存储布局**。
- 它是 pgvector 的**增量**：不要卸载 pgvector、老 HNSW 索引依旧可用；同一张表两种索引可以共存对比基准。

# 总结

同一份 `vector` 数据、同一种 `ORDER BY <=> LIMIT` 查询，pgvectorscale 把索引从"内存常驻图"（HNSW）换成"磁盘友好图 + 统计量化"（StreamingDiskANN），以数量级更低的内存支撑千万~亿级向量的 99% 召回检索。选型路径很清晰：**百万级以下用 pgvector HNSW 即可；上规模、内存吃紧、或带标签过滤的检索，切到 pgvectorscale**。
