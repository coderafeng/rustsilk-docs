# 概述

> 官方仓库：**[ChuckHend/pg_vectorize](https://github.com/ChuckHend/pg_vectorize)**

**pg_vectorize** 是一个"嵌入流水线编排器"：在数据库里**自动完成文本 → 嵌入向量的转换与持续同步**，并提供对接主流大语言模型（LLM，如 OpenAI、Ollama、SentenceTransformers）的接口。它能帮您快速启动并实现向量搜索、全文搜索和混合搜索的自动化维护，从而在 Postgres 上高效构建 RAG 系统和搜索引擎。

它解决的是向量应用最脏的一段活——**嵌入的生成与保鲜**：源表内容变了，对应向量必须重算；模型升级了，全量向量需要重刷；大批量文档要先分块（chunking）再嵌入。pg_vectorize 把这套 ETL 变成一句 SQL 注册的任务，后台增量执行。

架构上它大量依赖三个兄弟组件：

- **[pgvector](025.pgvector.md#概述)**：向量存储与相似性搜索；
- **[pgmq](120.pgmq.md#概述)**：以消息队列编排后台工作任务（哪些行需要重算嵌入）；
- **[SentenceTransformers](https://huggingface.co/sentence-transformers)**：本地推理引擎（也支持 OpenAI/Ollama 等远程模型）。

pg_vectorize 提供了两种方式，为任意 Postgres 数据库添加语义搜索、全文搜索和混合搜索功能，轻松构建基于 **检索增强生成（RAG）** 的应用：

- **HTTP 服务器**（推荐用于托管数据库，如 RDS/Supabase）：运行一个独立的 Rust 服务，它连接到 Postgres 并公开 REST API（`POST /api/v1/table`、`GET /api/v1/search`）；
- **Postgres 扩展（SQL）**：把扩展装进 Postgres，用 SQL 函数驱动，例如 `vectorize.table()`（`vectorize.search()` 需要 Postgres 对文件系统的访问权限，托管库通常走 HTTP 模式）。

# 安装

扩展模式装库即可（`cascade` 会带上 pgvector/pgmq/pg_cron 依赖）：

```sql
CREATE EXTENSION vectorize cascade;
```

Docker 一键起"Postgres + pg_vectorize + HTTP 服务 + Ollama 本地模型"全家桶：

```bash
# 克隆仓库后，example/ 目录下提供了 docker-compose
git clone https://github.com/ChuckHend/pg_vectorize
cd pg_vectorize
docker-compose up -d        # 起 postgres(5432) 与 http 服务(8000)
```

使用 OpenAI/Ollama 等远程模型时，需先注册 API Key（`vectorize.update_api_key` 或 HTTP 模式下配置环境变量），具体以官方 README 为准。

# 注册一张"自动嵌入"表

准备源表，然后把它交给 vectorize：

```sql
CREATE TABLE docs (
    id SERIAL PRIMARY KEY,
    title TEXT,
    body   TEXT
);
INSERT INTO docs (title, body)
SELECT 'pg_vectorize ' || i, 'Postgres is a relational database. ' || repeat('lorem ipsum. ', 10)
FROM generate_series(1, 100) i;

-- 注册嵌入任务：自动分块、生成向量、随源表变化增量更新
SELECT vectorize.table(
    job_name    => 'docs_job',
    "table"     => 'docs',
    primary_key => 'id',
    columns     => ARRAY['title', 'body'],
    transformer => 'sentence-transformers/all-MiniLM-L6-v2',
    schedule    => '*/10 * * * *'       -- 兜底全量对账的 cron 周期
);
```

要点：

- **参数内建表**：每个任务会在同名 schema 下生成 `docs_job.search_view`（搜索结果）、`docs_job.queue_meta`（任务队列统计）、`docs_job.transform_r`（转换记录）等视图/表；
- **分块可配**：`args => ARRAY['chunk_size => 350', 'chunk_overlap => 100', 'chunk_prefix => ' || quote_literal('title')]`；
- **换模型即重刷**：改 `transformer` 后任务会自动重新计算全部嵌入。

# 搜索

语义（向量）搜索——返回按相似度排序的原文片段：

```sql
SELECT * FROM vectorize.search(
    'relational database',
    job_name    => 'docs_job',
    num_results => 10
);
-- 返回每行包含匹配的原文块（content）、相似度（similarity）与关联字段（metadata）
```

也可以直接查任务视图做 SQL 级组合：

```sql
SELECT * FROM docs_job.search_view
ORDER BY similarity DESC LIMIT 5;
```

全文与混合模式：同一套任务框架支持 BM25 风格的全文搜索视图与"向量 + 关键词"混合排序（`search_type` 参数，见官方文档），用于专有名词、编号这类关键词敏感的查询。

# HTTP 模式

托管数据库（没有文件系统权限）场景下，起独立服务后 REST 调用：

```bash
# 创建任务
curl -X POST http://localhost:8000/api/v1/table -d '{
  "job_name": "docs_job",
  "table_name": "docs",
  "schema": "public",
  "columns": ["title", "body"],
  "primary_key": "id",
  "search_type": "semantic",
  "transformer": "sentence-transformers/all-MiniLM-L6-v2"
}'

# 检索
curl "http://localhost:8000/api/v1/search/docs_job?query=database&num_results=10"
```

# 运维观察

```sql
-- 队列积压与任务健康
SELECT * FROM docs_job.queue_meta;

-- 已生成向量与分块明细
SELECT * FROM docs_job.transform_r LIMIT 5;

-- 停掉/删除任务
SELECT vectorize.drop('docs_job', force => true);
```

# 避坑

- **扩展模式的文件系统权限**：`vectorize.search()` 本地推理要写 HuggingFace 模型缓存目录，RDS 之类托管库装不了——直接用 HTTP 模式。
- **模型选择决定向量维度**：换 transformer 等于换向量空间，必须让任务重刷全表，期间搜索质量会抖动。
- **schedule 是兜底不是主通道**：增量更新靠触发器 → pgmq 队列驱动，cron 只做对账；队列消费停滞时先查 HTTP 服务/后台 worker 是否活着。
- 大表首次注册会触发**全量嵌入**，OpenAI 按 token 计费模式下先估算成本。

# 总结

pg_vectorize 把 RAG 应用里"分块 → 嵌入 → 同步 → 检索"的胶水层下沉进 Postgres：一条 `vectorize.table()` 换掉一个 Python ETL 服务。它适合中小团队快速落地语义搜索；当嵌入逻辑复杂（多路召回、自定义重排）时，这些编排能力会以 SQL 表达得比较勉强，那时回归应用层管线、只保留 **[pgvector](025.pgvector.md#概述)** 做存储更合适。
