# 概述

> 官方文档：**[ltree — 表示层级树状数据的标签](https://www.postgresql.org/docs/18/ltree.html)**
> 
> 中文版镜像：**[ltree — 表示层级树状数据的标签](https://pgsql.cc/docs/18/ltree.html)**

**ltree** 是 PostgreSQL 官方 contrib 插件，提供一种数据类型 `ltree`，用于表示**存储在层级树（hierarchy tree）结构中的数据标签**。标签形如 `Top.Country.Education`，是由点（`.`）分隔的"节点标签（label）"序列，天然适合建模**目录树、组织架构、分类体系、评论楼中楼**这类父子层级关系。

它要解决的问题是经典的"用邻接表（`parent_id`）查层级很痛苦"：

- 查"某个分类下的所有子孙"需要**递归 CTE** 一层层展开；
- 查"某个节点的全部祖先路径"同样要递归；
- 想给路径建索引？普通 B-tree 帮不上忙。

ltree 把整条路径存进**一个值**里（`A.B.C`），并提供专门的运算符（`@>` 祖先、`<@` 后代、`~` 正则路径、`?` 文本查询）与 **GiST / GIN 索引**，让"某节点下所有后代""路径前缀匹配"这类查询变成**一条带索引的普通 SQL**。

与同样处理层级数据的 **ltree vs recursive CTE vs 嵌套集（materialized path 手工拼接）** 相比：ltree 写简单、查快、可索引；代价是要维护冗余路径列——层级移动（reparent）时需要批量改写子孙路径。

# 安装

ltree 属于 contrib 套件，随主流发行版的 server 包一起分发：

```bash
# Debian/Ubuntu（contrib 已并入 server 包）
apt install postgresql-18
# CentOS/RHEL
dnf install postgresql18-contrib
```

在目标数据库中启用：

```sql
CREATE EXTENSION ltree;

-- 可选：psql 中确认扩展已加载
\dx ltree
```

# 数据类型与字面量

`ltree` 值就是一条点分路径，每个 label 只能是**字母、数字和下划线**（不能以数字开头，长度 ≤ 256 字节）：

```sql
CREATE TABLE categories (
    id     int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name   text NOT NULL,
    path   ltree                      -- 完整物化路径
);

INSERT INTO categories (name, path) VALUES
('Programming',    'Top'),
('Rust',           'Top.Rust'),
('Systems',        'Top.Rust.Systems'),
('Web',            'Top.Rust.Web'),
('Databases',      'Top.Databases'),
('PostgreSQL',     'Top.Databases.PostgreSQL');
```

> 也可以从普通 text 转换：`SELECT text2ltree('Top.Databases');`，反向用 `ltree2text(path)`。

# 核心运算符

| 运算符                     | 含义                      | 示例                                  |
|----------------------------|---------------------------|---------------------------------------|
| `<@`                       | 左是右的**祖先或自身**    | `'Top.Rust' <@ 'Top.Rust.Web'` → true |
| `@>`                       | 左是右的**后代或自身**    | `'Top.Rust.Web' @> 'Top.Rust'` → true |
| `~`                        | lquery 路径匹配（类正则） | `'Top.Rust' ~ 'Top.*'` → true         |
| `?`                        | ltxtquery 关键词查询      | `'Top.Rust' ? 'Rust & Web'` → false   |
| `\|\|`                     | 路径拼接                  | `'Top' \|\| 'Rust'` → `'Top.Rust'`    |
| `<` `<=` `=` `!=` `>=` `>` | 路径字典序比较            | 用于排序                              |

lquery 语法（`~` 运算符）速记：

- `*`：任意**单个** label；`**`：任意**零个或多个** label
- `%tw*`：以 `tw` 开头的 label 匹配
- `Top.{Rust|Databases}.*`：花括号表示"或"

```sql
-- Rust 生态下所有直接子类
SELECT name FROM categories WHERE path ~ 'Top.Rust.*';

-- Top 下任意深度的 PostgreSQL
SELECT name FROM categories WHERE path ~ 'Top.**.PostgreSQL';
```

# 常用函数

| 函数                                                 | 说明                                    |
|------------------------------------------------------|-----------------------------------------|
| `nlevel(path)`                                       | 路径层数（label 个数）                  |
| `subltree(path, start, end)`                         | 截取子路径（左闭右开）                  |
| `subpath(path, len)` / `subpath(path, start, len)`   | 去掉前 N 级 / 从第 start 级取 len 级    |
| `ltree2text` / `text2ltree`                          | 类型互转                                |
| `index(path, subpath)`                               | 子路径首次出现的位置                    |
| `subltree(a, b)` / `ltree_isparent` / `ltree_rchild` | 兼容旧版的祖先/后代判断                 |
| `label_ltree(text)`                                  | 单字符通配 label（配合 `~` 做前缀匹配） |

```sql
-- 每个分类的层级深度
SELECT name, nlevel(path) AS depth FROM categories ORDER BY path;

-- 取 'Top.Databases.PostgreSQL' 中去掉首级的部分 → 'Databases.PostgreSQL'
SELECT subpath('Top.Databases.PostgreSQL', 1);
```

# 索引

ltree 提供 **GiST** 与 **GIN** 两种索引操作符类，专门加速祖先/后代/路径匹配：

```sql
CREATE INDEX idx_categories_path_gist ON categories USING gist (path);
CREATE INDEX idx_categories_path_gin  ON categories USING gin  (path);
```

- **GiST**：适合 `@>`、`<@`、`~` 混合查询，回表排序开销低，是最常用选择；
- **GIN**：按 label 建倒排，`@>`（某 label 的祖先链命中）类查询更省空间，但构建更慢。

验证是否走索引（小表会始终顺序扫描，可临时 `SET enable_seqscan = off`）：

```sql
EXPLAIN SELECT * FROM categories WHERE path <@ 'Top.Rust';
```

# 实战：配合触发器自动维护路径

物化路径最大的坑是**父节点改名/移动后路径失效**，用触发器统一维护：

```sql
-- 移动分类时，同步改写自己与所有子孙的路径前缀
CREATE OR REPLACE FUNCTION move_subtree(old_path ltree, new_path ltree)
RETURNS void AS $$
    UPDATE categories
    SET path = subpath(new_path, 0, nlevel(new_path))
        || subpath(path, nlevel(old_path))
    WHERE path <@ old_path;
$$ LANGUAGE sql;

-- 用法：把 'Top.Rust.Web' 整体挪到 'Top.Databases' 下
SELECT move_subtree('Top.Rust.Web', 'Top.Databases.Rust_Web');
```

# 避坑

- **lquery/ltxtquery 不是正则引擎**：`~` 只支持 lquery 语法（`*`、`**`、`%`、`{a|b}`），别按 POSIX 正则的习惯写。
- **label 不允许连字符/点**：`'Top.Rust-Core'` 会报错，清洗数据时先用 `replace(lower(x), '-', '_')`。
- **层级移动必须全量改写子孙路径**：这正是物化路径的写放大代价；如果业务"reparent"极频繁，考虑邻接表 + 递归 CTE 或 ltree 只作查询加速列。
- `?`（ltxtquery）匹配的是**路径中是否出现某 label**，与层级位置无关（`'*Rust'` 这种通配在旧版才允许），别和 `~` 混用场景。

# 总结

ltree 用"一个可索引的字符串路径"换掉了大段递归 CTE：读多写少的分类树、组织架构、BOM 清单等场景，它是**最轻量的层级方案**——不引入外部依赖、纯官方 contrib、GiST/GIN 直接可用。写频繁（经常挪动节点）时再权衡邻接表递归查询方案。
