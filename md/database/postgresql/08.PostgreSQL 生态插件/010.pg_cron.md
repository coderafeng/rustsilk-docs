# 概述

> 官方仓库：**[citusdata/pg_cron](https://github.com/citusdata/pg_cron)**（Citus Data 出品，现为 Microsoft 维护）

**pg_cron** 是一个基于 cron 语法的 PostgreSQL **作业调度器**，直接作为数据库扩展在 PostgreSQL 内部运行——不需要 crontab、不需要外部调度系统，用纯 SQL 就能注册定时任务。

它的工作方式是：扩展启动一个**后台工作进程（background worker）** 跟踪 `cron.job` 表中的任务，到达调度时间后，pg_cron 会建立一条到本机的 Postgres 连接（或在同数据库内直接生成后台进程）来执行 `command` 里的 SQL。

```sql
CREATE TABLE cron.job (
    jobid bigint primary key default pg_catalog.nextval('cron.jobid_seq'),
    schedule text not null,             -- cron 表达式
    command text not null,              -- 要执行的 SQL
    nodename text not null default 'localhost',
    nodeport int not null default pg_catalog.inet_server_port(),
    database text not null default pg_catalog.current_database(),
    username text not null default current_user
);
```

并发语义：pg_cron 可以**并行运行多个作业**，但**同一个作业同时只会跑一个实例**——如果第二次触发时上一次还没跑完，新实例会排队，等前一个完成立刻启动。

典型场景：每日 `VACUUM ANALYZE`、定时分区维护（配合 **[pg_partman](./105.pg_partman.md)**）、小时级 ETL 汇总、清理过期数据（配合 **[pgmq](./120.pgmq.md)** 队列归档）。

# 安装

pg_cron 需要**预加载**（后台工作进程必须在服务启动时挂载），仅 `CREATE EXTENSION` 不够：

```bash
# Debian/Ubuntu
apt install postgresql-18-cron
# RHEL/CentOS（PGDG 源）
dnf install pg_cron_18
# Docker：官方镜像 tensorchord 或使用 citusdata/pg_cron 镜像
```

修改 `postgresql.conf` 后**重启**服务器：

```ini
shared_preload_libraries = 'pg_cron'
cron.database_name = 'postgres'   # 扩展安装在哪个库，任务也默认调度到哪个库
```

然后在指定数据库中创建扩展：

```sql
CREATE EXTENSION pg_cron;
```

> 提示：较新版本提供 `cron.use_background_workers` GUC（默认 false，用 libpq 连接执行；置为 true 时直接在同库内 fork 后台工作进程执行，不能用于 `template1` 等库）。

# 调度任务

`cron.schedule()` 注册任务，返回 job 编号：

```sql
-- 每天凌晨 3 点全库 VACUUM
SELECT cron.schedule('nightly-vacuum', '0 3 * * *', 'VACUUM');

-- 每 15 分钟刷新一张物化视图
SELECT cron.schedule('refresh-mv', '*/15 * * * *',
    'REFRESH MATERIALIZED VIEW CONCURRENTLY mv_daily_sales');

-- 不命名任务（jobname 省略），自动生成任务号
SELECT cron.schedule('1 * * * *', 'DELETE FROM login_log WHERE created_at < now() - interval ''30 days''');
```

调度表达式支持标准 5 字段 cron（分 时 日 月 周），以及 `@hourly`、`@daily`、`@weekly`、`@monthly`、`@yearly` 等常用宏。**调度时间跟随服务器系统时区**，写任务前先确认服务器时区，避免"凌晨三点"其实落在业务高峰。

修改与删除：

```sql
SELECT cron.alter_job(2, schedule := '0 */6 * * *');  -- 改任务 2 的调度
SELECT cron.unschedule('nightly-vacuum');             -- 按名字停止并删除
SELECT cron.unschedule(1);                            -- 按 jobid 删除
```

跨库/指定连接目标执行（任务实际连接 `nodename:nodeport/database` 并以 `username` 身份运行）：

```sql
SELECT cron.schedule_in_database(
    'archive-partition', '30 2 * * *',
    'SELECT partman.run_maintenance()',
    'analytics', 'postgres', 'localhost', 5432
);
```

# 查看任务与执行历史

```sql
-- 当前注册的任务
SELECT jobid, schedule, command, database, username, active FROM cron.job;

-- 执行历史（老记录会被 pg_cron 自动轮转清理）
SELECT jobid, status, return_message, start_time, end_time,
       end_time - start_time AS duration
FROM cron.job_run_details
ORDER BY start_time DESC LIMIT 10;
```

`status` 取值：`succeeded` / `failed` / `running`。监控告警可以直接基于这张表做（如连续 failed 计数）。

# 权限模型

- **谁能调度**：默认只有超级用户可以调用 `cron.schedule`；
- 超用户可以给普通用户授权，让他们在**自己有权连接的库**里调度任务：

```sql
GRANT EXECUTE ON FUNCTION cron.schedule(text, text, text) TO app_user;
```

- 任务以 `username` 列指定的身份执行；该用户必须能经受支持的方式登录目标库（pg_hba 配置对 `localhost` 的连接生效）。

# 避坑

- **忘了 shared_preload_libraries**：只 `CREATE EXTENSION` 不重启，`cron.job` 表存在但永远不会有任务跑。
- **任务静默失败**：SQL 报错只会记录在 `job_run_details.status='failed'`，不会通知任何人——生产环境务必配合监控扫这张表。
- **同库互斥**：同一个 job 未完成不并行；若某任务偶尔跑超一个调度周期，会出现"跳过排队"现象，应优先优化任务而非盲目缩短间隔。
- **调度时区陷阱**：任务按服务器系统时区触发，跨时区部署时先用 `SHOW timezone` / 操作系统时区核对，再决定 cron 表达式。
- **不能动态控制 cron.database_name 之外的调度入口**：其它数据库要能执行任务，需要 `schedule_in_database` 显式指定 database/用户，且 pg_hba 允许本机连接。
- 依赖后台进程的方案（如 Docker 单机）里，数据库重启后任务定义保留在 `cron.job` 表中，不会丢失——但**正在运行中被杀掉的 job 不会自动重试**。

# 总结

pg_cron 把"定时跑一条 SQL"从运维层的 crontab 拉回到了数据库内：任务定义随数据库备份走、权限随角色走、历史随 `job_run_details` 走。它是 pg_partman 分区维护、pgmq 消息清理、物化视图刷新的官方"配套心脏"；但注意它是**至少一次触发**语义，对错过调度窗口没有补偿（Postgres 宕机期间错过的任务不会补跑），强时效场景需要外部调度系统兜底。
