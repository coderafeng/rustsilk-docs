# 概述

> 官方仓库：**[postgresml/postgresml](https://github.com/postgresml/postgresml)**（文档站 postgresml.org）

**PostgresML**（扩展名 `pgml`）是一个"数据库内机器学习"平台：把训练、推理、模型管理直接做成 SQL 函数，让机器学习变成 Postgres 的一次普通查询，从而消灭"数据库 → 特征仓库 → Python 服务 → 写回数据库"的往返链路。它自带 Rust 实现的多线程训练引擎与 CPU 优化的推理运行时，覆盖三类能力：

- **经典 ML**：`pgml.train()` 一条 SQL 完成分类/回归/聚类训练，内置 XGBoost、LightGBM、线性模型、神经网络等多种算法与超参搜索、模型选择；
- **Transformer 推理**：`pgml.transform()` 调用 HuggingFace 模型把文本转成嵌入向量（配合 **[pgvector](025.pgvector.md#概述)** 做语义搜索）、`pgml.generate()` 跑生成式模型；
- **在线预测**：`pgml.predict(model_id, features)` 直接在 SQL 里出分，配合物化视图/触发器可实现"数据一落地、预测即更新"。

模型与训练数据同在 Postgres 里，意味着版本管理、权限、备份、事务天然复用数据库设施。需要注意：核心团队 2024 年并入 Timescale 后开源版迭代放缓，选型时请把"维护活跃度"计入评估（备选思路见 **[pg_vectorize](035.pg_vectorize.md)** + 应用层模型服务）。

# 安装

官方强烈建议使用其预装 Docker 镜像（内含 Conda Python 环境与 Rust 推理引擎）：

```bash
docker run -it --rm --pull always --name postgresml \
  -e POSTGRES_PASSWORD=postgres -p 5432:5432 \
  quay.io/timescale/postgresml:latest
# 镜像名/启动参数以官方 README 为准
```

进入容器内的 psql 后启用扩展：

```sql
CREATE EXTENSION pgml;
```

在已有 Postgres 上源码安装需要 Rust 工具链、Python（conda）与 PG 开发包，仓库 `postgresml/` 目录下 `make && make install`，步骤较多，建议直接抄官方 Installation 文档。

验证安装：

```sql
SELECT pgml.version();
```

# 训练：一条 SQL 一个模型

以经典的加州房价数据集演示（库内自带示例数据）：

```sql
-- 从 sklearn 数据集导入一张表
SELECT * FROM pgml.load_dataset('california_housing');

-- 训练一个回归模型：项目名 / 任务 / 算法 / 数据源
SELECT * FROM pgml.train(
    project_name => 'CA Housing',
    task         => 'regression',
    algorithm    => 'lightgbm',
    dataset      => 'pgml.california_housing',
    target_column => 'MedHouseVal'
);
```

产出的是一个 `model_id`，同一项目下多次 `train()` 会自动做基准对比（默认按 F1/RMSE 等任务指标选最优）。更换算法只需改 `algorithm`：`xgboost`、`linear_regression`、`neural_nets`、`kneighbors`……

查看已训练模型：

```sql
SELECT * FROM pgml.snapshot_models;   -- 旧版文档中也写作 pgml.deployments / jobs 视图
```

# 预测：SQL 内在线推理

```sql
-- 用模型 42 对新样本出分
SELECT pgml.predict(42, ARRAY[8.3252, 41, 6.98, 1.023, 322, 2.5556, 37.88, -122.23]);
```

真实业务里通常整表批量打分或写进应用查询：

```sql
SELECT id, pgml.predict(42, features_array) AS score
FROM samples
ORDER BY score DESC
LIMIT 10;
```

`pgml.deploy()` 可以选择把某项目的"默认模型"钉住（`best_score` / `production` 策略），之后按项目名预测，无须关心模型 id 变化。

# 嵌入与生成

把 HuggingFace 模型当函数用，产出直接落进 `vector` 列：

```sql
-- 文本 → 嵌入（输出可用于 pgvector 检索）
SELECT pgml.transform(
    'sentence-transformers/all-MiniLM-L6-v2',
    inputs => ARRAY['PostgreSQL is a relational database.']
);
```

典型管线：`transform()` 生成嵌入 → 写入 pgvector 列 → HNSW 索引 → 语义检索，全程不出数据库。

# 避坑

- **资源画像完全不同**：训练是 CPU/内存怪兽，`pgml.train` 在承载 OLTP 的主库上跑大表等于生产事故——训练任务放副本或独立实例。
- **版本耦合**：pgml 对 PG 大版本、Python 环境、模型格式都很敏感，跨版本升级后旧模型未必可加载，把"模型 id + 训练参数"纳入迁移清单。
- **维护风险**：开源版更新放缓，重度依赖前先验证社区活跃度；只想要"库内嵌入"的话，**[pg_vectorize](035.pg_vectorize.md)**（外部模型 API/本地推理编排）或应用层嵌入 + pgvector 是更主流的组合。
- 函数签名在各小版本间有出入（如 `train` 的参数名），报错时先 `\df pgml.*` 对一下当前实例的真实签名。

# 总结

PostgresML 是"SQL 即机器学习"的激进实践：数据不出库、训练预测都是函数调用，做特征-模型-推理一体化的内部工具非常顺手。但它把重计算压进数据库进程的形态，与主流"库内只做推理"的架构相悖，加上维护放缓，今天的推荐用法是：**嵌入生成可以试（transform + pgvector），核心训练/服务仍放专职平台**——这与 **[pgvector](025.pgvector.md)** / **[pg_vectorize](035.pg_vectorize.md)** 的分工是一致的。
