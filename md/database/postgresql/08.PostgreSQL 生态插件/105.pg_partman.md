# 概述

> 官方仓库：**[pgpartman/pg_partman](https://github.com/pgpartman/pg_partman)**

pg_partman 是一个用于**创建和管理基于时间和基于编号的表分区集**的 PostgreSQL 扩展。从 5.0.1 版本开始，仅支持内置的声明式分区，旧的基于触发器的分区方法已被弃用。

PostgreSQL 内置的声明式分区功能提供了创建分区表及其子表的命令。pg_partman 利用 PostgreSQL 提供的内置声明式功能，并在此基础上添加了额外的功能和增强特性，从而简化了分区管理。pg_partman 扩展 PostgreSQL 分区功能的一个关键方式是提供了一种**自动化子表维护**的方法（例如，根据保留策略添加新子表或删除旧子表）。pg_partman 还具备**将现有表转换为分区表或反之亦然**的功能。

它解决的正是手工分区最烦人的三件事：

1. **提前建分区**——不建就报"no partition of relation found"，pg_partman 按 `premake` 自动预建；
2. **过期分区下线**——`retention` 策略自动 DETACH/删除旧分区，冷热生命周期一句话声明；
3. **存量大表改造**——`partition_data()` 在线把非分区表搬成分区表，不锁写。

# 安装

普通扩展安装（无预加载要求），后台维护进程可选：

```bash
# Debian/Ubuntu（PGDG 源）
apt install postgresql-18-pg-partman
```

```sql
CREATE EXTENSION pg_partman;   -- 对象都装在 partman schema 下
```

可选的内置调度器 `pg_partman_bgw`（等价于免配 pg_cron 的定时器）：

```ini
# postgresql.conf（重启生效）
shared_preload_libraries = 'pg_partman_bgw'
pg_partman_bgw.interval = 3600        # 每小时跑一次 run_maintenance()
pg_partman_bgw.role = 'postgres'
pg_partman_bgw.dbname = 'postgres'
```

不启用 bgw 时，用 **[pg_cron](./010.pg_cron.md)** 调度 `SELECT partman.run_maintenance();` 即可。

# 使用示例

## 时间分区：一步到位

```sql
-- 建父表（PostgreSQL 原生声明式分区）
CREATE TABLE access_logs (
    id bigint GENERATED ALWAYS AS IDENTITY,
    created_at timestamptz NOT NULL DEFAULT now(),
    path text,
    status int
) PARTITION BY RANGE (created_at);

-- 交给 pg_partman 托管：按周分区、预建 4 个、保留 6 个月
SELECT partman.create_parent(
    p_parent_table => 'public.access_logs',
    p_control      => 'created_at',
    p_type         => 'range',
    p_interval     => '1 week',
    p_premake      => 4
);

-- 配置保留策略：超期分区自动 DETACH 后删除
UPDATE partman.part_config
SET retention = '6 months',
    retention_keep_table = false   -- false=删除分区表；true=只 DETACH 保留数据
WHERE parent_table = 'public.access_logs';
```

之后写入任意时间范围的数据，`run_maintenance()` 会确保"当前 + premake 个未来分区"始终存在：

```sql
SELECT partman.run_maintenance();   -- 由 bgw/pg_cron 定时调用，运维无感
```

## 编号分区：按 ID 段切

```sql
CREATE TABLE orders (id bigint, payload jsonb) PARTITION BY RANGE (id);

SELECT partman.create_parent(
    p_parent_table => 'public.orders',
    p_control      => 'id',
    p_type         => 'range',
    p_interval     => '10000000'      -- 每千万一个分区
);
```

## 存量表在线改造

```sql
-- 已有 5000 万行的非分区表 big_table → 按月分区
CREATE TABLE big_table_new (LIKE big_table INCLUDING ALL)
PARTITION BY RANGE (created_at);
SELECT partman.create_parent('public.big_table_new', 'created_at', 'range', '1 month');

-- 分批搬运（p_batchid/p_batch_amt 控制每轮行数，避免长事务）
SELECT partman.partition_data(
    p_parent_table => 'public.big_table_new',
    p_batchamt     => 500000,
    p_analyze      => true
);
```

v5 还提供 `reorganize_partition`（把非分区表原地切成带分区的表，走"分区表交换"路径）与 `apply_setting_maintenance()` 等批量维护函数。

## 元数据视图

```sql
-- 所有托管分区表的配置与统计
SELECT parent_table, partition_interval, premake, retention,
       max_partition, keep_table
FROM partman.part_config;

-- 子分区清单与边界
SELECT inhrelid::regclass AS child
FROM pg_inherits WHERE inhparent = 'public.access_logs'::regclass;
```

# 索引与约束提醒

分区表的索引/外键必须建在**父表**上（声明式分区自动传播到子表）；`PRIMARY KEY`/`UNIQUE` 必须包含分区键。查询想只扫相关分区，WHERE 里要带上分区键的**常量或可证明裁剪的条件**（详见 PostgreSQL 官方 Partitioning 章节）。

# 避坑

- **没有维护调度 = 只建了个坑**：premake 窗口耗尽后未来分区不再自动出现，插入超范围数据直接报错——上线第一天就把 `run_maintenance()` 挂进 pg_cron/bgw。
- **retention 删除是物理 DROP**：`retention_keep_table=false` 配 `retention_keep_index` 组合下手很狠，历史数据先确认有备份/归档再开删除。
- **时间列类型要匹配**：`range` + 时间分区推荐 `timestamptz`；用 `date` 时 interval 只接受日级，粒度规划完全不同。
- **默认分区（DEFAULT）与 pg_partman 不共存的迷思**：可以建 DEFAULT 分区兜底迟到数据，但会掩盖 premake 不足的问题，生产建议关 DEFAULT、让报错暴露调度故障。
- 大版本升级前查 pg_partman 的 release notes：v4→v5 API 有破坏性变更（函数参数改名、触发器分区移除）。

# 总结

pg_partman 是"声明式分区的自动驾驶"：**建分区、滚分区、删分区**三件事从 DBA 例行工单变成一次性声明。时间序列大表（日志、账单、事件）是它的绝对主场；如果你的负载是"带时间戳的追加写 + 窗口查询"且想要连续聚合/压缩，可以对比 **[TimescaleDB](./070.timescaledb.md)**；若只要原生分区 + 托管维护，pg_partman 是最小成本的正确答案。
