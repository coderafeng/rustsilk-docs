# 概述

> 官方文档：**[postgres_fdw — 访问外部 PostgreSQL 服务器](https://www.postgresql.org/docs/18/postgres-fdw.html)**
> 
> 中文版镜像：**[postgres_fdw — 访问外部 PostgreSQL 服务器](https://pgsql.cc/docs/18/postgres-fdw.html)**

postgres_fdw 模块提供外部数据包装器 `postgres_fdw`，可用于**访问存储在外部 PostgreSQL 服务器中的数据**。它把远端库的表挂载成本地"外部表"（foreign table）：查询照常写 SQL，postgres_fdw 负责把**能下推的部分**（投影、过滤、JOIN、聚合）翻译成远程 SQL 发过去执行，只把结果集拉回来——两个 Postgres 之间的联邦查询零 ETL。

典型场景：

- **跨库聚合**：分库分表的历史遗留系统，用一个查询库汇总各分片的报表；
- **数据搬迁/同步验证**：升级迁移期间新旧库互查对账；
- **读写分离旁路**：把只读的外部数据源映射进来给 BI 用；
- FDW 框架的旗舰实现——理解它之后，mysql_fdw/mongo_fdw/oracle_fdw 等第三方包装器的用法同构。

# 安装

本地和远端都必须是 PostgreSQL；contrib 自带，无需重启：

```sql
CREATE EXTENSION postgres_fdw;
```

# 使用示例：四步挂载远端表

```sql
-- 1) 创建扩展对象：服务器（远端实例的入口）
CREATE SERVER remote_sakila
FOREIGN DATA WRAPPER postgres_fdw
OPTIONS (host '10.0.0.21', port '5432', dbname 'sakila');

-- 2) 用户映射：本库用户用哪个远端账号连接
CREATE USER MAPPING FOR CURRENT_USER
SERVER remote_sakila
OPTIONS (user 'reader', password 'secret');
-- 生产环境用 passwordfile / sslmode=verify-full 或通道文件管理凭据

-- 3) 建外部表（逐表定义）
CREATE FOREIGN TABLE f_customer (
    customer_id int,
    first_name  varchar(45),
    last_name   varchar(45),
    email       varchar(50),
    store_id    smallint
) SERVER remote_sakila OPTIONS (schema_name 'public', table_name 'customer');

-- 或批量导入整 schema（还支持 EXCEPT 列表、prefix/后缀等参数）
IMPORT FOREIGN SCHEMA public LIMIT TO (film, actor, inventory)
FROM SERVER remote_sakila INTO remote_schema;

-- 4) 查询！本地表 JOIN 远端表
SELECT c.last_name, count(i.inventory_id) AS rentals
FROM f_customer c
JOIN inventory_summary i ON i.customer_id = c.customer_id   -- 本地汇总表
GROUP BY 1 ORDER BY 2 DESC LIMIT 10;
```

远端凭据建议用 `.pgpass`/环境变量方案，避免明文写在 `USER MAPPING` 里（见 **[用户与权限](../05.PostgreSQL%20数据库管理/055.用户与权限.md)**）。

# 下推（pushdown）：性能命门

postgres_fdw 会把语句拆成"远端执行 + 本地执行"两段。`ORDER BY`、`WHERE`、聚合、甚至 JOIN **在语义等价且远端支持时**都会被拼进远程 SQL：

```sql
EXPLAIN (VERBOSE)
SELECT count(*) FROM f_customer WHERE store_id = 1;
-- Foreign Scan
--   -> Remote SQL: SELECT count(*) FROM public.customer WHERE store_id = 1
```

**看不到 Remote SQL 包住你的过滤条件 = 整表往回拉**。常见不满足：表达式含本地独有函数、参数类型转换、`COLLATE` 差异。优化手段：

```sql
-- 让远端连接使用与本地一致的行为（PG 版本差距大时尤其有用）
ALTER SERVER remote_sakila OPTIONS (ADD use_remote_estimate 'true',
                                    ADD fetch_size '5000');
-- use_remote_estimate：在远端跑 EXPLAIN 估行，复杂查询计划质量更好
-- fetch_size：大结果集分批取，控制内存
```

外部表也**可写**：`INSERT/UPDATE/DELETE` 会转发到远端执行（远端账号需有权限），跨库分布式事务是**尽力而为**——远端提交失败时本地会报错，但不保证两库原子性。

# 避坑

- **连接是会话级复用的**：一个后端对同一 SERVER 保持一条远端连接；空闲后断开重连，高频短查询场景注意远端 `max_connections` 与连接风暴（配 PgBouncer 在远端兜住）。
- **网络是性能天花板**：即便下推完美，跨机房延迟也救不了交互式查询；FDW 适合"批量拉汇总"，不适合"高频小查询"。
- **类型/字符集对齐**：外部表列定义与远端不一致时可能静默截断或转换报错，`IMPORT FOREIGN SCHEMA` 是防手滑的首选。
- 远端表结构变更后外部表不会自动跟随（列漂移导致错位/报错），改版记得重导定义。
- 监控视角里远端执行出现在**远端实例**的 pg_stat_activity/pg_stat_statements，本地看只有 Foreign Scan——两头都要会看。
- 安全：外部表本质是"带凭据的远程通道"，收紧 `USER MAPPING` 与 SERVER 的 USAGE 权限。

# 总结

postgres_fdw 用最小代价打通"库间数据孤岛"：建 SERVER → 映射用户 → 导入表结构，联邦查询即可跑，且优化器会尽量把活推给远端干。它与 **[Citus](./110.citus.md)** 的分工：Citus 是"把数据真正分布出去"，FDW 是"数据留在原地、查询跨过去"——对账、报表整合、渐进式拆分，选后者起步最稳。
