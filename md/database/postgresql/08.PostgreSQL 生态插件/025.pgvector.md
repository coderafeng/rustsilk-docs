# 概述

> 官方仓库：**[pgvector/pgvector](https://github.com/pgvector/pgvector)**

**pgvector** 是 Postgres 生态事实标准的**开源向量相似性搜索**扩展。它给 Postgres 带来向量数据类型与配套的相似度操作符、ANN 索引，让"存业务数据 + 存嵌入向量 + 向量检索"留在同一个数据库里完成——无需引入 Milvus/Qdrant/Chroma 等独立向量库，天然继承 ACID 事务、备份恢复、权限与复制能力。

核心能力一览：

| 能力     | 说明                                                                                                        |
|----------|-------------------------------------------------------------------------------------------------------------|
| 数据类型 | `vector`（float32，≤16384 维）、`halfvec`（float16，≤64000 维）、`bit`（二值向量）、`sparsevec`（稀疏向量） |
| 距离搜索 | L2、内积、余弦、L1，以及 `bit` 的 Hamming/Jaccard                                                           |
| 精确搜索 | 无索引时顺序扫描，结果 100% 准确                                                                            |
| 近似索引 | **HNSW**（0.5.0+，默认推荐）、**IVFFlat**（0.4.0+）                                                         |
| 过滤检索 | 与任意 SQL `WHERE` 组合；0.8.0 的迭代索引扫描缓解"过滤后召回不足"                                           |
| 量化     | `halfvec`/`bit` 列可做二值/半精度压缩存储与检索                                                             |

典型场景：语义检索、RAG 知识库、图片/音频相似搜索、推荐系统召回层——通常与 **[pg_vectorize](./035.pg_vectorize.md)**（自动生成嵌入）、**[pgvectorscale](./030.pgvectorscale.md)**（大规模性能加强）搭配。

# 安装

```bash
# Docker（最快体验）
docker run -d --name pgvector -e POSTGRES_PASSWORD=postgres -p 5432:5432 pgvector/pgvector:pg18

# Debian/Ubuntu（PGDG 源）
apt install postgresql-18-pgvector
# RHEL/CentOS（PGDG 源）
dnf install postgresql18-pgvector

# 源码
git clone --branch v0.8.1 https://github.com/pgvector/pgvector.git
cd pgvector && make && sudo make install
```

在数据库中启用：

```sql
CREATE EXTENSION vector;
```

# 基本使用：存储与精确搜索

```sql
CREATE TABLE items (
    id   bigserial PRIMARY KEY,
    embedding vector(3)          -- 3 维向量列
);

INSERT INTO items (embedding) VALUES ('[1,2,3]'), ('[4,5,6]'), ('[7,8,90]');

-- 欧氏距离最近邻（精确计算，小表够用）
SELECT id, embedding <-> '[3,1,2]' AS distance
FROM items
ORDER BY embedding <-> '[3,1,2]'
LIMIT 5;
```

距离操作符速查：

| 操作符        | 距离              | 适用                        |
|---------------|-------------------|-----------------------------|
| `<->`         | L2 欧氏距离       | 图像、多数 embedding 模型   |
| `<#>`         | **负**内积        | 向量已归一化时等价于余弦    |
| `<=>`         | 余弦距离          | 文本 embedding（OpenAI 等） |
| `<+>`         | L1 曼哈顿距离     | 0.7.0+                      |
| `<~>` / `<%>` | Hamming / Jaccard | `bit` 二值向量              |

> 建索引时**必须选与查询一致的操作符类**：用 `<=>` 查询就建 `vector_cosine_ops`，混用不会命中索引。

# 索引：HNSW 与 IVFFlat

```sql
-- HNSW：默认推荐，召回率高、构建慢、内存占用大
CREATE INDEX ON items
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

-- IVFFlat：先聚类再探簇，构建快、需要定期重建以匹配数据分布
CREATE INDEX ON items
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);
```

查询侧的精度/速度旋钮：

```sql
-- HNSW：候选队列长度，默认 100，越大召回越高、越慢
SET hnsw.ef_search = 200;

-- IVFFlat：探测簇数，默认 1；经验值 lists/10 ~ lists/4
SET ivfflat.probes = 10;
```

参数经验值（官方 README 建议）：

- `lists` ≈ `行数 / 1024`（100 万行以内最多 10000，千万行用 10000~100000）；
- `m = 16`、`ef_construction = 64` 是通用的起步配置，召回不够再加大 `ef_construction`。

# 组合过滤与迭代扫描

向量检索最常见的形态是"相似度 + 业务条件"：

```sql
SELECT * FROM items
WHERE id > 100                      -- 普通过滤条件
ORDER BY embedding <-> '[3,1,2]'
LIMIT 5;
```

传统 ANN 索引在强过滤下会"扫够即止"导致结果不足，0.8.0 引入**迭代索引扫描**持续翻页直到凑满 LIMIT：

```sql
-- 全局开启
SET hnsw.iterative_scan = relaxed_order;
SET ivfflat.iterative_scan = relaxed_order;
```

# 性能要点

- **索引构建很吃内存**：大表建 HNSW 前先 `SET maintenance_work_mem = '1GB'`（或调高 `temp_tablespaces` 走磁盘），并可调 `max_parallel_maintenance_workers` 并行构建；
- **维度上限**：`vector` 列可存 16384 维，但**建索引只支持 ≤2000 维**——更高维需降维或改用 `halfvec`（索引支持到 4000 维）；
- **量化存储**：`halfvec(768)` 空间减半；配合二值化（`bit`）可做"粗排召回 + 原向量精排"两段式检索；
- **写入放大**：HNSW 插入需维护图，批量导入场景可先 COPY 后建索引。

# 避坑

- **忘记 ORDER BY 距离操作符**：`WHERE embedding <-> x < 0.5` 这种写法不走索引，是逐行精确计算；正确姿势是 `ORDER BY ... LIMIT` + 外层过滤。
- **精确 vs 近似的语义差异**：没建索引时 pgvector 做**精确**最近邻；刚建好索引"变快了但结果变了"是正常现象（HNSW 是近似算法），验收时用召回率评估。
- **操作符类不匹配静默退化**：查询用了 `<->` 但索引是 `vector_ip_ops`，不会报错，只是不走了索引——用 `EXPLAIN` 确认出现 `Index Scan using ... (KNN)`。
- 距离 `<#>` 返回的是**负内积**，想要"分数越大越相似"需取负。
- 大表（千万级以上、要求 >99% 召回低延迟）先试 **[pgvectorscale](./030.pgvectorscale.md)** 再考虑外部向量库。

# 总结

pgvector 让"向量检索"成为 Postgres 的一个普通列类型：schema、事务、备份、权限全部复用现有体系，对绝大多数中等规模（百万~千万向量）的语义搜索与 RAG 场景已经够用。它的扩展面很好——向上有 pgvectorscale/pgcontext 做性能加强，向下有 pg_vectorize 做嵌入编排，是 Postgres AI 技术栈的地基。
