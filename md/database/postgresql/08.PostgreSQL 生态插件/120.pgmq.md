# 概述

> 官方仓库：**[pgmq/pgmq](https://github.com/pgmq/pgmq)**
> 
> 官方文档：https://pgmq.github.io/pgmq/latest/

**pgmq**（Postgres Message Queue）是一个轻量级的消息队列，类似于 AWS SQS 和 RSMQ，但基于 Postgres。特性：

- 轻量级——没有后台工作进程或外部依赖，只有 Postgres SQL 对象；
- 保证在可见性超时（visibility timeout）内向消费者"仅一次"送达消息；
- 使用消息组键的先进先出（FIFO）队列进行有序处理；
- 支持基于主题的路由，可用通配符模式实现发布/订阅和基于内容的路由；
- 消息会一直保留在队列中，直到被显式删除；
- 为了长期保存和重放，消息可以被**归档**而不是删除。

它的世界观极简：**每个队列就是一张表**（`pgmq.q_<队列名>`），消费就是带锁的 SELECT + DELETE。这带来两个巨大红利——运维零额外组件（备份/监控/权限全走 Postgres 老路），以及消息与业务数据**同库同事务**（"扣库存 + 发消息"原子化，不再需要 outbox 表）。代价是吞吐与延迟不及专业 MQ（Kafka/RocketMQ），适合中低频任务派发、邮件/通知、作业编排、轻量事件流。

# 安装

Docker（预装扩展）：

```bash
docker run -d --name pgmq-postgres -e POSTGRES_PASSWORD=postgres \
  -p 5432:5432 ghcr.io/pgmq/pg18-pgmq:v1.10.0
```

已有 Postgres 实例：从 PGDG 源装 `postgresql-18-pgmq`（或 GitHub Releases 二进制），然后：

```sql
CREATE EXTENSION pgmq;   -- 对象安装在 pgmq schema 下
```

纯 SQL 安装（无编译环境时）：`psql -f pgmq-extension/sql/pgmq.sql <连接串>`，功能等价，升级方式不同。支持 PostgreSQL 14~18。

# 使用示例：SQS 风格六件套

```sql
-- 1) 创建队列
SELECT pgmq.create('my_queue');           -- 实际表：pgmq.q_my_queue

-- 2) 发送（JSON 消息体，返回 msg_id；可带 delay 秒）
SELECT * FROM pgmq.send(queue_name => 'my_queue', msg => '{"foo":"bar1"}');
SELECT * FROM pgmq.send(queue_name => 'my_queue', msg => '{"foo":"bar2"}', delay => 5);
SELECT * FROM pgmq.send_batch('my_queue',
    ARRAY['{"foo":"bar3"}','{"foo":"bar4"}']::jsonb[]);

-- 3) 读取：取 2 条，不可见 30 秒（超时未删则重新可见——至少一次语义）
SELECT * FROM pgmq.read(queue_name => 'my_queue', vt => 30, qty => 2);

-- 4) 完成处理：删除；或 pop = 读取并立即删除
SELECT pgmq.delete('my_queue', 6);
SELECT * FROM pgmq.pop('my_queue');

-- 5) 归档（移出队列、保留可重放）
SELECT pgmq.archive('my_queue', 2);
SELECT * FROM pgmq.a_my_queue;            -- 归档表 a_<队列名> 可直接 SQL 查

-- 6) 销毁
SELECT pgmq.drop_queue('my_queue');
```

消费者伪代码（应用侧循环）：

```text
loop:
    msgs = pgmq.read(queue, vt=30, qty=10)
    for m in msgs: process(m); pgmq.delete(queue, m.msg_id)
    if msgs empty: sleep(poll_interval)
```

处理失败的消息**不用任何操作**——VT 到期自动回队重试；配合 `read_with_poll`（带 `max_poll_wait_ms` 长轮询）可以减少空转。

## 高级队列能力

- **FIFO 有序**：发送时给 `group_id`，同组消息按序消费（v1.x 起，具体参数见版本文档）；
- **主题路由 / 发布订阅**：较新版本支持按 topic 通配符把消息投给多个订阅队列，取代手工多 send；
- **保留与指标**：`pgmq.metrics()` / `pgmq.metrics_all()` 输出队列深度、在途、 oldest_visible，可直接接监控；
- **事务性**：在 `BEGIN` 里业务写入 + `pgmq.send` 同提交，实现原生事务性发件箱。

# 消费模型与参数

| 概念                         | 说明                                                            |
|------------------------------|-----------------------------------------------------------------|
| Visibility Timeout (`vt`)    | 读取后消息隐藏的秒数；必须 > 你的最长处理时间，否则会被重复消费 |
| `delay`                      | 发送后延迟可见（定时任务的最小实现）                            |
| `read_ct`                    | 被读取次数——死信判断依据（超阈值转人工）                        |
| `enqueued_at / last_read_at` | 排队与到期时间，做延迟/积压告警                                 |

# 避坑

- **至少一次，不是恰好一次**：VT 内没处理完 → 第二消费者重复拿到。消费端必须幂等（按业务键去重）。
- **高吞吐别硬扛**：十万级 TPS、严格顺序全队列、百万级积压是 Kafka 的地盘；pgmq 单队列百万行内表现最佳，大积压时及时 archive/扩容消费并行度。
- **空轮询风暴**：多消费者 `psql` 循环不带退避会把 CPU 打满——用 `read_with_poll` 或外部控制节奏。
- **表膨胀**：删除/归档后的行靠 vacuum 回收，高频队列关注 autovacuum 对该表的定制阈值（`ALTER TABLE pgmq.q_x SET (autovacuum_vacuum_scale_factor=0.02)`）。
- 权限：消费者角色只需 `pgmq` schema 下的函数 EXECUTE + 队列表读写，别直接给超级账号跑 worker。

# 总结

pgmq 把"队列"降级成"一张表 + 几个函数"，换来零运维与事务一致性——在 Postgres 已是核心存储的架构里，它是通知、任务派发、事件驱动的最小可行答案；当规模越过"每队列百万级消息、毫秒级广播"的线，再迁移专业 MQ。**[pg_vectorize](035.pg_vectorize.md)** 内部正是用 pgmq 做嵌入任务的队列编排，可作为生产级用法参考。
