# 概述

- JSON 类型用于存储 RFC 7159 定义的 JSON 数据。相比用 text 存，优势是**强制每个值都符合 JSON 规则**，并提供一大批 JSON 专用的 **[函数和操作符](../07.PostgreSQL%20内置函数/015.JSON函数.md#概述)**。
- PostgreSQL 提供两种存储类型：**json** 和 **jsonb**，并为高效查询提供 **jsonpath** 类型。
- 核心区别在效率：
    - **json**：存输入文本的**精确副本**，每次处理都要重新解析；保留空白、键顺序、重复键。
    - **jsonb**：存**解析后的二进制**，写入稍慢但读取显著更快；**不**保留空白/键顺序/重复键，**支持索引**。
- 经验法则：**绝大多数应用直接用 jsonb**，除非你确实依赖“保留键顺序/原始文本”这类特殊需求（如某些遗留系统对对象键顺序有假设）。
- JSON 数据也能建成关系表，二者可在同一应用共存互补；但即便追求灵活，也建议文档有**相对固定的结构**，方便聚合查询。

# json vs jsonb 速查表

| 维度         | json                          | jsonb                                    |
|--------------|-------------------------------|------------------------------------------|
| 内部存储     | 输入文本精确副本              | 解析后的分解式二进制                     |
| 写入速度     | 快（不解析）                  | 略慢（需转换）                           |
| 读取/处理    | 每次重新解析，慢              | 免解析，快                               |
| 索引支持     | 不支持                        | 支持（GIN / btree / hash）               |
| 保留空白     | 是                            | 否                                       |
| 保留键顺序   | 是                            | 否（按内部规则重排）                     |
| 保留重复键   | 是（全部保留，末值生效）      | 否（只留最后一个）                       |
| 数字精度限制 | 无额外限制                    | 受限于 numeric，拒绝超范围/NaN/Infinity  |
| 推荐场景     | 需保真原始文本/键顺序         | 默认选择，尤其要查询和索引               |

> [!tip]
> 拿不准就选 **jsonb**。需要索引、要做包含/存在查询、要按内部字段检索，都只有 jsonb 能高效支撑。

# JSON 基本类型映射

把文本 JSON 转成 jsonb 时，RFC 7159 的基本类型会映射到原生 PostgreSQL 类型，因此带来一些额外的小限制（这些限制不适用于 json）：

| JSON 基本类型 | PostgreSQL 类型 | 说明                                                             |
|---------------|-----------------|------------------------------------------------------------------|
| string        | text            | 不允许 `\u0000`，不允许表示数据库编码不可用字符的 Unicode 转义   |
| number        | numeric         | 不允许 NaN 和 infinity 值；超出 numeric 范围会被拒绝             |
| boolean       | boolean         | 只接受小写 `true` 和 `false`                                     |
| null          | （无）          | SQL NULL 与 JSON null 是不同概念                                 |

- 数据库编码非 UTF8 时，JSON 类型无法严格符合规范（RFC 要求 JSON 字符串用 UTF-8）。
- jsonb 输入更严格：会把合法的 Unicode 转义（含代理对）折叠为等效单字符存储。

# 输入与输出语法

输入/输出语法遵循 RFC 7159。下面都是合法的 json（或 jsonb）表达式：

```sql
-- 标量/基本值
SELECT '5'::json;

-- 数组（元素类型不必一致）
SELECT '[1, 2, "foo", null]'::json;

-- 对象（键必须是加引号的字符串）
SELECT '{"bar": "baz", "balance": 7.77, "active": false}'::json;

-- 可任意嵌套
SELECT '{"foo": [true, "bar"], "tags": {"a": 1, "b": null}}'::json;
```

原样输入输出时，json 回显完全相同的文本，jsonb 则丢弃无语义空白并重排键：

```sql
SELECT '{"bar": "baz", "balance": 7.77, "active":false}'::json;
                     json
-------------------------------------------------
 {"bar": "baz", "balance": 7.77, "active":false}

SELECT '{"bar": "baz", "balance": 7.77, "active":false}'::jsonb;
                     jsonb
--------------------------------------------------
 {"bar": "baz", "active": false, "balance": 7.77}
```

数字按底层 numeric 行为输出，E 记法会被展开：

```sql
SELECT '{"reading": 1.230e-5}'::json, '{"reading": 1.230e-5}'::jsonb;
         json          |          jsonb
-----------------------+-------------------------
 {"reading": 1.230e-5} | {"reading": 0.00001230}
```

> [!note]
> 构造与处理 JSON 的内置函数详见 **[JSON函数](../07.PostgreSQL%20内置函数/015.JSON函数.md#概述)**。

# jsonb 包含与存在

**测试包含**是 jsonb 的核心能力，json 没有对应功能。包含检查“一个 jsonb 文档是否包含另一个文档”，除注明外下列均返回真：

```sql
-- 标量只包含相同值
SELECT '"foo"'::jsonb @> '"foo"'::jsonb;

-- 数组包含子集，元素顺序无关、重复只算一次
SELECT '[1, 2, 3]'::jsonb @> '[1, 3]'::jsonb;
SELECT '[1, 2, 3]'::jsonb @> '[3, 1]'::jsonb;
SELECT '[1, 2, 3]'::jsonb @> '[1, 2, 2]'::jsonb;

-- 对象包含子集
SELECT '{"product": "PostgreSQL", "version": 9.4}'::jsonb @> '{"version": 9.4}'::jsonb;

-- 结构必须匹配：数组不会“穿透”匹配嵌套数组
SELECT '[1, 2, [1, 3]]'::jsonb @> '[1, 3]'::jsonb;    -- 假
SELECT '[1, 2, [1, 3]]'::jsonb @> '[[1, 3]]'::jsonb;  -- 真
SELECT '{"foo": {"bar": "baz"}}'::jsonb @> '{"bar": "baz"}'::jsonb; -- 假
```

例外：数组可以包含一个基本值，但该规则不对称：

```sql
SELECT '["foo", "bar"]'::jsonb @> '"bar"'::jsonb;  -- 真
SELECT '"bar"'::jsonb @> '["bar"]'::jsonb;          -- 假
```

**存在操作符** `?` 可看作包含的变体，测试某字符串是否在**顶层**作为对象键或数组元素出现：

```sql
SELECT '["foo", "bar"]'::jsonb ? 'bar';        -- 真：作为数组元素
SELECT '{"foo": "bar"}'::jsonb ? 'foo';        -- 真：作为键
SELECT '{"foo": "bar"}'::jsonb ? 'bar';        -- 假：不看值
SELECT '{"foo": {"bar": "baz"}}'::jsonb ? 'bar'; -- 假：只在顶层匹配
```

对象比数组更适合做包含/存在测试——对象内部针对搜索做了优化，无需线性扫描。

> [!tip]
> 包含 `@>` 是**嵌套**的，可用整棵子结构做查询从而命中索引；存在 `?` 只看**顶层**。想跳过子对象显式选择，优先用 `@>`。

# jsonb 索引

GIN 索引用于高效检索大量 jsonb 文档中出现的键或键/值对。提供两种操作符类，在性能与灵活性间权衡：

| 操作符类        | 支持操作符                    | 特点                                  |
|-----------------|-------------------------------|---------------------------------------|
| `jsonb_ops`默认 | `?` `?\|` `?&` `@>` `@?` `@@` | 灵活，任意键可查；索引较大            |
| `jsonb_path_ops`| `@>` `@?` `@@`                | 更小更快，但**不支持键存在 `?`**      |

```sql
-- 默认 GIN 操作符类
CREATE INDEX idxgin ON api USING GIN (jdoc);

-- 非默认 jsonb_path_ops（更小、更有针对性）
CREATE INDEX idxginp ON api USING GIN (jdoc jsonb_path_ops);
```

命中索引的查询示例：

```sql
-- 查找 company 为 Magnafone 的文档（@> 可用简单 GIN 索引）
SELECT jdoc->'guid', jdoc->'name' FROM api WHERE jdoc @> '{"company": "Magnafone"}';
```

但下面这句里 `?` 没有直接作用在被索引列上，简单 GIN 索引命中不了：

```sql
SELECT jdoc->'guid' FROM api WHERE jdoc -> 'tags' ? 'qui';
```

可以用**表达式索引**针对常查路径加速：

```sql
CREATE INDEX idxgintags ON api USING GIN ((jdoc -> 'tags'));
```

也可改用包含写法，让简单 GIN 索引直接支撑：

```sql
SELECT jdoc->'guid' FROM api WHERE jdoc @> '{"tags": ["qui"]}';
```

- **简单索引**（对整列建 GIN）灵活得多，支持任意键查询，但会为每个键和值都存副本，体积大。
- **表达式索引**只索引指定路径数据，通常更小更快，但只覆盖该路径。

GIN 也支持 jsonpath 匹配操作符 `@?` 和 `@@`：

```sql
SELECT jdoc->'guid' FROM api WHERE jdoc @? '$.tags[*] ? (@ == "qui")';
SELECT jdoc->'guid' FROM api WHERE jdoc @@ '$.tags[*] == "qui"';
```

> [!warning]
> `jsonb_path_ops` 不会为不含任何值的结构（如 `{"a": {}}`）生成索引项，查这类结构需全索引扫描、很慢。频繁做这种搜索的应用不适合它。

jsonb 还支持 btree 和 hash 索引，通常只在需要比较**整个文档是否相等**时才有用。btree 对 jsonb 的排序规则大致为：

```text
对象 > 数组 > 布尔 > 数字 > 字符串 > null
键值对多的对象 > 键值对少的对象
元素多的数组 > 元素少的数组
```

（存在历史例外：顶层空数组排在 null 之前；对象键按存储顺序比较，短键先于长键。）

# jsonb 下标

jsonb 支持数组风格的下标表达式，用于**提取和修改**元素，规则与 `jsonb_set` 的 path 参数一致。结果是 jsonb 类型；数组下标从 0 开始，负数从末尾反向计数；不支持切片。

```sql
-- 按键提取
SELECT ('{"a": 1}'::jsonb)['a'];
-- 按路径提取嵌套值
SELECT ('{"a": {"b": {"c": 1}}}'::jsonb)['a']['b']['c'];
-- 按数组下标提取
SELECT ('[1, "2", null]'::jsonb)[1];

-- 更新：赋予的值也必须是合法 jsonb（注意 '1' 的引号）
UPDATE table_name SET jsonb_field['key'] = '1';

-- 用带下标的 WHERE 过滤，比较值也需是 jsonb
SELECT * FROM table_name WHERE jsonb_field['key'] = '"value"';
```

下标赋值在边界情况与 `jsonb_set` 不同：源值为 NULL 时按下标暗示类型当空对象/空数组处理；对不足长度的数组指定下标会追加 NULL 填充到可达；中间层不是对象/数组则报错回滚。

```sql
-- 原为 NULL 的列变为 {"a": 1}
UPDATE t SET j['a'] = '1';
-- 原为 [] 的列变为 [null, null, 2]
UPDATE t SET j[2] = '2';
```

# jsonpath 类型

jsonpath 类型实现对 SQL/JSON 路径语言的支持，提供解析后的路径表达式二进制表示，供 JSON 查询函数使用。语法借鉴 JavaScript 约定：

- 点号 `.` 访问成员，方括号 `[]` 访问数组。
- 数组下标从 **0** 开始（区别于从 1 开始的原生 SQL 数组）。
- 变量：`$` 当前被查询值，`$varname` 命名变量，`@` 过滤表达式中的当前项。
- 访问器：`.key`、`.*`（通配成员）、`.**`（递归通配，PG 扩展）、`[index]`、`[start to end]`、`[*]`，支持 `last` 关键字。
- 嵌入字符串字面量遵循 JS 约定，用双引号，`\"` 表示引号、`\\` 表示反斜杠。

```sql
-- 示例：用 jsonpath 过滤
SELECT * FROM api
WHERE jdoc @@ '$.tags[*] == "qui" || $.tags[*] == "enim"';
```

更多操作符与方法参见 **[JSON函数](../07.PostgreSQL%20内置函数/015.JSON函数.md#概述)**。

# 转换（过程语言）

部分扩展为过程语言实现了 jsonb 转换：`jsonb_plperl` / `jsonb_plperlu` 映射为 Perl 数组/hash/标量；`jsonb_plpython3u` 映射为 Python 字典/列表/标量。其中 `jsonb_plperl` 属“受信任”扩展，非超级用户有 CREATE 权限即可安装，其余需超级用户。

# 实战 SQL

```sql
-- 建表：用户档案，动态属性放 jsonb
CREATE TABLE users (
    id      bigserial PRIMARY KEY,
    profile jsonb NOT NULL
);

INSERT INTO profile_demo VALUES
('{"name":"Alice","city":"Hangzhou","tags":["dev","ops"],"age":30}'),
('{"name":"Bob","city":"Beijing","tags":["dev"],"age":25}');

-- 取字段
SELECT profile->>'name' AS name, profile->>'city' AS city FROM users;

-- 包含查询（可命中 GIN）
SELECT * FROM users WHERE profile @> '{"city":"Hangzhou"}';

-- 存在查询（顶层键）
SELECT * FROM users WHERE profile ? 'age';

-- jsonpath 过滤
SELECT profile->>'name' FROM users WHERE profile @@ '$.age > 28';

-- 建 GIN 索引加速属性检索
CREATE INDEX idx_users_profile ON users USING GIN (profile jsonb_path_ops);

-- 用下标修改单个字段
UPDATE users SET profile['verified'] = 'true' WHERE id = 1;
```

# 最佳实践

1. **默认选 jsonb**，需要索引和内部检索时更是如此；只有在要保真原始文本/键顺序时才用 json。
2. **给需要检索的 jsonb 列建 GIN 索引**；确定只用 `@>`/jsonpath 时用 `jsonb_path_ops`（更小更快）。
3. **热点查询路径建表达式索引**（如 `((j->'tags'))`），兼顾性能与索引体积。
4. **文档保持相对固定结构**，别把完全无 schema 的 blob 塞进去，否则难以聚合与约束。
5. **控制单个文档大小**：更新会在整行加行锁，大文档加剧锁争用；一个文档应表示一个原子数据项。
6. **能规范化的稳定字段拆成真实列**，只把稀疏/易变属性放 JSONB（混合建模）。
7. **查询用 `->>` 取 text、`->` 取 jsonb**，别混用；比较值记得保持类型一致。
8. **需要业务规则时用 CHECK/生成列/表达式约束**兜住 JSON 里的关键字段。

# 常见坑

1. **json 不支持索引**，也别指望它有包含/存在操作符——这些是 jsonb 独有。
2. jsonb **不保留键顺序和重复键**，别把顺序当语义依赖。
3. `@>` 要求**结构匹配**，数组不会穿透匹配其内嵌数组（`'[..]' @> '[1,3]'` 为假）。
4. 存在 `?` **只看顶层**，深层键不会被匹配到。
5. `jsonb_path_ops` **不支持 `?` 键存在**，且对无值结构 `{"a":{}}` 无索引项。
6. jsonb 会**拒绝 NaN/Infinity、超 numeric 范围数字、`\u0000`**，json 相对宽松。
7. 布尔只认小写 `true`/`false`；对象键必须加引号——这是常见输入报错来源。
8. 更新 JSON 任意深层字段都会**重写整行**，高频局部更新要警惕膨胀与锁。
9. 数据库编码非 UTF-8 时无法严格符合 JSON 规范。
10. 直接对整列 `to_jsonb`/函数包裹做 WHERE，会让普通索引失效，需表达式索引。
11. 下标赋值路径中间层若是标量会**报错回滚**，不是静默忽略。
12. `->` 返回 jsonb、`->>` 返回 text，`WHERE col->>'k' = 'v'` 才走 text 比较，别漏写引号层。

# 总结

- **json 存原文（保序、无索引），jsonb 存二进制（快、可索引）**，绝大多数场景直接用 jsonb。
- jsonb 的价值在包含 `@>`、存在 `?`、jsonpath `@@` 配合 **GIN 索引**做属性检索。
- 把稳定字段规范化为真实列、易变稀疏属性放 JSONB，控制文档大小、给热点路径建索引，是落地关键。
