# 概述

- **uuid** 类型用于存储 128 位“通用唯一标识符”（UUID，某些系统称 GUID），遵循 RFC 9562 / ISO/IEC 9834-8:2005 及相关标准。
- 核心价值：在**分布式系统**里提供比序列（sequence）更强的唯一性保证——序列只在单个数据库内唯一，UUID 由算法生成，碰撞概率极低。
- 内部只占 **16 字节**，比把 UUID 存成 36 字符的 text 更省空间、比较更快。
- 输入格式宽松（大小写、花括号、连字符可省略），但**输出永远是标准小写带连字符形式**。
- PostgreSQL 原生支持生成 **UUIDv4（随机）** 和 **UUIDv7（时间有序，PG18+）**；其他版本也可存入，只是要在应用端生成。
- 主键选型经验：需要全局唯一、跨库合并、离线生成 → UUID；纯单库高写入、追求索引紧凑 → 仍优先考虑 BIGINT/IDENTITY。

# 类型速查表

| 维度     | 说明                                              |
|----------|---------------------------------------------------|
| 存储大小 | 16 字节（固定）                                   |
| 标准显示 | `a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11`（36 字符） |
| 别名     | `uuid` 无变体                                     |
| 生成函数 | `gen_random_uuid()`（v4）、`uuidv7()`（v7，PG18+）|
| 索引表现 | B-tree 可直接索引，但随机 v4 会造成索引写入分散   |
| 排序     | 按 128 位二进制值整体比较                          |

# 为什么用 uuid 而不是 text 存

很多人习惯把 UUID 存成 `char(36)` / `varchar`，这是常见误区：

- **空间**：uuid 16 字节；text 存 36 字符至少 36 字节 + 变长头，索引也跟着膨胀。
- **校验**：uuid 输入即做格式合法性检查，text 什么都收。
- **比较**：uuid 按定长二进制比较，比字符串逐字符 collation 比较更快。
- **语义**：函数、隐式转换、类型安全都围绕 uuid 展开。

结论：只要是 UUID，就**用 uuid 类型存**，不要用 text。

# 输入与输出

UUID 标准写法是一串小写十六进制数字，用连字符分成 8-4-4-4-12 五段，共 32 个十六进制位（128 位）：

```text
a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11
```

PostgreSQL 也接受以下变体输入：

```text
A0EEBC99-9C0B-4EF8-BB6D-6BB9BD380A11     -- 大写
{a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11}   -- 花括号
a0eebc999c0b4ef8bb6d6bb9bd380a11         -- 省略连字符
a0ee-bc99-9c0b-4ef8-bb6d-6bb9-bd38-0a11  -- 每 4 位加连字符
{a0eebc99-9c0b4ef8-bb6d6bb9-bd380a11}    -- 混合格式
```

```sql
SELECT 'A0EEBC99-9C0B-4EF8-BB6D-6BB9BD380A11'::uuid;
```

结果（始终标准化为小写带连字符）：

```text
                uuid
--------------------------------------
 a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11
```

> [!note]
> 输出总是采用标准形式，无论输入用了哪种变体。

# UUID 版本与选择

RFC 9562 定义了多种 UUID 版本，各有生成要求和优缺点：

| 版本    | 生成方式        | 特点                                     | 适用                       |
|---------|-----------------|------------------------------------------|----------------------------|
| UUIDv1  | 时间 + 节点 MAC | 时间有序，但会泄露 MAC、可能重复          | 遗留系统                   |
| UUIDv4  | 完全随机        | 无顺序、碰撞极低、索引写入分散            | 通用主键、token            |
| UUIDv7  | 时间戳 + 随机   | **时间有序**，对 B-tree 索引友好（PG18+） | 需要全局唯一又要良好写入   |

- PostgreSQL 原生生成支持 **v4**（`gen_random_uuid()`）与 **v7**（`uuidv7()`）。
- uuid 数据类型可存储**任意版本**，即便数据库不帮你生成，也能存应用端产生的值。

# 生成 UUID

生成 UUID 的函数详见 **[UUID函数](../07.PostgreSQL%20内置函数/065.UUID函数.md#概述)**。常用做法：

```sql
-- 随机 UUIDv4（PG13+ 内置，无需扩展）
SELECT gen_random_uuid();

-- 时间有序 UUIDv7（PG18+）
SELECT uuidv7();

-- 作为列默认值
CREATE TABLE accounts (
    id      uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    name    text
);

INSERT INTO accounts (name) VALUES ('alice') RETURNING id;
```

> [!tip]
> 在 PG13 之前，`gen_random_uuid()` 需要 `pgcrypto` 扩展；PG13 起已内置，直接用即可。老项目升级时可留意这一点。

# 实战 SQL

```sql
-- 建表：uuid 主键 + 默认生成
CREATE TABLE devices (
    id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    label       text,
    created_at  timestamptz DEFAULT now()
);

-- 插入并回取生成的 id
INSERT INTO devices (label) VALUES ('sensor-01') RETURNING id;

-- 按 uuid 精确查询（走主键索引）
SELECT * FROM devices WHERE id = 'a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11';

-- 与其他表关联
SELECT d.label, r.value
FROM devices d
JOIN readings r ON r.device_id = d.id;

-- 从 text 安全转换（非法值会报错，可用于校验）
SELECT 'a0eebc99-9c0b-4ef8-bb6d-6bb9bd380a11'::text::uuid;

-- 提取 UUID 的版本位（第 13 个十六进制位）
SELECT substring(id::text from 15 for 1) AS version_bit FROM devices LIMIT 5;
```

# 最佳实践

1. **一定用 uuid 类型存**，不要用 char(36)/varchar。
2. **需要时间有序 + 索引友好**（PG18+）优先选 `uuidv7()`，缓解随机 v4 的索引写放大。
3. **单库、纯自增场景别盲目上 UUID**：BIGINT IDENTITY 在索引紧凑性、范围扫描、复制上仍有优势。
4. **分布式/多写/离线生成/对外开放 ID**（不希望暴露总量）时，UUID 很合适。
5. **给 uuid 主键配好填充因子**：随机 v4 会导致 B-tree 页频繁分裂，可适当降低 fillfactor 或改用 v7。
6. **应用端也能生成**：把字符串以标准/变体格式传入即可，PostgreSQL 会规范化。
7. **对外接口输出用标准小写形式**，避免大小写不一致引发比对问题。

# 常见坑

1. uuid 只存“值”，**不保证你用的是哪个版本**，也不校验唯一性由谁保证。
2. 把 UUID 存成 text 会**白白多占一倍以上空间**，索引也随之膨胀、比较更慢。
3. 随机 UUIDv4 做主键会造成 **B-tree 索引写入分散、页分裂多**，海量写入下明显。
4. `gen_random_uuid()` 在 **PG13 前需 pgcrypto 扩展**，直接调用会报函数不存在。
5. 输入变体很宽松，但**输出永远标准小写**，别指望保留你输入的大写或花括号。
6. UUID **不天然可比大小有意义**：v4 是随机值，`ORDER BY uuid` 只是按二进制排，没有业务顺序。
7. 128 位 ID 作为**外键**会放大所有关联表和索引的存储成本，需权衡。
8. 别把 UUID 当“安全随机数/密钥”用——它的设计目标是唯一性，不是密码学随机性。
9. 想在旧版本用 v7 需借助第三方扩展或应用端生成，PostgreSQL 原生 `uuidv7()` 是 PG18 才有。

# 总结

- uuid 是 128 位、16 字节的定长类型，**存 UUID 就用它**，别用 text。
- PostgreSQL 原生支持生成 v4（`gen_random_uuid()`）和 v7（`uuidv7()`，PG18+），也可存任意版本。
- 需要全局唯一、分布式/离线生成、对外不暴露规模时用 UUID；纯单库高吞吐主键仍应权衡 BIGINT。
- 担心随机 v4 的索引写放大，就上时间有序的 v7。
