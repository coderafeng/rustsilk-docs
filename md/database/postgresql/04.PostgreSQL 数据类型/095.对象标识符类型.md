# 概述

- PostgreSQL 内部用 **OID（Object Identifier，对象标识符）** 唯一标记系统目录里的每一个对象（表、类型、函数、操作符、排序规则等）。
- **oid** 类型就是那个 4 字节无符号整数；围绕它还有一族 **reg\* “引用类型”**（regclass、regproc、regtype 等），存的是 OID，但**输入输出时自动与对象名互转**，对人更友好。
- 核心价值：在 SQL 里“用名字引用一个数据库对象”，并让 catalog 之间能高效地按整数关联。
- **不要把它们当业务主键**：OID 会被回收重用（32 位会绕回），系统表之间的 OID 也不跨库唯一。
- 日常最常用：`'my_table'::regclass`、`pg_typeof(x)`（返回 regtype）、查 `pg_class.oid`、`indrelid` 等系统列。

# 类型速查表

| 类型           | 引用对象            | 输入接受          | 输出显示            |
|----------------|---------------------|-------------------|---------------------|
| oid            | 任意对象（裸整数）  | 整数              | 整数                |
| regclass       | 表/视图/索引/序列等 | 名或 OID          | 表名（自动加 schema）|
| regproc        | 函数（无重载区分）  | 名或 OID          | 函数名              |
| regprocedure   | 函数（带签名）      | `name(args)`      | `name(args)`        |
| regoper        | 操作符（无重载）    | 名或 OID          | 操作符名            |
| regoperator    | 操作符（带参数类型）| `name(types)`     | 带类型              |
| regtype        | 数据类型            | 名或 OID          | 类型名              |
| regcollation   | 排序规则            | 名或 OID          | 排序名              |
| regconfig      | 文本搜索配置        | 名或 OID          | 配置名              |
| regdictionary  | 文本搜索词典        | 名或 OID          | 词典名              |

> [!note]
> 从 PostgreSQL 2.6 起 **oid 是无符号整数**，比较时按无符号规则；早期版本的“有符号 oid、负数”行为已不存在。系统表里保留的“系统 OID 常量”（如 `pg_class` 的固定 OID）自 12.0 起大部分已被移除，别再依赖硬编码 OID 值。

# oid 类型

`oid` 只是一个 4 字节无符号整数，本身没有跨库含义：

```sql
SELECT oid, relname FROM pg_class WHERE relname = 'my_table';
```

- 输出就是纯数字。它不像 reg\* 类型会翻译成对象名。
- **会被重用**：对象删除后其 OID 将来可能被分配给新对象；32 位空间用尽后也会绕回（wraparound）。
- 因此 oid 适合当“同一数据库、同一时刻”的 catalog 关联键，**不适合存进业务表当长期外键**。

# reg* 引用类型：用名字引用对象

reg\* 类型内部存 OID，但**输入可用对象名、输出显示对象名**，解析依赖 `search_path`。最常用的是 **regclass**：

```sql
-- 用名字拿到表 OID，再喂给系统函数
SELECT reltuples::bigint AS est_rows
FROM pg_class
WHERE oid = 'my_table'::regclass;

-- 输出自动显示为（带 schema 限定的）表名
SELECT 'my_table'::regclass;
-- public.my_table
```

regtype 用于引用类型：

```sql
SELECT pg_typeof(1);            -- integer (regtype)
SELECT 'timestamptz'::regtype;  -- timestamp with time zone
```

regprocedure 能区分重载函数（需带签名），regproc 不能：

```sql
SELECT 'abs(numeric)'::regprocedure;   -- 指定重载
SELECT 'abs'::regproc;                  -- 无歧义时可用，重载多会报错
```

# 输入与输出规则

- **输入**：可以是对象名（按 `search_path` 解析）、也可以是 OID 数字；对带签名的 regprocedure/regoperator，需 `name(type, type)` 形式。
- **输出**：显示对象名；regclass 只在**不在当前 search_path 可见**时才带 schema 前缀（“最短可解析名”）。
- **对象不存在 → 报错**（reg\* 类型会去 catalog 解析，找不到就 `relation "xxx" does not exist`）。这点和裸 oid 不同——裸 oid 不校验存在性。

> [!warning]
> `'不存在的东西'::regclass` 会**直接报错**，不会返回 NULL。写动态 SQL/工具类查询时，要么先判断存在，要么捕获异常。这也是很多人把用户输入直接 `::regclass` 时踩到的坑。

# 排序与比较

- reg\* 类型底层是 OID，**排序按 OID 数值**，不是按名字字母序。
- 等值比较：`'a'::regclass = 'public.a'::regclass` → **true**（都指向同一对象），即使文本不同。
- 想按名字排序需 `::text` 后再排：`ORDER BY col::text`。

# 与 name / text 的关系

- **name** 类型：系统目录里存对象名用的定长（63 字节 + 结尾）字符串，会自动截断超长名，大小写按标识符规则处理。日常业务表更推荐 `text`。
- **text/varchar**：普通字符串，不校验对象是否存在。
- regclass 之类是“**指向真实对象的引用**”，name/text 只是“**名字字符串**”——只有前者能表达“这就是那张表”。

# 实战 SQL

```sql
-- 1) 查某表的估计行数（用 regclass 定位）
SELECT relname, reltuples::bigint
FROM pg_class
WHERE oid = 'orders'::regclass;

-- 2) 动态取表的列信息（regclass 当函数参数）
SELECT attnum, attname, format_type(atttypid, atttypmod) AS type
FROM pg_attribute
WHERE attrelid = 'orders'::regclass
  AND attnum > 0 AND NOT attisdropped;

-- 3) 判断对象是否存在，避免 ::regclass 报错
SELECT to_regclass('orders') IS NOT NULL AS table_exists;
SELECT to_regclass('no_such') IS NOT NULL;  -- false，且不报错

-- 4) 看某表达式/列的类型（regtype）
SELECT pg_typeof(now()) AS t;   -- timestamp with time zone

-- 5) 索引关联到表（都按 OID）
SELECT i.indexrelid::regclass AS index,
       i.indrelid::regclass   AS table
FROM pg_index i
WHERE i.indrelid = 'orders'::regclass;
```

> [!tip]
> 需要“存在才解析、不存在返回 NULL”时，用函数 **`to_regclass()` / `to_regtype()` / `to_regproc()`** 等，而不是 `::regclass` 硬转——后者遇到不存在对象会报错。

# 最佳实践

1. **工具/运维类 SQL 用 regclass/regtype 引用对象**，比手写 OID 可读、可移植。
2. **对可能不存在的对象用 `to_regclass()` 探测**，别用 `::regclass`（会抛错）。
3. **不要把这些 OID 存进业务表当长期外键**——会被重用、跨库不唯一。
4. **需要按对象名排序时先 `::text`**，别默认 OID 序就是名字序。
5. **别硬编码系统对象的 OID 值**（新版本很多固定 OID 已移除/变动），用名字解析。
6. 展示给用户看用 regclass 的“名”输出；程序内部关联用裸 OID 更快。
7. 处理用户可控的对象名时注意 **SQL 注入与 schema 污染**：`'x'::regclass` 会按 search_path 解析，必要时显式带 schema。

# 常见坑

1. **OID 会绕回重用**：32 位无符号整数，长期看不保证“全历史唯一”，别当永久键。
2. **OID 不跨数据库唯一**：同一张表在两个库里 OID 可能不同，dump/restore 后也可能变。
3. **`'missing'::regclass` 直接报错**，不返回 NULL——探测存在性要用 `to_regclass()`。
4. **reg\* 排序按 OID 不按名字**，`ORDER BY regclass_col` 出来的顺序可能反直觉。
5. **输出会自动加/去 schema 前缀**（最短可解析名），跨 schema 环境别依赖固定文本形式。
6. **regproc 无法区分重载函数**，多个同名函数会报错，需用 regprocedure 带签名。
7. **裸 oid 不校验对象存在**，写错数字不会报错，容易埋雷。
8. **name 类型会静默截断超长标识符**（63 字节），别拿 name 存任意长字符串。
9. 老教程里的“系统表固定 OID 常量”在新版本大多已不可依赖，别照抄。
10. 把 regclass 结果直接当文本比较（`='my_table'`）可能因 schema 限定不同而误判，比较前先归一。

# 总结

- oid 是 4 字节无符号整数对象标识；regclass/regtype/regprocedure 等 reg\* 类型在其上做“名字 ⇄ OID”的自动解析，便于用名字引用数据库对象。
- 主要用于系统目录查询和运维工具 SQL：**存在性探测用 `to_reg*()`，排序按 OID，别存进业务表当长期键**。
- 记住 OID 会重用、不跨库唯一，且 `::regclass` 遇不存在对象会报错——这三点覆盖了绝大多数坑。
