# 概述

- **域类型（domain）** 基于一个已有的数据类型，附加一组**约束**（NOT NULL、CHECK、默认值等），形成一个“带规则的别名类型”。
- 目的：把“邮箱格式、价格必须 > 0、州代码必须在白名单里”这类**跨列复用的约束与语义**集中定义一次，多列引用，避免到处写 CHECK。
- 语法：`CREATE DOMAIN ... AS <base_type> CHECK (...) DEFAULT ...`。
- 域**在赋值时强制约束**，但有几个重要盲点（`ALTER TABLE`、外部键、跨域不通用），下文“限制”里详解。
- 与 `CHECK` 约束的取舍：约束只在一两列用 → 直接写 CHECK；多列/多表复用同一业务规则 → 用 domain。

# 速查表

| 操作             | 写法                                                       |
|------------------|------------------------------------------------------------|
| 定义域           | `CREATE DOMAIN email AS text CHECK (VALUE ~ '@');`         |
| 带默认值         | `CREATE DOMAIN pct AS int DEFAULT 0 CHECK (VALUE <= 100);` |
| 基于另一个域     | `CREATE DOMAIN work_email AS email CHECK (VALUE LIKE '%@x.com');` |
| 使用             | `CREATE TABLE t (e email);`                                |
| 改约束           | `ALTER DOMAIN d ADD CONSTRAINT c CHECK (...);`             |
| 改所有列的默认值 | `ALTER DOMAIN d SET DEFAULT ...;`                          |
| 删除域           | `DROP DOMAIN d;`                                           |

# 创建域

`CREATE DOMAIN` 指定基础类型和一组约束：

```sql
CREATE DOMAIN us_postal_code AS text
CHECK (
    VALUE ~ '^\d{5}$'
    OR VALUE ~ '^\d{5}-\d{4}$'
);

CREATE TABLE sniffs (us_zip us_postal_code);
-- 合法
INSERT INTO sniffs VALUES ('85719');
-- 报错：violates check constraint
INSERT INTO sniffs VALUES ('abcdef');
```

`VALUE` 是被赋的值；域里还能引用列级约束、`NOT NULL`、`DEFAULT`。

```sql
CREATE DOMAIN positive_amount AS numeric
    CHECK (VALUE > 0)
    DEFAULT 100;   -- 列没写默认值时会带出域默认
```

# 基于其他域

域可以**建立在另一个域之上**，进一步收紧约束（继承父域规则并叠加）：

```sql
CREATE DOMAIN email AS text CHECK (VALUE ~ '^\S+@\S+$');
CREATE DOMAIN work_email AS email CHECK (VALUE ~ '@corp\.com$');
-- 'a@b.com' 是合法 email，但不是合法 work_email
```

也可以**放宽**默认值（子域重新设 DEFAULT）。但注意：**不能移除 NOT NULL 或父域 CHECK**——域层次只能收紧不能放松约束。

# 使用域

任何需要类型的地方都能用域，包括列、函数参数/返回、变量：

```sql
CREATE TABLE users (
    id    bigserial PRIMARY KEY,
    email email NOT NULL,
    level pct
);

CREATE FUNCTION send_mail(to_addr email, subject text) ...
```

**域在赋值时执行约束**。这意味着：

- `INSERT`、`UPDATE`、`COPY`、以及 `SELECT` 里显式转成域类型的表达式，都会触发校验。
- 查询取回时，如果列类型是 domain，结果会带 domain 的类型标签，客户端可按域处理。

# 修改和删除域

```sql
ALTER DOMAIN email ADD CONSTRAINT must_be_short CHECK (length(VALUE) < 100);
ALTER DOMAIN email DROP CONSTRAINT must_be_short;
ALTER DOMAIN email SET NOT NULL;
ALTER DOMAIN email SET DEFAULT 'nobody@example.com';
```

**注意**：`ALTER DOMAIN ADD CONSTRAINT` / `SET NOT NULL` 默认会**校验所有已存在数据**，有违反的行会失败。加 `NOT VALID` 可先跳过存量，只对新数据生效，之后再 `VALIDATE CONSTRAINT`。

`DROP DOMAIN` 只在没有列/函数依赖它时才能删；有依赖需 `CASCADE`，会连带影响引用对象，谨慎。

# 限制与常见坑

域用起来很优雅，但有几个**必须知道**的坑：

1. **`ALTER TABLE ... SET DATA TYPE` 到某个 domain 时，可能不校验现有数据。**
   PostgreSQL 会做类型转换，但**不会像 INSERT 那样**逐行触发 CHECK（只跑必要转换）。因此存量数据可能“绕过”新域约束。
2. **域上的 `CHECK` 约束不能引用其他列。** 域是标量级约束，只能用 `VALUE`；跨列规则还得靠表级 CHECK。
3. **域上的约束在 `CREATE TABLE LIKE`、部分 `ALTER TABLE` 场景可能被跳过。** 需要显式 `VALIDATE CONSTRAINT` 兜底。
4. **外键不能引用 domain 列**：PostgreSQL 目前不允许把外键指向域类型列（因为域的等值/比较语义有歧义）。需要引用完整性时用基础类型。
5. **不同 domain 之间不通用**：即使底层同为 `text`，`email` 和 `url` 两个域在函数重载、隐式转换上是**不同类型**，不能直接混用。
6. **`ALTER TABLE` 修改列到已有 domain 时，可能不重新校验已有行**（见 1）；上线前手动跑一次 `VALIDATE CONSTRAINT` 或直接 UPDATE 一遍。
7. 域**没有“标识列 / serial”**这种列级默认值语义；域上的 DEFAULT 是值级默认，行为略有差异。
8. **PL/pgSQL 里的变量类型可用 domain**，但 `STRICT` 等函数选项对 domain 处理可能有细微差异，测试环境验证。
9. **删除/收紧域可能连带影响依赖对象**（列、函数），`DROP` / `ALTER` 前用 `\d` 或查 pg_depend 看引用。
10. 域对**性能几乎无影响**（约束本质仍是 CHECK），但会让查询计划器对统计信息的估计略粗（当成基础类型看）。

# 实战 SQL

```sql
-- 1) 定义业务规则集中管理
CREATE DOMAIN us_phone AS text
    CHECK (VALUE ~ '^\+?1?[-. (]*\d{3}[-. )]*\d{3}[-. ]*\d{4}$');

CREATE DOMAIN non_empty_text AS text
    CHECK (VALUE <> '' AND VALUE IS NOT NULL);

-- 2) 多列复用
CREATE TABLE contacts (
    id       bigserial PRIMARY KEY,
    name     non_empty_text,
    phone    us_phone,
    fax      us_phone
);

-- 3) 上线前对存量数据补校验（避免 ALTER 时的盲点）
ALTER DOMAIN us_phone ADD CONSTRAINT must_area_code
    CHECK (VALUE ~ '^\+1[2-9]') NOT VALID;
-- 之后想真正生效：
ALTER DOMAIN us_phone VALIDATE CONSTRAINT must_area_code;

-- 4) 收紧或删除
ALTER DOMAIN us_phone DROP CONSTRAINT must_area_code;
DROP DOMAIN us_phone;   -- 没有依赖才能删
```

# 最佳实践

1. **有跨列复用的“值级”业务规则时**（邮箱、电话、州代码、金额下限）用 domain，集中一处定义。
2. **给域起符合业务语义的名字**（`us_phone` 而非 `phone_domain`），列声明即文档。
3. **收紧用 `NOT VALID` + `VALIDATE CONSTRAINT` 分两步**，避免 `ALTER DOMAIN` 在生产上锁很久。
4. **表级/跨列约束仍用 CHECK**，域只解决“单值合法性”。
5. **别把域当外键目标**——需要被引用完整性的字段直接用基础类型。
6. **域变更后跑一次 `VALIDATE CONSTRAINT` 或全表 UPDATE**，把可能漏检的存量数据补上。
7. **不同子系统避免共用同一个域**：域收紧/放宽会影响所有引用方，跨模块建议各定义各的。

# 总结

- domain 是“带约束、带默认值的类型别名”，让“值级业务规则”一处定义、多处复用。
- 强约束在赋值时生效，但对 `ALTER TABLE`、外键、跨域、存量数据校验有盲点——上线要显式 `VALIDATE`。
- 单值合法性用 domain，跨列规则用 CHECK，需要被引用完整性时不要用它当外键目标。
