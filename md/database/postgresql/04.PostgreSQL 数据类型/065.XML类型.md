# 概述

- **xml** 类型用于存储 XML 数据。相比用 text 存，它的优势是会**校验输入良构性**，并提供一批类型安全的 **[支持函数](../07.PostgreSQL%20内置函数/070.XML函数.md#概述)**。
- 使用前要求 PostgreSQL 编译时启用了 libxml（`configure --with-libxml`）；官方发行包一般都带。
- 既能存完整 **DOCUMENT**，也能存多根/多顶层文本节点的 **CONTENT** 片段。
- **不提供任何比较操作符**：无法直接对 xml 列做 `=` 或建普通索引，这是使用 XML 类型最大的落地障碍。
- 只校验“良构（well-formed）”，**不基于 DTD / XML Schema 做验证**。
- 现实经验：除非是 SOAP、公文、遗留集成等强制 XML 的场景，**新项目的半结构化数据一般优先选 JSON/JSONB**，XML 生态在 PostgreSQL 里相对冷门。

# 类型速查表

| 维度       | 说明                                                       |
|------------|------------------------------------------------------------|
| 存储内容   | 良构 XML 的文本（DOCUMENT 或 CONTENT）                     |
| 校验       | 仅检查良构性，不按 DTD/Schema 验证                         |
| 比较操作符 | 无，不能直接 `=` / `<` / 排序                              |
| 直接建索引 | 不支持（无可索引的比较操作符），需用表达式索引绕过         |
| 关键函数   | `xmlparse`、`xmlserialize`、`xmlexists`、`xpath`、`xmltable`|
| 编码建议   | 服务器编码用 UTF-8 时最高效、最不容易出错                  |

# DOCUMENT 与 CONTENT

xml 类型即可存储 XML 标准定义的良构“文档（DOCUMENT）”，也可存储“内容片段（CONTENT）”。后者参照 XQuery/XPath 数据模型中更宽松的“文档节点”概念，粗略说就是**可以有多个顶层元素或字符节点**。

用 `IS DOCUMENT` 判断某个值是完整文档还是内容片段：

```sql
SELECT '<a/><b/>'::xml IS DOCUMENT;   -- false（多根，属于 CONTENT）
SELECT '<a><b/></a>'::xml IS DOCUMENT; -- true
```

# 创建 XML 值

从字符数据生成 xml 值，按 SQL 标准用函数 `xmlparse`：

```sql
XMLPARSE ( { DOCUMENT | CONTENT } value )
```

示例：

```sql
XMLPARSE (DOCUMENT '<?xml version="1.0"?><book><title>Manual</title><chapter>...</chapter></book>')
XMLPARSE (CONTENT 'abc<foo>bar</foo><bar>foo</bar>')
```

按 SQL 标准，这是把字符串转成 XML 值的**唯一**方法；但 PostgreSQL 特有下面两种写法也可用：

```sql
xml '<foo>bar</foo>'
'<foo>bar</foo>'::xml
```

即使输入值指定了 DTD，xml 类型**也不会依据 DTD 验证**输入，目前也没有内置支持按 XML Schema 等其他模式语言验证。

反向操作，从 xml 生成字符串，用 `xmlserialize`：

```sql
XMLSERIALIZE ( { DOCUMENT | CONTENT } value AS type [ [ NO ] INDENT ] )
```

- `type` 可以是 `character`、`character varying` 或 `text`（及别名）。
- `INDENT` 让结果美化缩进输出；`NO INDENT`（默认）只输出原始字符串。
- 直接 `::text` 转换得到的也是原始字符串。

当字符串与 xml 互相转换而未经过 XMLPARSE/XMLSERIALIZE 时，选 DOCUMENT 还是 CONTENT 由会话参数决定：

```sql
SET XML OPTION { DOCUMENT | CONTENT };
-- 或 PostgreSQL 风格
SET xmloption TO { DOCUMENT | CONTENT };
```

默认值是 **CONTENT**，因此允许所有形式的 XML 数据。

# 编码处理

在客户端、服务器及其间传输的 XML 上处理多种字符编码要格外小心：

- **文本模式**（常用）下，PostgreSQL 会把客户端与服务器之间的字符数据转换为目标端编码，表示 xml 的字符串也在其中。这会导致内嵌编码声明失效——因此**输入的编码声明会被忽略**，内容被假定为当前服务器编码。客户端必须在发送前把 XML 转成当前客户端编码；输出时 xml 值不带编码声明，客户端应假定数据采用当前客户端编码。
- **二进制模式**下不执行编码转换，XML 中的编码声明会被识别；缺省声明时假定为 UTF-8（PostgreSQL 不支持 UTF-16）。输出时除非客户端编码是 UTF-8，否则会带上指明客户端编码的声明。

> [!tip]
> 让 **XML 数据编码 = 客户端编码 = 服务器编码**（推荐全 UTF-8）时，处理最高效、最不容易出错，因为 XML 在内部以 UTF-8 处理。

> [!note]
> 当服务器编码不是 UTF-8 时，某些与 XML 相关的函数在非 ASCII 数据上可能完全无法工作，尤其是 `xmltable()` 和 `xpath()`，这是已知问题。

# 访问 XML 值

xml 类型很特殊，因为它**不提供任何比较操作符**（对 XML 不存在良定义且通用的比较算法）。因此：

- 无法通过把 xml 列与搜索值比较来检索行；XML 值通常应伴随一个独立键字段（如 ID）。
- 因为无比较操作符，**不能直接在 xml 列上建索引**。需要快速搜索时可行方案：把某个表达式转成字符串再建**表达式索引**，或针对某个 XPath 表达式建索引；实际查询也必须使用同一个被索引表达式。
- 也可借助 PostgreSQL 的全文检索加速 XML 的文本搜索，但当前发行版仍缺少所需预处理支持。

比较 XML 的一种兜底办法是先转成字符串再比，但字符串比较对 XML 语义（空白、属性顺序等）通常帮助不大。

# 常用函数

| 函数                          | 作用                                        |
|-------------------------------|---------------------------------------------|
| `xmlparse(DOCUMENT\|CONTENT)` | 字符串 → xml（标准）                        |
| `xmlserialize(... AS type)`   | xml → 字符串，可 INDENT 美化                |
| `xmlexists(xpath XML)`        | 判断 XPath 是否匹配到内容，返回 boolean     |
| `xpath(expr, target)`         | 按 XPath 1.0 提取，返回 xml 数组            |
| `xpath_exists(expr, target)`  | XPath 存在性判断                            |
| `xmltable(...)`               | 把 XML 拆成行列，像表一样 SELECT（最实用）  |
| `extract / xpath`             | 旧式取值函数（部分已 deprecated）           |
| `text(xml)`                   | 转为原始字符串                              |

更多细节参见 **[XML函数](../07.PostgreSQL%20内置函数/070.XML函数.md#概述)**。

# 实战 SQL

```sql
-- 建表：用 xml 存一份订单报文
CREATE TABLE orders (
    id     serial PRIMARY KEY,
    doc    xml
);

INSERT INTO orders (doc) VALUES (
$$<order id="1001">
  <customer>Alice</customer>
  <item sku="A-1" qty="2"/>
  <item sku="B-7" qty="1"/>
</order>$$
);

-- 用 xmltable 把 XML 拆成关系行（最常用的读法）
SELECT x.item_sku, x.item_qty
FROM orders o,
XMLTABLE('/order/item'
    PASSING o.doc
    COLUMNS
        item_sku text PATH '@sku',
        item_qty int  PATH '@qty'
) AS x;

-- 存在性判断：是否含 customer 节点
SELECT id FROM orders
WHERE xmlexists('/order/customer' PASSING doc);

-- 用 XPath 取值
SELECT xpath('/order/customer/text()', doc) FROM orders WHERE id = 1;

-- 表达式索引加速“按客户名查”
CREATE INDEX idx_orders_customer ON orders
    ((xpath('/order/customer/text()', doc)[1]::text));
```

# 最佳实践

1. **新项目半结构化数据优先 JSONB**，除非协议/遗留集成强制 XML。
2. **读 XML 首选 `xmltable()`**，把层级报文摊平成行列，比反复 `xpath()` 更清晰高效。
3. **给需要检索的路径建表达式索引**，并把查询写成命中同一表达式，绕开“xml 不能直接索引”。
4. **统一 UTF-8**（数据、客户端、服务器三端一致），避免非 ASCII 函数失效。
5. **xml 列旁配一个业务主键（ID）**，检索、更新、关联都用键，不依赖 XML 内容比较。
6. **写入前确认良构**：非法 XML 会被 xml 类型直接拒绝，导入大文件时先小样验证。
7. **显式用 XMLPARSE/XMLSERIALIZE 控制 DOCUMENT/CONTENT 与缩进**，别依赖会话默认。

# 常见坑

1. xml 类型**没有比较操作符**，`WHERE doc = '...'`、`ORDER BY doc` 都用不了。
2. **不能直接在 xml 列建索引**，只能用表达式索引变通。
3. 只校验**良构性**，不会按 DTD/XML Schema 验证，别指望它做模式校验。
4. 需要 `--with-libxml` 编译，精简版镜像/源码编译若没启用则无法使用 xml 类型。
5. **服务器编码非 UTF-8 时，`xpath()`/`xmltable()` 对非 ASCII 数据可能直接罢工**。
6. 文本模式下输入的编码声明会被忽略，按当前服务器编码处理，容易乱码。
7. 默认 `xmloption` 是 CONTENT，切到 DOCUMENT 后多根片段会报错。
8. `::text` 得到的是原始串，要美化输出得用 `XMLSERIALIZE(... INDENT)`。
9. 部分老函数（如 `extract()`）已 deprecated，迁移时注意替换为 `xpath()`。

# 总结

- xml 类型能校验良构性并提供类型安全的 XML 函数，但**无比较操作符、不能直接索引**，用起来限制多。
- 读报文首选 `xmltable()`，检索靠表达式索引 + 业务主键，编码尽量全链路 UTF-8。
- 除非协议或遗留系统强制，**半结构化数据优先考虑 JSONB**，XML 在 PostgreSQL 中属于相对冷门路线。
