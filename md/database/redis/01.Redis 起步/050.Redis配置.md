# 概述

`redis.conf` 是 Redis 的行为总开关：网络绑定、内存上限与淘汰、持久化、安全、客户端与可观测参数分组管理；改错一组参数，代价从"连不上"到"丢数据"不等。

- 官方文档：<https://redis.io/docs/latest/operate/oss_and_stack/management/config/>
- 完整模板：源码包内 `redis.conf`（逐参数注释），或 `CONFIG GET '*'` 导出当前实例全量参数

# 参数分组速查

**网络与进程**

| 参数 | 默认 | 说明 |
|------|------|------|
| `bind` | `127.0.0.1 -::1` | 监听地址；对外服务改 `0.0.0.0` 必须同时上防火墙/安全组 |
| `protected-mode` | `yes` | 未显式设置 `bind` 且无密码时，拒绝非回环地址连接；**不要用关它来解决连接问题** |
| `port` | `6379` | 服务端口 |
| `daemonize` | `no` | 容器/系统服务场景保持 `no`，交给 supervisor 托管 |
| `logfile` | 空（stdout） | systemd 部署走 journald，不必设置 |
| `dir` | `./` | RDB/AOF 落盘目录，所有持久化路径的锚点 |
| `databases` | `16` | db 数量（Cluster 模式强制 16 且不可改） |

**内存与淘汰**

| 参数 | 默认 | 说明 |
|------|------|------|
| `maxmemory` | `0`（不限） | 到达上限触发淘汰；**容器/虚机部署必须设置**（呼应 [040.Docker运行Redis](./040.Docker运行Redis.md)） |
| `maxmemory-policy` | `noeviction` | 淘汰策略：`noeviction`/`allkeys-lru`/`allkeys-lfu`/`allkeys-random`/`volatile-lru`/`volatile-lfu`/`volatile-random`/`volatile-ttl` |

缓存实例常用 `allkeys-lru`；只有"带 TTL 的键才可淘汰"的语义才选 `volatile-*` 系；`allkeys-lfu` 适合访问热度分布悬殊的缓存。

**持久化**

| 参数 | 默认 | 说明 |
|------|------|------|
| `save` | `3600 1 300 100 60 10000` | RDB 快照触发条件（秒 变化数），多档空格分隔；设空串关闭 |
| `appendonly` | `no` | AOF 开关；**6.2+ 默认混合持久化**（AOF 重写后基座为 RDB 格式） |
| `appendfsync` | `everysec` | `always`（最安全最慢）/`everysec`（默认折中）/`no`（OS 决定） |

**安全**

| 参数 | 说明 |
|------|------|
| `requirepass` | 全局密码（仅兼容旧客户端；`""` 关闭） |
| `aclfile` | ACL 规则文件路径；6.0+ 按用户/密码/命令/键模式授权 |
| `acllog-max-len` | ACL 拒绝事件环形日志长度 |

**客户端与复制/集群（起步阶段先知道存在）**：`timeout`（空闲客户端断开，0 为不断开）、`tcp-keepalive`（默认 300s）、`maxclients`（默认 10000）、`client-output-buffer-limit`（复制/发布订阅缓冲上限）、`replicaof`、`cluster-enabled`。

**可观测**：`slowlog-log-slower-than`（微秒，默认 10000）、`latency-monitor-threshold`（默认 0 关闭）、`notify-keyspace-events`（默认 `""` 关闭）。

# 操作步骤（CONFIG 命令与持久化变更）

```bash
redis-cli CONFIG GET maxmemory-policy
redis-cli CONFIG SET maxmemory allkeys-lru      # 运行时生效，重启丢失
redis-cli CONFIG REWRITE                         # 把运行时差异写回 conf 文件（需可写权限）
redis-cli CONFIG RESETSTAT                       # 清零 INFO 统计
```

修改 `redis.conf` 后重启生效的参数（如 `bind`、`appendonly`）无法 `CONFIG SET`；以 `CONFIG GET` 能否命中判断一个参数是否动态。

# 验证

```bash
redis-cli CONFIG GET save
redis-cli INFO persistence | grep -E 'aof_enabled|rdb_last_save_time'
redis-cli CLIENT INFO | head -1        # 当前连接视角确认超时/缓冲参数已应用
```

# 避坑

- **`CONFIG SET` 不落盘**：运行时改动重启即失，运维习惯应是"改 conf → `CONFIG REWRITE` 对齐 → 验证"，或只改 conf 后重启，两条路别混。
- **`save ""` + `appendonly no` = 纯易失存储**：缓存可以这么配，任何"数据不能丢"的库不可以——先明确实例角色再动持久化参数。
- **`maxmemory 0` 在容器里最危险**：看似"不限制很灵活"，实际把淘汰权交给了内核 OOM-Killer；上限永远要显式设置。
- **`timeout` 与连接池心跳**：设置了空闲超时而客户端池没有心跳/保活，会出现"连接莫名被服务端掐断"；两边要么都设，要么都不设。
- **多实例不同 conf 的 `dir` 撞车**：一台机器跑多实例时，`dir` 不隔离会导致 RDB/AOF 互相覆盖——目录规划从 `dir` 开始。

# 总结

配置管理的核心是"角色决定参数"：缓存实例看 `maxmemory-policy`，持久化实例看 `appendonly/appendfsync/save`，对外实例看 `bind/protected-mode/ACL`。运行时调参用 `CONFIG SET`，**固化用 `CONFIG REWRITE`**，并让配置文件本身成为唯一真相源（容器场景挂载进镜像路径）。参数分组记牢，后面 [08.工程化](../08.工程化/000.工程化概述.md) 的持久化、高可用篇章会逐组展开。
