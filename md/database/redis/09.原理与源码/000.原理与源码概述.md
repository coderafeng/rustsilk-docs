# 概述

本章从**原理视角**解释 Redis 为什么快、内存怎么管、命令怎么被调度——把散落在各章的机制串成一条"数据在内存里如何被组织与流转"的主线。纯源码逐行剖析不在本笔记范围，聚焦"理解行为背后的设计"。

- 归属与可用性：Redis 开源核心机制（各特性版本以标注为准）
- 官方文档：<https://redis.io/docs/latest/develop/>（内部机制散见于各专题与 `redis.io/topics/*`）

> [!note] 章节定位
> [08.工程化](../08.工程化/000.工程化概述.md) 讲"怎么配、怎么用、怎么避坑"（工程视角）；本章讲"为什么会这样"（原理视角）。同一主题（如持久化、复制）在两章各有一个入口，本章只补机制与权衡。

# 单线程与事件循环

**为什么单线程还这么快**

- 命令执行是**单线程串行**：省去了锁与上下文切换开销，简单命令在内存上执行本就是纳秒级，瓶颈通常在**网络 IO 与内存**，而非 CPU。
- 代价是**任何慢命令都会阻塞全局**——`KEYS`、大 key 的 `DEL`、重脚本都会让后面的请求排队（这就是各章反复强调"禁用 KEYS、用 UNLINK、脚本要短"的根因，呼应 [070.大key与热key](../08.工程化/070.大key与热key.md)）。

**事件循环（ae 事件驱动库）**

- Redis 自研轻量事件循环封装 `epoll`/`kqueue`/`select`，用**文件事件**（客户端读写）+ **时间事件**（`serverCron`：过期清理、统计、复制心跳等）驱动。
- 6.0 起引入**多线程 IO**：网络数据的读取/写回交给 IO 线程池，**命令执行仍是单线程**——既提吞吐又不破坏原子性，无需给命令加锁。

# 底层编码（内存表示）

同一类型按规模在"紧凑线性结构"与"通用哈希/树结构"间自动切换，小对象省内存、大对象保性能。`OBJECT ENCODING key` 可随时查看当前编码（以下阈值参数与 [02 章](../02.Redis%20数据类型和命令/000.数据类型概述.md) 各类型篇一致）：

| 类型 | 小数据量编码 | 超阈值后编码 | 关键阈值参数 |
|------|-------------|-------------|-------------|
| String | `int` / `embstr`（≤44 字节） | `raw` | 长度 44 为界 |
| Hash | `listpack` | `hashtable` | `hash-max-listpack-entries`(128)、`-value`(64) |
| List | `quicklist`（listpack 节点串成的双向链表） | 同左（可 `list-compress-depth` 压缩中间节点） | `list-max-listpack-size` |
| Set | `intset`（纯整数）/ `listpack` | `hashtable` | `set-max-intset-entries`(512)、`set-max-listpack-entries`(128) |
| Sorted Set | `listpack` | `skiplist` + `hashtable`（双结构） | `zset-max-listpack-entries`、`-value` |

**要点**

- **SDS（简单动态字符串）** 是所有字符串的底座：O(1) 取长度、预分配减少重分配、二进制安全。
- **listpack 于 7.0 取代 ziplist**：消除"连锁更新"最坏情况，且不再依赖相邻节点长度字段。
- **编码转换通常不可逆**：转成 hashtable/skiplist 后即使删回小规模也不会自动降级（重建键才行），压测要按线上真实规模建模。
- **跳表而非红黑树**：ZSet 用 skiplist 实现范围查询，实现简单、并发无关（单线程无所谓锁）、区间查找友好。

# 内存管理

**过期键的删除：惰性 + 定期**

- **惰性删除**：访问 key 时才检查 TTL，过期则删——省 CPU，但过期 key 可能长期占内存。
- **定期删除**：`serverCron` 周期性地随机抽样一批带 TTL 的 key、删除其中过期的，控制两者权衡的参数是 `active-expire-effort`。
- 因此 `TTL`/过期不是精确闹钟（呼应 [080.了解基础命令](../01.Redis%20起步/080.了解基础命令.md)）：主节点删除后通过复制把 `DEL` 传给副本，副本不自行过期以保一致。

**内存达到 maxmemory：淘汰**

- 由 `maxmemory-policy` 决定，8 种策略按"范围(全部/仅带 TTL) × 算法(LRU/LFU/random/ttl)"组合（详见 [050.Redis配置](../01.Redis%20起步/050.Redis配置.md)）。
- **近似 LRU/LFU**：不维护全局链表，而是**随机采样 N 个 key**（`maxmemory-samples`，默认 5）比较其空闲时间/访问频次来淘汰，用少量内存换 O(1)；`lfu-log-factor`/`lfu-decay-time` 控制 16 位计数器的对数饱和与衰减。

**内存碎片与后台回收**

- `activedefrag` 开启活动碎片自动整理；`MEMORY DOCTOR` 给诊断建议，`MEMORY PURGE` 主动尝试把空闲页归还 OS（`MALLOC_TRIM`）。

# 持久化 / 复制 / 分片（原理视角）

- **持久化**：RDB 靠 `fork` + COW 拿一致性快照，AOF 靠追加 + 重写压缩，混合持久化取两者之长。核心矛盾是 **fork 内存放大** 与 **刷盘频率 vs 数据安全**（详见 [010.持久化](../08.工程化/010.持久化RDB与AOF.md)）。
- **复制**：`PSYNC2` 用 `replid + repl-offset + 环形 backlog` 把全量/增量统一到一条协议里，支持复制图（副本再级联）；本质**异步**，故非强一致（详见 [030.主从复制](../08.工程化/030.主从复制.md)）。
- **分片**：Cluster 用 16384 哈希槽 + Gossip 总线做路由与故障检测；16384 而非 65536 是为让心跳包里的槽位图足够小、且经验上单集群节点数上限内够用（详见 [050.Cluster](../08.工程化/050.Cluster集群.md)）。

# RESP 与 pipeline

- **RESP**（REdis Serialization Protocol）：客户端-服务端协议，简单类型（+/-/:/$/*）易解析；RESP3（6.0+）增加 map/double/boolean/大数/push 等，向"服务端主动推送"演进（呼应 [04.发布订阅](../04.发布订阅/000.发布订阅概述.md)）。
- **pipeline 管道**：把多条命令一次性发出、批量收回复，**摊薄网络往返 RTT**；注意 pipeline 只是"打包传输"，命令**仍逐条原子执行**，不保证整组原子——需要原子用事务/Lua（见 [06.可编程性](../06.可编程性/000.可编程性概述.md)）。

# 避坑

- **别用单线程=一定慢 或 一定快 的直觉**：单线程让"简单命令"极快，但也意味着"一个慢命令拖垮全场"——理解这点才明白为什么大 key、`KEYS`、重脚本是生产红线。
- **编码转换不是双向的**：不要指望删空元素后 listpack 自动回来；建模时按峰值规模估算内存。
- **近似 LRU 有偏差**：`maxmemory-samples` 太小会偏离真 LRU（可能淘汰掉其实还热的 key）；调大更准但淘汰开销更高，是精度换 CPU 的取舍。
- **`embstr` 只到 44 字节**：临界值附近频繁在 `embstr`/`raw` 间不同分配策略，短字符串批量写入时留意编码分布（`--memkeys`/`OBJECT ENCODING` 采样）。
- **pipeline 不保证原子、也别无限大**：一条 pipeline 塞太多命令会占满输出缓冲区、放大延迟，且中途出错其余命令仍会执行。
- **定期删除是抽样不是全扫**：极端"大量 key 同一时刻过期"时，定期删除来不及清，惰性删除又没访问到——内存会短时冲高，过期时间要主动打散（呼应 [060.缓存雪崩](../08.工程化/060.缓存穿透击穿雪崩.md)）。

# 总结

Redis 的性能与行为几乎都能回溯到三个设计原点：**① 内存 + 单线程串行执行**（快、无锁，但慢命令即全局灾难）；**② 按规模切换的紧凑编码**（小对象省内存、大对象保 O(logN)/O(1)，代价是转换不可逆）；**③ 近似算法换确定性**（LRU/LFU 采样、定期删除抽样、Geohash 精度上限）。把这三条吃透，各章的"避坑清单"就不再是孤立的规矩，而是同一套原理的必然推论。
