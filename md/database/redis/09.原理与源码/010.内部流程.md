# 概述

[000.原理与源码概述](./000.原理与源码概述.md) 回答了"Redis 单线程为什么还快"，本篇把镜头拉近到**一条命令的完整生命周期**：从客户端把字节写进 socket，到 Redis 把回复刷回 socket，中间经过连接管理、RESP 解析、命令表查找、过期/内存检查、执行、回复缓冲几个阶段。理解这条链路，才能解释"为什么慢命令拖垮全场""为什么 pipeline 不保证原子""为什么阻塞命令不占线程"这些散落在各章的现象。

- 归属与可用性：Redis 开源核心机制（各版本以标注为准）
- 官方文档：<https://redis.io/docs/latest/develop/>（内部机制散见于各专题与 `redis.io/topics/*`）

# 一条命令的完整链路

```text
client ──socket──▶ [读事件] acceptClient / readHandler
                        │
                        ▼
                  输入缓冲区累积字节 ──▶ 解析 RESP 协议 → argv
                        │
                        ▼
                  lookupCommand(命令表) → redisCommand
                        │
             ┌──────────┴───────────┐
     processCommand 前置检查          │  MULTI 排队？→ 入队不执行
   (arity/权限/过期/内存/OOM)         │
                        ▼
                  call() 执行命令 → 写 robj / 读 dict
                        │
                        ▼
                  输出缓冲区累积回复 ──▶ [写事件] beforeSleep 里 sendReplyToClients
                        │
                        ▼
client ◀──socket────────┘
```

| 阶段 | 关键函数/结构 | 要点 |
|------|--------------|------|
| 接入 | `acceptHandler` | 每个客户端一个 `client`，带输入/输出缓冲区 |
| 读取 | `readQueryFromClient` → 输入缓冲 | TCP 分包可能只收到半条命令，先缓存等凑齐 |
| 解析 | `processInputBuffer` → RESP 解码 | 生成 `argv`（命令名 + 参数数组） |
| 查表 | `lookupCommand` | 命令表是一张 `dict`，O(1) 找到实现函数 |
| 前置 | `processCommand` | 校验参数个数、ACL、`maxmemory`、过期、只读副本等 |
| 执行 | `call` → 具体 `xxxCommand` | 真正读写数据；记录延迟统计、喂 AOF |
| 回复 | 输出缓冲 → `sendReplyToClients` | 多数回复在 `beforeSleep` 批量刷出 |

# 事件循环如何驱动这一切

Redis 用自研的 **ae 事件循环**（封装 `epoll`/`kqueue`/`select`）串行调度两类事件（呼应 [000.概述](./000.原理与源码概述.md#单线程与事件循环)）：

- **文件事件**：客户端 socket 可读 → 走上面的"读取→解析→执行→回复"；可写 → 把输出缓冲刷给内核。
- **时间事件**：`serverCron` 周期性执行，负责过期键抽样清理、统计、内存淘汰预判、复制心跳、渐进 rehash 步进等。
- **`beforeSleep`**：每轮事件循环进入阻塞等待前执行，是"把攒下的回复发出去、把 AOF 刷一刷、推进 rehash"的收口点。

**关键**：整条链路里"解析 + 执行"都在**同一个线程串行**完成，命令之间不交错——这是 Redis 无需给命令加锁、单命令天然原子的根因。

# 阻塞命令：不占线程的等待

`BLPOP`、`BRPOP`、`XREAD BLOCK`、`WAIT` 等阻塞命令**不会死等在执行线程里**：命令检测到"暂时无数据"时，把客户端挂到对应 key 的**阻塞列表**上并立即返回，事件循环继续处理别的请求；等别的命令产生数据时再回调唤醒。因此一个 `BLPOP` 卡住不会冻结整个实例（但大量阻塞客户端会占内存与连接，见 [08.工程化/070.大key与热key](../08.工程化/070.大key与热key.md)）。

# 事务 / Lua / pipeline 的执行时机差异

三者都"一次发多条"，但在链路里的落点完全不同，这是高频混淆点：

| 机制 | 何时执行 | 原子性 | 说明 |
|------|---------|--------|------|
| **pipeline** | 每条命令到达即各自 `call` 执行 | 单命令原子，**整组不原子** | 只是把多次网络往返打包，中途出错其余命令照常执行 |
| **事务 `MULTI/EXEC`** | `MULTI` 只入队，`EXEC` 时一次性连续执行队列 | 队列内**不被插入**（单线程串行） | 无回滚：某条报错，其余仍执行 |
| **Lua 脚本** | `EVAL` 时整段原子执行 | **整段原子** | 脚本期间其它命令排队，故脚本必须短（呼应 [06.可编程性](../06.可编程性/000.可编程性概述.md)） |

# 6.0 多线程 IO 的边界

6.0 引入 **IO 线程**只并行化链路里的"读取解析"和"写回编码"两段，**命令执行仍是单线程**。所以：

- 提的是**网络与协议编解码**吞吐，不是让命令并发跑；
- 依然不需要给命令加锁，原子性不变；
- 默认关闭（`io-threads-do-reads` 等），需按核数配置（见 [01.Redis 起步/050.Redis配置](../01.Redis%20起步/050.Redis配置.md)）。

# 过期与淘汰在链路中的位置

- **惰性删除**发生在 `lookupKeyRead`：命令访问到过期 key 时才删（所以 `TTL` 不是精确闹钟）。
- **定期删除**发生在 `serverCron` 的 `activeExpireCycle`：抽样清理带 TTL 的库。
- **内存淘汰**发生在 `processCommand` 里执行命令**之前**：达到 `maxmemory` 时先 `performEvictions` 腾空间再执行。

三条共同决定"key 什么时候真正消失"，细节见 [030.value 底层原理](./030.value底层原理.md) 与 [08.工程化/060.缓存穿透击穿雪崩](../08.工程化/060.缓存穿透击穿雪崩.md)。

# 避坑

- **别把 pipeline 当事务**：pipeline 只省网络往返，不保证一组命令原子落地；要原子用事务或 Lua。
- **慢命令 = 全局排队**：链路里"执行"是单线程串行的，一条 `KEYS`、大 key 的 `DEL`、重脚本会让后面所有请求卡在它后面——生产红线（用 `SCAN`、`UNLINK`、短脚本）。
- **阻塞命令不是免费的**：不占执行线程，但每个阻塞客户端长期占一个连接与缓冲区内存，数量要有上限。
- **输出缓冲能撑爆内存**：客户端消费慢而服务端狂写时，`client-output-buffer-limit` 到阈值会**直接断开客户端**（尤其 pubsub/复制），排查"莫名掉线"先看这里。
- **`beforeSleep` 才真正刷回复**：命令 `call` 返回不等于字节已发出，统计延迟时要理解"回复入缓冲"与"刷给内核"是两个时刻。

# 总结

一条命令的一生 = **读事件 → 输入缓冲 → RESP 解析 → 命令表查找 → 前置检查 → 单线程执行 → 输出缓冲 → 写事件刷回**，全程由 ae 事件循环串行驱动。抓住"执行阶段单线程串行"这条主线，就能自证：单命令为何天然原子、慢命令为何拖垮全局、阻塞命令为何不冻结实例、多线程 IO 为何不破坏原子性——它们都只是这条链路在不同条件下的必然表现。
