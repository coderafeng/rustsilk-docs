# 概述

在 Redis 里，**key 是定位一个 value 的索引**。一条命令 `GET student:S001` 的真正含义是：拿 `student:S001` 这个字符串，去当前数据库的**键空间字典**里 O(1) 找到对应的 `redisObject` 指针。本篇讲 key 在内存中如何被组织、如何被查找、如何登记过期、以及集群下如何决定归属分片——它是 [030.value 底层原理](./030.value底层原理.md) 的"另一半"：一个管**怎么找到值**，一个管**值长什么样**。

- 归属与可用性：Redis 开源核心机制
- 官方文档：<https://redis.io/docs/latest/develop/>（`redis.io/topics/design`、`redis.io/topics/cluster-spec`）

# key 本体：一段二进制安全的 SDS

key 本身就是一个 **SDS（简单动态字符串）**，与 value 用的字符串是同一套底座：二进制安全（可含 `\0`）、O(1) 取长度。因此 key 可以是任意字节序列，但实践中约定用可读文本。同一数据库内 key 唯一，重复 `SET` 同名 key 会覆盖旧 value 并清掉其 TTL（除非 `KEEPTTL`）。

# 键空间：一个 db 两张 dict

Redis 用 `server.db[]` 保存多个逻辑库（默认 16 个，`SELECT n` 切换），每个库是一个 `redisDb`：

```c
typedef struct redisDb {
    dict *dict;     // 键空间：key(SDS) -> value(redisObject*)
    dict *expires;  // 过期字典：key(SDS) -> 过期时间(绝对毫秒 long long)
    dict *blocking_keys;  // 阻塞命令的等待队列
    int id;         // 库编号
} redisDb;
```

- **`dict`（键空间）**：存所有 key→value 指针，是查找主路径。
- **`expires`（过期字典）**：**单独一张表**只存"哪些 key 带 TTL、几点过期"，value 不拆出来——所以过期信息和小规模 listpack 编码互不干扰。
- 查找：`lookupKeyRead(db, key)` → `dictFind(db->dict, key)`，平均 O(1)；读路径顺带做惰性过期检查（见 [010.内部流程](./010.内部流程.md#过期与淘汰在链路中的位置)）。

> [!note] 为什么过期要单开一张 dict
> 如果把 TTL 塞进 value 对象，会让"不带过期"的每个 value 都多背一个字段。拆成独立 `expires` 表后，只有设了 TTL 的 key 才占过期字典的一项，绝大多数无 TTL 的 key 零额外开销。

# dict 结构与渐进式 rehash

键空间和过期字典都是 `dict`。`dict` 内部是一张哈希表数组 `dictht[2]`：

| 结构 | 作用 |
|------|------|
| `dictht.table[]` | 桶数组，每个桶挂一条 `dictEntry` 链表 |
| `dictEntry` | `{ key, val(union), next }`，`next` 处理**哈希冲突（链地址法）** |
| `used` / `size` | 已用节点数 / 桶总数，二者之比即**负载因子** |

**渐进式 rehash**：当负载因子过高（默认 ≥1，且未在后台重写时 ≥5）需要扩容，`dict` 同时保留 `ht[0]`（旧）和 `ht[1]`（新），把重建拆成很多小步：

- 每次对 dict 的写操作、以及 `serverCron` 定时，都顺带迁移**一小段桶**从 `ht[0]` 到 `ht[1]`；
- 迁移期间查找/删除**两张表都查**，新增只进 `ht[1]`；
- 全部迁完后释放 `ht[0]`，`ht[1]` 转正。

**为什么渐进**：一次性重哈希百万 key 会长时间阻塞单线程（呼应 [010.内部流程](./010.内部流程.md#避坑) 的"慢命令"红线）；拆步摊薄，用"两次查表"的常数开销换"绝不长时间卡住"。

# 过期：登记、惰性删除、定期抽样

- **登记**：`EXPIRE`/`PEXPIRE`/`SET ... EX` 把 key 与绝对过期时间写进 `expires` 字典。
- **惰性删除**：读/写命中时若已过期才删——省 CPU，但过期 key 可能长期占内存。
- **定期删除**：`serverCron` 的 `activeExpireCycle` 周期性随机抽样带 TTL 的库、删掉其中已过期的，`active-expire-effort` 调节力度。

因此 TTL 不是精确闹钟；主从下由主节点删除后经复制传播 `DEL`，副本不自行过期以保一致（呼应 [08.工程化/030.主从复制](../08.工程化/030.主从复制.md)）。

# key 的哈希与 Cluster 分片

- **单机**：dict 用 **MurmurHash2** 计算 key 的桶下标。
- **集群**：Cluster 不用 dict 分桶，而是 `CRC16(key) % 16384` 把 key 映射到 **16384 个哈希槽**，槽再分配到各主节点。要用 `{}` **hash tag** 强制相关 key 落同一槽，才能做多 key 命令/事务（详见 [08.工程化/050.Cluster集群](../08.工程化/050.Cluster集群.md)）。

# 命名规范：key 是"可解析的坐标"

key 是纯字符串、Redis 不解释其结构，但**约定命名能让 key 自身携带语义**，便于 `SCAN MATCH`、按维度设 TTL、监控归因。本项目样本采用 `业务:实体:标识:维度` 四段式（见 [01.Redis 起步/090.样本数据](../01.Redis%20起步/090.样本数据.md)）：

| 示例 key | 拆解 |
|----------|------|
| `student:S001` | 实体 student : 标识 S001 |
| `exam:E2:SUB2:rank` | 考试 E2 : 科目 SUB2 : 维度 rank |
| `class:C1:attendance:20240902` | 班级 C1 : 出勤 : 日期 |
| `cache:class:C1:profile` | 前缀 cache 标明用途，便于批量清理 |

# 避坑

- **别用 `KEYS *` 遍历键空间**：它 O(N) 扫全 dict、单线程下直接卡死，用 `SCAN` 游标增量遍历（渐进 rehash 保证 `SCAN` 不漏不重语义）。
- **key 太长浪费内存**：每个 key 都是一段独立 SDS，百万级键下前缀冗余可观；但也别短到不可读，权衡命名与体积。
- **hash tag 用错毁扩展性**：`{}` 内内容相同会把海量 key 挤进**同一个槽**，形成单点热点，Cluster 扩容也分不开。
- **`expires` 与 value 编码是两回事**：给 hash 的**整键**设 TTL，不等于给字段设 TTL；字段级过期是 Hash 自己的 `HEXPIRE`（见 [02 章 Hash](../02.Redis%20数据类型和命令/020.Hash%20哈希.md)）。
- **多 db 不是隔离手段**：`SELECT` 的逻辑库在 Cluster 下只有 db0，跨库也不共享过期/淘汰统计，别拿它做多租户隔离。

# 总结

key 层回答"值在哪、几点消失、归哪个分片"：**key 本体是 SDS**，**键空间是 dict（key→robj 指针）**，**过期是独立的 expires dict**，三者叠加渐进式 rehash 把重排成本摊平。集群下 key 再经 CRC16 落到 16384 槽。把 key 命名成"可解析的坐标"，是这些底层机制在工程上最划算的呼应。
