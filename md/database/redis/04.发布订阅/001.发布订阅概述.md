# 概述

Redis 的发布/订阅（Pub/Sub）是一种**消息广播**机制：发布者把消息发到某个频道（channel），所有订阅了该频道的订阅者都会收到。它解耦了"谁在发"和"谁在收"。

- 归属与可用性：Redis 开源核心能力（频道订阅 2.0+，模式订阅 2.8+，分片 Pub/Sub 7.0+）
- 官方文档：<https://redis.io/docs/latest/develop/interact/pubsub/>

Redis 的发布/订阅机制采用**至多一次（at-most-once）**消息传递语义。顾名思义，这意味着消息只会传递一次；一旦消息由 Redis 服务器发出，就不会再次发送。如果订阅者此刻无法处理消息（例如由于错误或网络断开），消息将**永久丢失**。

> [!tip] 需要更强交付保证？
> Pub/Sub 是"在线广播"，不存储消息。如果你的应用需要消息持久化、离线补偿或"至少一次"投递，应改用 **Redis Streams**（详见 [060.Stream 流](../02.Redis%20数据类型和命令/060.Stream%20流.md)）——流中的消息会被持久化，支持消费组、ACK 与至多/至少一次语义。

# 原理

**三种订阅方式**

| 命令 | 订阅对象 | 说明 |
|------|----------|------|
| `SUBSCRIBE` | 一个或多个精确频道 | 收到发到这些频道的消息 |
| `PSUBSCRIBE` | glob 模式（如 `news.*`） | 匹配的所有频道消息都收 |
| `SSUBSCRIBE` | **分片频道**（sharded，7.0+） | 集群下按 key 槽路由，避免全广播风暴 |

对应的退订为 `UNSUBSCRIBE` / `PUNSUBSCRIBE` / `SUNSUBSCRIBE`；发布统一用 `PUBLISH channel message`。

**即发即弃（fire-and-forget）**

- 消息**不落盘、不排队**：服务器只在内存里维护"频道→订阅者连接"映射，收到 `PUBLISH` 就推给当前所有订阅者，然后丢弃。
- 没有订阅者时，`PUBLISH` 返回 0，消息直接消失。

**RESP 推送协议**

- RESP2：订阅者收到 `[message, channel, payload]` 等数组帧。
- RESP3（Redis 6.0+，`HELLO 3` 协商）：改为**推送帧（push）**，与命令回复分离，客户端处理更清晰。

**集群下的 Pub/Sub**

- 传统 `SUBSCRIBE`/`PUBLISH` 在 Cluster 中会**广播到所有节点**（因为订阅状态在各节点本地），大集群下有放大开销。
- 7.0 引入**分片 Pub/Sub（Sharded Pub/Sub，`SSUBSCRIBE`）**：频道名参与哈希槽路由，消息只在承载该槽的节点间传播，显著降低集群广播压力。

# 命令与实操

**发布端**

```text
PUBLISH news:sports "Game result: 3-1"
# 返回收到该消息的订阅者数量；0 表示当前无人订阅
```

**订阅端**

```text
SUBSCRIBE  news:sports news:tech      # 订阅精确频道
PSUBSCRIBE news.*                     # 订阅所有 news. 前缀频道
SSUBSCRIBE shard:orders               # 集群：分片频道订阅
```

**观测订阅状态（PUBSUB 家族）**

```text
PUBSUB CHANNELS news.*     # 当前有订阅者的频道列表（可带 glob 过滤）
PUBSUB NUMSUB  news:sports # 指定频道的订阅者数
PUBSUB NUMPAT              # 匹配的 pattern 订阅总数（PSUBSCRIBE）
PUBSUB SHARDCHANNELS       # 分片频道列表（7.0+）
```

**快速验证（两个终端）**

```bash
# 终端 A：先订阅
redis-cli SUBSCRIBE news:sports
# 终端 B：发布，观察 A 是否即时收到
redis-cli PUBLISH news:sports "hello"
```

# 典型场景

- **配置/缓存失效广播**：多实例应用监同一频道，收到消息即刷新本地缓存（配合 [060.缓存穿透击穿雪崩](../08.工程化/060.缓存穿透击穿雪崩.md) 的多级缓存失效）。
- **实时通知 / 在线消息**：IM 在线状态、弹幕、监控告警的即时下发。
- **跨进程事件总线（轻量）**：不需要可靠投递、允许丢的尽力通知（如埋点触发、任务唤醒信号）。

# 避坑

- **别把 Pub/Sub 当消息队列**：它**不持久化、无 ACK、离线即丢**。要"消息不能丢"用 [Streams](../02.Redis%20数据类型和命令/060.Stream%20流.md)（消费组 + `XACK` + PEL）或专业 MQ。
- **慢消费者拖垮全局**：订阅者处理不及时，消息在其输出缓冲区堆积，超 `client-output-buffer-limit pubsub` 会被**直接断开连接**并丢消息。生产要给订阅端限速/减负。
- **`PSUBSCRIBE` 模式匹配有成本**：每次 `PUBLISH` 都要对所有 pattern 做匹配，海量 pattern 订阅会拉高延迟——能用精确频道就别用通配。
- **集群误用全广播**：老式 `SUBSCRIBE` 在 Cluster 下全网广播，频道多、节点多时风暴明显。7.0+ 优先用 `SSUBSCRIBE` 分片订阅。
- **订阅连接是阻塞态**：进入订阅模式后，该连接一般只能处理订阅相关命令，拿来做别的读写要另开连接（呼应客户端"订阅用独立连接"约定）。
- **没有"历史消息回放"**：晚加入的订阅者收不到加入之前的任何消息；需要"新订阅者也能拿到最近状态"的场景，得配合持久化的 key 或 Stream 补首屏。

# 总结

Pub/Sub 的定位是**实时、扇出、即发即弃的广播**：一句话选型——**"能丢、要即时"用 Pub/Sub；"不能丢、要回放"用 Streams**。落地记三条：订阅端限速防缓冲区打满、集群优先分片订阅 `SSUBSCRIBE`、需要交付保证就别硬用 Pub/Sub。命令面很小（`PUBLISH`/`S*SUBSCRIBE`/`PUBSUB`），但语义边界（不持久化 + 至多一次）必须刻在选型第一性里。
