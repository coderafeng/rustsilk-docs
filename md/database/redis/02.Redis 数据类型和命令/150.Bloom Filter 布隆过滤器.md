# 概述

Bloom Filter 是概率型集合过滤器：判断"元素**肯定不存在**或**可能存在**"，以极小内存（错误率 1% 时约 10 bit/元素）支撑海量成员判断，典型用途是缓存穿透防护与去重预检。

- 归属与可用性：原 RedisBloom 模块能力，**自 Redis 6.2 起并入开源版**
- 官方文档：<https://redis.io/docs/latest/develop/data-types/probabilistic/bloom-filter/>

底层是** scalable Bloom**（多级子过滤器）：容量写满后自动按 `EXPANSION` 倍数新建子过滤器，早期子过滤器保留、新元素落入新子过滤器——所以**误判率会随子过滤器层数增加而累积上升**，这是它与教科书单级 Bloom 最大的行为差异。

# 命令速查

| 命令 | 说明 | 复杂度 |
|------|------|--------|
| `BF.RESERVE key error_rate capacity [EXPANSION c] [NONSCALING]` | 显式创建：`error_rate` 如 `0.01`，`capacity` 为预期元素数；`NONSCALING` 禁止扩容（满了报错） | O(1) |
| `BF.ADD key item` / `BF.MADD key item...` | 添加（键不存在时按默认参数自动创建：误差 0.01、容量 100、扩张 2） | O(k) |
| `BF.EXISTS key item` / `BF.MEXISTS key item...` | 判断"肯定不存在 / 可能存在" | O(k) |
| `BF.CARD key` / `BF.MCARD key...` | 已加入元素计数 | O(1) |
| `BF.INFO key` | 容量、子过滤器层数、实际误判率等 | O(1) |
| `BF.INSERT key [CAPACITY c] [ERROR e] [EXPANSION x] [NOCREATE] [NONSCALING] ITEMS item...` | 批量添加并可指定创建参数（`NOCREATE` 与 `CAPACITY/ERROR` 互斥） | O(k·n) |
| `BF.SCANDUMP` / `BF.LOADCHUNK` | 分块导出/导入，用于迁移备份 | O(n/m) |

# 典型场景

- **缓存穿透防护**：查询前先 `BF.EXISTS`，"肯定不存在"直接返回空，不打数据库；写入缓存时 `BF.ADD`。注意 Bloom **不能删**——数据被删除后仍会放行查询，需接受这一侧的"假命中"（见避坑）。
- **爬虫/风控 URL 判重**：`BF.RESERVE crawler:seen 0.001 100000000` 预先按亿级容量建过滤器，`BF.ADD` 返回值即“是否首次抓取”，比 Set 省两个数量级内存。
- **推荐已读过滤**：信息流"已读不出"用 Bloom 做粗筛，误推（约 0.1% 已读当未读）业务可接受时远优于存全量 Set。

# 避坑

- **误判方向不对称**："不存在"是绝对的，"存在"是概率的。防护场景要接受极小比例放行；强一致判重（金融、幂等扣款）禁用。
- **删不了元素**：单条删除无解，只能整键重建。删除比例高时改用 [Cuckoo Filter](./160.Cuckoo%20Filter%20布谷鸟过滤器.md)（支持 `CF.DEL`）。
- **容量规划是生命线**：默认容量只有 100，写入几千条后子过滤器层层扩张，误判率远超 0.01。上线前按 `基数 = 容量 × 子过滤器增长` 估算，或直接 `BF.RESERVE` 给足预算；`BF.INFO` 观察 filter count 与 misprobability。
- **`BF.ADD` 返回值有歧义**：元素"已可能存在"时返回 0，但误判会让**新元素也返回 0**——别把它当精确的"是否首次出现"计数用。
- 多级结构使**查询要逐层扫子过滤器**：元素规模增长后 `BF.EXISTS` 延迟会随层数上升，热点读场景优先 `NONSCALING` + 足够容量。

# 总结

Bloom Filter 的核心交易是"用 1% 的假阳性换三个数量级的内存"，它最锋利的两个用法是缓存穿透门禁与超大规模判重。用好它的关键不在命令，而在两件事：**容量预算**（`BF.RESERVE` 给足，避免子过滤器无限扩张导致误判率失控）和**删除语义**（不能删；删除频繁就转 Cuckoo，需要精确就转 Set）。把它放在"粗筛/预检"这一层，让精确判断留在数据库，是最稳的架构位置。
