# 概述

Stream 是按时间顺序排列的条目序列，每个条目包含字段-值对，支持消费者组模式。

- 归属与可用性：Redis 开源核心类型（5.0+）
- 官方文档：<https://redis.io/docs/latest/develop/data-types/streams/>

底层是**基数树（radix tree）串联 listpack 节点**：条目按 ID（毫秒时间-序列号）有序追加，稀疏节点优化范围跳转。Stream 是 Redis 内唯一"消息可持久堆积、可回溯、支持消费组确认"的类型，语义上对标 Kafka 而非 Pub/Sub（后者见 [04.发布订阅](../04.发布订阅/000.发布订阅概述.md)：离线即丢、至多一次）。8.x 系列密集补强消费组语义：**8.2 确认即删 `XACKDEL`/条件删除 `XDELEX`**、**8.6 幂等生产 IDMP（`XADD IDMP` + `XCFGSET`）**、**8.8 显式释放 `XNACK`**（见 [Redis 8.2](../10.Redis%20版本特性/050.Redis8.2.md)）。

# 命令速查

| 命令 | 说明 | 复杂度 |
|------|------|--------|
| `XADD key * f v [f v...] [MAXLEN \| MINID ~ n] [NOMKSTREAM] [IDMPAUTO p-id \| IDMP p-id i-id]` | 追加条目（`*` 自动 ID；`~` 近似裁剪；IDMP 幂等去重 8.6+） | O(1) |
| `XLEN key` / `XRANGE key - + [COUNT n]` | 长度 / 按 ID 区间读 | O(1) / O(N) |
| `XREAD COUNT n BLOCK ms STREAMS key id` | 客户端视角读取（`$` 只收新消息） | O(N) |
| `XGROUP CREATE key group $ [MKSTREAM]` | 创建消费组（`ENTRIESREAD` 7.0+） | O(N) |
| `XREADGROUP GROUP g c COUNT n BLOCK ms STREAMS key >` | 消费组领取（`>` 新消息；ID 重投 PEL） | O(N) |
| `XACK key group id...` | 确认消费完成 | O(1) |
| `XNACK key group <SILENT\|FAIL\|FATAL> IDS n id... [RETRYCOUNT n] [FORCE]` | 显式释放 PEL 消息待重投，并标记投递状态（8.8+） | O(N) |
| `XPENDING key group [[IDLE n] min count [consumer]]` | 查看待确认列表（PEL） | O(N) |
| `XCLAIM` / `XAUTOCLAIM key group c min-idle-time 0 [COUNT n]` | 接管超时消费者手中的消息（6.2+ 自动版） | O(N) |
| `XTRIM key MAXLEN ~ n [MINID id] [LIMIT]`（7.0+） | 裁剪长度 | O(N) |
| `XINFO STREAM\|GROUPS\|CONSUMERS key` | 观测流/组/消费者状态 | O(1)/O(N) |
| `XACKDEL key group [KEEPREF\|DELREF\|ACKED] IDS n id...` | **原子地**确认并删除条目（8.2+） | O(1)/条 |
| `XDELEX key [KEEPREF\|DELREF\|ACKED] IDS n id...` | 删除条目并按策略处理消费组引用（8.2+） | O(1)/条 |
| `XCFGSET key [IDMP-DURATION s] [IDMP-MAXSIZE n]` | 配置流的 IDMP 幂等窗口（8.6+） | O(1) |

# 典型场景

1. **日志/事件溯源**：`XADD events:order * order_id 88 status paid`，事后 `XRANGE` 任意回放。
2. **竞争消费（任务队列）**：同一组内多 Worker `XREADGROUP` 每条消息只被一个消费者拿到；不同组各自收到全量（扇出）。
3. **崩溃恢复**：消费者处理完必须 `XACK`；宕机后其他实例用 `XAUTOCLAIM stream grp me 60000 0` 接管 idle 超 60s 的消息，不丢单。
4. **阻塞订阅新消息**：`XREAD BLOCK 5000 STREAMS news $`，近实时且离线期间的消息上线可补读（对比 Pub/Sub 直接丢失）。
5. **控制体积**：生产端 `XADD ... MAXLEN ~ 100000`，或定期 `XTRIM MINID <水位>` 按时间裁剪。
6. **确认即删省内存**：短 TTL 事件流消费完即无回放需求，`XACKDEL orders grp ACKED IDS 1 <id>` 一步完成 ACK+删除，PEL 与条目同时收缩（8.2+）。
7. **生产端幂等（IDMP）**：重试可能重复 `XADD` 的场景，生产者在窗口内用同一 `IDMP producer-id idempotent-id` 发送，重复投递直接返回原条目 ID，消费侧不必再去重（8.6+，窗口用 `XCFGSET` 调）。

# 操作示例

## 成绩录入消费组全流程

```bash
# 1) 生产（样本流：stream:score:events）
redis-cli XADD stream:score:events '*' student_id S001 subject_id SUB2 exam_id E2 score 108 operator teacher:吴刚
# 2) 建组（0 = 从头回放全部历史；MKSTREAM 顺带建流）
redis-cli XGROUP CREATE stream:score:events grading 0 MKSTREAM
# 3) 消费：'>' 领取新消息，处理完必须 ACK
redis-cli XREADGROUP GROUP grading worker-1 COUNT 10 BLOCK 5000 STREAMS stream:score:events '>'
redis-cli XACK stream:score:events grading '1727481600000-0'
# 4) 观测：谁积压了多少
redis-cli XPENDING stream:score:events grading
```

## 崩溃恢复：接管超时消息

```bash
# worker-1 宕机，idle 超过 60s 未确认的消息改挂到 worker-2 名下继续处理
redis-cli XAUTOCLAIM stream:score:events grading worker-2 60000 0 COUNT 10 JUSTID
```

## 确认即删：XACKDEL（8.2+）

```bash
# 短 TTL 事件流无回放需求：ACK + 删除一步完成，PEL 与条目同时收缩
redis-cli XACKDEL stream:score:events grading ACKED IDS 1 '1727481600000-0'
# 只删条目不确认（DELREF 一并删除本组 PEL 引用）用 XDELEX
redis-cli XDELEX stream:score:events DELREF IDS 1 '1727481600001-0'
```

## 失败重投控制：XNACK（8.8+）

```bash
# 这条成绩数据异常处理不了，丢回组内待重投，并标记为一次失败投递
redis-cli XNACK stream:score:events grading FAIL IDS 1 '1727481600000-0'
```

## 生产端幂等：IDMP（8.6+）

```bash
# 教师重复提交同一条成绩：窗口内同一 (生产者, 幂等ID) 直接返回原条目 ID 而非新增
redis-cli XADD stream:score:events IDMP teacher:吴刚 'S001:SUB2:E2' '*' student_id S001 subject_id SUB2 exam_id E2 score 108
# 调大去重窗口/容量
redis-cli XCFGSET stream:score:events IDMP-DURATION 3600 IDMP-MAXSIZE 10000
```

幂等 ID 用业务键（学号+科目+考试），不要用随机值，否则去重形同虚设。

# 避坑

- **忘 XACK 是慢性泄漏**：PEL 无限增长、`XPENDING` 变慢、内存被"已投递未确认"条目占住——消费侧务必 ACK（8.2+ 可直接 `XACKDEL`），并用 `XINFO GROUPS` 的 pending 做监控；确定不再重投的用 `XNACK` 显式释放。
- **`KEEPREF`/`DELREF`/`ACKED` 决定删条目时如何处置各组 PEL 引用**：选错会让别的消费组持有悬空 ID，`XCLAIM` 时报错——多组共享的流上删条目优先用 `XDELEX` 而非裸 `XDEL`（后者 8.2+ 也接受这组选项）。
- **IDMP 窗口有限**：`IDMP-DURATION`/`IDMP-MAXSIZE` 之外的重复不拦截，幂等 ID 仍建议用业务键（订单号+操作）而非随机值。
- **at-least-once ⇒ 必须幂等**：重投（XCLAIM/重启读 PEL）意味着同一 ID 可能被处理两次，消费逻辑要按消息 ID 去重。
- `XGROUP CREATE ... $` 只消费"建组之后"的新消息；想全量回放用 `0`——选错起点会静默丢历史。
- `XADD MAXLEN n`（不带 `~`）是**精确裁剪**，每写一条可能同步搬移大量条目拖慢写入，用 `~` 近似裁剪。
- 不加 `COUNT` 限制的 `XRANGE` 全量读取一次拉爆网络；BLOCK 0 永久阻塞同 List 注意事项。
- Stream 不会自动收缩历史：只 XADD 不 XTRIM，流就是只增日志——按保留窗口设 `MINID` 裁剪任务。

# 总结

- Stream = 可持久、可回溯、带消费组的迷你 Kafka：可靠性消息场景首选，优于 List 队列与 Pub/Sub；
- 生命周期三件套：**XADD 限长（MAXLEN ~/MINID）→ XREADGROUP + XACK 消费 → XAUTOCLAIM 接管**；
- 观测靠 `XINFO STREAM/GROUPS/CONSUMERS` 与 `XPENDING`，PEL 水位是第一个该报警的指标。
