# 概述

Stream 是按时间顺序排列的条目序列，每个条目包含字段-值对，支持消费者组模式。

- 归属与可用性：Redis 开源核心类型（5.0+）
- 官方文档：<https://redis.io/docs/latest/develop/data-types/streams/>

底层是**基数树（radix tree）串联 listpack 节点**：条目按 ID（毫秒时间-序列号）有序追加，稀疏节点优化范围跳转。Stream 是 Redis 内唯一"消息可持久堆积、可回溯、支持消费组确认"的类型，语义上对标 Kafka 而非 Pub/Sub（后者见 [04.发布订阅](../04.发布订阅/000.发布订阅概述.md)：离线即丢、至多一次）。

# 命令速查

| 命令 | 说明 | 复杂度 |
|------|------|--------|
| `XADD key * f v [f v...] [MAXLEN ~ n] [NOMKSTREAM]` | 追加条目（`*` 自动生成 ID；`~` 近似裁剪） | O(1) |
| `XLEN key` / `XRANGE key - + [COUNT n]` | 长度 / 按 ID 区间读 | O(1) / O(N) |
| `XREAD COUNT n BLOCK ms STREAMS key id` | 客户端视角读取（`$` 只收新消息） | O(N) |
| `XGROUP CREATE key group $ [MKSTREAM]` | 创建消费组（`ENTRIESREAD` 7.0+） | O(N) |
| `XREADGROUP GROUP g c COUNT n BLOCK ms STREAMS key >` | 消费组领取（`>` 新消息；ID 重投 PEL） | O(N) |
| `XACK key group id...` | 确认消费完成 | O(1) |
| `XPENDING key group [[IDLE n] min count [consumer]]` | 查看待确认列表（PEL） | O(N) |
| `XCLAIM` / `XAUTOCLAIM key group c min-idle-time 0 [COUNT n]` | 接管超时消费者手中的消息（6.2+ 自动版） | O(N) |
| `XTRIM key MAXLEN ~ n [MINID id] [LIMIT]`（7.0+） | 裁剪长度 | O(N) |
| `XINFO STREAM\|GROUPS\|CONSUMERS key` | 观测流/组/消费者状态 | O(1)/O(N) |
| `XACKDEL` / `XDELEX key group id... [KEEPREF\|DELREF\|ACKED]` | 确认即删（8.2，见 [Redis 8.2](../10.Redis%20版本特性/050.Redis8.2.md)） | O(1) |
| `XNACK key group id...` | 放弃认领放回 PEL 待接管（8.8） | O(N) |

# 典型场景

1. **日志/事件溯源**：`XADD events:order * order_id 88 status paid`，事后 `XRANGE` 任意回放。
2. **竞争消费（任务队列）**：同一组内多 Worker `XREADGROUP` 每条消息只被一个消费者拿到；不同组各自收到全量（扇出）。
3. **崩溃恢复**：消费者处理完必须 `XACK`；宕机后其他实例用 `XAUTOCLAIM stream grp me 60000 0` 接管 idle 超 60s 的消息，不丢单。
4. **阻塞订阅新消息**：`XREAD BLOCK 5000 STREAMS news $`，近实时且离线期间的消息上线可补读（对比 Pub/Sub 直接丢失）。
5. **控制体积**：生产端 `XADD ... MAXLEN ~ 100000`，或定期 `XTRIM MINID <水位>` 按时间裁剪。

# 避坑

- **忘 XACK 是慢性泄漏**：PEL 无限增长、`XPENDING` 变慢、内存被"已投递未确认"条目占住——消费侧务必 ACK（8.2+ 可直接 `XACKDEL`），并用 `XINFO GROUPS` 的 pending 做监控。
- **at-least-once ⇒ 必须幂等**：重投（XCLAIM/重启读 PEL）意味着同一 ID 可能被处理两次，消费逻辑要按消息 ID 去重。
- `XGROUP CREATE ... $` 只消费"建组之后"的新消息；想全量回放用 `0`——选错起点会静默丢历史。
- `XADD MAXLEN n`（不带 `~`）是**精确裁剪**，每写一条可能同步搬移大量条目拖慢写入，用 `~` 近似裁剪。
- 不加 `COUNT` 限制的 `XRANGE` 全量读取一次拉爆网络；BLOCK 0 永久阻塞同 List 注意事项。
- Stream 不会自动收缩历史：只 XADD 不 XTRIM，流就是只增日志——按保留窗口设 `MINID` 裁剪任务。

# 总结

- Stream = 可持久、可回溯、带消费组的迷你 Kafka：可靠性消息场景首选，优于 List 队列与 Pub/Sub；
- 生命周期三件套：**XADD 限长（MAXLEN ~/MINID）→ XREADGROUP + XACK 消费 → XAUTOCLAIM 接管**；
- 观测靠 `XINFO STREAM/GROUPS/CONSUMERS` 与 `XPENDING`，PEL 水位是第一个该报警的指标。
