# 概述

Array 是稀疏的、可按整数索引寻址的字符串序列，支持 O(1) 随机访问、范围读取和服务端聚合，设置高位索引不会分配大量内存。

- 归属与可用性：**Redis Array 模块**（Stack 组件，Rust 实现），开源版 Redis 需自行 `loadmodule`；未随 Redis 8 一体化发行，**命令语法以官方仓库 README 为准**
- 官方资料：<https://github.com/redis-develop/redisarray>（文档入口 <https://redis.io/docs/latest/develop/data-types/>）

设计要点：与 List 的"两端操作链表"不同，Array 面向**按索引随机访问**的场景——链表做 `LINDEX 中间` 是 O(N)，而 Array 是 O(1)；内部用稀疏分段结构，写入高位索引只分配所在段。

# 典型场景

1. **事件日志/环形缓冲**：以自增序号为索引追加、按索引区间回放，不需要 List 的"两端语义"时更贴切。
2. **传感器读数序列**：`index = 时间片编号`，随机点查某天第 N 个采样点，稀疏性避免为空时段付费。
3. **追加密集型时间线**：既要随机访问又偶尔补写历史位点的场景（List 无法按位插入 O(1)）。

# 避坑

- **环境可用性是第一道坑**：仅 Redis Stack 镜像内置该模块，普通 `redis:` 镜像与 Redis 8 开源一体化发行版均无对应命令——选型前先 `COMMAND DOCS` 确认，否则方案直接不成立。
- 与 List 的边界：需要阻塞弹出/两端队列 → List；需要按索引读写 → 才考虑 Array；需要消息可靠性+消费组 → Stream。
- 稀疏结构"设置高位索引不爆内存"≠零成本：段仍会按需分配，超大索引空间要配合裁剪策略。
- 该模块生态资料少、演进慢，**生产选型务必做命令级 POC**，并准备 Hash 分桶（`h:{uid}:{i}`）作为退路方案。

# 总结

- Array 填补"按索引 O(1) 随机访问的字符串序列"这一生态位，与 List/Stream 三者按访问模式区分；
- 属 Stack 模块且未并入开源一体化发行版，用之前先确认命令存在；
- 本教程对该类型只做概念级讲解，深入用法以模块 README 与实测为准。
