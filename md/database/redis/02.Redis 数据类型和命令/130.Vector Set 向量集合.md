# 概述

Vector Set 是能存储固定维度数值向量的集合类型，向量组织在 **HNSW 邻近图**上，支持 KNN（取最近 K 个）与距离阈值查询、JSON 属性过滤——Redis 原生 AI 检索的基础构件。

- 归属与可用性：**Redis 开源核心类型，自 Redis 8.0 引入**（命令表 13 条 `V*` 命令）
- 官方文档：<https://redis.io/docs/latest/develop/data-types/vector-sets/>

设计要点：写入时以 `FP32`（十六进制压缩串）或 `VALUES`（浮点字面量列表）提供向量，可选 `REDUCE` 边写边降维、`Q8`/`BIN` 量化换内存与速度；查询 `VSIM` 既可用外部向量也可用**集合内已有元素**（`ELE`）找相似。属性经 `VSETATTR`/`SETATTR` 以 JSON 挂到元素上，供 `FILTER` 表达式过滤。**8.4 起新增 `VRANGE`** 按字典序区间浏览元素（见 [Redis 8.4](../10.Redis%20版本特性/060.Redis8.4.md)）。

# 命令速查

| 命令 | 说明 | 复杂度 |
|------|------|--------|
| `VADD key [REDUCE dim] (FP32 \| VALUES n) v1 v2... element [CAS] [NOQUANT \| Q8 \| BIN] [EF e] [M m] [SETATTR json]` | 写入/更新元素向量；`REDUCE` 降维、`Q8/BIN` 量化、`M/EF` 建图参数、`CAS` 比较并设置（防并发覆盖） | O(log N) |
| `VSIM key (ELE \| FP32 \| VALUES n) target [COUNT k \| EPSILON δ] [WITHSCORES] [WITHATTRIBS] [EF e] [FILTER expr] [FILTER-EF effort]` | 相似检索：`ELE` 以已有元素为锚点；`COUNT` KNN 与 `EPSILON` 距离阈值互斥；`FILTER` 按属性表达式过滤 | O(log N) |
| `VEMB key element [RAW]` | 取元素嵌入向量（`RAW` 返回未量化原值） | O(1) |
| `VSETATTR key element json` / `VGETATTR key element` | 写 / 读元素 JSON 属性（供 `VSIM FILTER` 用） | O(1) |
| `VREM key element...` | 删除元素 | O(log N)/个 |
| `VCARD key` / `VDIM key` | 元素数 / 当前（降维后）维度 | O(1) |
| `VISMEMBER key element` | 判断元素是否存在 | O(1) |
| `VRANGE key start end [count]` | 按**字典序**区间浏览元素（非相似度检索，8.4+） | O(log K + M) |
| `VRANDMEMBER key [count]` | 随机取样 | O(N) |
| `VLINKS key element [WITHSCORES]` | 查看元素在 HNSW 图**各层的邻居**（调试连通性/召回用） | O(1) |
| `VINFO key` | 集合元数据：维度、量化方式、M/EF 等建图参数 | O(1) |

# 典型场景

- **语义检索**：文档切块后 `VADD docs VALUES 3 0.11 0.22 0.33 chunk_1 SETATTR '{"tenant":"a"}'`；查询 `VSIM docs VALUES 3 q1 q2 q3 COUNT 10 FILTER ".[tenant] == a" WITHSCORES`——属性过滤实现多租户隔离，配合应用层 rerank 出最终结果。
- **"以物找物"**：商品推荐直接 `VSIM items ELE item_123 COUNT 20 WITHSCORES`，无需把 item_123 的向量取回客户端再喂回去。
- **RAG 记忆存储**：对话摘要嵌入写入 `docs` 集合，命中元素用 `VGETATTR` 回读原文指针/元数据，向量与业务属性同键共存。
- **内存吃紧的量化降本**：大规模召回先 `BIN`（1 bit/维）粗筛再对候选重排精算，或 `Q8` 换约 4 倍内存节省；`REDUCE` 可在写入时直接降维。
- **精确并发更新**：模型重算向量后 `VADD ... <vec> element CAS`——向量未被他人改动才更新，避免双写覆盖。

# 操作示例

## 学情画像相似检索（4 维小向量示意）

```bash
# 1) 写入学生画像向量（样本前 4 维），带班级/类型属性
redis-cli VADD "vset:student:profile" VALUES 4 0.82 0.91 0.15 0.44 S001 SETATTR '{"class":"C1","type":"数学强"}'
redis-cli VADD "vset:student:profile" VALUES 4 0.55 0.62 0.71 0.40 S002 SETATTR '{"class":"C1","type":"均衡"}'
redis-cli VADD "vset:student:profile" VALUES 4 0.79 0.88 0.35 0.52 S003 SETATTR '{"class":"C1","type":"理科强"}'
# 2) 一个新转入生向量做 KNN，找最相似的 3 人
redis-cli VSIM "vset:student:profile" VALUES 4 0.80 0.90 0.20 0.45 COUNT 3 WITHSCORES
# 3) 仅在 C1 班内检索 + 回读命中学生的元数据
redis-cli VSIM "vset:student:profile" VALUES 4 0.80 0.90 0.20 0.45 COUNT 3 FILTER ".[class] == C1" WITHATTRIBS
redis-cli VGETATTR "vset:student:profile" S001
```

## 以人找人（ELE 锚点）

```bash
# 以集合内已有的 S001 为锚点找相似学生，省去“取回向量再喂回去”一次往返
redis-cli VSIM "vset:student:profile" ELE S001 COUNT 3 WITHSCORES
```

## 量化收益评估（NOQUANT vs Q8）

```bash
# 同一批画像向量分别写入精度集与量化集，用 TRUTH 全量对照评估召回损失
redis-cli VADD "vset:profile.exact" VALUES 4 0.82 0.91 0.15 0.44 S001 NOQUANT
redis-cli VADD "vset:profile.q8"     VALUES 4 0.82 0.91 0.15 0.44 S001 Q8
redis-cli VSIM "vset:profile.q8" ELE S001 COUNT 10 TRUTH        # 精确全扫作为 ground truth
```

## 索引健康诊断

```bash
redis-cli VINFO "vset:student:profile"                    # 维度/量化方式/M、EF 参数
redis-cli VLINKS "vset:student:profile" S001 WITHSCORES # 看 S001 在 HNSW 各层的邻居，排查孤点
redis-cli VCARD "vset:student:profile"; redis-cli VDIM "vset:student:profile"
```

# 避坑

- **量化不可兼得**：`Q8`/`BIN` 显著省内存提速但损失召回精度，`NOQUANT` 保真；上线前用 `VSIM ... TRUTH`（精确全扫描对照）评测召回率，别凭感觉选。
- **属性过滤是带成本的**：`FILTER` 命中候选变少时由 `FILTER-EF` 控制补偿搜索力度——选择性强（如租户只占 1%）时调大补偿或直接**按租户分 key** 物理隔离。
- **维度/降维要前后一致**：`REDUCE` 之后 `VDIM` 是降维值，查询向量必须匹配同维；模型换版本（768 → 1536）需重建集合，不能混存。
- **`EPSILON` 与 `COUNT` 互斥**：阈值查询结果数不定，大集合注意爆返回；KNN 用 `COUNT`。
- **`VLINKS` 是图邻居不是业务链接**：它返回 HNSW 各层相邻元素，用于诊断索引质量；"多向量对象/文档-片段关联"命令表中不存在，建模请在应用层用前缀 ID + `VGETATTR` 实现。
- **`VRANGE` 是字典序而非距离序**：按元素名浏览用，"按距离遍历"只有 `VSIM`。
- 索引参数 `M`/`EF`（建图）与查询期 `EF` 是**延迟/召回/内存的三角权衡**，`VINFO` 核对当前参数，召回不达标先调查询 `EF`。

# 总结

Vector Set 让 Redis 8+ 成为"轻量向量库"：服务端 KNN、属性过滤、量化/降维三件事原生解决，省掉独立向量服务的运维成本。选型边界要诚实：千万级以上向量、严格混合检索仍该上专业向量库；"缓存/会话本来就在 Redis，顺手做语义召回"的场景里它是工程最短路径。量化策略（`NOQUANT/Q8/BIN`）与 `M/EF` 在写入前定好，它们决定后续所有查询的质量上限。
