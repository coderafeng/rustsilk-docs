# 概述

Top-K 在 Stream-CMS（带指数衰减的 Count-Min Sketch + 最小堆）基础上实时维护"出现频次最高的 K 个元素"榜单，内存固定、天然适配流量类场景的"新数据权重更高"。

- 归属与可用性：原 RedisBloom 模块能力，**自 Redis 6.2 起并入开源版**
- 官方文档：<https://redis.io/docs/latest/develop/data-types/probabilistic/>

与手工"Hash 计数 + ZSet 排序"相比，它的优势是**元素基数无上限、内存有上限**；与 CMS 相比，它内置了榜单和衰减，不用自己扫候选集。

# 命令速查

| 命令 | 说明 | 复杂度 |
|------|------|--------|
| `TOPK.RESERVE key width depth [decay t]` | 创建：`width` 即榜单容量（`TOPK.LIST` 最多返回这么多条，**没有独立的 k 参数**）、`depth` 哈希层数、`decay` 衰减底数（默认约 `1.08`）；键不存在时 `TOPK.ADD` 会按模块默认参数自动创建 | O(1) |
| `TOPK.ADD key item [item ...]` | 记账并上榜尝试，**返回被挤出榜单的元素**（无挤出返回 nil/空） | O(d) |
| `TOPK.INCRBY key item delta [item delta ...]` | 按权重增减计数 | O(d) |
| `TOPK.QUERY key item [item ...]` | 判断 item 当前是否在 Top-K 榜单内 | O(d) |
| `TOPK.COUNT key item [item ...]` | 查询估计频次（衰减后的计数） | O(d) |
| `TOPK.LIST key [WITHCOUNT]` | 返回榜单（按频次降序；`WITHCOUNT` 附带计数） | O(k) |
| `TOPK.INFO key` | 返回 k、width、depth、decay | O(1) |

# 典型场景

- **热搜/热门商品榜**：`TOPK.RESERVE hot:search 1000 7 2.4`，每次搜索 `TOPK.ADD`，前端直接 `TOPK.LIST WITHCOUNT` 取榜单；百万级不同查询词只占固定内存，衰减参数让"新热"快速压过"旧热"。
- **限流异常探测**：对来源 IP 记账，`TOPK.LIST` 即当前最热的 N 个来源，配合 [Count-Min Sketch](./170.Count-Min%20Sketch%20计数最小略图.md) 的全量频次粗筛形成两层雷达。
- **推荐候选粗排**：内容曝光/点击流实时维护 Top-K 候选，再进精排模型——比 ZSet 全量维护便宜，且自带时效性。

# 避坑

- **`TOPK.ADD` 的返回不是"是否新增"**：它返回被挤出的元素（用于外部级联清理），新手常误读为布尔值；判断在榜请用 `TOPK.QUERY`。
- **频次是估计值**：`TOPK.COUNT` 继承 Stream-CMS 的高估特性，别用于结算/对账；榜单排序同理只保证"大概率靠前"。
- **`decay` 是业务节奏参数**：默认值未必适配你的窗口——快热搜调小（遗忘快）、慢榜单调大；上线前用回放流量验证榜单稳定性。
- **参数组合靠压测定**：`width` 定榜单上限、`depth` 定误差、`decay` 定时效，不是越大越好（内存≈ w×d 个计数器），要按回放流量验证。
- 榜单外元素**不保留精确计数**：跌出 Top-K 后再翻红要重新积累，冷启动期内存里它“查无此人”——需要完整历史用 ZSet。

# 总结

Top-K = “固定内存 + 实时榜单 + 自动遗忘”三件套，是热搜、热门资源、流量雷达类需求的标准解。参数职责要分清：`width` 定榜单容量、`depth` 定估计误差、`decay` 定时效长短。它与 ZSet 的分界线在于**元素基数是否无界**——基数有界且要精确排名时用 ZSet，基数无界只要“当前最热的 N 个”时用 Top-K。
