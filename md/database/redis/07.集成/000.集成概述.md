# 概述

在不同编程语言与框架中接入 Redis——本章梳理主流**客户端库**的能力矩阵与选型要点。图形化管理工具（Another Redis Desktop Manager、RedisInsight 等）见 [060.可视化客户端工具](../01.Redis%20起步/060.可视化客户端工具.md)，本章只讲代码里的客户端。

- 归属与可用性：客户端为第三方库，与 Redis 服务端协议（RESP2/RESP3）对接
- 官方文档：<https://redis.io/docs/latest/develop/clients/>

> [!tip] 一句话选型
> 几乎所有生产问题都不出在"选哪个库"，而出在**连接池配置、超时与重试、是否支持 Sentinel/Cluster/TLS**。先按语言选社区最主流的那个，再把精力放在下面「高频用法」与「避坑」。

# 高频用法

**连接池（一切性能的地基）**

- 客户端应**复用连接**而非每请求新建。Lettuce/redis-py/node-redis/ioredis 内部维护连接；Jedis 需显式 `JedisPool`；.NET 用单例 `ConnectionMultiplexer`。
- 关键参数：最大连接数、获取连接超时、空闲回收。池太小→高并发拿不到连接报错；太大→压垮服务端 `maxclients`。

**超时与重试**

- 必须设**连接超时**与**命令超时**，避免服务端抖动时线程被无限挂住；重试要带**退避与上限**，且只对幂等操作重试。

**pipeline / 批量**

- 大量独立命令用 `pipeline` 摊薄 RTT（原理见 [09.原理与源码](../09.原理与源码/000.原理与源码概述.md)）；但 pipeline 不保证原子，要原子用事务/Lua（[06.可编程性](../06.可编程性/000.可编程性概述.md)）。

**高可用与集群接入**

- Sentinel：配置哨兵节点列表，由客户端自动 `get-master-addr-by-name` 并在故障转移后重连（见 [040.Sentinel](../08.工程化/040.Sentinel哨兵.md)）。
- Cluster：必须用**支持 MOVED/ASK 重定向**的 cluster-aware 客户端（见 [050.Cluster](../08.工程化/050.Cluster集群.md)）。

# 典型场景

- **Web 会话/缓存**：应用框架的 Redis session store、Spring Cache / 各语言 ORM 二级缓存，底层都走上述客户端。
- **分布式锁/限流**：Java 优先 Redisson（锁、信号量、限流器开箱即用），其它语言用 Lua 脚本自行实现（见 [020.事务与分布式锁](../08.工程化/020.事务与分布式锁.md)）。
- **消息/任务**：Pub/Sub 或 Streams 的消费端一般要求**独立长连接**，不要和缓存读写共用同一个池连接。

# 避坑

- **一个 `Redis` 实例打天下 / 每次 new 一个客户端**：前者可能连接混用不当，后者连接风暴。用单例 + 连接池，按业务隔离必要时分池。
- **Jedis 连接多线程共享**：Jedis 连接非线程安全，裸共享会数据错乱——要么用 `JedisPool`，要么换 Lettuce（线程安全）。
- **不设命令超时**：默认某些客户端无读超时，服务端 `MONITOR`/大 key 卡住时，客户端线程被永久阻塞，故障沿调用链放大。
- **Pub/Sub 订阅连接被复用**：订阅是阻塞长连接态，和业务请求抢同一个连接会互相饿死——订阅要独占连接。
- **序列化格式绑死**：不同语言/服务读写同一 key 时，值编码（JSON/msgpack/pickle/Java 原生）不一致会导致互相读不懂。跨语言键统一用 JSON 或明确约定的二进制格式。
- **忽略 RESP3 / Client Side Caching 开关**：需要服务端推送、缓存失效通知（`CLIENT TRACKING`）时要显式启用 RESP3 并选支持该特性的客户端版本。
- **集群下用非 cluster 客户端 / 跨 slot 多键**：普通客户端遇到 `MOVED` 直接报错；`MSET`/Lua 跨槽 key 报 `CROSSSLOT`——用 hash tag 归槽（见 [050.Cluster](../08.工程化/050.Cluster集群.md)）。

# 总结

集成层的心法只三条：**① 按语言选社区最主流、明确支持 Sentinel/Cluster/TLS 的客户端；② 把连接池、超时、重试这三样配好，胜过纠结库的 benchmark；③ 分清"请求型用法"（缓存，走池化短请求）与"订阅型用法"（Pub/Sub/Streams，独占长连接）**。库是入口，稳定性来自配置——把客户端参数与服务端 [050.Redis配置](../01.Redis%20起步/050.Redis配置.md) 对齐，才算真正接好。
