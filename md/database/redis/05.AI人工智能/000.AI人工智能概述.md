# 概述

Redis 是一个**内存数据平台**，为 AI 应用所需的速度与结构而生：它存储并索引向量嵌入与结构化元数据，从而以毫秒级延迟支撑语义搜索、实时检索与智能体记忆。

- 归属与可用性：**基础向量检索属 Redis 开源版（8.0+）**；语义缓存、Context Retriever、代理构建器、CDC 数据同步等属 **Redis Cloud / Redis Software 商业能力**
- 官方文档：<https://redis.io/docs/latest/develop/ai/>

Redis 在 AI 场景的五类能力：

- **向量搜索**——用 KNN 与范围查询、结合元数据过滤器，跨 Hash 和 JSON 存储并查询向量嵌入；
- **语义缓存**——通过 LangCache 重用语义相似提示的缓存响应，降低 LLM API 成本；
- **智能体记忆**——为 Agent 提供短期会话记忆与跨交互持续存在的长期记忆；
- **结构化数据访问**——用 Context Retriever 把业务数据转成受控工具，供代理可靠查询；
- **实时数据同步**——用 CDC 把关系库的变更近实时同步到 Redis，保证代理用的是最新信息。

> [!warning] 能力边界（写作与选型务必逐项标注归属）
> 上述能力并非开源版全都有：**语义缓存（LangCache）、Context Retriever、交互式代理构建器、实时数据同步（CDC）属于 Redis Cloud / Redis Software 商业能力**；开源版（Redis 8+）提供的是向量检索基础能力——Vector Set、HNSW/FLAT 向量索引、KNN/范围查询与元数据过滤（详见 [Vector Set](../02.Redis%20数据类型和命令/130.Vector%20Set%20向量集合.md)）。

# 开源版能做的：向量检索

Redis 开源版提供**两条**向量存储/查询路径，按数据形态选：

| 路径 | 底层类型 | 适合 | 核心命令 |
|------|----------|------|----------|
| **Vector Set**（8.0 原生） | 独立向量集合类型 | 一个对象一个向量、相似性搜索为主 | `VADD` / `VSIM` / `VLINK` / `VSETATTR` |
| **Query Engine（Search）** | 在 Hash/JSON 上建二级索引 | 向量 + 大量结构化字段联合过滤 | `FT.CREATE ... VECTOR` / `FT.SEARCH` |

**共同能力**

- **索引算法**：`FLAT`（暴力精确，小规模）与 `HNSW`（近似、大规模低延迟），`VSIM` 或查询时可选 `EF`/`EPS` 调精度-性能。
- **距离函数**：`L2`（欧氏）、`IP`（内积）、`COSINE`（余弦，文本嵌入最常用）。
- **KNN 与范围查询**：取 Top-K 最近邻，或"距离阈值内全部返回"。
- **元数据过滤**：先按标量字段（类别、时间、权限）过滤再算相似，或"后置过滤"，避免把不相关候选算进结果。

# 语义缓存与智能体记忆（概念）

> [!note] 归属提示
> 下列多为**商业能力**或需自建，此处讲**概念**，帮你判断"能不能用开源版拼出来"。

- **语义缓存**：把"问题→LLM 回答"以**向量**为键缓存；新问题先做向量相似检索，命中阈值内就直接返回缓存答案，省一次昂贵的 LLM 调用。开源版可用 **Vector Set + 应用层阈值**自行实现精简版；托管版是 LangCache。
- **智能体记忆**：
  - *短期/会话记忆*：用 Hash / List / Stream 存对话轮次，设 TTL 自然过期；
  - *长期记忆*：把历史事实向量化存入 Vector Set，检索时按语义召回，配合 `VLINK` 关联多向量对象。
- **RAG 检索链路**：文档切块 → 嵌入 → 存 Redis（向量 + 原文 + 元数据）→ 查询时向量召回 Top-K → 拼进 Prompt 交给 LLM。Redis 在其中承担**低延迟向量库 + 特征/缓存存储**。

# 典型场景

- **语义搜索 / 推荐**：商品、内容、图片以 embedding 入库，`COSINE` 近邻召回相似项。
- **RAG 知识库**：企业文档向量化，问答时检索增强，控制答案有据可依。
- **异常/相似检测**：把请求特征向量化，`VSIM` 找最相似的已知恶意样本做近重复判定。
- **LLM 成本治理**：语义缓存挡掉重复/近重复提问，显著降低 API 调用量。

# 避坑

- **别把商业能力当开源自带**：在自建/非 Cloud 环境指望 LangCache、Context Retriever、CDC 会直接碰壁——先确认部署形态（呼应上方能力边界）。
- **HNSW 是近似算法、不保证 100% 召回**：`M`/`EF` 太小会漏真近邻；对召回敏感的场景用 `FLAT` 或调大 `EF` 并用 `EPS` 控制精度（参数见 [Vector Set](../02.Redis%20数据类型和命令/130.Vector%20Set%20向量集合.md)）。
- **维度与距离函数要和嵌入模型对齐**：换 embedding 模型后旧向量与新查询向量不在同一空间，结果全废——模型升级要**重建索引**。
- **元数据过滤要防"过滤后候选不足"**：`FILTER` 是后置过滤，Top-K 里可能被滤到所剩无几；高选择率过滤要增大候选或用范围查询。
- **向量很吃内存**：百万级高维 float32 向量动辄数 GB，内存规划要单列；必要时用**量化/降维**（Vector Set 支持）压缩存储。
- **语义缓存的相似度阈值是双刃**：设太松会把"看着像但语义不同"的错误答案缓存命中（答非所问），要按业务容忍度校准并留人工兜底。

# 总结

用一句话给 Redis 在 AI 栈里定位：**它是"贴近在线链路的低延迟向量与特征存储"，不是离线训练平台**。开源版把**向量检索底座**（Vector Set / Search + HNSW/FLAT + 元数据过滤）给足，足以自建语义缓存与 RAG 召回；**语义缓存托管版、Context Retriever、CDC** 等是商业增值。选型三步：**① 确认部署形态能不能用某能力；② 数据以向量为主还是向量+结构化联合（决定 Vector Set 还是 Search）；③ 用 COSINE + HNSW 起步，再按召回/延迟调 EF/M**。
