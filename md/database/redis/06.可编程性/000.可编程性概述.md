# 概述

可编程性指**把逻辑下推到 Redis 服务端执行**，减少往返、保证一段操作的原子性。Redis 提供两条途径：**Lua 脚本**（EVAL）与 **Redis Functions**（7.0+，FCALL）。

- 归属与可用性：Lua 脚本为全版本核心能力；Redis Functions 为 **7.0+**
- 官方文档：<https://redis.io/docs/latest/develop/programmability/>

Redis 提供了一个编程接口，允许你在服务器端执行自定义脚本。脚本由 Redis 内置的**沙箱 Lua 解释器**执行（目前唯一支持的引擎就是 [Lua](https://www.lua.org/)）。在 Redis 7 及更高版本中，你还可用 **Redis Functions** 来管理和运行脚本；在 6.2 及更低版本，只能用 Lua 脚本 + `EVAL` 命令对服务器编程。

> [!tip] 脚本 vs 函数，怎么选
> **EVAL 脚本**：临时、按 SHA 缓存在内存、重启/`SCRIPT FLUSH` 即失效。**Functions**：命名、**持久化**（写入 AOF、复制到副本、重启仍在）、按库（library）管理。需要长期复用、跨重启存活的服务端逻辑用 Functions；一次性小逻辑用 EVAL。

# 原理

**为什么下推**

- **原子性**：一段脚本作为**单个命令**在服务端执行，中途绝不被其他客户端命令打断——这是"读-判断-写"（CAS）的正确姿势（对比 [020.事务与分布式锁](../08.工程化/020.事务与分布式锁.md) 里 WATCH 的乐观重试）。
- **省往返**：把多次网络往返压成一次请求，热路径上延迟收益明显。

**EVAL 家族**

- `EVAL script numkeys key [key ...] arg [arg ...]`：直接传脚本源码；脚本内通过 `KEYS[1..]`、`ARGV[1..]` 取参。
- `SCRIPT LOAD script` → 返回 SHA1；`EVALSHA sha1 numkeys ...`：只传 40 字节摘要，省带宽。
- `SCRIPT EXISTS/FLUSH/KILL`：查缓存、清空、中止。

**Functions 家族**

- `FUNCTION LOAD [REPLACE] code` 注册一个库（可含多个函数）；`FCALL fn numkeys ...` 调用，`FCALL_RO` 为只读版（可在副本执行）。
- `FUNCTION LIST/STATS/DELETE/DUMP/RESTORE/FLUSH/KILL`：管理与观测。

**Lua API（沙箱内可用的 redis.*）**

- `redis.call`（出错即中止脚本并向客户端报错）与 `redis.pcall`（出错返回 error 表，可捕获）；
- `redis.error_reply` / `redis.status_reply` 自定义回复；`redis.sha1hex`；`cjson`/`cmsgpack` 编解码；`redis.log` 写日志；`redis.set_repl` 控制脚本内是否立即复制。

**复制与确定性**

- 服务端会尽力把脚本的**效果（effects）**而非脚本本身复制给副本/写入 AOF，避免非确定性（如随机、时间）导致主从不一致；违反确定性约束时脚本会报错。脚本内随机请用 `math.random` 前 `redis.call('TIME')` 显式播种，或改用确定性写法。

# 命令与实操

**Lua 脚本：原子 CAS 扣库存**

```text
EVAL "local v = tonumber(redis.call('GET', KEYS[1]) or '0')
      if v >= tonumber(ARGV[1]) then return redis.call('DECRBY', KEYS[1], ARGV[1]) end
      return -1" 1 inventory 3
```

**缓存脚本 + EVALSHA 复用**

```bash
sha=$(redis-cli SCRIPT LOAD "return redis.call('GET', KEYS[1])")
redis-cli EVALSHA "$sha" 1 user:1001
# 命中 NOSCRIPT 时（缓存被清/副本切换）回退到 EVAL 重传，这是客户端库的常规兜底
```

**Redis Function：注册库并调用**

```text
FUNCTION LOAD "#LUA\nredis.register_function('ping_pong', function(keys, args) return 'pong:'..args[1] end)\n"
FCALL ping_pong 0 hello        # -> "pong:hello"
FUNCTION LIST withcode         # 查看已注册库与源码
FUNCTION DELETE <lib-name>
```

**集群下的脚本：KEYS 必须同槽**

```text
# 用 hash tag 让两个 key 落同一槽，否则报 CROSSSLOT / keys don't hash to the same slot
EVAL "return {redis.call('GET',KEYS[1]), redis.call('GET',KEYS[2])}" 2 {u:1001}:name {u:1001}:age
```

# 典型场景

- **分布式锁的安全释放**（`GET` 比对 value + `DEL` 原子，见 [020.事务与分布式锁](../08.工程化/020.事务与分布式锁.md)）。
- **限流/计数**：令牌桶、滑动窗口计数在脚本里原子读改写，避免并发超发。
- **带条件的更新**：库存扣减、余额冻结、"不存在才写"等 read-modify-write。
- **AI/检索管线里的组合操作**：向量近邻 + 过滤 + 回填一步到位（配合 [05.AI人工智能](../05.AI人工智能/000.AI人工智能概述.md)）。

# 避坑

- **脚本阻塞整个实例**：Lua 与命令执行同在单线程，**死循环或重计算脚本会让 Redis 卡住**所有请求。默认 `lua-time-limit`（5 秒）后其他命令收到 BUSY；用 `SCRIPT KILL`/`FUNCTION KILL` 中止——但若脚本**已写数据**，kill 会拒绝，只能 `SHUTDOWN NOSAVE` 兜底（呼应持久化篇）。
- **别在脚本里做慢操作或等外部 IO**：Lua 沙箱禁止访问网络/文件系统，也不要放 `SLEEP` 类逻辑。
- **`NOSCRIPT` 是常态不是 bug**：`EVALSHA` 可能因脚本缓存被逐出、副本升级为主后缓存空、`SCRIPT FLUSH` 而失败——客户端要捕获并回退 `EVAL` 重传（成熟驱动已内置）。
- **集群 KEYS 必须同槽**：脚本声明的所有 key 要落同一哈希槽，否则拒绝执行；跨槽需求用 hash tag 归并，或拆成多次调用（别为凑同槽把海量 key 塞一个 tag，见 [050.Cluster](../08.工程化/050.Cluster集群.md)）。
- **脚本要显式声明 KEYS**：把 key 当 `ARGV` 传进 `redis.call('GET', ARGV[1])` 会让集群路由/`CLUSTER KEYSLOT` 与 key 空间通知失灵——凡是 key 一律走 `KEYS[]`。
- **Functions 持久化的双刃**：Function 库会随 AOF/RDB 恢复、复制到副本，`FLUSHALL` 不清函数库（要 `FUNCTION FLUSH`）；升级/迁移时注意函数库与脚本引擎版本兼容。
- **随机/时间等非确定性**：直接依赖 `TIME`、`RANDOMKEY` 会破坏可复制的确定性，脚本被中止并报 `Can't write to script` 类错误；改由服务端算好后作参数传入。

# 总结

一句话：**"要原子 + 少往返"就下推**——一次性逻辑用 `EVAL`/`EVALSHA`，长期复用/需持久化用 **Functions**（7.0+）。三条铁律贯穿始终：**脚本必须短小且不阻塞**（否则拖垮单线程）、**key 一律走 `KEYS[]` 且集群下同槽**、**`EVALSHA` 要配 `NOSCRIPT` 回退**。它与事务/WATCH 解决同一类"并发正确性"问题，但脚本能表达"读后再决定写什么"，是 WATCH 乐观重试之外的更强手段。
