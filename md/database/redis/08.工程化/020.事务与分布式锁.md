# 概述

MULTI/EXEC/WATCH 事务、CAS（Lua）以及基于 SET NX PX 的分布式锁与 Redlock 争议。

- 归属与可用性：事务/Lua 为 Redis 开源核心能力；分布式锁是基于命令的用法模式（非专门机制）
- 官方文档：<https://redis.io/docs/latest/develop/interact/transactions/>、<https://redis.io/docs/latest/develop/reference/distributed-locks/>

一句话定位：**Redis 的单线程模型天然保证"单命令原子"，事务/Lua 把"多命令"也变原子；但 Redis 事务没有回滚、与关系库事务完全不是一回事。分布式锁则是"用 Redis 做跨进程互斥"的用法，它有正确的用法，也有公认的边界。**

# 原理

**事务（MULTI/EXEC）**

- `MULTI` 开启，后续命令**入队不执行**，`EXEC` 一次性原子执行整段；执行期间不会插入其他客户端命令。
- **没有回滚**：入队时语法错误的命令会让整个事务 `EXECABORT` 拒绝；但**运行期错误**（如对 String 键 `LPUSH`）只让该条失败，其余照常提交——这与 ACID 事务的根本差异必须记牢。
- `WATCH key`：乐观锁/CAS。`EXEC` 前若被 WATCH 的 key 变了，事务**放弃执行返回 nil**，由客户端重试；`UNWATCH` 取消。

**Lua 脚本（真正的原子 CAS）**

- `EVAL`/`EVALSHA` 把一段脚本作为**单个原子命令**在服务端执行，中途绝不被其他命令打断，可读改写回——这是"检查再操作"（CAS）的正确姿势。
- `SCRIPT LOAD` 缓存脚本返回 SHA1，`EVALSHA sha1 numkeys key...` 引用执行，省传输。详见 [06.可编程性](../06.可编程性/000.可编程性概述.md)。

**分布式锁**

- 互斥靠一条命令原子完成：`SET resource myrandomvalue NX PX 30000`——`NX` 只在不存在时设（获取）、`PX` 带过期（防死锁）、随机 value 标识持有者（安全释放）。
- 释放必须"判断是我的锁再删"，这是两步操作，**必须用 Lua 保证原子**，否则会误删别人续期后的锁。

# 配置与实操

**事务 + WATCH（乐观锁）**

```text
WATCH inventory
val = GET inventory          # 客户端读到当前值
MULTI
DECRBY inventory 1
EXEC                         # 若 inventory 在 WATCH 后被改，返回 nil（事务未执行），需重试
```

**Lua 原子 CAS（库存扣减，读-判-写一体）**

```text
EVAL "local v = tonumber(redis.call('GET', KEYS[1])) if v and v >= tonumber(ARGV[1]) then return redis.call('DECRBY', KEYS[1], ARGV[1]) else return -1 end" 1 inventory 3
```

**分布式锁：加锁 + Lua 安全解锁**

```text
# 加锁（客户端生成唯一随机值 client-id 作为 value）
SET lock:order:42 <client-id> NX PX 30000

# 解锁（Lua 保证"比较 + 删除"原子）
EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end" 1 lock:order:42 <client-id>
```

- 长任务需**看门狗（watchdog）** 在锁到期前用 Lua 续期（`PEXPIRE`）；或直接交给成熟客户端（Redisson 的 `RLock` 已内置续期与可重入）。

# 避坑

- **别把 Redis 事务当数据库事务**：无回滚、无隔离级别，运行期错误不会撤销已执行部分——需要"要么全成要么全败"的业务，得自己在应用层补偿。
- **`WATCH` 重试要设上限与退避**：热点 key 上 CAS 容易反复失败，无脑 `while(nil)` 重试会打满 CPU 并加剧冲突。
- **锁的过期时间是死线不是护栏**：`PX` 设 30s，但业务可能跑 35s——锁提前过期后被别人抢走，你释放时会（在未用 Lua 时）误删他人锁。**value 必须是唯一随机串，解锁必须走 Lua 比对**。
- **红锁（Redlock）别当免费午餐**：多节点加锁降低单点故障影响，但它依赖"进程暂停时间 << 锁 TTL"这一假设。Martin Kleppmann 的经典批评指出：GC/网络/OOM 造成的**长 STW 暂停**会让持锁者在锁已过期后仍以为自己持有，破坏互斥；用锁保证"正确性/ exactly-once"是不可靠的，需 fencing token（而 Redis 不提供单调递增 token 的强保证）。
- **锁只保证"尽量互斥"，不保证"不重复执行"**：对账、扣款等强正确性场景，锁之外还要数据库唯一约束 / 幂等键兜底；Redis 锁的正确定位是**效率优化（减少无谓竞争）而非正确性保证**。
- **单实例锁 ≠ 高可用**：主节点加锁后未及复制就宕机，锁会随数据丢失——要么接受"极端情况可能重复"，要么用 Redlock/上层方案，但都要清楚各自的代价。

# 总结

三层能力递进：单命令原子（天然）→ 多命令原子（事务，但无回滚）→ 读-判-写原子（Lua CAS，最灵活）。分布式锁是 Lua 原子性的一个典型应用，公式记死：`SET key <随机值> NX PX <ttl>` 加锁 + Lua 比对 value 解锁 + 看门狗续期。Redlock 的争议不是"能不能用"，而是"别拿它当强一致正确性保证"——**Redis 锁解决效率，正确性永远要业务侧幂等兜底**。
