# 概述

Redis Cluster 通过**哈希分片**把数据水平切到多个主节点，每主可带副本，实现写扩展与自动故障转移。

- 归属与可用性：Redis 开源核心能力（3.0 引入，随版本持续增强）
- 官方文档：<https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/>

一句话定位：**哨兵解决"单主的高可用"，Cluster 解决"单机装不下 / 单主写不动"。代价是：多 key 操作受限、客户端要懂重定向、运维复杂度陡增——能不上就别为了"看起来高级"而上。**

# 原理

**哈希槽（hash slots）**

- 全集群固定 **16384 个槽**，每个 key 经 `CRC16(key) mod 16384` 落到某槽，槽被分配给各个主节点。
- 增删节点 = **迁移槽**，不改 key 到槽的映射，只改"槽归谁"。

**MOVED 与 ASK 重定向**

- 客户端连到不含目标槽的节点：
  - **MOVED**：槽已永久属于别的节点，返回正确地址，客户端应更新本地槽映射缓存并重连。
  - **ASK**：槽**正在迁移**中，本次去那个节点问，但不更新缓存（临时转向）。
- 智能客户端（cluster-aware）缓存 slot→node 表，直连正确节点，靠 MOVED 自我纠偏。

**cluster name / 节点总线**

- 节点间通过**集群总线**（数据端口 + 10000）用 Gossip 通信、故障检测、配置协商。
- `CLUSTER MEET` 互相握手成环；故障判定与哨兵类似（主观 PFAIL → 客观多数确认），多数主下线即整集群 `fail`（可读可写全停，除非开 `cluster-require-full-coverage no`）。

# 配置与实操

**开启集群（redis.conf 关键项）**

```bash
cluster-enabled yes
cluster-config-file nodes-6379.conf   # 节点自动维护，勿手改
cluster-node-timeout 15000
appendonly yes                        # 集群推荐开 AOF
protected-mode no                     # 跨机组建时（生产用 bind+防火墙替代，别裸奔）
cluster-require-full-coverage no      # 部分槽不可用时其余槽仍可服务
```

**创建集群（redis-cli 原子化，5.0+ / redis-cli 工具）**

```bash
# 3 主 3 从示例：--cluster-yes 免交互确认
redis-cli --cluster create 10.0.0.1:6379 10.0.0.2:6379 10.0.0.3:6379 \
  10.0.0.4:6379 10.0.0.5:6379 10.0.0.6:6379 --cluster-replicas 1 --cluster-yes
```

**运维命令**

```bash
redis-cli -c -p 6379 CLUSTER INFO        # 或用 redis-cli --cluster-info
redis-cli --cluster check 10.0.0.1:6379  # 槽覆盖/副本健康体检
redis-cli -p 6379 CLUSTER KEYSLOT mykey  # 看某 key 落哪个槽
# 扩缩容：迁移槽（reshard 交互式）
redis-cli --cluster reshard 10.0.0.1:6379
redis-cli --cluster rebalance 10.0.0.1:6379   # 自动均衡槽分布
```

**多 key 操作：用 hash tag 归到同槽**

```text
# {user} 是 hash tag，槽由 {} 内内容决定 → 两 key 落同一槽，才能进同一多键命令/事务
SET {user:1001}:name  zf
SET {user:1001}:age   30
```

# 避坑

- **跨槽多 key 命令直接报 `CROSSSLOT`**：`MSET`/`SINTERSTORE`/多 key `DEL`/事务里的多 key，必须**同槽**——用 **hash tag `{...}`** 强制归槽。但别把太多 key 塞进同一 tag，否则槽均衡失效、单节点被打爆（人为造热 key）。
- **`SELECT` 多 db / `FLUSHDB db N` 不可用**：集群只有 **db0**，`redis-cli -n 2` 在集群下无效——依赖多库隔离的设计要重构为 key 前缀。
- **只开 2 主 0 从别叫"高可用"**：无副本则主挂即该段槽全丢服务；每主至少 1 副本才有故障转移。官方建议**最小生产拓扑是 3 主 3 从**。
- **`cluster-require-full-coverage` 的两难**：默认 `yes` 时任一槽不可用整集群拒写；设 `no` 可局部降级但业务要能容忍部分 key 报错——按一致性预期显式决定，别用默认撞运气。
- **客户端必须是 cluster-aware**：普通单机客户端遇到 MOVED 不会自动重定向，表现为大面积 `MOVED` 错误。选型时确认驱动支持 Cluster（Jedis Cluster、Lettuce Cluster、go-redis 等）。
- **迁移/扩缩容期间的性能抖动**：`reshard` 搬槽会占用源/目标节点带宽与 CPU，且短暂出现 ASK 重定向；大集群迁移要限流、避开高峰。
- **监控要下钻到节点与槽**：只看一个入口节点会漏判——`CLUSTER SLOTS`/`--cluster check`、各节点 `INFO`、`instantaneous_ops_per_sec` 都要采（呼应 [070.大key与热key](./070.大key与热key.md)）。
- **总线端口（+10000）没开**：只放行 6379 会导致节点无法组环、集群"各节点看着对方都 down"。跨机部署务必同时放行 `端口` 和 `端口+10000`。

# 总结

Cluster 用 16384 槽 + Gossip 总线把"水平扩展 + 自动转移"打包，代价是**编程模型收窄**（单 db、跨槽多 key 受限、需 hash tag）和**运维复杂度上升**。判断线：**读扩展用主从副本、单主高可用用哨兵、只有"容量或写吞吐超单机"才上 Cluster**。落地四件事：3 主 3 从起步、放行总线端口、客户端选 cluster-aware、用 `--cluster check` 常态化体检。
