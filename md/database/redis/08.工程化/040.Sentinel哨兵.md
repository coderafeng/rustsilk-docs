# 概述

Sentinel（哨兵）在主从之上提供监控、通知与**自动故障转移**，并帮客户端发现当前主节点。

- 归属与可用性：Redis 开源核心能力（Sentinel V2，5.0+ 稳定）
- 官方文档：<https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/>

一句话定位：**主从解决"有没有副本"，哨兵解决"主挂了谁来当新主、客户端怎么知道"。它不改数据通路，只做"看门 + 投票 + 改选 + 告知"。**

# 原理

**哨兵做四件事**

1. **监控（Monitoring）**：每个 Sentinel 每秒 PING 主、副本和其他 Sentinel，感知存活。
2. **通知（Notification）**：故障、转移完成等事件通过发布订阅（`+switch-master` 频道）推给客户端/运维。
3. **自动故障转移（Failover）**：主被判定失效后，选一个副本提升为新主，让其余副本改挂新主，并持续同步拓扑。
4. **配置提供（Client notification）**：客户端连哨兵问"现在主是谁"（`SENTINEL get-master-addr-by-name`），拿到地址后再连真正的 Redis 主。

**主观下行 vs 客观下行（SDOWN / ODOWN）**

- **SDOWN（主观下行）**：单个 Sentinel 在 `down-after-milliseconds` 内没收到有效回复，自己认为主挂了。
- **ODOWN（客观下行）**：足够多（达到 quorum）的 Sentinel 都 SDOWN，才共识"主真的挂了"——**避免单哨兵误判**。
- 判定 ODOWN 后，Sentinel 之间通过 Raft 风格选举出一个 **leader Sentinel** 来执行故障转移。

**quorum 的含义**

- `sentinel monitor mymaster <ip> <port> <quorum>`：quorum 是"判定 ODOWN 所需的 Sentinel 数量"，**不是**"故障转移需要多少哨兵投票同意"，也**不是**多数派写入。
- 哨兵本身要**奇数个（≥3）**部署，避免自身选举脑裂。

# 配置与实操

**sentinel.conf（最小可用）**

```bash
port 26379
sentinel monitor mymaster 127.0.0.1 6379 2   # 名字 mymaster；主地址；quorum=2
sentinel down-after-milliseconds mymaster 5000  # 5 秒无响应即 SDOWN
sentinel failover-timeout mymaster 60000        # 故障转移超时/重试间隔
sentinel parallel-syncs mymaster 1              # 转移后同时向新主全量同步的副本数
# 主开了密码时：
sentinel auth-pass mymaster <master-password>
dir /var/lib/redis-sentinel
logfile "/var/log/redis/sentinel.log"
```

**启动与观测**

```bash
redis-sentinel /etc/redis/sentinel.conf     # 或 redis-server sentinel.conf --sentinel
redis-cli -p 26379 SENTINEL masters
redis-cli -p 26379 SENTINEL master mymaster
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster   # 客户端就问这个
redis-cli -p 26379 SENTINEL replicas mymaster
redis-cli -p 26379 PUBLISH +switch-master '*'   # 订阅拓扑变更
```

> [!tip] 客户端怎么接
> 别让业务硬编码主地址。用支持 Sentinel 的客户端（Jedis/Lettuce/Redisson/go-redis 等），配置哨兵列表，由库自动 `get-master-addr-by-name` 并在转移时重连。

# 避坑

- **哨兵数量别是偶数、别只部署 1 个**：单哨兵 = 它挂了整个高可用就没了；2 个哨兵在彼此失联时无法达成 quorum。生产标准是 **3 个及以上、跨机架/可用区**。
- **quorum ≠ 故障转移多数派**：达到 quorum 只代表"认可主下线"，能否成功转移还要求**多数 Sentinel 在线并选出 leader**。只调低 quorum 会让误判概率上升。
- **`parallel-syncs` 调大会引发读空窗**：转移后若多个副本同时全量同步，它们短暂不可用，读流量全压到剩余节点——一般设 1，牺牲转移速度换稳定。
- **客户端超时设置与 `down-after` 不匹配 → 抖动放大**：`down-after` 太短，网络一抖就触发转移；太长则真故障恢复慢。要与业务容忍度、网络质量一起权衡。
- **哨兵不解决脑裂的数据丢失**：故障转移期间旧主可能已接受写却未被新主复制，切主后这部分写丢失——哨兵提供的是**可用性**，不是**强一致**。需要更少丢失可配合 `min-replicas-to-write`（见 [030.主从复制](./030.主从复制.md)）。
- **配置被哨兵自写回**：Sentinel 会把自己发现拓扑**改写回 sentinel.conf**（`sentinel known replica ...` 等行）。容器化部署若把该文件挂成只读会启动失败——要给哨兵可写目录或用独立 configmap。
- **TLS/认证要三处一致**：客户端→哨兵、哨兵→哨兵（`sentinel resolve-hostnames`、TLS 端口）、哨兵→Redis（`auth-pass`）任一处配错都会"哨兵看着主但从不上 ODOWN 或无法操作"。

# 总结

哨兵 = 监控 + 投票（SDOWN→ODOWN）+ 选 leader + 自动改选主 + 告知客户端。它把"主挂了要人肉切"变成"秒级自动切"，代价是**只提供可用性、不保证零丢失**。落地三条铁律：**哨兵 ≥3 且奇数、跨故障域部署、客户端走 `get-master-addr-by-name` 而非硬编码**。数据量大到单机扛不住写时，哨兵就不再是答案——那是 [050.Cluster 集群](./050.Cluster集群.md) 的领域。
