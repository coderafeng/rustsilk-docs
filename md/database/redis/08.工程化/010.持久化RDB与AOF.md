# 概述

RDB 快照与 AOF 日志两种持久化机制的原理、配置与选型（含混合持久化）。

- 归属与可用性：Redis 开源核心能力（全版本）
- 官方文档：<https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/>

一句话定位：**RDB 管"恢复快"，AOF 管"丢得少"，混合持久化把两者拼成默认最优解**。它们都不是备份——是进程重启后数据不裸奔的兜底机制，跨实例的数据搬迁仍要靠 [030.主从复制](./030.主从复制.md)。

# 原理

**RDB（Redis Database）**

- 某一时刻全量数据集的二进制压缩快照，文件即 `dump.rdb`。
- 触发：`SAVE`（主线程阻塞，几乎不用）/ `BGSAVE`（fork 子进程写）；或 `save <秒> <变化数>` 规则自动触发后台快照；复制全量同步、 shutdown 也会生成。
- fork 后子进程共享内存页，靠 **COW（Copy-On-Write）** 读取一致性快照；父进程期间写入才触发页复制。
- 恢复时直接内存映射加载，**比 AOF 重放快一个量级**。

**AOF（Append Only File）**

- 把每条写命令以协议格式追加进 `appendonly.aof`，重启时**重放命令**重建数据。
- 刷盘策略 `appendfsync`：`always`（每命令 fsync，最安全最慢）、`everysec`（默认，最多丢 1 秒）、`no`（交给 OS，性能最好最不可靠）。
- 文件单调膨胀，靠 **AOF 重写（`BGREWRITEAOF`）** 压缩：把多条命令合并成能表达最终数据集的最小命令集（如多次 `INCR` 合成一条 `SET`）。

**混合持久化（`aof-use-rdb-preamble`，4.0+，6.2 起默认开）**

- AOF 重写时，文件**基座用 RDB 二进制格式**（负责快速加载），重写期间的**增量命令用 AOF 文本**追加在尾部（负责少丢数据）。
- 兼顾两者优点，是当前默认推荐形态。

# 配置与实操

**RDB**

```bash
# save <秒> <key 变化数>：满足任一条件即触发 BGSAVE；注释掉或 save "" 关闭自动快照
save 3600 1 300 100 60 10000
stop-writes-on-bgsave-error yes     # 快照失败时拒绝写入，防止"以为在持久化其实没落盘"
rdbcompression yes                  # LZF 压缩
rdbchecksum yes                     # 尾部校验和
dbfilename dump.rdb
dir /var/lib/redis                  # 落盘目录（所有持久化文件的锚点）
```

**AOF**

```bash
appendonly yes                      # 打开 AOF（改此值需重启）
appendfilename "appendonly.aof"
appendfsync everysec                # always | everysec | no
auto-aof-rewrite-percentage 100     # 相比上次重写后增长 100% 触发
auto-aof-rewrite-min-size 64mb      # 且文件不小于此值才自动重写
aof-use-rdb-preamble yes            # 混合持久化（默认已开）
aof-load-truncated yes              # 重启遇到残缺 AOF 时尽量加载到最后可用命令
```

**观测与手动操作**

```bash
redis-cli INFO persistence | grep -E 'rdb_last_save_time|rdb_changes_since_last_save|aof_enabled|aof_delayed_fsync'
redis-cli BGSAVE                    # 手动触发后台快照
redis-cli LASTSAVE                  # 最近快照的时间戳
redis-cli CONFIG SET appendfsync no # 大批量导入临时关刷盘，导完再改回 everysec
```

# 避坑

- **fork 是延迟毛刺的头号来源**：大内存实例 fork 需复制页表，可能阻塞主线程数百毫秒到秒级；且快照期间高写入触发大量 COW，瞬时内存可逼近翻倍——`maxmemory` 要给容器留余量（呼应 [050.Redis配置](../01.Redis%20起步/050.Redis配置.md)）。
- **`stop-writes-on-bgsave-error yes` 是把双刃剑**：磁盘满/权限错导致 BGSAVE 失败时，实例会拒绝一切写入（业务侧表现为大面积报错）——这是保护而非 bug，要配合磁盘监控。
- **AOF `everysec` 仍有 1 秒窗口**：宣称"开了持久化就零丢失"是错的；要求零丢失需 `always` + 半同步语义，而 Redis 复制本身是异步的（见 [030.主从复制](./030.主从复制.md)），真正的强一致要靠架构兜底。
- **只开 RDB 关掉 AOF = 丢一个快照周期的数据**：默认 `save` 规则最密也到 60 秒，分钟级数据丢失对某些业务不可接受——生产常"两者都开、走混合持久化"。
- **AOF 关闭又开启的切换坑**：`appendonly no→yes` 运行中实例需重启才完全生效；老数据没有 AOF 基线，混合持久化要等第一次 `BGREWRITEAOF` 才成型。
- **别把 `dump.rdb` 当备份策略**：单文件、无历史版本；要 PITR/多副本得把 RDB/AOF 定时拷贝到对象存储，或用商业版的云备份能力。

# 总结

持久化选型的决策树：能容忍分钟级丢失、追求恢复速度 → RDB；要秒级持久性 → AOF（`everysec`）；两者都要 → 混合持久化（默认即可）。所有配置的地基是 `dir` 隔离与磁盘容量监控——**fork 内存放大**和 **`stop-writes-on-bgsave-error`** 是最常踩的两个生产坑。持久化解决的是"单机重启不裸奔"，跨机可靠归复制与哨兵/集群（[030](./030.主从复制.md)~[050](./050.Cluster集群.md)），别用它背高可用的锅。
