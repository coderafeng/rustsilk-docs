# 概述

**大 key**（单 value 体积/元素数过大）与**热 key**（单 key 访问频次畸高）是两类高频性能事故源。本篇讲如何用命令发现、如何治理。

- 归属与可用性：`--bigkeys`/`MEMORY USAGE`/`--hotkeys` 全版本；服务端 `HOTKEYS` 命令为 **Redis 8.6+**（本地 [10 章 8.6](../10.Redis%20版本特性/070.Redis8.6.md#概述) 已记录）
- 官方文档：<https://redis.io/docs/latest/operate/oss_and_stack/management/analysis/>

一句话定位：**大 key 是"太重"——一次操作就拖慢单线程；热 key 是"太挤"——访问量集中到单点。两者独立（可以小但热、大但冷），治理思路完全不同，别混为一谈。**

# 原理

**大 key 为什么危险**

- Redis 单线程执行命令：一个 `HGETALL` 命中含百万字段的 Hash、或 `DEL` 一个几百 MB 的 key，会**独占主线程**阻塞所有其他请求；删除大 key 的内存回收同样卡顿（需 `UNLINK` 异步化）。
- 复制/持久化：大 key 让全量同步的 RDB 传输、AOF 重写更重；网络带宽被单 key 打满。
- 内存不均：集群下大 key 落在某一分片，造成**单节点内存/CPU 畸高**，槽再平衡也搬不动（键不可拆分）。

**热 key 为什么危险**

- 单 key 每秒被读几万/几十万次：读本身是内存访问不算慢，**灾难在伴随效应**——该 key 的命令在事件循环里高频排队，把单线程串行瓶颈暴露无遗；集群下热点集中在**承载它的那一个分片**，其余节点空闲，资源利用率畸形。
- 伴随写操作的热 key（秒杀扣库存、计数器）更危险：写阻塞同线程其他命令，易触发客户端超时重试雪崩，甚至被哨兵/集群误判节点故障而错误转移。

# 配置与实操

**发现大 key**

```bash
redis-cli --bigkeys                        # SCAN 采样，按类型报告各自"最大" key（不阻塞，但只给每类 top1）
redis-cli --memkeys                        # 类似遍历，报告 key 的内存占用排行思路
MEMORY USAGE product:detail                # 精确测单个 key 字节数
OBJECT ENCODING mykey                      # 看编码（ziplist/listpack 退化说明元素多）
HLEN / ZCARD / SCARD / LLEN <key>          # 元素数量维度评估"逻辑大小"
# 8.6+：key 内存大小直方图指标 db0_distrib_*_sizes（INFO）按类型看分布
```

**发现热 key**

```bash
# 传统：需把淘汰策略设为 LFU，再采样扫描（会"为了体检改体质"）
redis-cli --hotkeys                        # 仅 allkeys-lfu / volatile-lfu 下可用，基于 LFU 计数器
OBJECT FREQ mykey                          # LFU 频次计数（同样依赖 LFU 策略）

# Redis 8.6+ 原生 HOTKEYS：不强制切 LFU，服务端内置追踪（子命令语法以官方文档为准）
redis-cli HOTKEYS                          # 实时返回访问最频繁的 key 列表
# 典型用法：作为"告警触发后的诊断工具"临时跑一次，而非高频轮询（轮询会退化成像 MONITOR 的开销）

# 通用旁路：INFO 里的瞬时指标定位嫌疑段
redis-cli INFO stats | grep instantaneous_ops_per_sec
SLOWLOG GET 20                             # 慢查询常指向大 key 操作
MONITOR                                    # 全量命令流，性能杀手，仅限本地临时诊断，禁用于生产
```

**治理大 key**

```text
拆分：把大 Hash 按字段哈希成 user:1001:h0 ~ hN 多个小 Hash；大 List 分段
异步删：用 UNLINK 代替 DEL（后台 lazyfree 回收，不阻塞主线程）
换结构/瘦身：只存必要字段；大 value 压缩后再存；集合设上限 + 定期裁剪（LRANGE + LTRIM）
```

**治理热 key**

```text
分片：hot:product:1001 -> hot:product:1001:{0..9}，读时随机落到一个副本分片，写时聚合
多级缓存：应用本地缓存（Caffeine）挡在最前，Redis 只兜本地 miss
读写分离：热读打到多个只读副本（见 030 主从）
请求合并：单飞（singleflight）把并发同 key 回源合并为一次
```

# 避坑

- **`--bigkeys` 只给"每种类型最大的一个"，不是全量排行**：它会 SCAN 全库但按类型报告 top1，且对大 key 的"大小"按元素数而非字节估——定位到嫌疑 key 后要用 `MEMORY USAGE` 复核真实字节。别把它当精确报表。
- **`redis-cli --hotkeys` 的前提是 LFU**：默认 LRU/noeviction 下它返回空或不可用；而为了查热 key 去把线上实例改成 `allkeys-lfu` 属于"为了体检改体质"——**8.6+ 优先用原生 `HOTKEYS`**，或走代理层/客户端埋点统计。
- **`MONITOR` 生产禁用**：它把每条命令广播给 monitor 客户端，高 QPS 下严重拖慢服务端甚至打满带宽，只能用于秒级临时诊断。
- **集群下要逐节点查**：`--bigkeys`/`--hotkeys`/`HOTKEYS` 只反映连接的**单个节点**；热点/大键可能只在某分片，需在每个 master 分别执行或用 `--cluster` 工具遍历。
- **`DEL` 大 key 会阻塞**：删除百万元素集合是 O(N) 主线程操作——一律用 `UNLINK`（异步）或 `SCAN` 分批删；这正是"发现大 key → 删除时又造一次事故"的经典连环坑。
- **热 key 拆分要防"合并不一致"**：把计数分散到 `{0..9}` 分片后，读总量需 `MGET`/累加所有分片，写入与统计口径要一起改，否则读数失真。
- **别用 hash tag 制造人为热点**：集群里 `{xxx}` 会把 key 聚到同槽——给热 key 加统一 tag 等于主动把压力焊死在一个节点（呼应 [050.Cluster](./050.Cluster集群.md)）。

# 总结

两条正交的治理线：**大 key 治"重量"**——`--bigkeys`+`MEMORY USAGE` 发现，拆分 + `UNLINK` 异步删 + 结构瘦身；**热 key 治"集中度"**——LFU/`HOTKEYS`（8.6+ 首选）/代理统计发现，分片 + 多级缓存 + 读写分离 + 请求合并。共同红线：**发现类命令（`--bigkeys`/`--hotkeys`）本身要低侵入、逐节点跑，删除永远走 `UNLINK`，绝不用 `MONITOR` 硬扫生产**。
