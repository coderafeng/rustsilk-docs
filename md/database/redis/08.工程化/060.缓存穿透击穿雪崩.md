# 概述

三大缓存故障的成因与防护：**穿透**（查不存在的 key）、**击穿**（单个热点 key 过期）、**雪崩**（大批 key 同时过期 / 实例宕机）。

- 归属与可用性：应用架构与 Redis 命令/概率结构（[布隆过滤器](../02.Redis%20数据类型和命令/150.Bloom%20Filter%20布隆过滤器.md)）结合的治理模式
- 官方文档：<https://redis.io/docs/latest/develop/>（缓存模式为工程实践，非单一命令）

一句话定位：**三者都是"缓存没挡住请求，压力砸到数据库"，区别只在"为什么没挡住"。分清成因，防护手段才对得上。**

# 原理

**缓存穿透（Penetration）**

- 现象：请求的 key **在缓存和数据库里都不存在**（如查 id=-1、乱造的手机号），缓存永远 miss，每次都会击穿到 DB。
- 危害：恶意刷不存在的 key，等于绕过缓存直接打死数据库。
- 成因关键词：**数据根本不存在**。

**缓存击穿（Breakdown / hot key expiry）**

- 现象：某个**热点 key 突然过期**的瞬间，海量并发同时 miss，一起涌向 DB 去"重建"这一个 key。
- 与穿透区别：击穿的数据**是存在的**，只是缓存恰好失效那一瞬。
- 成因关键词：**单个热 key 的过期空窗**。

**缓存雪崩（Avalanche）**

- 现象：**大量 key 在同一时刻集体过期**，或**缓存实例整体宕机**，瞬时全部请求回源 DB，DB 连接被打满、连锁超时，雪崩式扩散。
- 与击穿区别：击穿是"一个 key"，雪崩是"一片 key / 整个缓存层"。
- 成因关键词：**过期时间高度集中 or 缓存不可用**。

# 配置与实操

**穿透 → 空值缓存 + 布隆过滤器**

```text
# 方案 A：缓存空对象（短 TTL），实现最简单
GET product:-1            -> (nil)
# 回源 DB 仍无数据时：
SET product:-1 "" EX 60   # 缓存一个空标记，用较短过期，防内存膨胀

# 方案 B：布隆过滤器前置拦截"一定不存在"的 key（详见 02 章 Bloom Filter）
BF.ADD  bloom:product_ids  1001 1002 1003
BF.EXISTS bloom:product_ids -1    # -> 0（不存在，直接拒绝，根本不碰 DB）
```

**击穿 → 互斥重建 or 逻辑过期**

```text
# 互斥锁重建：只放一个请求去回源，其余等待
SET lock:product:1001 <cid> NX PX 5000     # 抢到锁者查 DB 回填并 DEL 锁
# 逻辑过期：value 内嵌 expire_at，不设真实 TTL；发现"逻辑过期"的单个请求异步刷新，其余读旧值
```

**雪崩 → 过期打散 + 高可用 + 限流兜底**

```text
# 过期时间加随机抖动，避免同刻集体失效
SET product:1001 <json> EX 3600            # 改为 EX (3600 + rand(0,300))
```

- 高可用：主从 + 哨兵 / Cluster，别让缓存层单点宕机（见 [030](./030.主从复制.md)~[050](./050.Cluster集群.md)）；
- 限流熔断：DB 侧设连接上限与熔断（Sentinel/Hystrix/Resilience4j），回源被打满时快速失败而非无限堆积；
- 多级缓存：本地缓存（Caffeine）挡在最前，减轻 Redis 与 DB 压力（呼应 [070.大key与热key](./070.大key与热key.md)）。

# 避坑

- **空值缓存要设短 TTL 并限长**：给"不存在"也缓存正 TTL，会让真实数据上线后长期读到空——空标记用**较短过期**（几十秒）。
- **布隆过滤器有误判率、且不支持删除**：`BF.EXISTS` 返回"存在"可能是假阳性（仍会放行到 DB，只是概率可控）；返回"不存在"才 100% 可信。数据会大量删除的场景要用 [Cuckoo Filter](../02.Redis%20数据类型和命令/160.Cuckoo%20Filter%20布谷鸟过滤器.md)。
- **互斥重建别死锁**：重建锁必须带 `PX` 过期，回源失败也要能释放，否则一个请求卡住 = 该 key 永久不可用。
- **逻辑过期牺牲强一致**：它读到的是"逻辑上已过期"的旧值，适合能容忍短暂陈旧的场景（商品详情），不适合强一致读（余额）。
- **随机抖动量级要够**：`3600 + rand(0,5)` 抖动窗口太小仍可能集中；按缓存总量与 QPS 估一个能真正打散峰值的抖动区间。
- **雪崩的"整层宕机"分支不是 TTL 能解决的**：再散的过期时间也扛不住 Redis 全挂，必须靠**高可用架构 + DB 限流 + 降级预案**（返回兜底/静态值）组合。
- **别只盯缓存不看 DB 连接池**：三者的最终杀伤都体现在 DB 被打满，DB 侧的 max connections、慢查询、超时是最后一道闸，要一并压测设定。

# 总结

一张对应表收尾：**穿透→数据不存在→空值缓存/布隆过滤器；击穿→热 key 过期→互斥重建/逻辑过期；雪崩→集中过期或整层宕机→TTL 打散/高可用/限流降级**。共同心法：让"回源"这件事**要么不发生（前置拦截）、要么只发生一次（互斥）、要么被摊平（打散 + 限流）**。所有防护的兜底都是数据库侧的限流熔断——缓存治理永远要连 DB 保护一起设计。
