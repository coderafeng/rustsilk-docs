# 概述

Zed 由 Atom 与 Tree-sitter 的作者 Nathan Sobo 团队打造，目标是做一款「从头设计、性能优先」的代码编辑器。理解它的设计取舍，能帮你在遇到「和 VS Code 不一样」的地方时不再困惑。

## Zed 是什么

一句话概括：**Zed = 高性能原生编辑器 + 内置 AI Agent + 内置实时协作**。

它不是 VS Code 的插件宿主，也不是 Electron 应用，而是一个用 Rust 编写、直接调用 GPU 渲染的原生程序。它同时是一个「文本编辑器」和「轻量 IDE」——通过 LSP（Language Server Protocol）获得跳转、补全、诊断、重构等 IDE 能力，通过 Tree-sitter 获得精准的语法高亮与结构化选择。

## 为什么这么快：gpui

Zed 自研了一套 GPU 加速的 UI 框架 **gpui**（读作 "gooey"）。传统编辑器（如 VS Code）基于 Electron + Chromium，界面本质是网页，渲染经过多层抽象；而 gpui 直接用 Rust 把界面绘制指令提交给 GPU，跳过了浏览器引擎的开销。

gpui 带来的直接体感：

- **启动快**：冷启动通常在亚秒级。
- **输入零延迟**：按键到屏幕渲染的延迟极低，长文件滚动不卡顿。
- **多线程**：解析、渲染、语言服务在不同核心上并行，界面线程不被阻塞。

> [!note] gpui 不只是 Zed 的内部实现
> gpui 已经被抽取为可复用的 Rust GUI 框架，社区有用它构建独立桌面应用的尝试。本站 [GUI > GPUI Kit](../../../gui/gpui-kit/index.md) 章节即关注这一生态。

## 语法与智能：Tree-sitter + LSP

Zed 的代码理解能力来自两套标准技术的组合：

| 技术 | 作用 | 在 Zed 中的体现 |
|------|------|----------------|
| **Tree-sitter** | 增量式语法解析，生成语法树 | 语法高亮、结构化选择（`Alt+↑/↓` 按语法块选择）、代码折叠、Vim 模式的语义 motion |
| **LSP** | 语言服务器协议，与外部语言服务通信 | 跳转定义、查找引用、补全、诊断、重命名、code action、格式化 |

这就是为什么 Zed 的 Vim 模式比普通模拟更「聪明」——例如在 Rust 中用 `%` 跳转到匹配括号时，它能识别管道符 `|`；在 JavaScript 中 `w`（word motion）会把 `$` 当作单词字符。这些都依赖 Tree-sitter 的语法树。

## 与传统编辑器的核心区别

| 维度 | VS Code / IDEA | Zed |
|------|----------------|-----|
| 运行时 | Electron / JVM | 原生 Rust + gpui（GPU 渲染） |
| 扩展生态 | 极其庞大 | 精简，聚焦语言/主题/调试器，很多能力内置 |
| 协作 | 需要插件（Live Share 等） | 内置 Channels、语音、共享光标 |
| AI | 需要插件（Copilot 等） | 内置 Agent Panel、Inline Assistant、Edit Prediction |
| 编辑范式 | 非模态为主 | 非模态默认，但一等公民支持 Vim / Helix 模态编辑 |
| 配置方式 | GUI 设置界面为主 | `settings.json`（JSONC）为主，设置编辑器为辅 |

## 内置即开箱的能力

以下在 VS Code 里通常要装插件，在 Zed 里是内置的：

- 实时协作（语音 + 光标共享）
- AI 编码助手（Agent、Inline Assistant、Edit Prediction）
- 集成终端面板
- 项目级模糊搜索
- 基于 JSON 配置的 Task runner
- 通过 LSP 的内联诊断与 code action

## 适合谁 / 不适合谁

**适合**：追求极致响应速度、喜欢键盘流 / Vim、需要原生 AI 与协作、主要写 Rust/Go/TypeScript/Python 等主流语言的开发者。

**需要斟酌**：重度依赖某个冷门 VS Code 插件（如特定 DevOps、容器、测试运行器 UI）、需要完整中文界面、或依赖 JetBrains 系深度重构能力的用户——Zed 的扩展目录仍在成长，功能覆盖尚不如前两者全面。
