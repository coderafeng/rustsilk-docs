# 概述

Ubuntu 上的生产安装，我的习惯是**源码编译，把整套东西收进一个目录**：`/opt/openresty`。不走官方 APT 仓库，布局哲学是**多版本目录 + 配置随版本走 + 原子切换/回滚**，三条原则：

1. **配置随版本走**——程序与配置是一个整体，全部进 `app/versions/<版本号>/`。编译时**不指定 `--conf-path`**，配置就落在默认的 `versions/<ver>/nginx/conf/` 里；版本目录连同它携带的配置，构成一个完整、可直接回滚的单元。
2. **入口稳定**——对外只暴露 `app/current` 与 `sbin/openresty` 两个软链接，systemd 单元、运维脚本永远引用这两个稳定路径，升级与回滚只切链接、不改任何配置。
3. **可变状态与共享资源外置**——日志、PID、证书这三类"不该随版本搬家"的东西放在版本目录之外（`logs/`、`run/`、`cert/`），配置里一律写绝对路径引用，跨版本共享。

要点速览：

| 项目 | 值 |
|------|---|
| 安装根目录 | `/opt/openresty` |
| 版本目录 | `/opt/openresty/app/versions/1.31.8.1`（程序 + 配置，不可变单元） |
| 主配置 | `/opt/openresty/app/versions/1.31.8.1/nginx/conf/nginx.conf`（默认路径，未指定 `--conf-path`） |
| 版本入口 | `/opt/openresty/app/current -> app/versions/1.31.8.1`（软链接） |
| 命令入口 | `/opt/openresty/sbin/openresty -> app/current/bin/openresty`（软链接） |
| 错误日志 | `/opt/openresty/logs/error.log`（`--error-log-path` 指定，跨版本共享） |
| PID 文件 | `/opt/openresty/run/nginx.pid`（`--pid-path` 指定，跨版本共享） |
| 证书/密钥 | `/opt/openresty/cert/`（跨版本共享，conf 内绝对路径引用，升级不动） |
| systemd 单元 | `/etc/systemd/system/openresty.service` |

> [!note]
> 为什么配置不共用？共用一份配置 + 原地修改，意味着**回滚程序时配置回不了滚**——旧二进制配上新改过的配置，兼容性全靠运气。配置随版本走之后，`current` 一拨，程序、配置、`conf.d/`、`lua/` 一起回到过去，这才是完整的可逆。代价是升级时必须走一遍**配置迁移**（渲染 + diff + `-t` + 灰度），见下文升级流程。

# 目录布局

目标结构（版本目录内多展开一层，标出配置的默认落点）：

```text
/opt/openresty
├── app
│   ├── current -> /opt/openresty/app/versions/1.31.8.1
│   └── versions
│       └── 1.31.8.1
│           ├── bin                  # openresty 主程序、opm、resty 等
│           ├── luajit               # 随源码树构建的 LuaJIT2（openresty fork）
│           ├── lualib               # lua-resty-* 库（随版本走）
│           ├── nginx
│           │   ├── conf             # ★ 默认配置目录：nginx.conf、conf.d/、lua/
│           │   ├── html             # 默认页
│           │   └── sbin             # nginx 核心二进制
│           ├── pod                  # 文档
│           └── site                 # site 工具
├── cert                             # 证书/私钥，跨版本共享，升级不动
├── logs                             # access/error 日志，跨版本共享
├── run                              # nginx.pid（及升级期的 nginx.pid.oldbin）
└── sbin                             # 对外命令入口（软链接）
```

职责一句话版：`versions/<ver>/` 回答"装的是什么、怎么配的"；`cert/logs/run` 是运行状态与共享资源，谁版本上位都接着用同一份；`current` 与 `sbin/` 回答"别人怎么调用我"。任何调用方只允许引用 `sbin/openresty`，不允许写死版本号路径。

其中 `nginx/conf/` 是编译期的默认落点：OpenResty 构建时把 nginx 核心的 prefix 设为 `<prefix>/nginx`，所以不指定 `--conf-path` 时，`nginx -t` 报告的就是 `versions/<ver>/nginx/conf/nginx.conf`。`./configure` 结尾打印的 Configuration Summary 可以直接验证这一点（以 `--prefix=/opt/openresty` 为例）：

```text
nginx path prefix:           "/opt/openresty/nginx"
nginx configuration file:    "/opt/openresty/nginx/conf/nginx.conf"
```

业务扩展配置 `conf.d/` 与 Lua 代码目录 `lua/` 也一并放这里，随版本整体切换。另外注意：Summary 里 pid 与 error log 的默认值也在 `<prefix>/nginx/logs/` 下——下文 configure 参数里显式给出的 `--error-log-path` / `--pid-path` **不能省**，省了这两项就会跟着版本目录跑，与"共享状态外置"的设计相悖。

# 下载与编译

```bash
cd /usr/local/src
wget https://openresty.org/download/openresty-1.31.8.1.tar.gz
tar xzf openresty-1.31.8.1.tar.gz
cd openresty-1.31.8.1
```

configure 的核心取舍：`--prefix` 指进**版本目录**，配置不指定路径（默认吃进版本目录），只有日志和 PID 两个参数指到外面：

```bash
./configure \
  --prefix=/opt/openresty/app/versions/1.31.8.1 \
  --error-log-path=/opt/openresty/logs/error.log \
  --pid-path=/opt/openresty/run/nginx.pid \
  --with-luajit \
  --with-threads \
  --with-http_ssl_module \
  --with-http_v2_module \
  --with-http_realip_module \
  --with-http_stub_status_module \
  --with-http_gzip_static_module \
  --with-pcre-jit
```

| 参数 | 说明 |
|------|------|
| `--prefix=.../versions/1.31.8.1` | 安装根 = 版本目录；配置（`nginx/conf/`）、`lualib` 等全部产物收进不可变单元 |
| （未写 `--conf-path`） | **刻意为之**：配置默认落 `versions/<ver>/nginx/conf/nginx.conf`，随版本走，回滚程序即回滚配置 |
| `--error-log-path` / `--pid-path` | 日志与 PID 属跨版本共享状态，外置到 `logs/`、`run/` |
| `--with-luajit` | 显式声明使用 LuaJIT（OpenResty 默认随源码树构建内置的 openresty/luajit2 分支，此处写明意图） |
| `--with-threads` | 线程池，磁盘 IO（`aio threads`）不阻塞事件循环 |
| `--with-http_ssl_module` / `--with-http_v2_module` | HTTPS 与 HTTP/2 |
| `--with-http_realip_module` | 从 `X-Forwarded-For` 等头还原真实客户端 IP（前面还有 LB 时必备） |
| `--with-http_stub_status_module` | 活性探测与基础监控指标 |
| `--with-http_gzip_static_module` | 直接下发预压缩的 `.gz` 静态文件 |
| `--with-pcre-jit` | PCRE JIT 编译正则，`ngx.re.*` 与 location 正则匹配提速 |

需要四层代理（MySQL/Redis 前置、`stream_lua_module`）的话，这里再加 `--with-stream --with-stream_ssl_module`；要挂第三方 C 模块用 `--add-module=`。

```bash
gmake
gmake install
```

机器核多可以用 `gmake -j$(nproc)` 提速；`gmake` 与 `make` 在 Ubuntu 上等价。

# 建立入口软链接

```bash
# 版本入口：升级 = 只改这条链接指向
ln -sfn /opt/openresty/app/versions/1.31.8.1 /opt/openresty/app/current

# 共享状态/资源目录：make install 不会创建版本目录以外的东西，
# 这三个目录首次启动前必须就位
mkdir -p /opt/openresty/logs /opt/openresty/run /opt/openresty/cert

# 命令入口
mkdir -p /opt/openresty/sbin
ln -sfn /opt/openresty/app/current/bin/openresty /opt/openresty/sbin/openresty
```

注意两条都是 `ln -sfn`：`current` 已存在时，少了 `-n` 会把新链接建到旧目标**目录里面**去，是这类布局最经典的坑（详见避坑节）。

# systemd 托管

`/etc/systemd/system/openresty.service`——单元里全部引用稳定入口 `sbin/openresty`，不出现版本号：

```ini
[Unit]
Description=OpenResty Service
After=network.target

[Service]
Type=forking
PIDFile=/opt/openresty/run/nginx.pid
ExecStart=/opt/openresty/sbin/openresty
ExecReload=/opt/openresty/sbin/openresty -s reload
ExecStop=/opt/openresty/sbin/openresty -s quit
KillMode=mixed
KillSignal=SIGQUIT

[Install]
WantedBy=multi-user.target
```

- `Type=forking` + `PIDFile`：Nginx 传统 master-worker 自举后台的标准集成方式；
- `ExecReload` / `ExecStop` 走 `-s reload` / `-s quit`，由程序自己读 PID 文件发信号，比 `kill $MAINPID` 更贴合热升级期间的多 master 状态；
- 因为单元只引用 `sbin/openresty` 这个软链接，**切版本不需要 `daemon-reload`**。

```bash
systemctl daemon-reload
systemctl enable --now openresty
```

# 升级与回滚

配置是文本，不能复制完事。OpenResty 从"共用一份配置 + 原地升级"改成"配置随版本走"之后，升级的标准动作是**模板渲染 + diff + `-t` + 灰度验证**四连，再走热升级信号序列。

## 1) 装出新版本程序目录

按上文编译流程，`--prefix=/opt/openresty/app/versions/<新版本>`，装完后新目录自带一份**出厂默认配置**（`nginx/conf/nginx.conf`），它是本次迁移的"模板底座"。

## 2) 配置迁移（渲染 + 复制 + diff）

以旧版本 `1.31.8.1` 升到 `<新版本>` 为例：

```bash
OLD=/opt/openresty/app/versions/1.31.8.1
NEW=/opt/openresty/app/versions/<新版本>

# a. 业务子配置与 Lua 目录整体复制
cp -a $OLD/nginx/conf/conf.d $NEW/nginx/conf/
cp -a $OLD/nginx/conf/lua    $NEW/nginx/conf/

# b. 参考旧版主配置改新版：以新版出厂 nginx.conf 为底（保证不丢新版本
#    新增的指令与默认结构），人工把旧版的业务配置（server/location/lua
#    相关指令等）迁移进来，然后 diff 逐项过目
diff -u $OLD/nginx/conf/nginx.conf $NEW/nginx/conf/nginx.conf
```

diff 时逐项检查三类风险：

- **废弃指令**：新版是否移除/改名了旧版仍在用的指令（`-t` 能兜住一部分，但要读 release notes）；
- **默认值变化**：指令还在、默认值变了（超时、缓冲区、HTTP/2 行为等），diff 看不出来，靠变更日志；
- **LuaJIT / 模块行为变化**：`lua_*` 指令语义、`lua-resty-core` 版本要求，结合本库 02 章的 API 差异判断。

## 3) 校验（用新二进制验新配置，别用错对象）

```bash
$NEW/bin/openresty -t
# 必须直接调用新版本目录的 openresty——它读的是新版本自己的配置；
# 此时 sbin/openresty 还指向旧版本，用它 -t 验的是旧配置，白验
```

## 4) 热升级信号序列（OpenResty 与 Nginx 完全一致）

前提：第 3 步通过。整个过程不断连，新 master 起服后的观察期就是灰度验证窗口。

1. **切换软链接**——程序与配置一起切到新版本：

   ```bash
   ln -sfn /opt/openresty/app/versions/<新版本> /opt/openresty/app/current
   ```

2. **启动新 master**——向服务主进程发 `USR2`，新 master 以新二进制启动并读取**自己版本目录里的配置**，新旧两个 master 共存，老 worker 继续服务：

   ```bash
   systemctl kill --signal=USR2 openresty
   ```

3. **优雅关闭旧 worker**——`USR2` 之后主进程仍是旧 master（其 PID 已挪到 `nginx.pid.oldbin`），发 `WINCH` 让旧 worker 停止接受新连接、处理完存量请求后退出：

   ```bash
   systemctl kill --signal=WINCH openresty
   ```

4. **灰度观察后结束旧 master**——盯 `error.log`、监控指标、抽查接口，确认新 master 服务正常后发 `QUIT`，升级完成：

   ```bash
   systemctl kill --signal=QUIT openresty
   ```

## 5) 回滚

`current` 一拨，程序和配置一起回旧——这正是"配置随版本走"买来的东西：

```bash
ln -sfn /opt/openresty/app/versions/<旧版本> /opt/openresty/app/current
systemctl kill --signal=HUP openresty     # 旧 master 用旧二进制+旧配置重新拉起 worker
# 确认旧 worker 接管后，结束新 master。注意这一步不能再用 systemctl kill——
# MAINPID 始终是旧 master，再发 QUIT 会杀掉刚接管流量的旧进程；
# 而 USR2 之后 nginx.pid 里写的就是新 master 的 PID
kill -QUIT $(cat /opt/openresty/run/nginx.pid)
```

> [!note]
> 上面命令里的 `openresty` 是单元名，按你 systemd 里的实际名称替换。热升级期间机器上会同时存在新旧两套进程与两个 PID 文件（`nginx.pid` / `nginx.pid.oldbin`），`systemctl status` 看到两个 master 是正常状态，不是泄漏。

# 附：官方 APT 仓库方式（快速路径）

开发机或不需要自定义布局时，官方 APT 仓库三步可用（同样适用于 Debian，CentOS/RHEL 用对应 RPM 仓库）：

```bash
# 1) 导入 GPG key 并添加源
curl -fsSL https://openresty.org/package/pubkey.gpg \
  | gpg --dearmor -o /usr/share/keyrings/openresty.gpg
echo "deb [signed-by=/usr/share/keyrings/openresty.gpg] \
http://openresty.org/package/ubuntu $(lsb_release -sc) main" \
  > /etc/apt/sources.list.d/openresty.list
apt update

# 2) 安装（prefix 为 /usr/local/openresty/，自带 systemd 单元）
apt install -y openresty openresty-opm openresty-resty

# 3) 启动
systemctl enable --now openresty
```

包管理器的选型见 [080.包管理opm与luarocks](./080.包管理opm与luarocks.md)。

# 避坑

- **`ln -sf` 切链接会把软链建到目录里**：`current` 已指向旧版本时，`ln -sf 新目录 current` 因为 `current` 解析为目录，会在**旧版本目录内部**生成一个叫 `current` 的链接。切链接永远用 `ln -sfn`（`-n` 把链接本身当普通文件处理）。
- **改配置前先确认 current 指向哪个版本**：配置随版本走之后，"改配置"= 改某个版本目录里的文件。直接 `vim app/current/nginx/conf/nginx.conf` 看着人畜无害，切完 `current` 再编辑就会把改动写到错误的版本上。养成习惯：先 `readlink current`，或用配置管理/git 渲染到**目标版本目录**。
- **旧版本目录要冻结**：升级完成、`QUIT` 掉旧 master 之后，旧版本目录连同它的配置就是纯归档，只读不回改。真要修配置，改当前版本目录，下次升级时随迁移流程带走。
- **prefix 决定相对路径锚点**：nginx 配置里的相对路径（`access_log logs/x.log`、`include` 相对路径等）都相对 **nginx 核心 prefix**（即 `versions/<ver>/nginx/`）解析，落在版本目录内，切版本后旧日志、旧文件会跟着"搬家"甚至分裂成两份。业务配置里 `logs/`、`run/`、`cert/` 一律写 `/opt/openresty/...` 绝对路径。
- **conf.d/、lua/ 忘拷贝**：`include conf.d/*.conf` 的通配符匹配不到文件时**不报错**，`-t` 照样通过，上线才发现业务 location 全空。迁移完先 `diff <(ls $OLD/nginx/conf/conf.d) <(ls $NEW/nginx/conf/conf.d)` 数一遍文件个数。
- **用错二进制做 -t**：切 `current` 之前，`sbin/openresty` 仍是旧版本，用它 `-t` 验证的是旧配置新版本没验；切完之后用它 `-t` 又变成验新弃旧。升级窗口里的校验必须写全路径 `versions/<新版本>/bin/openresty -t`。
- **USR2 后立刻发 WINCH 是错的**：必须确认新 master 已就绪（`ps` 里出现两个 master、`error.log` 出现 "start worker process"）再动旧 worker；跳过第 2→3 步之间的灰度观察期，等于拿生产流量赌配置迁移没做错。
- **`run/` 目录不存在时启动失败**：`--pid-path` 指向的目录不会被自动创建，已在「建立入口软链接」节统一 `mkdir`；机器重启后该目录若被清空也会导致 `-s reload` 找不到 PID，长期运行建议给单元加 `RuntimeDirectory` 或定时脚本兼顾。
- **opm/第三方 Lua 库装在版本目录里**：`lua-resty-*` 会装进 `versions/<ver>/lualib`，属"配置随版本走"的一部分——升级流程要把新版本的依赖装回新目录（或纳入源码包一起构建），否则新 master 一启动就 `module 'resty.xxx' not found`。
- **证书目录别跟着版本搬家**：`cert/` 外置是刻意的——私钥跨版本共享、权限收紧到 root:root 600，`ssl_certificate` 指令写 `/opt/openresty/cert/...` 绝对路径。切版本不动证书，回滚也不用重签。
- **升级后 `-s quit` 关错对象**：`openresty -s quit` 读 `nginx.pid`，热升级完成后它已指向新 master，旧 master 的控制在 `nginx.pid.oldbin`。若第 4 步之后旧 master 还在，应对 `nginx.pid.oldbin` 里的 PID 发 `QUIT`，别重复执行 `-s quit` 把新进程关掉。

# 总结

这套布局把 OpenResty 的升级做成一条固定流水线：**装新版本目录（自带出厂配置）→ 配置迁移（复制 conf.d/lua、以出厂版为底渲染业务配置、diff 过三类风险）→ 新二进制 `-t` → `ln -sfn` 切 current → USR2 / WINCH / QUIT 热升级**。程序与配置绑成同一个不可变单元，回滚因此只需 `current` 一拨、`HUP` 一发，再按 `nginx.pid` 把新 master `QUIT` 掉，不存在"程序回了、配置没回"的半吊子状态。日志、PID、证书三类共享资源常驻版本目录之外，切版本零感知。日常改配置记住一条铁律：先 `readlink current` 确认改动落在哪个版本上。装完之后照着 [050.目录结构与配置文件](./050.目录结构与配置文件.md) 熟悉 `nginx.conf` 骨架，再进 [060.第一个HelloWorld](./060.第一个HelloWorld.md)。
