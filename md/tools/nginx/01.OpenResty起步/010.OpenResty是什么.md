# 概述

OpenResty® 是一个**基于 Nginx 与 LuaJIT 的高性能动态 Web 平台**，由章亦春（agentzh）主导维护。它把 Nginx、LuaJIT、`ngx_http_lua_module`、`lua-resty-core`、`lua-resty-lrucache`、`opm` 等十余个组件打包成一个可安装的发行版，让开发者可以在 Nginx 处理请求的**每一个阶段**用 Lua 脚本注入业务逻辑，同时保留 Nginx 原生事件驱动、非阻塞 IO 的高并发能力。

一句话：**用 Lua 在 Nginx 里写业务，性能接近 C，动态性接近脚本语言。**

# 它解决什么问题

传统 Web 架构里，Nginx 只做静态资源和反向代理，业务逻辑走 Java/Go/Python/Node 后端。当业务需要下面这些能力时，传统架构就会付出高代价：

| 需求 | 传统架构的痛点 | OpenResty 的方案 |
|------|--------------|----------------|
| 毫秒级动态路由/灰度 | 改配置要发布、重启或 Nacos 推 | `balancer_by_lua_block` 每次请求现算 |
| 统一鉴权 | 每个后端各自实现一遍 | `access_by_lua_block` 网关层拦一次 |
| 高频小缓存（token、限流计数） | 走 Redis 网络 RT 抖 | `lua_shared_dict` 进程内共享内存 |
| 上游降级熔断 | 应用层框架侵入 | `lua-resty-*` 网关层零改造 |
| 边缘改写响应 | 加一层 BFF 变慢 | `body_filter_by_lua_block` 就地改 |

**核心思想**：凡是必须在"流量入口"就地做的、需要动态生效的、对尾延迟敏感的逻辑，都值得从后端上移到 OpenResty。

# 三大特性

- **动态**：Lua 脚本可以热更新（`reload` 或 `lua_code_cache off` 调试期免 reload）；配置可以从共享字典、etcd、Consul 动态拉取；上游机器列表可以在 `balancer_by_lua` 里每次请求现算。
- **高性能**：底层跑在 Nginx 的单线程事件循环 + LuaJIT trace JIT + cosocket 非阻塞 IO 上。一个 worker 可以撑住数万活跃连接；官方 benchmark 里 `content_by_lua_file` 每秒数十万 QPS。
- **轻部署**：单机一个二进制 + 一个目录就能跑；不像微服务框架需要注册中心、配置中心、链路追踪四件套才能起步。K8s 里通常一个 ConfigMap + 一个 Deployment 就完事。

# 与相关项目的关系

```
          ┌────────────────────────────────────────┐
          │        业务侧（网关、鉴权、限流）        │
          │   Kong / APISIX / 你自己的 lua-resty-*  │
          └────────────────────────────────────────┘
                              ▲
                              │ 依赖
          ┌────────────────────────────────────────┐
          │              OpenResty 1.31.8.1         │
          │  ┌──────────┬──────────┬─────────────┐  │
          │  │  Nginx   │ LuaJIT   │ lua-nginx-  │  │
          │  │  core    │ 2.1      │ module 等   │  │
          │  │  1.31.8  │ fork     │ 一堆子项目   │  │
          │  └──────────┴──────────┴─────────────┘  │
          └────────────────────────────────────────┘
```

- **Nginx**：OpenResty 的"骨架"。任何 Nginx 指令都直接可用；OpenResty 只是往 Nginx 里加了 Lua VM 和一批 C 模块。
- **LuaJIT**：OpenResty 用的是自己的 **luajit2** 分支（比 LuaJIT 主线多了 x86_64 GC64、若干 bugfix 与 trace 观测性）。不是标准 Lua 5.1，也不是 Lua 5.4。
- **`ngx_http_lua_module`**：把 LuaJIT 嵌进 Nginx 的那个 C 模块，也是所有 `*_by_lua_block` 指令的实现。
- **`lua-resty-core`**：新版 Lua API 的官方实现（基于 FFI），逐步替代 `ngx.*` 老 API，性能更好；详见 [02 章 040.lua-resty-core 与 FFI](../02.Lua与OpenResty运行时内幕/040.lua-resty-core与FFI.md)。
- **Kong / APISIX**：构建在 OpenResty 之上的**产品**，不是 OpenResty 本身；你完全可以直接裸用 OpenResty 做自己的网关，本系列第 6 章会演示。
- **Tengine**：淘宝维护的 Nginx 分支，也集成了 `ngx_http_lua_module`；与 OpenResty 是**平行**关系，不是包含关系。选型上 OpenResty 生态更新更快、更"官方"，Tengine 侧重 in-flight 增强。

# 适用与不适用

**适用**：
- 需要动态生效的流量层逻辑（网关、鉴权、路由、限流、降级、A/B 分流）
- 高并发短请求（长尾延迟 <10 ms 场景）
- 边缘计算：就近渲染 HTML、拼装响应、加解密
- 四层 TCP/UDP 代理（MySQL 读写分离、Redis 前置）

**不适用**（选传统后端更合适）：
- **CPU 密集型**：Lua 里做加解密、图像、大循环会把 worker 卡住，一卡就是成千上万请求。
- **复杂业务领域模型**：几十张表、DDD 聚合根、事务协调——Lua 生态里没这套。
- **长任务与批处理**：应该走消息队列 + worker 池，不该霸占 Nginx worker。
- **需要强类型 / 大型团队协作**：Lua 的动态特性反过来会成为负担。

> [!tip] 心法
> OpenResty 的定位是**流量层**，不是**业务层**。把它当成可编程的 Nginx，不要当成可编程的 Java。

# 版本节奏

OpenResty 版本号形如 `A.B.C.D`，前三位是打包的 nginx core 版本（`A.B.C`），最后一位 `D` 是 OpenResty 自身的迭代号。本系列基线：

| 组件 | 版本 | 备注 |
|------|------|------|
| OpenResty | **1.31.8.1** | 本系列统一版本 |
| nginx core | 1.31.8 | 对应 openresty-1.31.8.1 内置版本 |
| LuaJIT | 2.1 (openresty/luajit2 fork) | 非官方主线 |
| ngx_http_lua_module | 0.10.27+ | 具体版本随 openresty 打包 |
| lua-resty-core | 0.1.28+ | 通过 `require "resty.core"` 加载 |
| OpenSSL | 打包版本随发行渠道不同 | 官方包用 3.x |

后续升级路线看官方 blog 与 GitHub Releases：<https://github.com/openresty/openresty/releases>。

# 总结

OpenResty 不是"Nginx 加强版"也不是"脚本框架"，它是**在 Nginx 事件循环里长出的一个可编程层**。选它，就是选择：**把流量层的动态性用 Lua 表达出来，同时保住 Nginx 的性能与稳定性底盘**。装好、跑通、明白阶段与包管理之后，剩下的都是 `lua-resty-*` 生态 API 的熟练度问题——从下一章 [020.Windows 安装 OpenResty](./020.Windows安装OpenResty.md) 开始。
