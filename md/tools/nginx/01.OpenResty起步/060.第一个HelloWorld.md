# 概述

Hello World 的目的不是打印字符串，是**跑通一次 Lua → 请求 → 响应**的完整链路，让你亲手验证：配置文件从哪儿被读、Lua 代码写在什么位置、reload 是否真的生效、`error.log` 在哪儿看。本文用 `content_by_lua_block` 打最小闭环，然后逐层加深到 `content_by_lua_file` + `ngx.say/ngx.print` + `cjson` 输出。

# 操作步骤

## 1) 最简配置

在 `/usr/local/openresty/nginx/conf/conf.d/` 新建 `hello.conf`（目录不存在就先 `mkdir -p`）：

```nginx
server {
    listen 8080;
    server_name localhost;

    location = /hello {
        default_type text/html;
        content_by_lua_block {
            ngx.say("<p>hello, world</p>")
        }
    }
}
```

`nginx.conf` 的 `http{}` 里已经有 `include conf.d/*.conf;` 就直接生效；没有就手动加一行。

## 2) 语法检查与启动

```bash
sudo openresty -t
# nginx: the configuration file /usr/local/openresty/nginx/conf/nginx.conf syntax is ok
# nginx: configuration file /usr/local/openresty/nginx/conf/nginx.conf test is successful

# 已在运行 → reload；未运行 → 直接启动
sudo openresty -s reload 2>/dev/null || sudo openresty

curl http://localhost:8080/hello
# <p>hello, world</p>
```

## 3) 用外部 Lua 文件

内联 `*_by_lua_block` 只适合几十行的骨架代码。稍微成规模就切到 `*_by_lua_file`，把逻辑放到 `.lua` 里：

```nginx
location = /hello2 {
    content_by_lua_file lualib/app/hello2.lua;
}
```

`lualib/app/hello2.lua`：

```lua
local cjson = require "cjson.safe"

local name = ngx.req.get_uri_args().name or "world"
ngx.header.content_type = "application/json; charset=utf-8"
ngx.say(cjson.encode({
    greeting = "hello, " .. name,
    worker_pid = ngx.worker.pid(),
    version  = "1.31.8.1",
}))
```

`reload` 后：

```bash
curl 'http://localhost:8080/hello2?name=rafeng'
# {"greeting":"hello, rafeng","worker_pid":12345,"version":"1.31.8.1"}
```

## 4) 观察日志

```bash
# error.log（默认 warn 级别，ngx.INFO 需先降到 info）
sudo tail -F /usr/local/openresty/nginx/logs/error.log

# 打开更详细的调试日志：nginx.conf 里 error_log logs/error.log info;
sudo openresty -s reopen    # 或用 kill -USR1 触发重开日志文件
```

代码里打日志：

```lua
ngx.log(ngx.INFO, "hello handler called, uri=", ngx.var.uri)
ngx.log(ngx.WARN, "arg missing: ", tostring(ngx.var.arg_name))
```

`ngx.INFO / ERR / WARN / DEBUG` 与 Nginx 的日志级别一一对应，低于 `error_log` 声明级别的会被过滤。

## 5) 用 curl 看响应头

```bash
curl -i http://localhost:8080/hello2?name=rafeng
```

期望响应头包含 `Content-Type: application/json; charset=utf-8`——这就是 `ngx.header.content_type = ...` 生效的证据。

## 6) 请求方法 / 请求体读取

```nginx
location = /echo {
    content_by_lua_block {
        ngx.req.read_body()                              -- 必须先读 body
        local args = ngx.req.get_post_args()             -- form-url-encoded
        local body = ngx.req.get_body_data()             -- 原始 body
        local method = ngx.req.get_method()
        ngx.say("method=", method, " args=", require("cjson").encode(args))
    }
}
```

```bash
curl -X POST -d 'a=1&b=2' http://localhost:8080/echo
# method=POST args={"a":"1","b":"2"}
```

`ngx.req.read_body()` **必须在 `get_body_data` / `get_post_args` 之前调用**——忘调是新手第一大坑，会得到 `nil`。

## 7) 状态码与提前终止

```lua
if not ngx.var.arg_name then
    ngx.status = ngx.HTTP_BAD_REQUEST
    ngx.say("missing query arg: name")
    return ngx.exit(ngx.HTTP_BAD_REQUEST)
end
```

`ngx.exit()` 立即结束当前请求，剩下的 Lua 代码不再执行。**任何 `ngx.exit` 都应该 `return ngx.exit(...)` 显式返回**，避免 IDE 与协程栈上的困惑。

一份完整的验收清单：

| 语法 | `openresty -t` | `syntax is ok / test is successful` |
| 内联 Lua | `curl localhost:8080/hello` | `<p>hello, world</p>` |

# 避坑

- **改 `content_by_lua_file` 指向的 `.lua` 后不 reload 不生效**：`lua_code_cache on` 下 Lua 字节码在 master 加载时缓存；生产靠 reload，开发期可以临时 `lua_code_cache off`（每请求重编，性能很差，别带上线）。
- **`content_by_lua_file` 相对路径**：相对于 `-p` 指定的 prefix，写 `lualib/app/hello2.lua` 就是 `/usr/local/openresty/nginx/lualib/app/hello2.lua`——不是 `/usr/local/openresty/lualib/`。要么用绝对路径，要么用 `$prefix` 变量。
- **`ngx.say` vs `ngx.print`**：`say` 自动加换行、`print` 不加；两者都会**分片输出**——一个请求可以多次调用；`ngx.say` 只在 `content_by_lua_*` 和 `body_filter_by_lua_*` 阶段可用。
- **`default_type` 决定 Content-Type**：不设就跟随 `nginx.conf` 的 `default_type application/octet-stream`，浏览器会变下载；`ngx.header.content_type = ...` 可以在 Lua 里覆盖。
- **`content_by_lua_*` 与 `proxy_pass` 冲突**：同一个 `location` 二者只能选一，写了 `content_by_lua_*` 就是"我自己产出响应"；要透传上游得走 `access_by_lua_*` + `proxy_pass`，或用 `lua-resty-http` 显式发请求。
- **`_by_lua_block` 里的花括号**：`{` `}` 是 Lua 语法而非 Nginx——`{` 后面必须紧跟 Lua 代码；如果代码里有字符串带 `}`，nginx 解析器不识别字符串，会截断；这也是**稍微成型的逻辑一定要用 `_by_lua_file`** 的原因。
- **worker 隔离**：`worker_pid` 每次可能不同——`lua_shared_dict` 之外的**普通 Lua 变量不跨 worker 共享**；跨请求状态请走 shared dict 或外部存储（Redis）。

# 总结

一个 Hello World 就能把「配置在哪儿 → 语法对不对 → 有没有 reload → 日志在哪里 → 响应类型对不对 → 状态码怎么走 → 请求体怎么读」这条主链摸完。跑通之后建议再做两件事：把 `_by_lua_block` 换成 `_by_lua_file` 感受一下外置代码的可维护性；把 `error_log` 级别降到 `info` 再打开 `debug`（需 `--with-debug` 编译），观察 cosocket 与非阻塞行为——为 [070.请求处理阶段总览](./070.请求处理阶段总览.md) 打基础。
