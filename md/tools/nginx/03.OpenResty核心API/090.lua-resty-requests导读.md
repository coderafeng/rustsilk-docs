# 概述

`lua-resty-requests` 是章玉峰写的 HTTP 请求/响应解析库——**不是**给客户端发请求用的（那个是 `lua-resty-http`），而是把"解析一段 HTTP 报文得到 request 对象"这件事封装好。用它做样板，能看清一个高质量 `lua-resty-*` 库的骨架。

# 库定位

```text
输入：原始 HTTP 字节流 / 一个字符串
输出：request 对象，method()/path()/query()/header()/body()
```

**为什么不直接用 `ngx.req.*`？** `ngx.req.*` 只在**有请求上下文**时可用；`lua-resty-requests` 是**纯 Lua 数据结构**，脱离 nginx 也能跑——适合做协议测试、代理层二次解析、单元测试。

# API 表面

```lua
local requests = require "requests"

-- 从 raw 报文构造
local req = requests.request_from_raw_table({
    "GET /foo?a=1 HTTP/1.1",
    "Host: example.com",
    "User-Agent: OpenResty",
    "",
    "hello=world",
})

req:method()          -- "GET"
req:uri()             -- "/foo"
req:query_string()    -- "a=1"
req:version()         -- "1.1"
req:header("host")    -- "example.com"
req:body()            -- "hello=world"
```

响应侧：

```lua
local resp = requests.response_from_raw_table({
    "HTTP/1.1 200 OK",
    "Content-Type: text/plain",
    "",
    "hi",
})
resp:status()          -- 200
resp:header("content-type")
resp:body()
```

# 高质量 lua-resty-* 库的骨架

读完 `lua-resty-requests` 你会发现它的目录长这样——**这是可以直接抄的模板**：

```text
lua-resty-requests/
├── lib/requests.lua                -- 主入口
├── lib/requests/parser.lua         -- 解析
├── lib/exceptions.lua              -- 异常
├── t/                              -- Test::Nginx 用例
│   ├── 000-sanity.t
│   ├── 001-request.t
│   └── ...
├── Makefile                        -- 一键 prove 测试
├── requests-0.x-1.rockspec         -- luarocks 元数据
├── opm.json                        -- opm 元数据（可选）
├── README.markdown                 -- API + 示例
└── LICENSE                         -- BSD 2-clause 常见
```

**要点**：
- 主入口 `lib/foo.lua` 只暴露少量函数，内部拆到 `lib/foo/*.lua`；
- `t/` 每个测试文件对应一个子能力；用 Test::Nginx，不用 busted；
- 双份元数据：`*.rockspec` 兼容 luarocks，`opm.json` 兼容 opm（见 [01 章 080.包管理](../01.OpenResty起步/080.包管理opm与luarocks.md)）；
- README 里放"最小可运行示例"，让读者复制粘贴就能跑。

# 库设计三条约定

## 1. 面向对象用 metatable + `new`

```lua
-- lib/requests.lua 简化版
local _M = { _VERSION = "0.x" }
local mt = { __index = _M }

function _M.new(_)
    return setmetatable({ _headers = {} }, mt)
end

function _M:method(m)
    if m then self._method = m end
    return self._method
end

return _M
```

**要点**：`_M.new` 返一个 `setmetatable({}, mt)`；方法用 `:` 语法糖；实例状态用 `_foo` 前缀表"私有"。

## 2. 错误返回 `nil, err`，不抛

```lua
function _M.parse(raw)
    local first, rest = raw:match("^(.-)\r\n(.*)$")
    if not first then return nil, "malformed request line" end
    -- ...
end
```

**理由**：抛异常会破坏 cosocket 协程栈；`nil, err` 让调用方决定怎么处理。

## 3. 纯 Lua 优先，避免 ffi

除非确实需要性能，不要引入 ffi。`lua-resty-requests` 全程纯 Lua，测试可以直接 `resty` 命令行跑，不用起 nginx——这是**能脱离宿主测试**的库更容易维护的关键。

# 与 `lua-resty-http` 的分工

| 库 | 场景 |
|----|------|
| `lua-resty-requests` | **解析**已存在的 HTTP 字节流；单元测试；中间件层改写 |
| `lua-resty-http` | **发起** HTTP 请求（客户端）；包装 cosocket 走 HTTP 协议 |
| `lua-resty-core` 里 `ngx.req` | 处理当前请求；有请求上下文时的首选 |

三者定位不同，用错会绕远路。

# 避坑

- **别在 hot path 上从 raw 解析**：`requests.request_from_raw_table` 每次 O(n)；能复用 `ngx.req` 就复用；
- **注意 case-sensitivity**：`req:header("Host")` 和 `req:header("host")` 结果不同——库内部 lowercase，但入参不 lowercase；写常量用小写；
- **`_VERSION` 字段**：库作者版本，不代表协议兼容；看 CHANGELOG。

# 总结

- `lua-resty-requests` = 解析用的纯 Lua HTTP 库；
- 骨架：`lib/` + `t/` + 双 rockspec/opm.json + README；
- 三条设计约定：`new + mt`、`nil, err`、纯 Lua；
- 与 `lua-resty-http`、`ngx.req` 各司其职。
