# 概述

Lua 里 **table 是唯一的数据结构**（数组、哈希、对象、模块、类、闭包都靠它）；**metatable 是唯一的"元行为"载体**（运算符重载、`__index` 继承、`__newindex` 拦截、`__len` 定制）。LuaJIT 里 table 内部是**"array part + hash part"混合体**，理解这两部分的重hash时机、`#` 语义、以及 metatable hook 的性能代价，是写出低延迟代码的前提。

# table 内部结构

```
Lua 层的 t = {10, 20, 30, name = "x", age = 1}
            │
            ▼
   ┌──────────────────┐
   │      TValue       │
   │  (GCObject*)      │
   └──────────────────┘
            │
            ▼
   ┌──────────────────────────────────┐
   │       Table (GCtable)            │
   │  ┌──────────┬──────────────────┐ │
   │  │ array    │ node (hash part) │ │
   │  │ [10,20,30]│ {name="x",       │ │
   │  │ *array    │  age=1, ...}    │ │
   │  │ *asize    │ *node, *next     │ │
   │  └──────────┴──────────────────┘ │
   │  metatable ptr                    │
   └──────────────────────────────────┘
```

- **array 部分**：连续内存，`t[1]` 到 `t[asize]`，直接下标访问，缓存友好。
- **hash 部分**：开放地址 + 链表混合，`t.name` / `t["k"]` / 非整数键全在这里；每个 node 有 `key`、`val`、`next`（同哈希桶的链）。
- **重hash（rehash）**：hash 满 或 array 需要扩容时触发；`luaH_resize` 把整表搬到新尺寸——**热路径上的频繁 rehash 会拖慢**。

## `#` 运算符的边界

`#t` 找的是"**边界**"：`t[n] ~= nil and t[n+1] == nil` 的 n。数组部分有 nil 空洞时，`#` 返回值**不确定**（可能是空洞前一个、也可能是全长度）：

```lua
local t = {1, 2, nil, 4}
print(#t)   -- 2 或 4（LuaJIT 与 5.1 都是不确定，靠内部实现）
```

**结论**：别在 array 里塞 nil；要"删除元素"用 `table.remove(t, i)` 保持紧凑。

## `ipairs` vs `for i=1,#t` vs `pairs`

| 遍历方式 | 支持 nil 中断 | 遍历 hash 部分 | JIT 友好度 |
|---------|-------------|--------------|-----------|
| `for i=1,#t` | 是（会读到 nil） | ❌ | ✅✅ |
| `ipairs` | 是（遇到 nil 停） | ❌ | ✅ |
| `pairs` / `next` | 否 | ✅ | △（`next` 有 NYI 风险） |

**热路径首选 `for i=1,#t`**，且用**局部 `n = #t`** 缓存长度避免每次重算：

```lua
local n = #t
for i = 1, n do ... end
```

# 预分配：避免 rehash

Lua 5.1 / LuaJIT 里的 `table` 库没有直接的 capacity 参数，但可以用两个技巧预分配：

## 1) `table.insert` 逐步增长

```lua
-- ❌：每次扩容都 rehash
local t = {}
for i = 1, 100000 do t[i] = i end

-- ✅：一次性构造大 array
local t = table.concat and {} or {}   -- 无直接语法
-- 实用写法：先赋 array 尾元素，让 Lua 一次扩容
t[100000] = 0                          -- 触发一次 array 扩到 ≥100000
t[100000] = nil                        -- 保留 size，清空槽位
for i = 1, 100000 do t[i] = i end      -- 之后无 rehash
```

## 2) FFI 造 struct array

数据是定长结构（每条记录 N 个字段）时，用 `ffi.new("struct rec[?]", n)` 直接一次分配；访问比 table 快 3-10x。详见 [040.lua-resty-core 与 FFI](./040.lua-resty-core与FFI.md) 与 05 章性能优化篇的 table 使用篇。

# metatable hook 与代价

LuaJIT 支持的元方法一览：

| 元方法 | 触发时机 | 代价 |
|-------|---------|-----|
| `__index` | `t[k]` 且 `k` 不在 t 里 | **一次函数调用或表查找**，热路径慎用 |
| `__newindex` | `t[k] = v` 且 `k` 不在 t 里 | 同上；rawset 会绕开 |
| `__call` | `t(...)` | 一次调用 |
| `__len` | `#t`（LuaJIT 也支持） | 每次长度都调 |
| `__eq` | `t1 == t2`（且两者同类型且都是表） | 每次比较都调，会废掉 intern 加速 |
| `__lt` / `__le` | `<` / `<=` | table.sort 里高频触发 |
| `__concat` | `t1 .. t2` | 每次字符串拼接 |
| `__add` / `__sub` / ... | 算术运算 | 每次运算 |
| `__tostring` | `tostring(t)` / `print(t)` | 只在格式化时 |
| `__metatable` | 保护 metatable 不被 `getmetatable` 拿到 | 一次性 |

**性能红线**：热循环里对每个元素触发 `__index` 函数 → 相当于给每次访问多插一次 call，JIT 会 side exit。

## 类继承：`__index` 用表 vs 用函数

```lua
local Animal = { legs = 4 }         -- 共享字段
Animal.__index = Animal             -- 表版：查找走 rawget(mt, k)，快

local Dog = setmetatable({}, Animal)
Dog.__index = Dog                   -- Dog 实例继承 Animal + Dog
function Dog:bark() return "woof" end

local d = setmetatable({}, Dog)
print(d.legs)                        -- 4，走两级 __index 表
```

**表版 `__index`**：LuaJIT 会尝试 specialize（`__index` 是 table 时，走 `luaH_get`），**性能可接受**。

**函数版 `__index`**：

```lua
setmetatable({}, {__index = function(t, k)
    return load_from_redis(k)      -- 每次都调函数
end})
```

函数版每次访问触发一次 call，NYI 风险大，热路径**避免**；用 `rawget` + 手动 fallback 代替。

## `__newindex` 与 `rawset`

```lua
local cache = {}
local t = setmetatable({}, {__newindex = function(o, k, v)
    cache[k] = v                    -- 拦截写入
    error("no direct write")        -- 或做验证
end})

t.x = 1                             -- 触发 __newindex
rawset(t, "x", 1)                   -- 绕过，直接写
```

**`rawset`/`rawget` 性能比 metatable hook 快得多**，但会绕过所有拦截——**在明确不需要 hook 的热路径上优先 raw 版**。

# 常见坑与写法

## 1) `t[k] = nil` 不删除 hash 槽

```lua
local t = {a=1, b=2, c=3}
t.b = nil
-- hash 部分还在，只是 val 变 nil；rehash 只在扩容时清
-- 长期"删除"操作多的表 → size 越滚越大，最终 rehash 摊薄成本变高
```

**解决**：需要频繁删除的表，定期用 `local n = {}; for k,v in pairs(t) do if v ~= nil then n[k]=v end end; t = n` 重建；或用 `lua-resty-lrucache`（自带驱逐，见 [06 篇](./060.字符串内部化与GC.md)）。

## 2) `next` 与 `pairs` 遍历时修改

```lua
-- ❌：未定义行为
for k, v in pairs(t) do
    if v.x then t[k] = nil end
end

-- ✅：先收集再删
local todel = {}
for k, v in pairs(t) do if v.x then todel[#todel+1] = k end end
for _, k in ipairs(todel) do t[k] = nil end
```

## 3) 表构造 vs 后置赋值

```lua
-- ✅：字面量构造一次到位
local t = {a=1, b=2, c=3}

-- ❌：三次扩容
local t = {}
t.a = 1; t.b = 2; t.c = 3
```

## 4) `#` 在混用 array+hash 时不确定

```lua
local t = {1, 2, 3, x=10, y=20}
print(#t)   -- 3（array 边界）；hash 部分不计入
```

## 5) `table.sort` 里 metatable 影响

`table.sort` 用 `<` 或 `__lt`；如果元素有 `__lt`，比较开销剧增且不稳定（可能触发 NYI）。排序元素尽量是**纯 number / string / 无元表 table**。

```lua
-- 观察内部结构（LuaJIT 有 jit.p 但不完整）

local function bench()

```

# 避坑

- **不要拿 `#t` 判空**：`#t == 0` 只反映 array 边界，hash 部分非空时 `#t` 也可能是 0；判空用 `next(t) ~= nil`（LuaJIT 与 5.4 语义一致）。
- **不要把 config 表挂 `__index` 函数**：配置读取是热路径，每次函数调用是负担；一次性 `setmetatable(cfg, {__index = default_table})` 用**表版**就好。
- **不要在 `__newindex` 里做 IO**：`t.x = 1` 触发 `__newindex` → 里面若走 cosocket，`t.x = 1` 会 yield → 上层代码假设"赋值是同步"就崩了。**`__newindex` 保持纯计算**。
- **`table.remove(t)` 尾删**：LuaJIT 里 `remove(t)` 是 O(1)；`remove(t, 1)` 头删是 O(n)——队列/栈用 table 是"够用"，高频场景改用环形 buffer 或 `lua-resty-stack`。
- **`table.unpack` 上限**：LuaJIT 里 `select('#', ...)` 与 `table.unpack` 参数上限是 `LUAI_MAXCSTACK`（几千到 8000），别把 10 万元表 unpack 到函数参数里。
- **别在 `pairs` 里同时插入新键**：Lua 参考手册明说未定义行为；LuaJIT 通常能跑，但**不保证**。

# 总结

**Lua 的性能与语义问题，八成是 table 的问题**。理解 array/hash 双部分 → 明白 `#` 为什么不可靠、rehash 为什么偶发抖动、metatable 函数版为什么慢；掌握 `rawget/rawset` 与预分配 → 大部分热循环提速 2-10 倍不难。字符串与 GC 是这套模型的"另一半"，见 [060.字符串内部化与 GC](./060.字符串内部化与GC.md)。
