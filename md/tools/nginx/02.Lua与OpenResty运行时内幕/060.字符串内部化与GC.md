# 概述

LuaJIT 的字符串是 **immutable + interned**（等价字面量共享同一份内存，比较是指针比较）。这带来两个副作用：**动态生成的短字符串**（比如 `tostring(i)`）会污染 intern 表；**GC 步进** 与字符串分配耦合，长字符串走"direct-allocated"路径但仍参与 GC。这一篇讲**内部化机制、GC 步进模型、常见性能陷阱与调优手段**。

# 字符串内部化（intern）

```lua
local a = "hello"
local b = "hello"     -- 与 a 指向同一个 GCstr
print(a == b)          -- true，指针比较
```

- **短字符串**（默认 <40 字节）：LuaJIT 通过哈希到 `gc->str` 表完成 intern；相同内容永远同一指针。
- **长字符串**（≥40 字节）：**不 intern**，`==` 会走内容比较；分配在专用 arena。

**Intern 表命中极快**，代价是：任何动态生成的字符串都会**尝试**进入 intern 表 → 表膨胀 → 每次分配都要哈希查找。

## 动态字符串的性能陷阱

```lua
-- ❌：热循环里每次生成新短字符串，都进 intern 表
for i = 1, 1e6 do
    local s = "k" .. i             -- 每次新 GCstr，intern 表爆炸
    t[s] = true
end

-- ✅：一次性预生成 key
for i = 1, 1e6 do
    t[i] = true                    -- 直接用数字键
end

-- ✅：确实要拼接，用长字符串（超过 40 字节就不 intern）
local key = "some_very_long_prefix_name_" .. i    -- >40 字节 → 跳过 intern
```

`ffi.string` 与 `tonumber` 也会造字符串；热路径上避免"每请求都 `tostring(ngx.var.xxx)`"。

# 字符串 GC

LuaJIT 用 **incremental mark-and-sweep**（默认）或 **generational**（OpenResty 分支支持 `jit.opt.start("gcs=gen")`）：

- **incremental**：每次分配触发一小步标记；延迟可预测，吞吐略低。
- **generational**（LuaJIT 2.1 fork 可开）：分 young/old 代，回收快，抖动大；短生命周期字符串密集的网关场景吞吐 +10-20%。

关键旋钮（`jit.opt.start`）：

| 参数 | 默认 | 效果 |
|-----|-----|-----|
| `gcpause=N` | 200 | 每次 GC 步进的最大停顿目标（微秒）；调小更平滑 |
| `stepsize=N` | 130 | 每步扫描多少字节；调大更省 CPU 但停顿更明显 |
| `gcsemul=N` | 0 | GC 触发阈值倍率 |
| `gcs=gen` | inc | 切换 GC 模式 |
| `sizebyte=off` | on | 关闭 GC 写屏障（高级） |

## 观察 GC 事件

```lua
local collectgarbage = require("jit").prof   -- 或标准 collectgarbage
ngx.timer.every(5, function()
    local mem = collectgarbage("count")   -- KB
    ngx.log(ngx.INFO, "lua mem=", mem)
end)

-- 手动强制
collectgarbage("collect")        -- 完整一轮
collectgarbage("step", 1024)     -- 步进 1024 单位
```

LuaJIT 里 `collectgarbage("setpause" / "setstepmul")` 也有效，但更推荐 `jit.opt.start` 直接改内部参数。

# `string.*` 库在 LuaJIT 里的实现

| API | 内部路径 | 备注 |
|-----|---------|-----|
| `string.rep(s, n)` | 分配新串 | n 大时避免 |
| `string.sub(s, i, j)` | **短子串**（<24 字节）也 intern；长子串新分配 | 别在循环里 `string.sub` 大串 |
| `string.format` | 走 `sprintf`，返回新串 | 与 `..` 差不多，可读性优先 |
| `string.find` | PCRE-lite | 简单查找；复杂模式改 `ngx.re` |
| `string.gsub` | 见 [030.NYI](./030.NYI与JIT失效.md) | **传函数回调时 NYI** |
| `table.concat` | 一次分配拼接 | **首选**：多次 `..` 慢 5-10x |

**核心口诀**：**用 `table.concat`，不用 `..` 拼接**。

```lua
-- ❌：n 次分配
local s = ""
for _, part in ipairs(parts) do s = s .. part end

-- ✅：一次分配
local s = table.concat(parts, "")
```

`..` 每次产生新字符串；`table.concat` 内部预分配总长度再一次拷。

# FFI 里的 `char*`

LuaJIT FFI 允许直接操作 C 字符串，绕过 Lua 层 GC：

```lua
local ffi = require("ffi")
local buf = ffi.new("char[?]", 1024)
ffi.copy(buf, "hello", 5)
local s = ffi.string(buf)             -- 拷成 Lua 字符串（进 intern）
local s2 = ffi.string(buf, 5)          -- 明确长度
-- 或者直接用 cdata，不拷：
local ptr = ffi.cast("const char *", buf)
```

**`ffi.string` 会拷进 Lua 堆**（新 GCstr）；高频场景要么复用同一个 cdata buffer，要么把 `ptr` 直接传给下游 FFI 函数（不转 Lua 字符串）。这是 Kong/APISIX 里字符串处理能提速 3-5x 的关键。

# 长字符串与大对象

- **>40 字节** 的字符串走"长串"分配，不 intern，比较走内容。
- **>1MB** 会直接走 `malloc` 分配，不受 intern 表影响；日志、模板这类**长文本**用 `string.rep` 或 `table.concat` 生成不会炸 intern 表。
- **不要把 base64 后的图片塞进 hash 键**（键太长会退化）；改存 shared dict（另见 [080 篇](./080.共享内存与worker通信.md)）。

# 避坑

- **别用 `tostring(x)` 打日志**：每次分配新串；用 `ngx.log(ngx.INFO, "x=", x)`，`ngx.log` 内部走变参拼接不产生 Lua 层字符串。
- **`string.format("%03d", n)` 热路径慎用**：LuaJIT 的 `format` 不是最优；`n < 100 and ("00"..n):sub(-3)` 之类的手写反而慢；真要极致性能用 `resty.string`。
- **`..` 混合类型**：`"x" .. 1` 会隐式 `tostring`；生产代码请显式 `tostring` 或用 `string.format`。
- **长循环里 `string.gsub` 传函数**：NYI 高发，见 [030.NYI](./030.NYI与JIT失效.md)；用 `ngx.re.gsub` 更好（走 `resty.core`）。
- **intern 表内存不计入 `collectgarbage("count")`**：`gc->str` 表自身是 C 端结构，Lua 层看不到；内存异常排查时 `openresty -V` + `pmap` 才是真相。
- **`ngx.now()` 与 `tostring(ngx.now())` 组合打日志**：`ngx.now()` 是秒级浮点（精度到 ms），转字符串会进 intern；批量日志用 `timer` 里聚合。

# 验证

```bash
# 观察 intern 表命中率
luajit -e '
    local ffi = require("ffi")
    ffi.cdef[[ typedef struct lua_State lua_State; int lua_gc(lua_State*,int,int); ]]
    -- 用 jit.bcsave / gcov 或直接读 collectgarbage("count") 前后差
    local t = {}
    for i = 1, 1e5 do t[i] = "key" .. i end
    print(collectgarbage("count"))    -- KB
'
```

生产环境用 `pmap -x <pid>` 或 `smem -p -k` 观察 nginx worker RSS；GC 与 intern 表的影响会体现在这里。

# 总结

LuaJIT 的字符串模型是**"intern + GC"**。掌握：**短串 intern 快但表可能爆、长串不 intern 但比较走 memcmp、`table.concat` 永远比 `..` 好、`jit.opt.start("gcs=gen")` 有 10-20% 免费吞吐、`ffi.string` 与 cdata 指针的选择决定要不要拷进 Lua 堆**。这些是后续性能优化章里"字符串操作"篇的实践基线，也是绝大多数"OpenResty 内存泄漏"排查的切入点。
