# 概述

**NYI（Not Yet Implemented）** 是 LuaJIT 里"当前无法编译成机器码的字节码/操作"的黑名单——录制 trace 遇到 NYI 就 abort，代码掉回解释器，性能可能**慢一个数量级**。这一篇给出：NYI 触发点清单、`-jv` 观测手段、OpenResty 场景里的具体避坑写法。

# 什么会触发 NYI

LuaJIT 官方维护 NYI 列表，主要类别（`vy.h`）：

| 类别 | 触发点 | OpenResty 场景 |
|-----|-------|---------------|
| **协程** | `coroutine.yield` / 部分 `resume` 路径 | 所有 `cosocket`、`ngx.location.capture`、`ngx.socket.tcp` 都会 yield → **不 JIT** |
| **pcall/error** | `xpcall` 有对应处理；`error(msg, level)` 动态 level 部分 NYI；`error()` 抛表也走 NYI | 业务里到处 `pcall(require, ...)`、`error("...")` |
| **debug 库** | `debug.sethook`、`debug.getinfo`、`debug.traceback` | `resty.core.traceback` 已用 FFI 绕开；标准 `debug.traceback` 在 NYI |
| **vararg** | 变长参数 `...` 展开（`BCALLM`） | 用 `table.pack(...)` 传给下游 → 触发 |
| **字符串** | `string.gsub` 传函数回调（`string.gsub(s,pat,fn)`） | 大量模板替换、SQL 参数拼装 |
| **表操作** | `setmetatable` 修改已有表的 metatable、`rawget`/`rawset` 部分路径 | 少量出现可忽略 |
| **函数** | 部分 `load` / `loadstring` 动态加载 | 热重载库 `lua-resty-hotreload` 相关 |
| **FFI** | `ffi.copy` 传字符串、`ffi.load` 动态加载 | 大部分 FFI 是 JIT-friendly，只有动态加载路径 NYI |

**注意**：cosocket 与 timer 的 yield 是**结构性 NYI**，不是"写得不好"——`ngx.socket.tcp()` 之后一定 yield，JIT 无法穿透；**别指望 `content_by_lua_block` 里的网络代码本身跑成机器码**，能 JIT 的是它周围的**纯计算热路径**（JSON 解析、路由表匹配、限流算法循环）。

# 观测：`-jv` / `vmprofile` / `jit.dump`

## 1) 命令行 `-jv`（打印 trace 起止）

```bash
luajit -jv hot.lua 2>&1 | head -30
# [TRACE   0] hot.lua:6 → 编译成功
# [TRACE 205] hot.lua:12 → NYI: BCALLM
```

看到 `NYI: XXX` 就定位到具体触发的字节码。

## 2) `jit.v` 在 nginx 内开启

```lua
-- init_worker_by_lua_block
local jit_v = require("jit.v")
jit_v.on(function(msg)
    ngx.log(ngx.INFO, "JIT: ", msg)
end)
```

`error.log` 里就能看到每条 trace 的编译/abort 事件。生产不要开。

## 3) `jit.dump`（写到文件）

```lua
local jit_dump = require("jit.dump")
jit_dump.open("w", "/tmp/jit.log")
jit_dump.on()
-- ... 跑一段业务 ...
jit_dump.off()
```

## 4) `vmprofile`（每函数采样，看谁掉回解释器）

```lua
local vmprofile = require("jit.vmprofile")
vmprofile.start()
-- 跑压力
local prof = vmprofile.stop()
for fn, count in pairs(prof) do
    if count > 100 then
        ngx.log(ngx.INFO, "HOT ", debug.traceback(fn), " calls=", count)
    end
end
```

`vmprofile` 会标注哪些函数被**多次以解释器方式**调用，就是 JIT 失效最集中的地方。

# 常见改写模式

## 1) 循环里避免 `error()`

```lua
-- ❌：每次循环都可能 error，导致 trace abort
for i = 1, n do
    local ok, err = pcall(function() ... end)
    if not ok then error(err) end     -- error 是 NYI 高发点
end

-- ✅：把 error 挪到循环外，循环内只设 flag
local first_err
for i = 1, n do
    local ok = process(i)
    if not ok and not first_err then first_err = i end
end
if first_err then error("failed at "..first_err) end
```

## 2) 变长参数：预打包

```lua
-- ❌：BCALLM
local function log(...)
    ngx.log(ngx.INFO, ...)
end

-- ✅：固定 arity
local function log2(a, b)
    ngx.log(ngx.INFO, a, b)
end
```

`ngx.log` 本身是 C 函数，性能损耗主要在 FFI 边界；把 Lua 侧的变长参数消除，让调用点 specialize。

## 3) 避免热路径里动态 `require`

```lua
-- ❌：require 每次都查表 → 编译时 NYI
for _, name in ipairs(mods) do
    local m = require(name)   -- 动态名字
    m.handle()
end

-- ✅：一次性预加载到 dispatch 表
local loaded = {}
for _, name in ipairs(mods) do loaded[name] = require(name) end
for _, name in ipairs(mods) do loaded[name].handle() end
```

## 4) 循环不变量提到外面

```lua
-- ❌：每次都取 ngx.var.host
for i = 1, n do
    do_something(ngx.var.host, i)
end

-- ✅：局部变量让 JIT 能 specialize
local host = ngx.var.host
for i = 1, n do
    do_something(host, i)
end
```

## 5) 用 FFI 替代 `string.pack`

`string.pack` 在 LuaJIT 里不存在；`string.format` + 手工拼装是 NYI；直接走 FFI 拷贝内存：

```lua
local ffi = require("ffi")
ffi.cdef[[
    struct pkt { uint32_t id; uint64_t ts; };
]]
local buf = ffi.new("struct pkt[?]", n)
for i = 0, n-1 do
    buf[i].id = i
    buf[i].ts = ngx.now() * 1000
end
```

比 `table.insert` + `string.pack` 组合快 10x。

# OpenResty 场景的实际影响

**content_by_lua_block 里的网络代码本身不 JIT**，但**周边纯计算**会：

| 场景 | 是否 JIT | 原因 |
|-----|---------|------|
| JSON 解析热循环 | ✅ | 纯计算 |
| 路由表匹配循环 | ✅ | 纯计算 |
| 限流令牌桶算法 | ✅ | 纯计算 |
| 加密摘要（`resty.string`） | ✅（走 FFI/OpenSSL） | FFI 边界友好 |
| HTTP 请求发送（cosocket） | ❌ | yield 结构上不可 JIT |
| Redis 查询（cosocket） | ❌ | 同上 |
| 日志写入（`ngx.log`） | 部分 ❌ | C 调用可 JIT，但字符串拼接易 NYI |
| 定时器回调 | 部分 ❌ | 回调本身可 JIT，跨 yield 不可 |

**结论**：**性能优化的重点在纯计算部分**，别指望把 `sock:receive()` 编成机器码就快；能编的是它**前后**的数据处理。

# 避坑

- **别在业务代码里手写 `bit.*`**：LuaJIT 的 `bit` 库部分函数是 NYI；能用 `+ - * /` 与位运算符就用（LuaJIT 2.1 的 `bit` 走 FFI，很快，但某些函数如 `bit.tohex` 有 NYI 路径）。
- **`pcall` 不是 NYI，但里面的错误路径是**：`pcall` 编译成 guard，正常走 trace；一旦 `pcall` 内部抛错 → 立刻 side exit，回到解释器。**热路径里 pcall 命中错误的比例 >1% 就该重构**。
- **`debug.traceback` 每次调用都 NYI**：用 `resty.core.traceback` 替换（见 04 篇），或干脆不在 content handler 里 traceback，改在 `log_by_lua` 里异步打。
- **`ngx.location.capture` 每次都 NYI**：这是设计上的，改不掉。要性能就走**批量合并子请求**或改 `cosocket`。
- **`jit.on()` 默认全开**，`jit.off(my_func)` 可以精准关；如果发现某个函数触发过多 side exit 拖慢整体，可以让它单独解释器跑，反而更稳。
- **`jit.flush()` 不解决根本问题**：只是清空 code cache；NYI 的函数下次执行还是会走解释器。别把它当"性能急救"。
- **trace abort 不等于慢**：LuaJIT 解释器本身也不慢（比 Lua 5.1 参考实现快 2-4x）；只有**密集热循环**掉回解释器才显著。日志类、IO 类代码即使不 JIT 也无感。

# 验证

```bash
# 跑一段你的业务代码，看 NYI 出现频次
luajit -jv -e '
    package.path = "./lualib/?.lua;"..package.path
    local handler = require("app.hello")
    for _ = 1, 10000 do handler({ uri = "/", args = {} }) end
' 2>&1 | grep -E 'NYI|abort' | sort | uniq -c
```

`-jv` 输出里出现 `NYI: ...` 就是命中，按前面的改写模式处理。

# 总结

NYI 是 LuaJIT 的"边界条件清单"。**结构性 NYI**（协程 yield、动态 require、vararg）改不掉，能改的是**写法性 NYI**（error 在循环里、`debug.traceback` 热路径、`string.gsub` 函数回调）。用 `-jv` / `vmprofile` 观测、把纯计算热路径圈出来、把 IO 逻辑留在 yield 侧——这才是 OpenResty 里"JIT 友好"的正确姿势。搞懂 NYI 之后，[040.lua-resty-core 与 FFI](./040.lua-resty-core与FFI.md) 讲 FFI 如何系统性地绕开 Lua 层的 NYI。
