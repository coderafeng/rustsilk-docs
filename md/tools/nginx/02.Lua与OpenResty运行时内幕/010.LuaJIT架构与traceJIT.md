# 概述

LuaJIT 不是"更快的 Lua 字节码 VM"——它是一台**基于 trace 的 JIT 编译器**：跑解释器记录一段"线性执行路径"（trace），编译成机器码，之后热路径直接跳过去。理解 trace 是什么、怎么触发、怎么观察，就理解了 OpenResty 里 Lua 性能的上限和天花板。

# 分层架构

```
   ┌──────────────────────────────────────────────┐
   │        Lua 源码 / 字节码 (BCB, 32-bit)         │
   └──────────────────────────────────────────────┘
                        │
                        ▼  ①解释器执行，profile 计数器
   ┌──────────────────────────────────────────────┐
   │   Interpreter (BC interpreter + hotcount)     │
   └──────────────────────────────────────────────┘
                        │  ②loop header 触发 trace 录制
                        ▼
   ┌──────────────────────────────────────────────┐
   │   Trace Recorder                              │
   │   ─ 沿解释器执行路径线性记录                  │
   │   ─ 遇到不可 JIT 的操作 → 停止（NYI / 编译失败）│
   │   ─ 记录 guard（分支条件、类型断言）           │
   └──────────────────────────────────────────────┘
                        │  ③录制结束，交给 IR 后端
                        ▼
   ┌──────────────────────────────────────────────┐
   │   IR（SSA 静态单赋值）→ 优化 → 后端          │
   │   ─ 类型 specialization、常量折叠、循环不变外提│
   │   ─ 寄存器分配（x86_64 用 GC64）              │
   └──────────────────────────────────────────────┘
                        │  ④生成机器码，进入执行
                        ▼
   ┌──────────────────────────────────────────────┐
   │   Native Code (trace entry)                   │
   │   ─ guard 失败 → side exit → 回到解释器或     │
   │     进入另一条 side trace                     │
   └──────────────────────────────────────────────┘
```

**关键区别**（vs V8 SpiderMonkey 类方法 JIT）：LuaJIT 编译的**不是函数，是"一次循环里走的那条路径"**——同一段代码，if 分支 A 和分支 B 会编成两条不同的 trace。这就是为什么它对**动态类型语言**特别有效：一条 trace 上类型是稳定的。

# trace 触发与终结

## Hot 判定

LuaJIT 里有两个计数器：
- **BC 热度**：基本块执行次数
- **Loop 热度**：向后跳转次数（`lj_vm_bcjit_hotcount` 初始 ~40，可调 `hotcount` 参数）

任一超阈值 → 请求 trace 编译（异步，通过 `lj_trace_hot()`）。

## Trace 结束时机

| 结束方式 | 场景 | 结果 |
|---------|-----|------|
| **Close** | 遇到向后跳转（loop back edge）且路径完整 | 编译成循环 trace，最理想 |
| **Side exit** | guard 失败（类型变了、分支走了另一路） | 回解释器 / 分一条 side trace 继续 |
| **Root abort** | 录制过程遇到 NYI（如 `coroutine.resume`、`error()`） | 本次放弃编译，代码回到解释器 |
| **Trace full** | 一条 trace 太长（默认 ~64K 指令） | 停止录制并编译已录部分，剩余留解释器 |

## Side trace

从主 trace 的某个 side exit 点开始再录一条，叫 side trace。多条 side trace 会**独立编译**，guard 成功走主 trace、失败跳 side trace。合理使用让 if 分支不再拖慢主循环，但**过多 side trace 会让 code cache 膨胀**。

# 在 OpenResty 里怎么用

**业务代码不需要"为 trace 而写"，只需要给 trace 创造可录制条件**：

```lua
-- ✅ 好：热路径主体是紧凑循环 + 稳定类型
local function sum_scores(t)
    local s = 0
    for i = 1, #t do
        s = s + t[i]        -- t[i] 一直是 number
    end
    return s
end

-- ❌ 坏：类型抖动 + 大量分支 → 频繁 side exit
local function sum_scores(t)
    local s = 0
    for i = 1, #t do
        local v = t[i]
        if v == nil then v = 0 end        -- 类型检查触发 guard
        if type(v) ~= "number" then        -- 又是 guard
            v = tonumber(v) or 0
        end
        s = s + v
    end
    return s
end
```

**类型稳定 > 分支整洁**——trace JIT 更喜欢"看起来朴素"的代码。

# 观测：`-j` 参数

```bash
# 1) 反汇编：看每条 trace 编成了什么
luajit -jdump hello.lua > jit.txt
# 或用 resty CLI（需要 nginx 侧设置环境变量）
LUAJIT_VM="dump:111" openresty   # 见 LuaJIT wiki

# 2) 只关心 NYI：为什么 trace 编不出来
luajit -jv hello.lua
# [trace   0 start hello.lua:3]
# [trace   0 stop → loop repeated 50 times]

# 3) 统计
luajit -jstat hello.lua
# JIT statistics: ... traces compiled / aborts / side exits / ...

# 4) 关掉 JIT（回到解释器）——用于 A/B 对照
luajit -e 'require("jit").off()' hello.lua
luajit -e 'require("jit").optimization=0' hello.lua   -- 只关优化
```

在 OpenResty 里，`jit` 库完全可用：

```lua
-- init_worker_by_lua_block 里
local jit = require("jit")
jit.opt.start("hotcount=80")     -- 更早编译（默认 40，热路径极短时值得调）
jit.flush()                       -- 手动清所有 trace，测试/灰度回滚时用
```

> [!warning]
> **不要在请求路径调 `jit.flush()`**——会让所有 worker 上的 trace 编译工作重来一遍，短时 CPU 抖动明显。只用于 A/B 实验或热重载 Lua 后强制重编。

# 避坑

- **`for i=1,n do` 是 trace 的好朋友，`while cond do` 不一定**：`while` 里的 `cond` 每次都会 guard，如果 cond 依赖外部变量（如 `shared_dict:get(...)`），guard 会失败；`for` 循环的 `n` 一旦被 specialize 到 trace 上就很稳。
- **`pairs` 迭代**在 LuaJIT 2.1 上是**可以 trace 的**（`next()` 有对应 handler），但**性能不如 `ipairs` / `for i=1,#t`**——因为 `next` 需要遍历内部 hash 部分，缓存不友好。
- **长闭包/深层 upvalue**：`upvalue` 通过内存引用，跨 trace 时 guard 会重；热路径上的 upvalue 尽量不超过 4-5 个。
- **不要 `require` 动态模块名**：`require(ngx.var.mod)` 让 trace 里的调用点无法 specialize，每次 side exit；改成显式分派表。
- **`goto` 与 label 打断 trace**：LuaJIT 2.1 支持 goto，但**跨循环的 goto 会 abort trace**——`break` 是安全的，`goto continue` 在循环里也是安全的，`goto` 出循环就是坑。
- **x86_64 上 GC64 默认打开**：OpenResty 的 luajit2 fork 在 x86_64 上默认开启 GC64（更大堆、更慢一点点 GC 步进但更稳）；`luajit -V` 看到 `GC64` 就是它。

# 验证

```bash
# 打开 dump，跑一个 hello handler 看有几条 trace
luajit -jdump -e '
local function hot(n)
  local s = 0
  for i = 1, n do s = s + i end
  return s
end
for _ = 1, 100 do hot(1000) end
' 2>&1 | head -50
# 期望看到 [trace   0 hot ...] / [trace   0 stop → loop ...]
```

在 OpenResty 里，把 `error_log` 打到 `info` + `LUAJIT_VM=dump:111` 环境变量重启，也能看到 trace 编译事件（仅调试用，别上生产）。

# 总结

LuaJIT 的 trace 编译把"跑得久的 Lua 循环"变成机器码，代价是**任何破坏"路径稳定性"的操作**（类型抖动、动态调用、NYI）都会退到解释器。**写热路径 Lua 的心法**：让循环紧凑、让类型稳定、少 guard、少 side exit；调优时靠 `-jv` 与 `-jdump` 观测，别凭感觉改。搞懂 trace 之后，[030.NYI 与 JIT 失效](./030.NYI与JIT失效.md) 讲它就是这套模型的"黑名单"。
