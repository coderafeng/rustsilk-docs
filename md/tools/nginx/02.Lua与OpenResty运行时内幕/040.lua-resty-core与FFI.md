# 概述

`lua-resty-core` 是 OpenResty 官方维护的**Lua API 新实现层**，用 **FFI** 直接调 nginx/lua-nginx-module 的 C 函数，逐步替代 lua-nginx-module 早期通过 C closure 封装的老 API。**在 OpenResty 里 `require "resty.core"` 让常用 API 提速 2-10 倍**；从 1.15 起官方包默认帮你自动加载（`init_by_lua_block` 里那行 `require "resty.core"`）。

这一篇讲：**FFI 为什么快、`resty.core.*` 家族都有谁、加载与生效方式、以及"到底要不要显式 require"的取舍**。

# FFI 快在哪

**传统 Lua → C 调用链**（`lua_getfield` → C 函数 → `lua_pushXXX` → 返回）：
```
Lua VM 字节码          C 栈操作             C 函数体
mov R0, "ngx"          lua_getglobal         ngx_http_lua__xxx
call R0, "say", R1     lua_pushlstring       ...
                       lua_call              ...
```
每次都涉及：**字符串查找、Lua 栈 push/pop、类型检查、GC 写屏障**。

**FFI 调用链**：
```lua
local ffi = require("ffi")
ffi.cdef[[ int ngx_http_lua_ffi_stat(uchar *path, int *st_size, ...); ]]
local C = ffi.C
local rc = C.ngx_http_lua_ffi_stat(path, size_ptr, ...)
```
- `ffi.cdef` 一次性解析 C 声明到内部类型表；
- 调用时 JIT 直接生成"把参数按 C ABI 放进寄存器 + call"的机器码；
- **无 Lua 栈、无字符串名查表、无 GC 写屏障**；
- 类型错误在**编译期**就 guard 住，不进解释器。

一个数量级的差距，尤其是**小函数、高频调用**（`ngx.re.match`、`ngx.escape_uri`、`ngx.encode_base64`）场景。

# `resty.core.*` 家族清单

装了 lua-resty-core 后，通过 `require "resty.core"` 一次性启用以下模块的重写版：

| 模块 | 替换的 API | 提速幅度 |
|-----|-----------|---------|
| `resty.core.base` | 内部工具 | — |
| `resty.core.uri` | `ngx.escape_uri` / `ngx.unescape_uri` | 3-5x |
| `resty.core.string` | `ngx.encode_base64` / `ngx.decode_base64` / `ngx.md5` / `ngx.sha1_bin` | 2-4x |
| `resty.core.re` | `ngx.re.match/find/gmatch/sub/gsub` | 2-6x（PCRE JIT 加成） |
| `resty.core.hash` | `ngx.md5` / `crc32` / `hmac` | 2-4x |
| `resty.core.time` | `ngx.now` / `ngx.time` / `ngx.today` / `ngx.localtime` / `ngx.http_time` | 3-5x |
| `resty.core.request` | `ngx.req.*` 一批 | 1.5-3x |
| `resty.core.response` | `ngx.resp.*` | 1.5-3x |
| `resty.core.misc` | `ngx.worker.*` / `ngx.get_phase` | 2-4x |
| `resty.core.coroutine` | `coroutine.*`（Nginx 版） | 1.5-2x（配合 07 篇） |
| `resty.core.cond` / `resty.core.rwbf` | `ngx.cond` / `ngx.rwlock`（内部原语） | 结构性 |
| `resty.core.pm` | 预编译 PCRE 匹配缓存 | 视场景 |
| `resty.core.var` | `ngx.var.*` 读写 | 2-5x |
| `resty.core.utils` | 类型判定 / 参数检查 | — |
| `resty.core.queue` / `resty.core.queue` | `ngx.queue`（LRU 底层） | — |

**没被替换的**：`ngx.socket.*`（cosocket 本身是 C 层 yield，FFI 帮不上）、`ngx.location.capture`、`ngx.shared.DICT`（本身有专用 C API，另走 `resty.core.shdict`）、`ngx.timer.*`。

# 加载方式

## 1) 自动（OpenResty 官方包默认）

Ubuntu APT 装的 `nginx.conf` 里通常已经带：

```nginx
init_by_lua_block {
    require "resty.core"
}
```

或走 `lua_resty_core` 模块的编译期默认。`openresty -V` 看到 `--with-lua-resty-core` 就是内置。

## 2) 手动启用

如果你自定义了 `nginx.conf`：

```nginx
lua_package_path "/usr/local/openresty/lualib/?.lua;;";

init_by_lua_block {
    require "resty.core"     -- 一次即可，之后 ngx.* 走新版
}
```

## 3) 单独启用某个模块

```lua
require "resty.core.re"    -- 只重写 ngx.re.*
require "resty.core.time"  -- 只重写时间相关
```

## 4) 关闭

不 `require "resty.core"` 就是关闭；`jit.off("return ngx.re.match")` 之类的手段对 FFI 版没意义。

# 验证是否生效

## 方法 1：查函数指针

```lua
print(ngx.re.match)
-- 老实现：function: builtin#XXX
-- 启用 resty.core：function: 0x7f...  （Lua 层 FFI wrapper）
```

## 方法 2：微基准

```lua
-- init_worker_by_lua_block 里
local t0 = ngx.now()
for _ = 1, 1e6 do
    ngx.re.match("hello, world", [[\w+]])
end
ngx.log(ngx.INFO, "ngx.re.match 1e6 in ", ngx.now() - t0, "s")
```

关掉 `require "resty.core"` 前后对比，差 2-6x。

## 方法 3：`resty` CLI 冒烟

```bash
resty -e '
    require("resty.core")
    print(type(ngx.re.match))  -- 期望 function
    print(ngx.re.find("abc123", "%d+"))   -- 3 6
'
```

# 与 `lua-resty-*` 生态的关系

- **业务库**（`lua-resty-http`、`lua-resty-redis`）本身**不依赖** `lua-resty-core`——它们用 `ngx.socket.tcp` 之类；但底层的 `cjson`、`bit`、`ffi` 会用到 `resty.core` 提供的加速版字符串函数。
- **Kong / APISIX** 默认 `require "resty.core"`；自研网关请照做。
- **测试**：`Test::Nginx` 用例里如果没启用 `resty.core`，某些断言（`ngx.re` 返回值细节）可能与生产不同——团队约定统一。

# 避坑

- **不要重复 `require "resty.core"`**：`package.loaded` 会缓存，但**如果 nginx.conf 里 init 阶段已经加载，业务代码再 require 会静默 no-op**；重复调用本身没坏处，别在热路径里做。
- **`resty.core` 加载顺序**：必须在**其它任何 `ngx.*` API 被调用前**加载；写在 `init_by_lua_block` 第一行最安全。
- **不是所有 `ngx.*` 都变快**：cosocket、`ngx.location.capture`、`ngx.timer.*` 与 FFI 无关；只有"简单字符串/时间/正则"这类边界薄的调用提速明显。
- **`resty.core` 与 `resty.core.base` 版本要严格匹配 OpenResty**：apt 装的 openresty 会拉对应的 lua-resty-core 版本；源码编译要显式 `--with-lua-resty-core=path` 或用官方 tarball（自带）。
- **`lua_code_cache off` 时 `require "resty.core"` 每请求跑一次**：开销被抵消；调试模式不评估性能。
- **别混用 `lpeg` 和 `resty.core.re`**：两者都能做正则/模式匹配，功能重叠；选一个团队规范。`lpeg` 有 C 扩展、`resty.core.re` 走 PCRE JIT，性能场景不同。
- **`resty.string`（Lua 层）与 `resty.core.string`（FFI）不要混淆**：前者是工具函数集（`to_hex`、`to_base64`），后者是重写 `ngx.*`。

# 总结

**`lua-resty-core` 是 OpenResty 性能模型里最"低成本高回报"的一环**：一行 `require "resty.core"`，纯计算热路径的字符串/时间/URI/正则操作全部走 FFI，快 2-10 倍。官方包默认帮你打开；自定义 `nginx.conf` 时不要漏。FFI 是它的**机制**，`resty.core` 是它的**封装**——想知道 FFI 本身怎么写，参考 [020.标准 Lua 与 LuaJIT 差异](./020.标准Lua与LuaJIT差异.md) 里的 `ffi.cdef` 示例；生产代码里直接依赖 `resty.core` 就够了，一般不需要自己写 FFI 声明。
