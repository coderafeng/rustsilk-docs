# 概述

Lua 的**协程（coroutine）** 是 OpenResty 支持"一个 worker 处理数万并发"的**核心机制**：每个 HTTP 请求跑在自己的 Lua 协程里，遇到 IO（cosocket、subrequest、`ngx.sleep`）就 `yield` 回 Nginx 事件循环；事件就绪时 Nginx 再 `resume` 那个协程。开发者写代码像同步，底层是异步非阻塞——这就是所谓的 **stackless 协程 + 事件驱动**模型。

# 三层关系

```
   ┌──────────────────────────────────────────────┐
   │  Nginx worker（一个进程 = 一个事件循环）      │
   │                                              │
   │  ┌──────────┐  ┌──────────┐  ┌──────────┐   │
   │  │ request  │  │ request  │  │ timer    │   │
   │  │ 协程 A    │  │  协程 B   │  │ 协程 C   │   │
   │  │ (Lua co) │  │  (Lua co) │  │ (Lua co) │   │
   │  └────┬─────┘  └────┬─────┘  └────┬─────┘   │
   │       │ yield        │ yield        │ yield   │
   │       ▼              ▼              ▼         │
   │  ┌───────────────────────────────────────┐   │
   │  │      ngx_http_lua_module (C 层)        │   │
   │  │      协程调度器 / resume 触发点         │   │
   │  └───────────────────────────────────────┘   │
   │       ▲              ▲              ▲         │
   │       │ 事件就绪      │              │         │
   │  ┌────┴──────────────┴──────────────┴────┐   │
   │  │      Nginx 事件循环（epoll/kqueue）     │   │
   │  └────────────────────────────────────────┘   │
   └──────────────────────────────────────────────┘
```

- **一个 worker 只有一个 OS 线程**——所有请求协程都在这一个线程上被 Nginx 主动切换。
- **切换点由 lua-nginx-module 埋在每个可 IO 阻塞的 API 里**：`sock:receive` / `sock:send` / `ngx.location.capture` / `ngx.sleep` / `ngx.wait` 等。
- **协程挂起时 worker 立刻可以处理其他事件**，这就是"单线程高并发"的实现。

# Lua 原生协程 vs OpenResty 里的协程

Lua 层的 `coroutine.create/resume/yield/status/wrap` 在 OpenResty 里**都可用**，但**不能直接 yield 到 nginx 事件循环**——只有走 `ngx.*` API 时才由 lua-nginx-module 内部触发"yield → epoll → resume"。业务代码里几乎不会手写 `coroutine.yield`；你写 `local res = sock:receive()` 就已经 yield 了一次。

`resty.core.coroutine`（[040 篇](./040.lua-resty-core与FFI.md)）把 Lua 原生协程 API 用 FFI 重写，**跨协程切换更快**。

# `ngx.thread.*`：同一请求内的并行

真正的"并行"发生在同一个请求 handler 里发多路 IO：

```lua
-- 并行拉两个上游
local http = require "resty.http"

local t1 = ngx.thread.spawn(function()
    local c = http.new()
    local res, err = c:request_uri("http://svc-a/foo")
    return res and res.status or err
end)

local t2 = ngx.thread.spawn(function()
    local c = http.new()
    local res, err = c:request_uri("http://svc-b/bar")
    return res and res.status or err
end)

local ok, res1 = ngx.thread.wait(t1)
local ok2, res2 = ngx.thread.wait(t2)

ngx.say(res1, " ", res2)
```

要点：

- `ngx.thread.spawn(fn, ...)` **立即开始执行** fn（不是排队），fn 里的第一个 yield 点让主协程回来继续。
- `ngx.thread.wait(...)` 阻塞当前协程直到**至少一个** thread 完成；返回谁先完成。
- 一个请求最多允许 `lua_max_running_timers` + `lua_max_pending_timers` 数量的 thread（默认各 4096），实际能开多少取决于内存。
- **`ngx.thread.kill(thread)`** 可以取消；被 kill 的 thread 里如果卡 cosocket，会强制释放 socket。

# `ngx.timer.*`：跨请求的异步任务

```lua
-- 每 5 秒刷一次上游列表
ngx.timer.every(5, function(premature)
    if premature then return end
    local ok, err = refresh_upstream_table()
    if not ok then ngx.log(ngx.WARN, "refresh failed: ", err) end
end)

-- 单次异步任务：log_by_lua 里做上报
log_by_lua_block {
    local payload = {
        uri = ngx.var.uri,
        status = ngx.status,
        rt = ngx.var.request_time,
    }
    ngx.timer.at(0, function(premature)
        if premature then return end
        -- 这里没有 ngx.ctx / ngx.var / ngx.req（响应已发完）
        local ok, err = report(payload)
        if not ok then ngx.log(ngx.WARN, err) end
    end)
}
```

**timer 里的世界**：

- **不能**读写 `ngx.ctx` / `ngx.var` / `ngx.req` / `ngx.status`（请求已结束）
- **可以**读写 `ngx.shared.DICT`（跨 worker）
- **可以**用 cosocket（timer 里的协程与请求协程共用事件循环）
- `premature` 参数：nginx 关闭/worker 退出时，未跑完的 timer 会被"提前触发"通知你清理；**永远先判 premature**。

# 请求协程生命周期

一个请求协程从创建到销毁：

```
1. nginx 收到连接 → lua-nginx-module 创建一个 Lua coroutine
2. coroutine.resume(co) → 进入 rewrite/access/content handler
3. handler 里每次 IO → yield；事件循环处理其他请求；就绪再 resume
4. handler 结束 → 协程自然终止
5. log_by_lua 又起一个协程（不复用）
6. worker 退出 / lua_max_running 达上限 → 剩余协程被 premature 通知
```

**每个阶段是同一协程还是新协程**：`rewrite/access/content` **同一个协程**（可共享 `ngx.ctx`）；`header_filter/body_filter/log` 各是不同上下文，`ngx.ctx` 仍可见但不保证同协程。

# 上下文与栈

```lua
-- 每个请求协程有独立的 Lua 栈（默认 size 256 slots）
-- 独立于 worker 的 C 栈；协程切换是"保存/恢复指针"，不拷栈帧

-- 深度受限：
--   lua_socket_buffer_size / client_body_buffer_size 等
-- 递归过深会抛 "stack overflow"（Lua 层，不是 segfault）
```

**栈是廉价的**（Lua 协程是 **heap-allocated**，创建/销毁 <1μs）；但**每个协程占内存**（默认栈 256 个 slot × 16B ≈ 4KB），上万并发就是几十 MB，需要预留。

# 避坑

- **不要在 `body_filter_by_lua` / `header_filter_by_lua` 里 yield**：这些是同步 C 回调，Lua 层协程不能安全挂起；`ngx.socket.tcp` 直接抛 `API disabled`。
- **不要在同一个请求协程里 `coroutine.resume(coroutine.create(...))` 手动跑**：绕过 lua-nginx-module 的调度，`ngx.*` 会拿不到请求上下文——用 `ngx.thread.spawn` 代替。
- **别忘 `premature` 判断**：`if premature then return end`；worker reload 时未跑完的 timer 会带 `premature=true` 通知你，不判就可能操作已失效的 shared dict。
- **`ngx.thread.wait` 只拿第一个完成**：要拿全部 → 多次 wait 每个 thread；要"最快成功、其他取消"→ wait 完 kill 其他。
- **`timer.at(0, ...)` 不是立即执行**：它是"下一个事件循环 tick 里执行"；同一请求的 handler 结束后才跑；要 truly 同步请内联。
- **timer 里 cosocket 与请求里的 cosocket 是两个连接池**：`sock:setkeepalive()` 后释放到 worker 全局池，不区分；但 `sock:close()` 就直接关。
- **协程数量控制**：`lua_max_running_timers 256; lua_max_pending_timers 4096;`（默认），压测环境要放大；超过上限时 `ngx.timer.at` 返回 "too many pending timers" 错误。
- **`pcall` 里的 yield 会污染栈**：`pcall(function() ngx.sleep(1) end)` 在 5.1 是**不支持跨 pcall yield** 的（有 C 边界），LuaJIT 里也一样；改用 `pcall` 包整段或用 `xpcall` + 无 yield 的分支。

# 验证

```lua
-- init_worker_by_lua_block 里
ngx.timer.every(1, function(premature)
    if premature then return end
    local co = coroutine.running()
    ngx.log(ngx.INFO, "timer co=", tostring(co))
end)

-- content handler 里
content_by_lua_block {
    local co = coroutine.running()
    ngx.log(ngx.INFO, "req co=", tostring(co))
    ngx.sleep(0.01)     -- 触发 yield → resume
    ngx.log(ngx.INFO, "req co=", tostring(co))   -- 同一个 co
}
```

日志里能看到"请求协程"和"timer 协程"是不同的 coroutine 指针；请求协程 sleep 前后指针不变（同一个协程被挂起再恢复）。

# 总结

OpenResty 的并发模型 = **一个 OS 线程 × N 个 Lua 协程 × 事件驱动**：请求协程承载 handler 逻辑，`ngx.thread.*` 做请求内并行，`ngx.timer.*` 做跨请求异步。理解协程 yield/resume 的边界——**哪些 API 会 yield、哪些上下文禁止 yield**——就掌握了一半 OpenResty 的性能与稳定性心法。剩下的另一半是 worker 间状态共享，见 [080.共享内存与 worker 通信](./080.共享内存与worker通信.md)。
