# 概述

技术之外，"要不要用 OpenResty"、"怎么说服团队"、"如何一步步引入生产"是**更常见**的阻力。本文按问答整理引入 OpenResty 的**方法论**，覆盖：立项、试点、平台化、退出策略。

# 一、什么时候该引入 OpenResty

## 触发信号

- 现有网关（nginx / HAProxy）**需要写逻辑**，靠 Lua/Perl 打补丁很痛；
- Java/Go 网关团队**发版周期长**（≥2 周），业务等不起；
- 有明确的**动态化诉求**：灰度、限流、鉴权、路由要秒级生效；
- 运维层面对"改配置就 reload nginx"能接受；
- 团队里有 1-2 人熟悉 nginx；Lua 可现学（语言本身不难）。

## 反向信号

- 只是想"跑一段业务代码" → 直接 Spring Boot / Go；
- 团队完全没有运维 nginx 的经验 → 学习曲线陡；
- 现有基础设施已经 All-in Envoy（Istio / Kong） → 增量学 OpenResty 收益有限；
- 需要复杂业务规则 / 大量第三方 SDK → 换 Go/Java。

**判据一句话**：**"IO 编排 + 动态配置 + 有 nginx 底子"** → 上；否则三思。

# 二、如何说服团队

## 反对意见与回应

| 反对 | 回应 |
|------|------|
| "Lua 太小众，招不到人" | 网关代码不需要 Lua 专家；有 nginx 底子的运维一周上手；核心由 1-2 人写、其他人用 |
| "生态小，库少" | 网关场景本身需求集中；`lua-resty-*` 覆盖足够；缺的库多为非核心 |
| "没有类型检查，容易写错" | 严格 luacheck + Test::Nginx；核心代码 PR 双人 review；上线前 wrk 基准 |
| "Kong / APISIX 已经基于 OpenResty，为什么不直接用" | **正解**——能不用自己写就别写；OpenResty 是底座，Kong/APISIX 是产品 |
| "线上出事谁负责" | 建 SRE 值守手册 + 演练；每个动态配置有回滚；见 [05 章 140](../05.OpenResty性能优化/140.OpenResty杀手锏动态.md) 生产纪律 |

## 决策路径

```text
Step 1: 明确"不用 OpenResty 会怎样"
    ↓ 说清楚痛点（配置生效慢、代码改动重、动态性差）
Step 2: 对比候选（Envoy / Kong / APISIX / 自研 OpenResty）
    ↓ 讲清楚"我们为什么不选其他"
Step 3: 找一个小场景做 PoC（一周量级）
    ↓ 拿真实数据（延迟、QPS、开发效率）说话
Step 4: 试点上线一个非核心业务（1 个月）
    ↓ 建运维手册 / 应急预案
Step 5: 平台化：把网关能力封装成 SDK / 服务
```

**不要一上来 All-in**。Step 3 的 PoC 通常能解决 80% 的争论。

# 三、PoC 场景选择

**好的 PoC**：
- **业务量小**：挂了不致命；
- **改动可控**：一周能出结果；
- **有对比基准**：能算"用了 OpenResty 快多少 / 慢多少"；
- **暴露核心痛点**：比如"配置热更"是刚需，PoC 就要证明这个。

**推荐场景**：
1. **API 网关侧的动态路由**——从配置中心拉规则；改配置秒级生效；
2. **鉴权前置**——JWT 校验放在网关，业务后端不用管；
3. **BFF 聚合**——一次请求聚合 3-5 个下游；
4. **灰度分流**——按 header 分流到不同 upstream；

**避开**：交易主链路、核心数据变更、涉及资金/风控的场景。

# 四、试点上线的六个月节奏

```text
Month 1  PoC + 架构评审
   ↓
Month 2  第一版网关；1 个非核心业务
   ↓
Month 3  观测体系完善：指标、日志、告警、Dashboard
   ↓
Month 4  第二个业务；开始有 SLA 承诺
   ↓
Month 5  平台化：SDK / 配置中心 / 权限模型 / 变更流程
   ↓
Month 6  生产化：容量演练、故障演练、灾备切换
```

**每月一个可交付物**；不要攒大招。

# 五、平台化的三个必要组件

## 1. 配置中心 + 变更流程

- 谁能改配置？（RBAC）
- 改之前怎么审？（PR / 双人 review）
- 改之后怎么回滚？（版本 + 一键回滚）
- 改错了怎么告警？（灰度 → 观察 → 全量）

## 2. 观测面板

- 网关本身的：QPS、延迟分位数、CPU、内存、worker 状态；
- 业务的：每个 API 的调用量、成功率、下游耗时；
- 动态化的：限流触发次数、熔断打开实例、灰度比例；

Grafana + Prometheus 或 OpenResty Dashboard。

## 3. SDK / 内部框架

- 网关代码统一骨架（路由 / 鉴权 / 限流 / 熔断 / 日志）；
- 业务同学**只需**注册路由 + 写 policy；不用碰 Lua；
- SDK 版本升级流程（半自动）；

**没有 SDK，OpenResty 只能服务 5-10 人；有 SDK 才能服务 100 人**。

# 六、退出策略

任何引入都要预设**退出条件**。三种退出：

- **降级**：OpenResty 挂了 → 直接透传 nginx（保留最基础的 location 匹配）；配置和代码要能在 nginx 侧独立起来；
- **替换**：Envoy 生态成熟到能覆盖 → 迁；把 OpenResty 侧的规则做成声明式配置（YAML / JSON），迁移成本可控；
- **收缩**：某些功能（业务鉴权、复杂规则）不适合放网关 → 挪回后端；OpenResty 只做路由；

**永远不要**：让业务逻辑"只在 OpenResty 里能跑"、脱离后无法工作。

# 七、常见答疑

## Q：Lua 会不会成为团队短板？

**A**：网关代码不是"人人写 Lua"；是"1-2 人写核心，业务同学写 policy 配置"。学习曲线主要在 nginx 阶段模型，Lua 语言本身一周熟练。

## Q：性能真的够吗？

**A**：网关场景（IO 编排）绰绰有余；见 [03 章 010](../03.OpenResty核心API/010.与其它开发平台的差异.md)。**CPU 密集**才瓶颈。

## Q：为什么不直接 APISIX / Kong？

**A**：**能用就用**——自研只在他们不满足时用（特殊业务、私有云、深度定制）。**不要重复造轮子**。

## Q：出了事故谁扛？

**A**：SRE 值守手册 + 变更审计 + 灰度机制。**没有运维保障就别引入**——见"生产纪律"（05 章 140）。

## Q：动态代码下发安全吗？

**A**：不鼓励。配置可以动态、代码要走发版。真要下发代码，加签名校验 + 双人授权；见 05 章 140。

# 八、避坑

- **过度动态**：所有东西塞 shdict = 无法调试；核心逻辑仍放代码；
- **平台化太早**：只有 1 个业务就抽 SDK = 抽象错位；3 个业务再抽；
- **只学不建**：读完文档不动手；PoC 是最短路径；
- **缺少观测**：上线才发现什么都看不到；先建指标再上线；
- **忽略退出策略**：绑得太深；重构时走不了。

# 总结

- 引入触发：**IO 编排 + 动态配置 + 有 nginx 底子**；
- 决策路径：PoC → 试点 → 平台化；
- 六个月节奏：每月一个交付；
- 平台化三件套：配置中心 + 观测 + SDK；
- 预设退出策略；不要 All-in；
- 能选 APISIX / Kong 就选，别自己造。
