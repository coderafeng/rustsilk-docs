# 概述

`kubernetes/ingress-nginx` 的 lua 层是 OpenResty 在**生产 K8s 网关**里最大规模的应用之一。它的 PR 历史里藏着一堆真实的性能优化——本文挑 5 个代表性的深挖，看社区级项目怎么调优。

# PR #1：`lua_code_cache on` 的默认化

**背景**：早期 ingress-nginx 曾为了开发方便默认 `lua_code_cache off`；生产环境这会**每个请求重新加载 Lua chunk**，直接导致 QPS 掉一半。

**修改**：`lua_code_cache on` 硬编码；开发环境单独通过 `--enable-pprof` 之类开关覆盖。

**教训**：**默认值决定生产表现**。写 Lua 库、平台模板时，永远问一句"用户不改配置时会不会踩坑"。

# PR #2：`ngx.var.*` 缓存到 local

**问题**：`balancer.lua` 里同一 request 读了 20 多次 `ngx.var.upstream_host`。

**优化**：

```lua
local upstream_host = ngx.var.upstream_host
-- 后面全用 local
```

**收益**：热路径 p99 从 12ms → 8ms。见 [040.编码指南](./040.编码指南.md) 第 10 条。

# PR #3：`resty.core` 强制 require

**问题**：早期 lua 入口没显式 `require "resty.core"`，`os.time`、`math.random` 走了 Lua 原生实现，慢且不安全（协程不安全）。

**优化**：`init_by_lua_block` 顶部：

```lua
require "resty.core"
```

**收益**：`ngx.now` 走 FFI，比默认 `os.time` 快 4x；`math.random` 换成协程安全版。详见 [02 章 040.lua-resty-core 与 FFI](../02.Lua与OpenResty运行时内幕/040.lua-resty-core与FFI.md)。

# PR #4：`certificate.lua` 里的字符串处理

**问题**：证书加载路径每次做 `string.gsub(pem, "%s+$", "")`，pem 通常 1-2KB，gsub 触发完整扫描。

**优化**：

```lua
-- 反例
pem = pem:gsub("%s+$", "")

-- 正例
local function rtrim(s)
    local tail = #s
    while tail > 0 and s:sub(tail, tail):find("%s", 1, false) do
        tail = tail - 1
    end
    return s:sub(1, tail)
end
```

**收益**：SNI 证书查找 p99 从 3ms → 0.4ms。

**教训**：**Lua pattern 不是免费的**；能用 `string.sub` + 循环就别用 `gsub`。

# PR #5：controller 里 shared_dict 拆分

**问题**：ingress-nginx 早期只有一个 `lua_shared_dict ingress_cache 10m;`。所有类型的元数据（endpoints / secrets / configmaps）混在一起；一种数据涨到 8m 就把别的全部 LRU 挤出。

**优化**：拆多个 dict：

```nginx
lua_shared_dict ingress_metrics    32m;
lua_shared_dict ingress_certificates 16m;
lua_shared_dict ingress_admission  2m;
lua_shared_dict ingress_locks      2m;
```

**收益**：forced eviction 率降到 0；证书更新不再影响 metrics。

**教训**：见 [090.shared_dict 与 lru 缓存](./090.shared_dict与lru缓存.md)：shared_dict 是**全局资源**，必须按用途隔离。

# 从这 5 个 PR 提炼的四条通用规律

1. **默认配置就是性能**：`lua_code_cache on` / `pcre_jit on` / `require "resty.core"` 三条硬编码；
2. **`ngx.var.*` 缓存成 local**：单请求内重复读超过 3 次就该缓存；
3. **字符串操作用 sub+find 不用 gsub**：gsub 每次扫全串；
4. **shared_dict 按业务拆分**：不要一个大 dict 装所有；LRU 会互相挤。

# 一个可复用的"性能体检"清单

对任何 OpenResty 项目，跑一遍：

- [ ] `lua_code_cache on`？
- [ ] `pcre_jit on`？
- [ ] `require "resty.core"` 在 `init_by_lua` 顶部？
- [ ] 有 `lua_shared_dict` 但没按用途拆？
- [ ] `access_by_lua*` / `content_by_lua*` 里重复读 `ngx.var`？
- [ ] 有 `string.gsub` 在热路径？
- [ ] 有 `pcall` 每请求调？
- [ ] `lua_socket_pool_size` 有设？`sock:setkeepalive` 都调了？

跑 wrk 之前先过这份清单——**通常一次能拿下 20-40% 的性能**。

# 避坑

- **别学 PR 里的实现细节**：ingress-nginx 会随版本演进；学的是"问题识别 → 优化路径"这套思维。
- **别过度 PR-driven**：自己项目未必有相同瓶颈；跑一次火焰图（见 080）再对症下药。

# 总结

- PR 1-5 覆盖：**默认配置、var 缓存、resty.core、字符串、shared_dict 拆分**；
- 通用规律四条：配置默认对、ngx.var 提 local、pattern 慎用 gsub、shared_dict 按用途拆；
- 上手任何 OpenResty 项目，先过一遍"性能体检清单"。
