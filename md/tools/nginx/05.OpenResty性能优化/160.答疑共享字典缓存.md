# 概述

关于共享字典与缓存，最常见的疑问集中在：**容量怎么估、命中率怎么算、跨机怎么同步、淘汰策略能不能改、和 Redis 怎么配合**。本文按问答整理。

# 容量与内存

## Q1：`lua_shared_dict` 到底占多少内存？

**声明 16m** 意思是 **slab 池 16 MB**，包含：
- slab 头部固定开销：约 100 KB；
- key/value 数据；
- 元数据（每 key 的 hash 节点、LRU 队列节点、过期时间戳）；

**实际能用的字节数 ≈ 声明值 − 200 KB − 每 key 平均 100 字节 × key 数量**。

假设存 100 万个 key，每 key 20 字节，每 value 200 字节：
- 数据本体 = 100 万 × (20 + 200) = 220 MB；
- 元数据 = 100 万 × 100 = 100 MB；
- 总需求 ≈ 320 MB；

**要 `lua_shared_dict cache 512m;` 才安全**。

## Q2：进程物理内存和 shdict 是什么关系？

`lua_shared_dict` 是**共享内存段**，被 worker mmap。多 worker 部署时**只占一份物理内存**——4 个 worker 用 16m shdict ≠ 64m；仍是 16m。

**但 shared_dict 会算进 worker RSS**——监控看到每个 worker RSS 都涨了 16m 是正常。

## Q3：能不能动态扩容？

**不能**。`lua_shared_dict` 大小在 nginx 启动时定死；改配置要 `reload`。想避免频繁 reload：一次给足；或走 Redis。

# 命中率

## Q4：怎么算命中率？

框架**不提供** hit/miss 计数——业务代码自己埋点：

```lua
local sh = ngx.shared.metrics
local v = sh_cache:get(key)
if v then
    sh:incr("cache_hit", 1, 0)
else
    sh:incr("cache_miss", 1, 0)
    v = fetch_origin(key)
    sh_cache:set(key, v, 60)
end
```

**别用 lrucache 内置指标**（无）；也不要拿 shdict `num()` 当命中率——那是"当前 key 数"，不是命中率。

## Q5：命中率 60%，正常吗？

看场景：
- **网关热点配置缓存**（路由、限流阈值）：99%+ 才正常；不到说明 TTL 或 key 设计有问题；
- **业务数据缓存**：60-80% 合理；再高可能没必要缓存；
- **负缓存**（防穿透）：命中率 = 攻击流量的比例；突然飙升 = 有人在探测不存在资源。

# 跨机同步

## Q6：多机器部署时 shdict 会同步吗？

**不会**。shdict 只在**同一台机器的 worker 之间共享**。跨机要么走 Redis，要么走 push 通知。

## Q7：配置中心推到多机怎么办？

**每条机器上的 OpenResty 独立拉**（pull 模式），或走消息队列 pub/sub（push 模式）。见 [130.动态限流限速](./130.动态限流限速.md)。

# 淘汰策略

## Q8：LRU 能改吗？

**不能**。shared_dict **只有 LRU**，不支持 LFU / FIFO / 自定义。想要别的策略：
- 业务代码维护"热度"，用 flags 存；淘汰时 `get_keys` + 排序 + delete（重）；
- 或干脆用 Redis（有多种策略）。

## Q9：`premature = true` 怎么办？

`set(k, v, ttl)` 返回第三个值 = `premature`；`true` 表示"因为容量不足，LRU 强制淘汰了别的 key"。

**处理**：

```lua
local ok, err, premature = sh:set(k, v, 60)
if premature then
    sh:incr("cache_forced_evict", 1, 0)     -- 打指标
    ngx.log(ngx.WARN, "forced eviction: ", err)
end
```

**告警**：`cache_forced_evict` 每秒 > 10 = 容量不够；扩 shdict 或减 TTL。

# 与 Redis 配合

## Q10：shdict 和 Redis 谁做 L1？

**shdict 是 L1，Redis 是 L2**——不是 lrucache 是 L1。原因：
- lrucache 每 worker 一份，跨 worker 不同步；命中率会打折；
- shdict 跨 worker，命中率高；
- Redis 跨机；

**极致追求延迟**：L0 = lrucache（每 worker）；L1 = shdict；L2 = Redis；L3 = DB。

## Q11：Redis 挂了 shdict 能顶上吗？

**能**——shdict 独立于 Redis。但注意：shdict 数据是"上次同步过来的"；Redis 挂时业务能读到旧数据；恢复后要主动刷新。

## Q12：shdict 数据能持久化吗？

**不能**。shdict 是纯内存；nginx stop 就丢。想持久化 → Redis / 文件 + `init_by_lua` 预加载。

# 并发与一致性

## Q13：多 worker 同时 incr 一个 key 会丢数据吗？

**不会**。`incr` 底层走 slab + 全局锁；单次操作原子。但 `get + 修改 + set` 三步不原子；要用 `cas` 或 `lua-resty-lock`。

## Q14：shdict 能保证跨机一致吗？

**不能**；跨机永远靠外部存储。

# 观测

## Q15：怎么监控 shdict？

三个关键指标：

```lua
-- /metrics
local sh = ngx.shared.my_cache
ngx.say("shdict_bytes_free ", sh:free_space())
ngx.say("shdict_keys ", sh:num())
ngx.say("shdict_forced_evict ", ngx.shared.metrics:get("cache_forced_evict") or 0)
```

**告警阈值**：
- `bytes_free / capacity < 0.2` → 预警；
- `forced_evict` 1 分钟 > 100 → 严重；
- `num()` 突然腰斩 → 可能被清空 / 有 bug。

# 避坑

- **shdict key 长度不设限**：单 key > 65535 字节会失败；控制在 200B 内；
- **shdict 里塞大 blob**：>100 KB 的 value 每次读写都 memcpy；改用 Redis；
- **`get_keys` 全局锁**：见 [03 章 040](../03.OpenResty核心API/040.shared_dict共享字典.md)；生产禁用；
- **flags 语义**：只支持 32-bit 整数；`cas` 会比对 flags；乱用会误伤。

# 总结

- 容量：按 key 数 + 元数据估；无热扩；
- 命中率：手动埋点；网关 99%+，业务 60-80%；
- 跨机：shdict 不管；上 Redis；
- 淘汰：只有 LRU；用 `premature` 告警；
- 一致性：单操作原子；复合操作要 cas / lock；
- 监控三件套：`bytes_free` / `num` / `forced_evict`。
