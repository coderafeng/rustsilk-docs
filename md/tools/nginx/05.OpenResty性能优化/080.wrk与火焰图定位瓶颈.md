# 概述

`wrk` 造负载 + `perf` 采火焰图 + FlameGraph 脚本出图——三件套组合是 OpenResty 性能定位的**标准流水线**。本文给完整操作。

# 一次端到端流程

```text
① 起 OpenResty + 目标业务
② 用 wrk 打固定速率（wrk2 -R）
③ 同时 perf record 采样 30s
④ stackcollapse-perf.pl 展平
⑤ flamegraph.pl 出 SVG
⑥ 打开 SVG，找"平顶山"
```

## ② wrk2 固定速率

```bash
wrk2 -t8 -c128 -d60s -R20000 --latency http://127.0.0.1:8080/api/hello
```

**为什么固定速率**：吞吐模式（wrk）会让 CPU 打满，火焰图看到的都是"CPU 已经饱和后的排队"；**固定速率**下 CPU 有余量，火焰图反映真实代码路径。

## ③ perf 采样

```bash
PID=$(pgrep -f "nginx: worker process" | head -1)
sudo perf record -F 99 -g -p $PID -- sleep 30
sudo perf script > out.perf
```

**关键**：`-F 99` = 99Hz 采样（避免与系统时钟共振）；`-g` 打开调用栈；`-- sleep 30` 采 30 秒。

## ④ 展平 + 出图

```bash
git clone https://github.com/brendangregg/FlameGraph
./FlameGraph/stackcollapse-perf.pl out.perf > out.folded
./FlameGraph/flamegraph.pl out.folded > flame.svg
```

打开 `flame.svg`（浏览器）：横向宽度 = 时间占比；纵向 = 调用栈；找**最宽的平顶**。

# 火焰图怎么读

```text
                              ┌─ ngx_http_process_request
                              ├─ ngx_http_run_posted_requests
ngx_master_process_cycle ─────┼─ ngx_event_accept
                              ├─ ngx_epoll_process_events
                              └─ lua_resume
                                 ├─ content_by_lua
                                 │  ├─ cjson.decode       ─── 平顶 15%
                                 │  └─ sock:send
                                 └─ lua_error
```

**读法**：
- 顶部宽的"平顶"= 真正消耗 CPU 的函数；
- 中间宽、顶窄 = 只是 pass-through；
- 底部整块 = 事件循环本身，正常。

## 常见热点与对策

| 平顶函数 | 意味着 | 优化 |
|---------|--------|------|
| `cjson.decode` | JSON 解析热 | 减小 body；或换 `lua-resty-json`；或缓存解析结果 |
| `ngx_palloc_small` | 内存分配多 | 见 030，table/string 池化 |
| `luaH_get_short_key` | table hash 查询 | 常量表；或数组化（030） |
| `pcre_exec` | 正则慢 | 检查 `o` 是否加了；见 070 |
| `lj_BC_FORI` | Lua for 循环 | 减迭代；或 hoist 常量（040） |
| `ngx_http_lua_socket_tcp_read` | cosocket 读 | 检查 setkeepalive；见 050 |
| `lj_record_alloc` | trace 里分配 | 见 02 章 010；把分配挪出 trace |
| `LJ_FLUSH_TRAP` | trace 结束 | 检查 NYI；见 02 章 030 |
| `[unknown]` | JIT 生成代码 | 正常 |

# 一个完整案例

**症状**：某 API p99 = 30ms，其他 <5ms。

**火焰图**：`cjson.decode` 上顶 22%；`lua_getstack` 12%。

**分析**：
1. `cjson.decode` 大占比 = 请求 body 大且热；
2. `lua_getstack` = 有 `error()` 或 `pcall` 频繁；

**改造**：
- body 侧提前判长度，> 8KB 才 decode；
- 把 `pcall(mylib.foo, ...)` 换成 `local ok, err = mylib.foo(); if not ok then ... end`（库内返回 err，不抛）；

**效果**：p99 30ms → 6ms；CPU 从 78% → 42%。

# Lua 层火焰图（`stapxx lua-stap-perf`）

普通 `perf` 看到的是 **C 栈**——Lua 函数全在 `luaV_execute` 一个大块里，看不到 Lua 层细节。想看 Lua 层：

```bash
sxx lua-stap-perf -p BIN=/usr/local/openresty/bin/openresty -- sleep 30
# 生成 perf.data；然后
perf script > out.perf
./FlameGraph/stackcollapse-perf.pl out.perf > out.folded
./FlameGraph/flamegraph.pl out.folded > lua-flame.svg
```

**注意**：需要 OpenResty 编译时 `--with-luajit-xcflags="-DLUAJIT_ENABLE_LUA52COMPAT"` 或 `-g`；否则 Lua 函数名被 strip。

# wrk 与 wrk2 组合用法

```bash
# 1. 用 wrk 找最大吞吐
wrk -t12 -c512 -d30s http://...

# 2. 用 wrk2 在这个吞吐的 60-70% 处采延迟
wrk2 -t8 -c128 -d60s -R <max_throughput * 0.6> --latency http://...

# 3. 同时 perf 采样
sudo perf record -F 99 -g -p <worker_pid> -- sleep 60
```

**理由**：满吞吐下延迟严重失真，火焰图看到的是"排队等待"；60% 速率下延迟接近真实业务场景。

# 避坑

- **本机压本机 = 假瓶颈**：wrk 与被测同机，火焰图 40% 是 wrk；分两台。
- **worker 数 ≠ CPU 数**：8 个 worker 但只采一个 PID → 只覆盖 1/8；用 `perf record -a` 或按 worker 数采样。
- **`lua_code_cache off`**：每次请求重编译 → 火焰图全是 `lua_load`；测前 `on`。
- **CPU 频率调节**：`cpupower frequency-set -g performance`；否则节能模式让延迟抖动。
- **NUMA 亲和**：`numactl --cpunodebind=0 --membind=0 openresty ...`；跨 NUMA 访存开销能到 30%。

# 总结

- 固定速率（wrk2）+ `perf record -F 99 -g` + FlameGraph 三步；
- 读图找**平顶**；对照热点表定位；
- Lua 层火焰图用 `stapxx lua-stap-perf`；
- 本机压测、`lua_code_cache off`、CPU 调频都会导致火焰图失真。
