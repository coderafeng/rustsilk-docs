# 概述

Lua 里除了 string，另一大内存分配源就是 **table**。table 每次 `{...}` 字面量都是新分配；`ipairs`/`next` 遍历有额外迭代成本；hash 部分扩容涉及 rehash。本文给出**热路径上 table 的写法纪律**。

# table 结构回顾

一个 Lua table = **数组部分 + 哈希部分**：

```text
Table
├── array   —— 连续内存，索引 1..n
└── hash    —— 开地址哈希表，键是任意 non-nil
```

**Lua 里没有 int-keyed B-tree**：`t[1000] = x` 不会撑出 1000 个数组槽位；反而进 hash。**这决定了两种极端**：

- **密集小整数键** → 数组，快；
- **稀疏/字符串键** → hash，稍慢。

# 反例与正例

## 预分配 size

```lua
-- 反例：多次 rehash
local t = {}
for i = 1, 1000 do t[i] = i end

-- 正例：一次到位
local t = table.new(1000, 0)      -- 数组 1000、hash 0（LuaJIT 扩展）
for i = 1, 1000 do t[i] = i end

-- 或从字面量：
local t = { [1000] = nil }         -- 触发 size 估算（不如 table.new 精准）
```

`table.new(narray, nhash)` 是 **LuaJIT 独有**（`require "table.clear"` 同理）；纯 Lua 里用 `#{}` 或预分配 dummy。

## 清空复用

```lua
-- 反例：每请求新建 table
function handle()
    local ctx = { step = 0, data = nil }
    ...
end

-- 正例：模块级复用 + clear
local ctx_pool = {}
local ctx_idx = 0

local function get_ctx()
    ctx_idx = ctx_idx + 1
    local ctx = ctx_pool[ctx_idx]
    if not ctx then
        ctx = table.new(4, 8)
        ctx_pool[ctx_idx] = ctx
    else
        table.clear(ctx)                     -- LuaJIT 保留容量、清内容
    end
    return ctx
end
```

`table.clear` = "保留 bucket、清 slot"；比 `t = {}` 少一次分配。

## 少用 `ipairs`

```lua
-- 反例：ipairs 每次调用 __index + iterator 状态
for _, v in ipairs(t) do sum = sum + v end

-- 正例：直接索引 + 长度缓存
local n = #t
for i = 1, n do sum = sum + t[i] end
```

**基准**：1M 次遍历，`ipairs` 200ms，直接索引 100ms。

**`#t` 有坑**：如果 t 里有 nil，`#t` 结果不保证；只用于"确保中间无 nil"的数组。

## 少用 pairs

`pairs(t)` 会走 `next`，遍历整个 hash 桶——**顺序不稳定**（受插入顺序、rehash 影响）。要顺序就 sort keys：

```lua
local keys = {}
for k in pairs(t) do keys[#keys+1] = k end
table.sort(keys)
for _, k in ipairs(keys) do process(t[k]) end
```

**代价**：keys 数组分配；对热路径不友好——能提前用数组就用数组。

## 数组化 struct

```lua
-- 反例：hash-keyed
local point = { x = 1, y = 2 }

-- 正例：数组 keyed + 常量索引
local X, Y = 1, 2
local point = { 1, 2 }
local x, y = point[X], point[Y]
```

**权衡**：可读性差；只在**海量对象**（百万级 point）时值得。

## 避免 table 里塞函数

```lua
-- 反例：每请求 new 一个带 method 的对象
local obj = {
    id = 1,
    handle = function() ... end
}

-- 正例：metatable 一次性
local mt = { __index = { handle = function(self) ... end } }
local obj = setmetatable({ id = 1 }, mt)
```

**metatable 是"类"**，实例只带数据；避免每对象携带函数引用（多份 hash slot）。

## 缓存 `#t` 结果

```lua
-- 反例：循环内重复 #t
for i = 1, #t do ... end     -- LuaJIT 会 hoist；但纯 Lua 每次算

-- 正例：缓存
local n = #t
for i = 1, n do ... end
```

LuaJIT 通常能 hoist `#t`（数组长度是常量），但**含 nil 时 `#t` 语义未定**，JIT 会退化解释执行。**永远缓存**。

## Weak table 做缓存

```lua
-- 反例：无界缓存 → 内存泄漏
local cache = {}
function get(k)
    if not cache[k] then cache[k] = expensive(k) end
    return cache[k]
end

-- 正例：weak value，允许 GC
local cache = setmetatable({}, { __mode = "v" })
```

`__mode = "v"` 让 value 变 GC 弱引用；只要 key 无人引用，value 会被回收。**做请求级缓存**很合适；**做 shared dict 的进程内 L1 层**用 `lua-resty-lrucache` 更严格。

# 组合：热路径 handler

```lua
local table_new   = require "table.new"
local table_clear = require "table.clear"
local POOL_SIZE   = 256
local pool        = table_new(POOL_SIZE, 0)
local pool_idx    = 0

local function get_ctx()
    pool_idx = pool_idx + 1
    if pool_idx > POOL_SIZE then pool_idx = 1 end
    local ctx = pool[pool_idx]
    if not ctx then
        ctx = table_new(4, 8)
        pool[pool_idx] = ctx
    else
        table_clear(ctx)
    end
    return ctx
end

-- 每请求：
local ctx = get_ctx()
ctx.user_id = 1
ctx.path = "/api/v1"
```

**效果**：QPS 从 20k → 30k；worker RSS 稳定；GC 频次下降 5-10x。

# 避坑

- **`table.new` 是 LuaJIT 扩展**：纯 Lua / OpenResty 之外的环境无。
- **`table.clear` 后 metatable 保留**：如果对象带 mt，clear 后仍走 mt 的 `__index`。
- **对象池跨协程不安全**：上面的 pool 只在**同一 worker、同一请求序列**里安全；不能跨 worker。
- **`#t` 有 nil 时是未定义**：中间 nil 会让 `#t` 在两个合法边界里任选；避免在数组里塞 nil。

# 总结

- 预分配：`table.new(n, m)`；
- 复用：`table.clear(t)` + 池；
- 遍历：数组 for 索引、避 ipairs、谨慎 pairs；
- 结构：小对象用数组 keyed、类用 metatable；
- Weak table 做进程内 cache；LRU 用 `lua-resty-lrucache`。
