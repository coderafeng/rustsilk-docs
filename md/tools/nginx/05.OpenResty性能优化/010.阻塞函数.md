# 概述

OpenResty 的性能铁律：**worker 里绝不允许阻塞**。一旦阻塞，同 worker 上其他所有请求都被卡住——QPS 断崖下跌。本文盘一遍**所有会阻塞的 API**，给替代品。

# 阻塞 API 清单

| 类别 | API | 阻塞原因 | 替代 |
|------|-----|---------|------|
| 文件系统 | `io.open` / `io.read` / `os.rename` | syscall 阻塞 | 移 privileged agent；或启动时预加载 |
| 系统调用 | `os.execute` / `os.exit` / `os.remove` | 同上 | privileged agent |
| 网络 | `socket`（LuaSocket 库） | 原生 socket | `ngx.socket.tcp` cosocket |
| DNS | `dns.resolve`（LuaSocket） | getaddrinfo | `lua-resty-dns-client` |
| HTTP 客户端 | `lua-requests` 同步 | 阻塞 IO | `lua-resty-http` |
| JSON | `cjson.decode` 超大 body | CPU 密集 → 相对"阻塞" | 分块 / 换流式解析 |
| 正则 | 动态 regex + `o` | CPU | 常量 regex |
| 睡眠 | `ngx.sleep` | 有意阻塞 | **不算阻塞**——协程 yield，事件循环继续 |
| 睡眠 | `resty.websocket` 长循环 | 见下 | 加超时 |
| Timer 回调 | 长循环无 yield | 事件饥饿 | 拆分 timer |
| FFI | 阻塞 C 函数（`sleep`, `read`） | 直通 libc | 用非阻塞 C 库 |
| `string.rep` 超大 | CPU | 分块或用 buffer |
| `os.getenv` | 不阻塞但不推荐 | — |

# 反例与正例

## 反例：LuaSocket

```lua
-- 危险：worker 卡住 5s
local socket = require "socket"
local sock = socket.connect("backend.local", 8080)   -- 同步
sock:send(request)
local resp = sock:receive()                          -- 同步
```

## 正例：cosocket

```lua
local sock = ngx.socket.tcp()
sock:settimeouts(1000, 3000, 3000)
local ok = sock:connect("backend.local", 8080)
sock:send(request)
local resp = sock:receive("*l")
sock:setkeepalive()
```

**语义一样**，但 cosocket 在 IO 时会 `coroutine.yield`，事件循环继续处理其他请求。

## 反例：`os.execute`

```lua
-- 危险：worker 卡几秒
os.execute("ls /tmp")
```

**替代**：
1. **能用 Lua 就用 Lua**：`lfs.dir` 也要 `privileged agent` 里跑；
2. 必须调外部命令 → 挪 `privileged_agent_by_lua*`；
3. **绝不在 content_by_lua 里 `os.execute`**。

## 反例：`io.open` 读配置

```lua
-- 危险：文件在 NFS 上时可能卡 100ms+
local fh = io.open("/etc/app/config.json")
local cfg = fh:read("a")
```

**正例**：

```lua
-- init_by_lua 里加载一次到全局
init_by_lua_block {
    local fh = assert(io.open("/etc/app/config.json"))
    APP_CONFIG = fh:read("a")
    fh:close()
}
```

**`init_by_lua` 里 `io.open` 是允许的**——此时 worker 还没 fork，不算阻塞。

## 反例：LuaSocket DNS

```lua
local resolver = require "socket.dns"    -- 阻塞
```

**正例**：`lua-resty-dns-client`；或直接给 IP。

# `ngx.sleep` 是唯一"合法的等待"

```lua
ngx.sleep(0.5)     -- 挂起当前 coroutine 0.5s；worker 无感
```

**不要**用 `while ngx.now() < t0 + 0.5 do end`——那是 busy wait，会 100% 吃满 CPU。

# Timer 回调里的隐性阻塞

```lua
-- 危险：timer 里跑大循环
ngx.timer.every(1, function(prem)
    if prem then return end
    for i = 1, 1000000 do
        heavy_work(i)               -- 期间 worker 完全无法处理请求
    end
end)
```

**正例**：**任何可能长于 1ms 的循环都 yield**：

```lua
ngx.timer.every(1, function(prem)
    if prem then return end
    for i = 1, 1000000 do
        heavy_work(i)
        if i % 1000 == 0 then ngx.sleep(0) end   -- yield
    end
end)
```

`ngx.sleep(0)` = "让出 CPU 但不真睡"；每一千次迭代一次足够。

# FFI 里的阻塞

```lua
local ffi = require "ffi"
ffi.cdef[[ int usleep(unsigned usec); ]]
ffi.C.usleep(100000)   -- 阻塞 worker 100ms！
```

FFI 直通 C 库；**任何 C 阻塞函数在 worker 里都是灾难**。要么放到 privileged agent，要么用 nginx 事件循环能感知的接口。

# 避坑

- **`pcall` 里的错误可能悄悄吞掉阻塞信号**：`coroutine.resume` 的 `break` 走不通；用 `ngx.timer.at(0, cb)` 而不是 pcall 包大循环。
- **第三方 Lua 库默认非协程安全**：`lua-cjson` 是安全的（纯 C）；但 `lpeg`、`openssl` 里有阻塞调用；接入前先审。
- **`resty.websocket` 长循环**：服务端 hold 连接 15 分钟不 yield，worker 会显示 100% CPU 但其实是被这一个请求霸占；给读操作 `sock:settimeouts`。

# 总结

- 阻塞 = worker 上所有请求一起卡；
- 一切文件/命令/socket/DNS 走 cosocket 或 privileged agent；
- `ngx.sleep` 是唯一合法的"等"；
- 长循环要 `ngx.sleep(0)` yield；
- FFI 里的 C 阻塞函数最隐蔽，接入前审。
