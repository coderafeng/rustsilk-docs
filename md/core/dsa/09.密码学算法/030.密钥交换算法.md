# 概述

对称加密快但有个鸡生蛋问题：密钥怎么送到对方手里？1976 年 Diffie 与 Hellman 给出了第一个公钥协议——**两个陌生人可以在完全被窃听的信道上，凭公开参数各自算出同一把秘密**，而窃听者只看到两串「半截话」。它的机关是模幂运算的单向性：\(g^a \bmod p\) 人人可算，但从 \(g^a\) 反推 \(a\)（离散对数问题）在足够大的群里不可行。DH 的孪生兄弟 ECDH 把群换成椭圆曲线点群，用 256-bit 参数达到传统 3072-bit 的安全性；而现代 TLS 把「静态密钥」换成「临时密钥」（ECDHE），顺手送掉一个奢侈品：**前向保密**——服务器私钥今天泄露，也解不开去年录下的流量。

- 所属章节：[000.密码学算法概述](./000.密码学算法概述.md)
- 时间复杂度：DH 一方生成公钥 \(O(\log^3 p)\)（模幂）、共享秘密一次模幂；ECDH 标量乘 \(O(\log n \cdot \text{点加})\)，X25519 约 50μs 级——比 RSA 密钥封装快一个量级
- 空间复杂度：公钥即一个群元素——DH 256 字节（2048-bit 群）、X25519 仅 32 字节
- 应用场景：TLS 握手（ECDHE  Finished 前的会话密钥协商）、Signal/WhatsApp 双棘轮（X3DH + X25519）、SSH 会话密钥、IPsec/IKE
- 与 RSA 封装的分工：RSA 传密钥需要「收方有公钥」且无前向保密；DH 类协议天生随机参与、临时密钥即弃——TLS 1.3 已只留 (EC)DHE 一族

3. Alice 把自己的红加进对方绿里 → 黄+蓝+红；Bob 把自己的蓝加进对方橙里 → 黄+红+蓝——**同一抹棕**。
4. 窃听者想用「橙 + 绿」调出棕色，会得到橙绿混合的脏色——**公钥相加不等于私钥相加**；要把橙色拆回黄与红，正是「离散对数」难题。

**动画 2：手算小群往返（\(p=23, g=5\)）**

1. 公开参数：素数 23、生成元 5（\(5^1..5^{22}\) 遍历 \(1..22\)，阶为 22）。
2. Alice 私钥 \(a=6\)：公钥 \(A = 5^6 \bmod 23 = 15625 \bmod 23 = 8\)（\(5^2=2, 5^4=4, 5^6=4\times2=8\)）。
3. Bob 私钥 \(b=15\)：公钥 \(B = 5^{15} \bmod 23\)：\(5^8 = 8^2 = 64\equiv18\)，\(5^{15}=5^8\cdot5^4\cdot5^2\cdot5 \equiv 18\times4\times2\times5 = 720 \bmod 23 = 19\)。
4. Alice 算共享：\(B^a = 19^6 \bmod 23\)：\(19^2=361\equiv16\)，\(19^4\equiv16^2=256\equiv3\)，\(19^6=3\times16=48\equiv 2\)。
5. Bob 算共享：\(A^b = 8^{15} \bmod 23\)：\(8^2=64\equiv18\)，\(8^4\equiv18^2=324\equiv2\)，\(8^8\equiv4\)，\(8^{15}=8^8\cdot8^4\cdot8^2\cdot8\equiv4\times2\times18\times8=1152\equiv 2\) ✓ **双方同得 2**，窃听者只见 \((8, 19)\)，从 8 反推 6 即离散对数。

# 详解

## 协议与安全性归约

DH 的三轮交互：

\[
g,\;p \text{ 公开} \;\Rightarrow\;
A = g^{a} \bmod p,\; B = g^{b} \bmod p
\;\Rightarrow\;
s = B^{a} = A^{b} = g^{ab} \bmod p
\]

**计算性 Diffie-Hellman（CDH）假设**：给定 \((g, g^a, g^b)\) 无法算出 \(g^{ab}\)。**判定性版本 DDH** 更强：\(g^{ab}\) 与群内随机元素不可区分——需要素数阶子群（否则可用 Jacobi 符号等判定手段区分 DDH 挑战值）。实践参数：RFC 3526 的 2048-bit MODP 群（\(p\) 为安全素数，\(p=2q+1\)，协议在阶为 \(q\) 的子群里跑），或直接换 ECDH（Curve25519/NIST P-256）。

小群演示版四语言——三行核心逻辑，把动画 2 跑给你看：

```java [Java]
// 教学演示：p=23, g=5, a=6, b=15 → 双方共享秘密均为 2
static final BigInteger P = BigInteger.valueOf(23), G = BigInteger.valueOf(5);
static BigInteger pub(long x)  { return G.modPow(BigInteger.valueOf(x), P); }
static BigInteger secret(BigInteger theirPub, long myPriv) {
    return theirPub.modPow(BigInteger.valueOf(myPriv), P);
}
// secret(pub(15), 6) == secret(pub(6), 15) == 2
```

```rust [Rust]
// 教学演示需大数库（num-big-digits modpow）；此处直接给出 u64 快速幂版
fn powmod(mut b: u64, mut e: u64, m: u64) -> u64 {
    let mut r = 1u64; b %= m;
    while e > 0 {
        if e & 1 == 1 { r = (r as u128 * b as u128 % m as u128) as u64; }
        b = (b as u128 * b as u128 % m as u128) as u64;
        e >>= 1;
    }
    r
}
// pub(6)  = powmod(5, 6, 23)  = 8
// pub(15) = powmod(5, 15, 23) = 19
// 共享：powmod(19, 6, 23) == powmod(8, 15, 23) == 2
```

```typescript [TypeScript]
// BigInt 版教学演示
const P = 23n, G = 5n;
function powmod(b: bigint, e: bigint, m: bigint): bigint {
  let r = 1n; b %= m;
  while (e > 0n) {
    if (e & 1n) r = (r * b) % m;
    b = (b * b) % m;
    e >>= 1n;
  }
  return r;
}
const pub = (x: bigint) => powmod(G, x, P);
const secret = (theirPub: bigint, myPriv: bigint) => powmod(theirPub, myPriv, P);
// secret(pub(15n), 6n) === secret(pub(6n), 15n) === 2n
```

```python [Python]
P, G = 23, 5
pub    = lambda x: pow(G, x, P)                  # 内置三参 pow 即快速幂
secret = lambda tp, mp: pow(tp, mp, P)
assert secret(pub(15), 6) == secret(pub(6), 15) == 2   # 动画 2 的往返
```

## 工程姿势：X25519 / ECDHE

真实部署不再手搓大素数群，而是直接用 **X25519**（Montgomery 曲线上的标量乘，DH 的椭圆曲线化身）：输入 32 字节私钥（clamp 后）、32 字节对方公钥，输出 32 字节共享秘密；无坐标管理麻烦、无签名歧义、每秒可算数十万次。Node/Rust/Python 的调用面几乎一致：

```java [Java]
// Java 15+：XDH（X25519）
KeyPairGenerator kpg = KeyPairGenerator.getInstance("XDH");
KeyPair alice = kpg.generateKeyPair();
KeyPair bob   = kpg.generateKeyPair();
KeyAgreement ka = KeyAgreement.getInstance("XDH");
ka.init(alice.getPrivate());
ka.doPhase(bob.getPublic(), true);
byte[] shared = ka.generateSecret();             // 32B，双方一致
// 用 HKDF 把 shared 拉伸成会话密钥（绝不直接用原始秘密当 key）
```

```rust [Rust]
// x25519-dalek
use x25519_dalek::{PublicKey, StaticSecret};
let alice = StaticSecret::random_from_rng(OsRng);
let bob   = StaticSecret::random_from_rng(OsRng);
let shared_a = alice.diffie_hellman(&PublicKey::from(&bob));
let shared_b = bob.diffie_hellman(&PublicKey::from(&alice));
assert_eq!(shared_a.as_bytes(), shared_b.as_bytes());   // 32 字节一致
```

```typescript [TypeScript]
// Node crypto：X25519 协商
import crypto from "node:crypto";
const alice = crypto.generateKeyPairSync("x25519");
const bob   = crypto.generateKeyPairSync("x25519");
const s1 = crypto.diffieHellman({ privateKey: alice.privateKey, publicKey: bob.publicKey });
const s2 = crypto.diffieHellman({ privateKey: bob.privateKey, publicKey: alice.publicKey });
// s1.equals(s2) → true；派生会话密钥走 HKDF
```

```python [Python]
from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes

alice = X25519PrivateKey.generate()
bob   = X25519PrivateKey.generate()
shared = alice.exchange(bob.public_key())          # 32B 原始共享秘密
key = HKDF(algorithms.SHA256(), 32, b"tls-demo", None).derive(shared)
```

注意最后两行的分工：`exchange` 出的是**群元素的原始字节**，分布并不均匀、长度固定 32B——**必须经过 KDF（HKDF）才能成为 AES 密钥**；跳过 KDF 直接当 key 用，等于把 DH 的输出分布问题转嫁给下游。

## 无认证的 DH = MITM 的乐园

原版 DH 不验证公钥来源：中间人 Eve 与 Alice 假装 Bob、与 Bob 假装 Alice，分别协商 \(s_1, s_2\)，然后「翻译」双方流量——**密钥交换协议自身无法自证身份**。修复选项：

- **静态签名**：长期私钥对「参数 + 临时公钥」签名（SSH 握手、Signal X3DH 的做法）；
- **密码派生认证**：双方共享低熵口令时用 PAKE（OPAQUE/SPAKE2），防「认证后的离线字典」；
- **TLS ECDHE**：服务器临时公钥进入 CertificateVerify 签名覆盖范围——私钥泄露只丢「身份」，不丢「历史会话」（前向保密）。

## 常见陷阱

::: danger 陷阱清单
1. **未校验公钥即参与运算**：对端发来的群元素可能不在子群里——小群攻击（Lim-Lee：\(p-1\) 含小素因子时逐素数泄露私钥低位）、无效曲线攻击（ECC 里对方公钥不在声明曲线上）。先做公钥验证/贡献校验，或直接用带验证的库。
2. **私钥取值范围不当**：DH 私钥应从 \([2, q-2]\) 采（\(q\) 为子群阶），过小或贴边的取值会直接泄露私钥信息。
3. **共享秘密裸用**：\(s\) 不是均匀随机比特串，长度也常常尴尬——KDF（HKDF）是协议的组成部分，不是可选装饰。
4. **重用临时密钥**：一次握手一对临时密钥（ephemeral）才有前向保密；「为了省 CPU 把 DH 密钥用一年」= 静态 DH = 没有 PFS。
5. **弱参数群**：Logjam 事件证明 512-bit export 群可被国家级算力实时攻破；用 RFC 7919 命名群（ffdhe2048+）或直接 X25519，别自定素数。
6. **把 DH 当签名用**：DH 不提供不可否认性也不提供认证——「协商出了密钥」不等于「对面是预期的人」，身份层必须单独解决。
:::

# 总结

- DH 的魔法 = 模幂单向性 + \(g^{ab}\) 的交换律：三轮消息、零预共享秘密，双方各算出同一把 \(s\)；窃听者卡在离散对数上。
- 现代形态是 **ECDHE**：椭圆曲线群（X25519）把参数缩到 32 字节，临时密钥即弃带来**前向保密**——TLS 1.3 的全部流量都跑在这条路上。
- 两条纪律撑住安全：**公钥要验证**（防小群/无效曲线攻击），**秘密要 KDF**（HKDF 之后才可当对称密钥）。
- 协商的密钥交给 [010.对称加密算法](./010.对称加密算法.md) 干活；身份认证交给签名（[070.数字签名](./070.数字签名.md)）；而离散对数难题的「格版继子」正是后量子时代的候选（[050.LLL格基规约](./050.LLL格基规约.md)）。
