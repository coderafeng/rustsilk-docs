# 概述

\(N\) 台缓存/存储节点，来一个 key 该去哪台？最朴素的做法 `hash(key) % N`——可一旦 \(N\) 变化（扩容、宕机、缩容），**几乎所有 key 的归属全部重算**，缓存瞬间集体失效、后端被击穿。一致性哈希（Consistent Hashing，Karger 1997）用「把 key 和节点都扔到同一个环上，key 顺时针找到的第一个节点归它」把这个致命缺点降到理论下界：**增删一个节点，只影响约 \(1/N\) 的 key**。它是分布式缓存（Memcached）、分布式存储、负载均衡分片的路由骨架。

- 所属章节：[000.应用与专题概述](./000.应用与专题概述.md)
- 时间复杂度：查询/插入 \(O(\log N)\)（有序环上二分找后继节点）；朴素线性扫描 \(O(N)\)
- 空间复杂度：\(O(N \cdot v)\)，\(v\) 为每节点虚拟节点数（用于均衡负载）
- 应用场景：分布式缓存路由、一致性分片、负载均衡、跨副本数据定位、分库分表键路由
- 关联：环上定位本质是有序结构上的后继查询（[03.树结构](../03.树结构/000.树结构概述.md) 的平衡 BST/跳表）；哈希环依赖 [01.基础数据结构/070.哈希函数设计](../01.基础数据结构/070.哈希函数设计.md)

1. 把哈希值域 \(0 \sim 2^{32}-1\) 首尾相接画成一个**环**。
2. **节点上环**：节点 A、B、C 各自哈希到环上三个点；key 落在两节点之间的弧段里，**顺时针遇到的第一个节点**就是它的家。例如 A 之后到 B 之前这段弧上的所有 key 归 B。
3. **删除 B**：原本归 B 的那段弧的 key 顺时针改投 C，**而 A 的 key 一个都不用动**——受影响范围仅 \(1/N\)。对比取模法：删任一改全部。
4. **倾斜问题**：真实哈希点不均，可能 A、B 挤在一起、C 孤守大段弧 → 负载严重失衡。
5. **虚拟节点解药**：每个物理节点拆成几十个「虚拟点」（如 `A#1…A#40`）均匀撒环，谁抢到弧段就转交对应物理节点；点越密，负载越均。动画用 40 个虚拟点演示「把大弧切碎均摊」。

# 详解

## 核心算法：环 + 二分后继

把值域看成一维坐标 \([0, 2^{32})\)，节点集映射成一组有序坐标。查询 key：

1. \(h = \text{hash}(key)\)；
2. 在**有序节点坐标数组**里二分找**第一个 \(\ge h\) 的节点**（upper_bound）；
3. 找不到就回绕到环首（下标 0）——即「顺时针」。

```java [Java]
import java.util.*;
public class ConsistentHash {
    private final TreeMap<Long, String> ring = new TreeMap<>();  // 有序环：坐标->物理节点
    private final int virtuals;
    public ConsistentHash(String[] nodes, int virtuals) {
        this.virtuals = virtuals;
        for (String n : nodes) addNode(n);
    }
    private long hash(String s) {                                // FNV-1a -> 32-bit 视作无符号
        long h = 1469598103934665603L;
        for (byte b : s.getBytes()) { h ^= b; h *= 1099511628211L; }
        return h & 0xffffffffL;
    }
    public void addNode(String node) {
        for (int i = 0; i < virtuals; i++)
            ring.put(hash(node + "#" + i), node);                // 虚拟点 -> 物理节点
    }
    public void removeNode(String node) {
        for (int i = 0; i < virtuals; i++) ring.remove(hash(node + "#" + i));
    }
    public String route(String key) {
        if (ring.isEmpty()) return null;
        Map.Entry<Long, String> e = ring.ceilingEntry(hash(key)); // 第一个 >= h
        return (e != null ? e : ring.firstEntry()).getValue();    // 无则回绕环首
    }
}
```

```rust [Rust]
use std::collections::BTreeMap;
pub struct ConsistentHash { ring: BTreeMap<u32, String>, virtuals: usize }
impl ConsistentHash {
    fn hash(s: &str) -> u32 {                                     // FNV-1a 32
        let mut h: u32 = 2166136261;
        for b in s.bytes() { h ^= b as u32; h = h.wrapping_mul(16777619); }
        h
    }
    pub fn new(nodes: &[&str], virtuals: usize) -> Self {
        let mut ch = ConsistentHash { ring: BTreeMap::new(), virtuals };
        for n in nodes { ch.add_node(n); }
        ch
    }
    pub fn add_node(&mut self, node: &str) {
        for i in 0..self.virtuals {
            self.ring.insert(Self::hash(&format!("{}#{}", node, i)), node.to_string());
        }
    }
    pub fn route(&self, key: &str) -> Option<&String> {
        let h = Self::hash(key);
        self.ring.range(h..).next()                               // 第一个 >= h
            .or_else(|| self.ring.iter().next())                  // 回绕环首
            .map(|(_, v)| v)
    }
}
```

```typescript [TypeScript]
class ConsistentHash {
  private ring = new Map<number, string>();     // 生产可用有序结构；此处示意
  private sorted: number[] = [];
  constructor(private virtuals = 40) {}
  private hash(s: string): number {              // FNV-1a 32-bit
    let h = 2166136261 >>> 0;
    for (let i = 0; i < s.length; i++) { h ^= s.charCodeAt(i); h = Math.imul(h, 16777619) >>> 0; }
    return h >>> 0;
  }
  addNode(node: string) {
    for (let i = 0; i < this.virtuals; i++) {
      const p = this.hash(`${node}#${i}`);
      this.ring.set(p, node); this.sorted.push(p);
    }
    this.sorted.sort((a, b) => a - b);
  }
  route(key: string): string | undefined {
    if (this.sorted.length === 0) return undefined;
    const h = this.hash(key);
    let idx = this.sorted.findIndex(p => p >= h);                 // 二分可替 findIndex
    if (idx === -1) idx = 0;                                       // 回绕
    return this.ring.get(this.sorted[idx]);
  }
}
```

```python [Python]
import bisect

class ConsistentHash:
    def __init__(self, nodes=(), virtuals=40):
        self.virtuals = virtuals
        self.ring, self.keys = {}, []
        for n in nodes:
            self.add_node(n)

    @staticmethod
    def _hash(s: str) -> int:                    # FNV-1a 32-bit
        h = 2166136261
        for b in s.encode():
            h = ((h ^ b) * 16777619) & 0xffffffff
        return h

    def add_node(self, node):
        for i in range(self.virtuals):
            p = self._hash(f"{node}#{i}")
            self.ring[p] = node
            bisect.insort(self.keys, p)

    def remove_node(self, node):
        for i in range(self.virtuals):
            p = self._hash(f"{node}#{i}")
            self.ring.pop(p, None); self.keys.remove(p)

    def route(self, key):
        if not self.keys:
            return None
        idx = bisect.bisect_left(self.keys, self._hash(key))      # 第一个 >= h
        idx %= len(self.keys)                                     # 回绕环首
        return self.ring[self.keys[idx]]
```

## 为什么迁移量只有 \(1/N\)

在**均匀哈希 + 足够多虚拟节点**的理想下，\(N\) 个节点把环切成 \(N\) 段等长期望弧，每段 \(1/N\)。删除某节点，只有它紧邻的**一段**弧重新分配给顺时针下一家——迁移 key 数 \(\approx 1/N\)。取模法 `hash%N` 则因模数改变使每个 key 的商余关系全体重排，迁移率 \(\approx (N-1)/N\)（几乎全迁）。这正是一致性哈希的存在理由。

**小验算**：\(N=4\) 扩到 \(N=5\)。一致性哈希理想迁移 \(\approx 1/5 = 20\%\)（新节点从各家匀走约 \(1/5\)）；取模法迁移 \(\approx 80\%\)。虚拟节点越多越接近 \(1/N\) 的理论值，实测偏差随 \(v\) 下降。

## 虚拟节点：负载与倾斜的解药

单物理点在环上只占一个位置，随机落点导致有的节点守大弧、有的守小弧。**每物理节点放 \(v\) 个虚拟点**（\(v\) 常取 100～200），把它的服务区间打散成 \(v\) 段均摊到全环：段数越多，按大数定律各物理点分到的总弧长越接近 \(1/N\)。代价是环大小 \(\to N\cdot v\)，二分仍是 \(O(\log(Nv))\)。异构机器可给强机配更多虚拟点（**加权**）。

## 有界负载一致性哈希（GLC）

朴素一致性哈希的**最坏**负载不均（少量虚拟点时可能某节点接 \(O(\log N/\log\log N)\) 倍负荷）。**Bounded-Load Consistent Hashing**（Google，用于 Spanner/Memcached）给每个节点设**硬容量上界**（如均值的 1.25 倍）：环上按顺时针分配 key，一旦某节点装满就溢出到下一家——用「允许少量回退点」换取「负载比有数学保证」。适合对尾延迟敏感的生产缓存。

## 常见陷阱

::: danger 陷阱清单
1. **虚拟节点太少**：负载倾斜、扩容迁移率偏离 \(1/N\)；小集群尤其要加密虚拟点（几十到几百）。
2. **哈希函数分布差**：弱哈希让节点坐标扎堆，环再大也没用——必须用雪崩性好的 32/64-bit 哈希（MurmurHash/xxHash/FNV），别用语言内建的不稳定 hashCode。
3. **值域回绕写错**：\(h\) 大于所有节点坐标时必须回绕到环首（`ceilingEntry` 空取 `firstEntry`）；漏了就是「大哈希 key 无处可去」的丢路由 bug。
4. **节点标识用地址且地址变更**：IP:port 作节点名，重启换端口=旧虚拟点全残留、新点重建，期间归属抖动；用稳定 node-id 或做优雅摘除。
5. **把它当强一致复制方案**：一致性哈希只解决**路由/归属**，不解决多副本一致性；跨副本读写仍需 quorum/Paxos，别指望哈希环保证「同一 key 永远只有一台有数据」。
6. **扩缩容风暴**：批量上下线时逐台触发重分布会连环迁移；配合迁移节流、双写过渡或 GLC 的有界迁移。
7. **热 key 与哈希无关**：一致性哈希保证「key 数量」均衡，不保证「访问量」均衡——一个爆款 key 仍打爆单点，需二级缓存/读写分离另治。
:::

# 总结

- 一致性哈希 = 「key 和节点同投一个环，key 顺时针找后继」，把增删节点的迁移量从取模法的「几乎全部」降到理论的 \(1/N\)——这正是分布式缓存抗击穿的地基。
- 环上路由是有序结构上的 successor 查询（TreeMap/BTreeMap/平衡树 + 二分），\(O(\log N)\)；虚拟节点解决落点倾斜并支持加权，有界负载（GLC）进一步给出最坏情况保证。
- 它的边界要拎清：只管**路由归属**、不管**副本一致性**、不管**访问热度**——把它塞进「解决一切分布式难题」的幻想是最大误区。
