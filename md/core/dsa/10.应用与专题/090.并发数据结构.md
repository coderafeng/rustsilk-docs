# 概述

多核时代，「一把全局锁」会让并行退化成串行。**并发数据结构**研究的是：多个线程同时读写同一结构时，如何在不牺牲正确性（原子性、一致性）的前提下，把「等待」压到最低。演化路线是一条「锁粒度不断变细、直到无锁」的阶梯：

**粗锁 → 分段锁（锁条带）→ 读写锁 → 乐观读（RCU/序列锁）→ 无锁（lock-free，CAS 重试）→ 等待自由（wait-free）**。

判断一个并发结构好坏有三把尺：**安全性**（不破坏不变式/无数据竞争）、**活性**（前进保证：lock-free 保证系统整体有进展、wait-free 保证每个线程各自有进展）、**性能**（吞吐、延迟、可扩展性随核数的曲线）。代表实现：Java `ConcurrentHashMap`、Disruptor 环形队列、Linux 内核 RCU、Crossbeam/Go channel。

- 所属章节：[000.应用与专题概述](./000.应用与专题概述.md)
- 时间复杂度：单次操作 \(O(\text{底层结构操作})\) + 争用开销；理想无争用与串行同阶，争用下取决于锁粒度/重试次数
- 空间复杂度：常需额外字（版本戳、Aba 防护 tag、帮助标记、epoch 槽）——lock-free 往往以空间换活性
- 应用场景：高并发缓存/计数、生产者-消费者队列、日志/事件总线、内核数据结构、数据库索引、并行调度器
- 前置：内存模型（happens-before、acquire/release、fence）是一切正确性的地基；不可变快照思路见 [080.可持久化数据结构](./080.可持久化数据结构.md)

1. 栈 `top → A → B → C`。线程 1 读 `oldTop=A`、算 `next=A.next=B`，准备 `CAS(top, A, B)`。
2. 线程 2 抢先：`CAS(top, A, B)` 成功，随后又 push 了新节点使 `top` **重新变回 A**（且 A.next 已不同）。
3. 线程 1 的 CAS 看「top 仍等于期望的 A」→ 误判成功 → 结构损坏——这就是 **ABA 问题**（值没变但含义变了）。
4. **解药一：带标签指针**——每次修改给指针配一个单调递增版本号，`A#1 ≠ A#7`，CAS 连带校验版本，ABA 现形。
5. **解药二：epoch/Hazard Pointer 回收**——被摘下的节点不立即释放，等「没有线程可能再引用它」才回收，避免 pop 到一半读到已 free 的 `A.next`（use-after-free）。
6. 动画定格在「CAS 失败→重读 top→重试」的乐观循环，直观呈现 lock-free 的「前进靠重试而非阻塞」。

# 详解

## 锁粒度阶梯：从粗到细

- **全局锁**：最简单、最不易错，但写多必串行；只适合低争用或读多（配读写锁）。
- **分段锁 / 锁条带（striping）**：把结构切成若干独立加锁的桶（`ConcurrentHashMap` 早期 Segment、LongAdder 的 Cell 数组），不同 key/桶互不阻塞——牺牲「跨段原子性」换并发。
- **读写锁**：多读单写，读读共享、写独占；读多写少利器，但写饥饿与「升级为写锁」是坑。
- **乐观读 / seqlock / RCU**：读端**不加锁**、只靠版本校验（seqlock：读前后版本一致才采信）或宽限期（RCU：写端延迟回收），把读的开销降到几乎等于无同步——Linux 内核读多写少结构的事实标准。
- **无锁（lock-free）**：CAS + 重试，不阻塞、不互斥；活性保证「至少一个线程能推进」。

## Michael-Scott 无锁队列 / Treiber 无锁栈

**Treiber 栈**（lock-free stack）是最小范例：push/pop 都靠对 `top` 的一次 CAS。

**Michael-Scott 队列**：`head`/`tail` 两个原子指针，enqueue 用 CAS 把 `tail.next` 指向新节点、再 CAS 推进 `tail`（**帮助式两阶段**：别的线程可代为完成第二步，保证 lock-free 前进）。它是无锁队列的经典骨架（Java `ConcurrentLinkedQueue`）。

```java [Java]
// Treiber 无锁栈（带版本标签防 ABA）
static class Node<T> { T val; long stamp; Node<T> next;
    Node(T v, long s, Node<T> n){ val=v; stamp=s; next=n; } }
final AtomicStampedReference<Node<Integer>> top = new AtomicStampedReference<>(null, 0);

void push(int v) {
    Node<Integer> cur, next; int stamp;
    do {                                  // 乐观重试环
        cur = top.getReference(); stamp = top.getStamp();
        next = new Node<>(v, stamp + 1, cur);
    } while (!top.compareAndSet(cur, next, stamp, stamp + 1));  // CAS 失败则重读重试
}
Integer pop() {
    Node<Integer> cur, next; int stamp;
    do {
        cur = top.getReference();
        if (cur == null) return null;
        stamp = top.getStamp(); next = cur.next;
    } while (!top.compareAndSet(cur, next, stamp, stamp + 1));
    return cur.val;
}
```

```typescript [TypeScript]
// 单线程 JS 无真正并行 CAS；此处用 SharedArrayBuffer + Atomics 表达 lock-free 语义
const sab = new SharedArrayBuffer(8);
const view = new Int32Array(sab);            // view[0]=top 指针槽
// Atomics.compareExchange 就是硬件 CAS：返回旧值，等于期望值才算成功
function casTop(expect: number, next: number): boolean {
  return Atomics.compareExchange(view, 0, expect, next) === expect;
}
function pushAndRetry() {
  let old: number;
  do { old = Atomics.load(view, 0); } while (!casTop(old, /* newTop */ old + 1));
}
```

```python [Python]
# CPython 有 GIL，纯 Python 无硬件级并行 lock-free；用 atomic 库/多进程表达。
# 语义层演示 CAS（真实 lock-free 结构应交给无 GIL 的实现或原生扩展）：
import threading
top = None
lock = threading.Lock()          # 退而求其次：正确性优先的悲观实现
def push(v):
    global top
    with lock:
        top = (v, top)
def pop():
    global top
    with lock:
        if top is None: return None
        v, top = top[0], top[1]
        return v
```

## 内存回收：lock-free 真正的难点

无锁结构里「谁来 free 一个刚摘掉的节点」极棘手——线程 A 正读 `node.next` 时线程 B 可能 free 了 `node`（use-after-free）。三大方案：

- **Hazard Pointers**：每个线程公告「我可能正在引用这些指针」，回收方扫描所有 hazard 记录，无人公告才真 free。精确但有 per-thread 开销。
- **Epoch-Based Reclamation（EBR）**：全局 epoch + 线程进入临界区记录所在 epoch；当所有线程都跨过某 epoch 边界（宽限期结束）才批量回收该 epoch 前的退役节点。RCU 即其工业化身。
- **Reference Counting（原子引用计数）**：如 `Arc`，简单但计数本身是争用点且有循环引用问题。

## 伪共享与缓存行

多核上两个逻辑独立的计数器若落在同一 **缓存行（通常 64B）**，一个核写会让另一核的该行 invalidate，引发 **false sharing**——吞吐雪崩。解药是 **padding/对齐**：把每个 Cell 用 `@Contended`（Java）、`#[repr(align(64))]`（Rust）、手动填充到独立缓存行。`LongAdder`/Disruptor 都靠这个把可扩展性拉满。

## 无锁 vs 等待自由 vs 阻塞

| 前进保证 | 含义 | 典型实现 |
|---------|------|---------|
| wait-free（等待自由） | **每个线程**有限步内完成，最坏延迟有界 | 某些队列/Bounded buffer、RSP 栈 |
| lock-free（无锁） | **系统整体**总有线程推进，单个可能反复重试（活锁风险） | Michael-Scott 队列、Treiber 栈 |
| obstruction-free | 独占运行时能有进展，冲突则让步 | 某些 STM 事务 |
| blocking（有锁） | 持锁线程挂起会阻塞他人 | mutex 保护的 map |

实时系统（音频/控制）要 wait-free 保证延迟上界；一般高并发吞吐场景 lock-free 足够。

## 常见陷阱

::: danger 陷阱清单
1. **ABA 误认为「值没变就安全」**：CAS 只比位值，指针复用/回退会伪造成功——必须用带标签指针、hazard pointer 或逻辑上不可回退的状态设计。
2. **忽略内存序**：无锁代码里 load/store 用 relaxed 会看到乱序——链接的指针必须先发布对象再发布指针（release 写、acquire 读），别默认 seq_cst 之外还省 fence。
3. **手搓无锁还自己 free**：绝大多数 use-after-free/损坏来自过早回收——要么用成熟库（crossbeam/`ConcurrentHashMap`），要么严格 EBR/HP。
4. **为「并发」上无锁，实际争用极低**：低争用时粗粒度锁 + 好结构反而更快更简单、更可维护；无锁是最后手段，profile 先行。
5. **伪共享**：分段/Cell 数组没按缓存行对齐，核数越多越慢（可扩展性曲线倒挂）——加 padding，先量 false sharing。
6. **误用「原子变量拼出复合不变式」**：单个字段都原子不代表整体一致（两个 CAS 之间被人插入）——跨字段原子性需单一 CAS 覆盖、锁、事务内存或帮助协议。
7. **把 lock-free 当「无等待」**：lock-free 允许单线程活锁/长期不推进；需要最坏延迟保证（实时）必须 wait-free。
:::

# 总结

- 并发数据结构的进化就是「锁粒度递减」的一条阶梯：全局锁→分段→读写→乐观读(RCU/seqlock)→无锁(CAS)→等待自由；每降一级都把「阻塞」换成更细的同步或重试，代价是复杂度与内存回收难题。
- 三把评价尺缺一不可：**安全性**（内存模型 + 正确的 acquire/release）、**活性**（lock-free vs wait-free 的前进保证）、**性能**（可扩展性曲线，警惕伪共享）——无锁不等于快，要看争用与缓存行为。
- Michael-Scott 队列、Treiber 栈是必会骨架，但生产环境优先用久经考验的实现（crossbeam、`ConcurrentLinkedQueue`、Disruptor、内核 RCU），把最危险的内存回收交给成熟轮子。
- 「不可变 + 快照」是绕开锁的一等公民：读端零同步的结构正是 [080.可持久化数据结构](./080.可持久化数据结构.md) 的天然并发读版本；分段思想（锁条带/分片）与 [070.一致性哈希](./070.一致性哈希.md) 的哈希分片在「降低争用」上同源，而哈希分片本身常构建在 [01.基础数据结构/080.冲突解决策略](../01.基础数据结构/080.冲突解决策略.md) 之上。
