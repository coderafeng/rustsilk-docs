# 概述

面对一个「几十亿 key、每秒千万次查」的缓存场景，最贵的往往不是「命中」而是「查了个不存在的 key 还跑去打后端」。**布隆过滤器（Bloom Filter，1970）** 用一个精巧的取舍解决它：牺牲「一定准」换来「极度省」。它是一串 \(m\) 位比特数组 + \(k\) 个独立哈希函数。插入时把元素经 \(k\) 个哈希映射到 \(k\) 个位置全部置 1；查询时看这 \(k\) 位是否**全为 1**——只要有一位是 0，元素**必然不在**集合里（无假阴性）；全为 1 则「可能在」，因为这些位也可能被别人置上（**有假阳性**）。它不存元素本身，所以省空间到极致，代价是「说不存在绝对靠谱、说存在只能给概率」，而且**标准布隆不支持删除**（一个位被多个元素共享，贸然清 0 会误伤）。

> [!tip] 工程落地
> Redis 的 `BF.ADD` / `BF.EXISTS` / `BF.MADD` 命令即布隆过滤器（RedisBloom 模块）的现成实现，详见 [Redis Bloom Filter 布隆过滤器](../../../database/redis/02.Redis 数据类型和命令/150.Bloom Filter 布隆过滤器.md)。

- 所属章节：[000.应用与专题概述](./000.应用与专题概述.md)
- 时间复杂度：插入/查询 \(O(k)\)——\(k\) 为哈希个数（常数级，通常 3～10），与集合大小无关
- 空间复杂度：\(O(m)\) 位；达假阳性率 \(p\) 时每元素约 \(\lceil \log_2(1/p) \rceil \approx 1.44\log_2(1/p)\) 位（最优 \(k\) 下）
- 应用场景：缓存穿透防护、爬虫 URL 去重、垃圾邮件/黑名单、集合成员预筛、数据库避免无谓查询、协同去重
- 哈希基础：依赖 [01.基础数据结构/070.哈希函数设计](../01.基础数据结构/070.哈希函数设计.md)；变体（Counting/Cuckoo）解决删除问题

# 详解

## 假阳性率与最优参数

插入 \(n\) 个元素后，某一位**仍为 0** 的概率：每个元素用 \(k\) 个哈希、每次命中该位概率 \(1/m\)，一位经历 \(kn\) 次「置 1 尝试」都失败的概率：

\[
P(\text{bit}=0) = \left(1 - \frac{1}{m}\right)^{kn} \approx e^{-kn/m}
\]

查询一个**不在集合**的元素，其 \(k\) 位全为 1（误判存在）的概率即假阳性率：

\[
p \approx \left(1 - e^{-kn/m}\right)^k
\]

对 \(k\) 求导取极小，得**最优哈希个数**与**最优位数**：

\[
k^* = \frac{m}{n}\ln 2, \qquad m^* = -\frac{n \ln p}{(\ln 2)^2}, \qquad k^* = \log_2(1/p)
\]

**手算验证**：目标 \(p=0.01\)（1%），\(n=10{,}000\)。
- \(k^* = \log_2(100) \approx 6.64 \to 7\) 个哈希；
- \(m^* = -\frac{10000\cdot \ln 0.01}{(\ln 2)^2} = \frac{10000\times 4.605}{0.4805} \approx 95{,}836\) 位 ≈ **11.7 KB**；
- 即每个元素约 \(95836/10000 \approx 9.6\) 位 ≈ 1.2 字节就能做到 1% 误判——对比哈希表存原始 key，省一到两个数量级。经验法则：**每元素位数 \(\approx 4.8\) 对应 \(p\approx2\%\)、\(\approx 9.6\) 对应 \(p\approx1\%\)**（每加一位，\(p\) 约减半）。

```python [Python]
import math

def optimal_params(n, p):
    m = math.ceil(-n * math.log(p) / (math.log(2) ** 2))   # 位数
    k = max(1, round(m / n * math.log(2)))                 # 哈希个数
    return m, k

def actual_fp(m, n, k):
    return (1 - math.exp(-k * n / m)) ** k                 # 代入上式

# optimal_params(10000, 0.01) → (95836, 7)；actual_fp(95836,10000,7)≈0.0098
```

## k 个哈希从哪来：双重哈希技巧

真跑 \(k\) 个独立哈希既慢又要存 \(k\) 个种子。Kirsch-Mitzenmacher 技巧只用两个基哈希 \(h_1, h_2\) 线性组合出第 \(i\) 个：

\[
g_i(x) = (h_1(x) + i\cdot h_2(x)) \bmod m, \quad i = 0..k-1
\]

理论上不改变渐近假阳性率，实测几乎一致，且把哈希计算从 \(k\) 次降到 2 次（一次 128-bit 哈希拆两半即可当 \(h_1,h_2\)）。

## 完整实现（四语言）

```java [Java]
import java.util.BitSet;
public class BloomFilter {
    private final BitSet bits; private final int m, k;
    public BloomFilter(int m, int k) { this.m = m; this.k = k; bits = new BitSet(m); }
    private long[] hashes(String s) {                 // 双重哈希：拆 128-bit 为 h1,h2
        long h1 = s.hashCode() & 0xffffffffL;
        long h2 = (h1 * 1000003L + s.length()) | 1L;  // 保证奇数，扩周期
        long[] g = new long[k];
        for (int i = 0; i < k; i++) g[i] = Math.floorMod(h1 + i * h2, m);
        return g;
    }
    public void add(String s) { for (long p : hashes(s)) bits.set((int) p); }
    public boolean mightContain(String s) {
        for (long p : hashes(s)) if (!bits.get((int) p)) return false;  // 有位为0→必不存在
        return true;                                                    // 全1→可能存在
    }
}
```

```rust [Rust]
pub struct BloomFilter { bits: Vec<bool>, m: usize, k: usize }
impl BloomFilter {
    pub fn new(m: usize, k: usize) -> Self {
        BloomFilter { bits: vec![false; m], m, k }
    }
    fn hashes(&self, s: &str) -> Vec<usize> {
        let h1 = fnv(s) as u64;
        let h2 = (h1.rotate_left(32) ^ 0x9e3779b97f4a7c15) | 1;   // 基哈希之二，取奇
        (0..self.k as u64).map(|i| (h1.wrapping_add(i.wrapping_mul(h2)) % self.m as u64) as usize).collect()
    }
    pub fn add(&mut self, s: &str) { for p in self.hashes(s) { self.bits[p] = true; } }
    pub fn might_contain(&self, s: &str) -> bool {
        self.hashes(s).iter().all(|&p| self.bits[p])   // 任一 false 即必不存在
    }
}
fn fnv(s: &str) -> usize { /* FNV-1a 64 */ 0 }
```

```typescript [TypeScript]
class BloomFilter {
  private bits: Uint8Array;
  constructor(private m: number, private k: number) { this.bits = new Uint8Array(m); }
  private hashes(s: string): number[] {
    let h1 = 2166136261 >>> 0;                        // FNV-1a
    for (let i = 0; i < s.length; i++) { h1 ^= s.charCodeAt(i); h1 = Math.imul(h1, 16777619) >>> 0; }
    let h2 = (h1 * 2654435761) >>> 0 | 1;
    return Array.from({ length: this.k }, (_, i) => (h1 + i * h2) % this.m);
  }
  add(s: string) { for (const p of this.hashes(s)) this.bits[p] = 1; }
  mightContain(s: string): boolean { return this.hashes(s).every(p => this.bits[p] === 1); }
}
```

```python [Python]
class BloomFilter:
    def __init__(self, m, k):
        self.m, self.k, self.bits = m, k, bytearray(m)
    def _hashes(self, s):
        b = s.encode()
        h1 = int.from_bytes(__import__('hashlib').sha256(b).digest()[:8], 'big')
        h2 = int.from_bytes(__import__('hashlib').sha256(b).digest()[8:16], 'big') | 1
        return [(h1 + i * h2) % self.m for i in range(self.k)]   # 双重哈希
    def add(self, s):
        for p in self._hashes(s): self.bits[p] = 1
    def might_contain(self, s):
        return all(self.bits[p] for p in self._hashes(s))         # 有位为0即必不存在
```

## 变体家族：补上删除与计数

| 变体 | 解决什么 | 代价 |
|------|---------|------|
| **Counting Bloom Filter** | 支持删除：每位存小计数器而非 1 bit，删时 -1 | 空间 ×（计数位宽，常 4 bit） |
| **Cuckoo Filter** | 删除 + 更省 + 高负载仍稳；存指纹 f 于两候选桶之一， cuckoo 踢出 | 需重插入、实现复杂 |
| **Spectral BF** | 带权重集合（多集合叠加计数） | 空间大 |
| **Scalable / Dynamic BF** | 不知道 \(n\) 多大：满了就叠一层新过滤器（级联） | 查询遍历多层，规模翻倍式增长 |
| **Blocked BF** | 把位分块、每元素占一块，缓存友好 + 支持批量 | 略高假阳性 |
| **Bloomier / IBF** | 可回查（存储映射的键值对，如 Invertible Bloom Lookup 做集合差） | 结构复杂 |

## 常见陷阱

::: danger 陷阱清单
1. **当成精确集合用**：布隆只会回答「一定没有 / 可能有」——把它当「说存在就真存在」的判据会引入业务错误；关键路径要在「可能有」后再回源精确确认。
2. **参数 \(n\) 估小**：实际元素远超预估 \(n\)，填充率飙升、假阳性雪崩（\(p\) 对 \(n/m\) 极敏感）；宁可高估或上 Scalable/动态分层。
3. **标准布隆硬删**：清某元素的位会连带清掉共享位、误删他人——要删除就换 Counting/Cuckoo Filter。
4. **哈希函数劣质或相关**：\(k\) 个哈希若不独立、或基哈希分布差（如弱 hashCode），位分布不均，实测假阳性远高于理论 \(p\)；用强哈希 + 双重哈希技巧。
5. **忘记位向量是共享状态**：并发写要用原子位操作或分片，否则读到撕裂状态；纯读快照可安全共享。
6. **拿假阳性率当唯一指标**：真实场景哈希计算次数 \(k\)、缓存 miss、内存带宽都影响吞吐；高 QPS 下 Blocked BF 的局部性往往比理论 \(p\) 更值钱。
7. **跨语言 hashCode 不一致**：Java 默认 `String.hashCode` 与 Python/Rust 不同——分布式多语言部署时各节点必须用同一哈希定义，否则过滤器互不认账。
:::

# 总结

- 布隆过滤器用「\(k\) 位全 1 才算可能存在」换极致省空间：**无假阴性、有假阳性、不可删（原版）**；三句话就是它的性格。
- 一切参数由一条假阳性公式 \(p\approx(1-e^{-kn/m})^k\) 决定，最优 \(k^*=\log_2(1/p)\)、\(m^*\approx1.2\,n\log_2(1/p)\) 位——「每元素位数每多 1，误判率约减半」是最好用的心算尺。
- 双重哈希把 \(k\) 次哈希降到 2 次；变体各司其职补洞：Counting 能删、Cuckoo 更省更适合高负载、Scalable 应对未知规模、Blocked 吃满缓存局部性。
- 它是 [01.基础数据结构/070.哈希函数设计](../01.基础数据结构/070.哈希函数设计.md) 的经典应用；工程上现成轮子见 [Redis Bloom Filter](../../../database/redis/02.Redis 数据类型和命令/150.Bloom Filter 布隆过滤器.md)；而「用少量随机化换空间/时间」的哲学与 [030.RANSAC算法](./030.RANSAC算法.md) 同源，与 [070.一致性哈希](./070.一致性哈希.md) 一起构成分布式预筛与路由的左膀右臂。
