# 概述

B 树是一棵**多路平衡查找树**：每个节点可容纳大量键与孩子，树高被扇出压得极矮，一次磁盘页读取即可二分一大批键——它是为「慢存储介质（磁盘/SSD）+ 页式 I/O」设计的索引结构。B+ 树是其工程改良：**数据只存叶子、非叶子纯做路由、叶子串成有序链表**，几乎垄断了数据库与文件系统索引。

**本篇收录**：B 树、B+ 树、B* 树

- 所属章节：[000.树结构概述](./000.树结构概述.md)

- 时间复杂度（n 个键、最小阶 m，树高 `h ≤ log_{⌈m/2⌉}((n+1)/2) + 1`）：

  | 操作 | 复杂度 | 实际含义 |
  |------|:------:|---------|
  | 查找 | O(log_m n) | 磁盘版「二分」：每层一次页读，千万级数据 3~4 层 |
  | 插入 | O(log_m n) | 路径下探 + 满节点分裂 |
  | 删除 | O(log_m n) | 借键/合并，维持最少 ⌈m/2⌉-1 个键 |

- 空间复杂度：O(n)，节点膨胀因子（fillfactor）预留页内空间
- 应用场景：
  - **B+ 树**：MySQL InnoDB 聚簇/二级索引、PostgreSQL B-tree 索引（默认索引类型，见 [PostgreSQL 索引](../../../database/postgresql/06.PostgreSQL%20索引/000.索引概述.md) 与 [005.索引类型](../../../database/postgresql/06.PostgreSQL%20索引/005.索引类型.md)）、SQLite、MongoDB WiredTiger、Oracle——关系型数据库索引的绝对主流；
  - **B 树**：文件系统的目录/块索引——NTFS、HFS+、ext4（dir_index）、F2FS；
  - 对照内存树：单机内存有序结构用 [红黑树](./040.AVL树与红黑树.md)/跳表，一旦落盘换 B/B+ 树，分野就在「I/O 次数」。

设阶 m=4（每节点至多 3 个键），依次插入 `10, 20, 5, 15, 25, 30`：

1. 键陆续填入根节点（兼叶子）：`[5, 10, 15, 20]`——已超上限 3 键；
2. **分裂**：以中间键 15 为界拆成左右两页 `[5, 10]` 与 `[15, 20]`，**中间键 15 复制（注意是复制不是移动，B+ 特性）**上升为新根的Separator；
3. 后续 `25, 30` 沿根的路由「15 → 右孩子」进入右页；
4. 右页再满再分裂， Separator `25` 上升——**树只在根分裂时长高，所有叶子永远同层**。

**动画：范围查询 `BETWEEN 6 AND 28`**
<!-- dsa.assets/bplus/bplus-range-scan.gif -->

1. 从根下探定位到第一个 ≥6 的叶子页（一次根到叶的路径，约 3 次页读）；
2. 命中后**不再回树**，沿叶子间的双向链表顺序右移，逐个收集 ≤28 的键；
3. 扫描代价 = 定位 O(log n) + 输出行数 O(k)，这就是「分页 ORDER BY id LIMIT」高效的结构原因。

# 详解

## B 树（B-树，非「B树-减一」的「B树」）

阶 m 的 B 树定义：每个节点含 `k` 个键与 `k+1` 个孩子（根除外至少 2 个）；除根外每节点至少 `⌈m/2⌉ - 1` 个键；键在节点内有序，孩子区间由键切分；**所有叶子同层**；**键可以携带数据、出现在任何层**。

查找即「页内二分 + 页间下探」：

```text
search(node, key):
  页内二分找 key
  命中 → 返回该槽位的数据
  未命中 → 落入孩子区间 child[i]，递归（一次磁盘页读）
```

插入自底向上：找到叶子槽位插入 → 溢出则**把中间键「移动」到父节点**、对半分裂；根溢出则树长高。B 树中间层就带数据，等值查询「命中即止」，平均路径有时比 B+ 更短（数据热在浅层时），但范围查询要中序回溯整棵树，且同容量下键更多 ⇒ 扇出更小 ⇒ 树更高。

## B+ 树：三处关键改动

| 改动 | B 树 | B+ 树 | 收益 |
|------|------|-------|------|
| 数据位置 | 所有节点带数据 | **只有叶子带数据**（或存行指针） | 非叶子纯键 ⇒ 同页塞更多键 ⇒ 扇出更大、树更矮 |
| 中间键语义 | 分裂时中间键**上移**（本层消失） | 分裂时中间键**复制**上界做 separator | 叶子层保留全部键，完备 |
| 叶子链接 | 无 | 叶子按序串成**双向链表** | 范围/排序/覆盖扫描退化为顺序读 |

InnoDB 的具体形态：主键树叶子存**整行**（聚簇索引），二级索引叶子存**主键值**，需「回表」再走主键树——二级索引范围扫描先沿自己叶子链走，再逐行主键查找，理解 B+ 结构才能理解索引合并、覆盖索引（`SELECT` 列全在二级索引里则免回表）等优化器行为。PostgreSQL 的 B-tree 还额外有 `fillscale`（默认 90%）预留、祖先指针（AAPM）处理并发分裂，细节见 [PostgreSQL 索引的基本操作](../../../database/postgresql/06.PostgreSQL%20索引/010.索引的基本操作.md)。

## B* 树：分裂改三分

B+ 节点的填充率往往只到 ~69%（分裂对半，两页各半）。**B\* 树**在节点满时先尝试把键**匀给相邻兄弟**（借位），兄弟也满才把「本页 + 兄弟 + 新页」**一分为三**、两个 separator 上移，把最小填充率从 1/2 提到 **2/3**。CDF（B\* 文件）、SQLite 表叶子（`WITHOUT ROWID` 与普通表叶子的 `fill_factor 20/60/30` 预留）都体现了这一思路。工程语境下 B\* 树远少于 B+，知道「匀→三分→才长高」即可。

## 阶怎么选

一棵 2000 万行、每行 1KB 的表在 InnoDB 16KB 页下：二级索引非叶子页约存 400 个键（16KB / (8B 主键 + 6B 指针)），**3 层 B+ 树可支撑 400 × 112（叶子页行数）× 400 ≈ 1.8 亿行**——「三层亿级」是 DBA 面试常客。层数 ≈ 主键查询的磁盘 I/O 次数，加上根页常驻内存，实际一次点查通常只有 1~2 次物理读。

## 常见陷阱

- 名字陷阱：**B-树 = B 树**（B-tree），不存在「B+ 减一」的 B-；别把「Balance」念成 bug。
- B 树分裂是**移动**中间键上移、B+ 是**复制**上移——手写实现混用会让叶子层丢键。
- 自平衡二叉树思维照搬到磁盘：红黑树每个节点一次 I/O 的「矮」毫无意义，磁盘结构拼的是**单页容量撑起的扇出**，不是层高技巧。
- 二级索引范围查询不能只走自己的叶子链——非覆盖列必须回表，优化器据此估算成本选择全表扫描还是索引扫描。
- 页分裂导致**写放大与碎片**：随机主键（UUID）插入把顺序写打散成随机写，这正是 MySQL 建议自增主键、MongoDB 建议有序 ObjectId 的原因；`FILLFACTOR`/`fillfactor` 调优即为此。

# 总结

- B 树用「多路 + 同层叶子 + 页内二分」把树高压到 log_m n，让查询次数 ≈ 磁盘 I/O 次数，是为慢介质而生的平衡树；
- B+ 树三刀改良——数据沉叶、中间键复制、叶子成链——换来更大扇出与顺序扫描，成为数据库索引的事实标准；B\* 树再把填充率从 1/2 提到 2/3；
- 「三层亿级」与「随机主键打碎顺序写」是理解工业索引（InnoDB/PostgreSQL）设计决策的两把结构钥匙。
