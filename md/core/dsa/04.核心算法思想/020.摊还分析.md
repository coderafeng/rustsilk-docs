# 概述

有些操作序列里混着「罕见的昂贵操作」：动态数组第 2^k 次 push 要整块搬迁，但平均每次 push 仍是 O(1)。**摊还分析**不孤立看单次操作的最坏界，而是证明「n 次操作的总代价上界」，把昂贵操作的成本摊给同伙——得到序列级别的平均最坏保证（均摊复杂度），而非依赖数据分布的概率平均。

**本篇收录**：聚合分析、记账法、势能法

- 所属章节：[000.核心算法思想概述](./000.核心算法思想概述.md)

- 结论速查（均摊界即「任意操作序列」下的平均每操作最坏保证）：

  | 结构/操作 | 单次最坏 | **均摊** | 经典出处 |
  |-----------|:-------:|:-------:|---------|
  | 动态数组 push | O(n)（扩容搬移） | **O(1)** | [010.数组](../01.基础数据结构/010.数组.md) 的 2 倍扩容 |
  | 动态数组 pop（伴收缩） | O(n) | **O(1)** | 负载因子 1/4 才缩容，防抖动 |
  | 二进制计数器 inc | O(log n)（连续进位） | **O(1)** | 聚合分析教科书例 |
  | 并查集 find/union（路径压缩+按秩） | O(log n) 级别 | **O(α(n))≈O(1)** | [040.并查集](../05.图结构与并查集/040.并查集.md) |
  | 哈希表 rehash | O(n) | **O(1)**（装载因子阈值触发） | [080.冲突解决策略](../01.基础数据结构/080.冲突解决策略.md) |

- 应用场景：解释「为什么倍增扩容而不是 +1 扩容」「为什么 Java `ArrayList`、Python `list` 的 append 敢标 O(1)」「为什么缩容阈值不能贴着扩容阈值」——凡增长/收缩/重建类结构，性能承诺都靠本篇三工具背书。

以从空表 push 15 个元素为例（倍增策略，搬移 k 个元素记代价 k+1）：

1. push #1：容量满 → 分配 1，**无搬移**，代价 1；
2. push #2：满 → 分配 2，搬 1 个，代价 2，本条记录「自己 1 + 欠搬移 1」；
3. push #3~#4：#3 直接放，#4 满 → 分配 4 搬 2，代价 3；
4. push #5~#8：#8 满 → 分配 8 搬 4，代价 5——**单次峰值在爬高**；
5. 算总账：8 次 push 总代价 = 1+2+1+3+1+1+1+5 = 15 < 8×3；15 次 push 总代价 < 45；
6. 得出结论：虽然第 2^k 次 push 最坏 O(2^k)，**任何 n 次序列总代价 ≤ 3n（聚合界）**，均摊 O(1)；若改成 +1 扩容，总代价变 Σk = Θ(n²)，均摊退化为 O(n)——倍增不是玄学，是摊还算术。

# 详解

## 工具一：聚合分析（直接算总账）

对任意操作序列，先用任何手段求出 **n 次操作的精确总代价上界 T(n)**，再除以 n 得均摊 `T(n)/n`。

二进制计数器是最佳示范：inc 的代价 = 翻转的 bit 数。bit 0 每 2 次翻 1 次、bit 1 每 4 次翻 1 次、bit i 每 2^(i+1) 次翻 1 次，n 次 inc 总翻转数

```text
Σ_{i≥0} ⌊n / 2^i⌋ ≤ n · Σ_{i≥0} (1/2)^i = 2n
```

故均摊 **O(1)**（最坏单次 Θ(log n) 确实存在，但不影响平均）。动态数组同理：第 i 次扩容搬 i/2 个元素，总搬移 `Σ i/2`（只对 2 的幂次求和）≤ n，加每次 push 的 O(1) 放置，总代价 ≤ 3n → 均摊 O(1)。

## 工具二：记账法（给操作定预付房租）

给不同操作**收取高于真实成本的「摊还代价」**，多余部分作为信用（credit）存在具体元素上，将来为昂贵的真实操作付账。信用永不透支 ⇒ 摊还代价处处是真实代价上界。

动态数组：每次 push 收 3 元（真实 1 元放自己 + 1 元预付自己将来被搬 + 1 元预付另一个兄弟被搬）。扩容搬 k 个元素时动用这 k 元素身上的 2k 信用正好付清 `k+1 ≤ 2k`。于是**每次 push 摊还 3 = O(1)**。

数组+pop 的「防抖动」也由记账解释：扩容在负载 1 触发、缩容在负载 1/4 触发，两次扩容之间至少攒了 n/2 次 push 的信用，够付缩容搬移——**阈值贴着 1/2 会导致 push/pop 交替时每次都搬表（均摊 Θ(n)）**。

## 工具三：势能法（给数据结构存蓄电池）

定义状态函数 `Φ(D_i)`（第 i 次操作后结构的「势能」，常用「潜在重建工作量」度量，如数组取 `Φ = 2·size - capacity`），令

```text
摊还代价 âᵢ = 真实代价 cᵢ + Φ(Dᵢ) − Φ(Dᵢ₋₁)
若 Φ(Dᵢ) ≥ Φ(D₀) 恒成立，则 Σcᵢ ≤ Σâᵢ（势能非负 ⇒ 摊还是上界）
```

动态数组（倍增）：`Φ = 2·size − capacity`。普通 push（没满）：c=1，ΔΦ=+2 → â=3；满时 push 触发搬 k 个（capacity=k）：c=k+1，新 Φ = 2(2k)−2k… 代入同样得 â≤3。与记账法结论一致，但势能法**不需要把信用落到具体元素上**，适合并查集这类「看不出谁攒了钱」的场景：`040.并查集` 的 O(α(n)) 界即由势能+路径压缩联合证明。

三工具选择：总账好算用聚合；能指明「谁为将来买单」用记账；状态复杂、想全局抽象一个「蓄电池」用势能。

## 常见陷阱

- **均摊 ≠ 平均情况**：均摊是对**最坏操作序列**的总账保证（确定性承诺），平均情况是对**输入分布**的期望（依赖概率假设）——快排的「平均 O(n log n)」是期望，`push 的 O(1)` 是均摊，别混着说。
- 均摊 O(1) 不承诺**单次延迟**：实时系统（游戏帧、交易撮合）里那次 O(n) 扩容照样会造成毛刺，工程上用渐进扩容/双缓冲把搬移拆到每次 push 一点（Rust `Vec` 不拆、Go slice 搬移即毛刺来源）。
- 势能函数选错方向会得到「摊还界不成立」：必须证明 `Φ ≥ Φ(D₀)` 恒成立，信用透支的记账是假证明。
- 倍增的**空间最坏近 2 倍**是均摊 O(1) 的代价；对内存敏感场景用 1.5 倍（α=3/2 仍可证均摊常数略大）或分段链表数组（无搬移）。

# 总结

- 摊还分析用「n 次操作总代价 ÷ n」替代「单次最坏」，聚合/记账/势能三条路殊途同归：总账、信用、势能，任选好算的那条；
- 倍增扩容、装载因子阈值、路径压缩的 O(1)/O(α(n)) 承诺全靠它背书——**阈值与倍率的每一个数字都是摊还算术的解**；
- 它给的是序列级最坏保证而非单次延迟，实时场景要警惕那一次 O(n) 尖刺。
